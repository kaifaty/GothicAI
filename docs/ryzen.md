# Проверки на Ryzen

## Как работает сейчас

`LLM=off scripts/ryzen.sh e2e` передаёт серверу `--llm off`: модели нет, каждый запрос без подходящего заранее объявленного «дано» записывается и вызывает `ModelOff`. Сценарий получает backend через `model_off(dialogue)` и объявляет `given(reason, who=..., when=..., calls=..., line=..., times=...)` либо `silent(...)`; совпадают адресат `cache_key`, необязательная подстрока последнего сообщения и оставшиеся разы. Непредложенный инструмент в «дано» тоже считается ошибкой. Итог всегда добавляет `model_off` и `givens_used`, в том числе после исключения сценария; причины использованных «дано» видны как `scenario <name>: given: <reason>`. В этом режиме фоновые циклы Director и Amends запускаются только в сценариях, которые их проверяют; летописец использует запасной эпилог без модели. Прогрев и предварительное открытие соединения запросами не считаются. По умолчанию e2e передаёт `--llm auto` (только вместе со сценарием). `scenarios/groups.py` задаёт `OFF` (19 сценариев тел, ходьбы и моста), `GIVEN` (пока пусто) и `LIVE` (7 сценариев). Для `OFF`/`GIVEN` выбирается `off`, для `LIVE` запуск требует явного `LLM=chatgpt|openai|local`, для ещё не переведённых сценариев остаётся `fake`. Явный режим, несовместимый с группой, останавливает запуск. В `neural-soak` каждая фраза путника между волнами объявлена одноразовым «дано»; `soak_talk` проверяет доставку реплики. `websocket` сохраняет свой backend к транспортной фикстуре и требует `SAVE=save_slot_1.sav`. Проверки — `test_llm_off.py`, `test_cli.py`, `test_feats.py`, `scripts/tests/test_e2e.py`; `graph` на `off` проходит, `hearing` должен провалить `model_off` с адресатом `CAVALORN`.

Флаги C/C++ для движка и `storygraph` задаёт [`scripts/ryzen-build.sh`](../scripts/ryzen-build.sh): `RelWithDebInfo`, `-O2 -g1 -DNDEBUG`. Его используют `ryzen.sh` (включая `bench.sh`), Linux-путь `build-engine.sh`, удалённые body/nav-скрипты, `perf.sh`, подготовка личной игры и capture-сборки; список целей ограничен тем, что запускается, включая тесты. Флаги входят в ключ кэша `ryzen.sh`, поэтому старая сборка с полным `-g` не подменяет тонкую. Mac не изменён; `body-baseline-remote.sh` сохраняет полный `-g`, записанный в эталонной идентичности. Замер 31 октября 2026 в `~/gothic-ai/ryzen-thin-builds`, один и тот же исходный worktree, GCC 15.2, Ninja, `gq quiet`, 12 потоков: чистая сборка целей по умолчанию с `-g` → чистая сборка `Gothic2Notr` с `-g1`; логический размер 7 248 069 933 → 896 755 319 байт, занято на диске 7 253 512 192 → 902 074 368 байт (6,755 → 0,840 ГиБ). Время полной сборки без configure — 240,81 → 153,96 с; добавление пустой строки в `game/main.cpp` и повторная сборка — 8,46 → 4,22 с, исходник затем восстановлен. `libOpenGothic.a` уменьшился с 1 304 477 314 до 92 975 322 байт, `Gothic2Notr` — с 554 648 952 до 105 321 064 байт. `addr2line -Cfipe build/opengothic/Gothic2Notr 0x17a260` вернул `main` и `game/main.cpp:73`; локальный `~/.codex/checks/gothic/engine-targets.sh` также читает helper из проверяемого worktree.

Агенты запускают e2e и полный серверный `pytest` через `scripts/ryzen.sh`. Нужен настроенный SSH-алиас `ryzen`. Первичная подготовка переносит с Mac только два INI и недостающие готовые части базы по отпечаткам, проверяет пользовательский тулчейн, без установки системных пакетов:

```sh
scripts/ryzen.sh setup
SAVE=/Volumes/DevSSD/Dev/projects/gothic/save_slot_1.sav SCENARIO=stages scripts/ryzen.sh e2e
scripts/ryzen.sh pytest
scripts/ryzen.sh pytest tests/test_protocol.py -q
BENCH_HOST=ryzen scripts/bench.sh blink /absolute/path/to/bench-output
scripts/gq status
scripts/ryzen.sh du
scripts/ryzen.sh clean
scripts/ryzen.sh clean-cache
```

Окружения задач с torch (`nav-bc4`, `nav-dagger3`, `body-bc`) готовит общий [`scripts/ryzen-venv.sh`](../scripts/ryzen-venv.sh): `source` файла и вызов `ryzen_task_venv <путь к venv> [доп. пакеты...]`. Новый venv использует Python 3.12, `torch==2.14.1` с PyPI без отдельного индекса, `numpy` и `pytest`. На Ryzen это CUDA-сборка `2.14.1+cu130`; одинаковые файлы в venv используют жёсткие ссылки из кэша `uv`. Помощник передаётся вместе со скриптами задачи, отдельная установка на Ryzen не нужна. В `body-bc` создание venv идёт онлайн, установка пакетов — офлайн.

Версия torch задана только в `ryzen-venv.sh`. Чтобы поднять её, поменяй `torch_version` в одном месте. Старые venv с другой версией получают предупреждение и остаются со своей версией, пока задача не пересоздаст их; в них ставятся только отсутствующие дополнительные пакеты с зависимостями, а найденная версия torch закрепляется в том же вызове установки. Проверка помощника — `uv run --no-project --with pytest python -m pytest -q scripts/tests/test_ryzen_venv.py`.

**Личная игра пользователя** устанавливается отдельно: с Mac `scripts/ryzen-play.sh install`, после слияний в `main` — `scripts/ryzen-play.sh update`. Клон `~/gothic-ai/play/` и значок **Gothic AI** в GNOME запускают ядро лаунчера в Ptyxis: fullscreen, звук PipeWire, последнее сохранение. Сеанс держит `gq quick --interactive --display-exclusive` до 6 часов (8 потоков, 8 ГБ RAM, 3 ГБ VRAM, `CPUWeight=1000`); ждёт текущие игры, печатая их имена, фоновые заявки старт не задерживают. Установка/сборка и `uv sync` идут отдельной обычной `quick`-заявкой. [Установка, вход ChatGPT, ключи, PortAudio и смоук без моделей](launcher.md#ryzen-linux); [правила интерактивного допуска](compute.md#очередь-gq). Поведение e2e и bench ниже сохраняется.

Для измерения памяти Linux есть `SCENARIO=memprobe LLM=fake MEMPROBE_PHASES=save MEMPROBE_CYCLES=8 scripts/ryzen.sh e2e`. Каждую фазу запускают отдельной игрой. `LOG_DIR/game.pid` содержит PID игры, `memprobe.jsonl` — RSS по шагам и группы `smaps` в конце цикла. `GAME_EXTRA_ENV` добавляет переменные только игре: одна строка `NAME=value` на переменную, без shell-подстановок. Например, `GAME_EXTRA_ENV=$'LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2\nMALLOC_CONF=prof:true'`. Без переменной окружение игры прежнее; `MEMPROBE_*` и `GAME_EXTRA_ENV` проходят через SSH-обёртку.

Для `memprobe` таймаут e2e по умолчанию 1200 с; явный `TIMEOUT` имеет приоритет. `MEMPROBE_CYCLE_PAUSE` добавляет паузу после каждого `cycle_end` для внешнего профилировщика (по умолчанию 0). [Измерения RSS на Ryzen](../reports/engine/2026-10-19-rss-growth/README.md) показывают удержание свободных анонимных страниц аренами glibc при повторной загрузке мира.

Нативные вызовы `memprobe` ждут `trigger_fired` своего одноразового триггера: `error` или отсутствие события прерывают сценарий до записи успешного шага. Счётчик триггера подтверждением выполнения программы не считается. Подписка устанавливается до отправки `graph_patch`; после успеха, ошибки и отмены временный триггер и подписка удаляются. Проверка — `server/tests/test_memprobe.py` и фаза `wave` на Ryzen.

`GOTHIC_DIR` для `setup` — локальная папка игры, по умолчанию `/Volumes/DevSSD/Dev/games/Gothic II`. На Ryzen настройки установки лежат в `~/gothic-ai/game-settings/system/`, отпечатки готовой базы и видео — в `~/gothic-ai/game-base.json`; сами части выбираются из кэша или хранилища. Каталог `~/gothic-ai/game` больше не нужен; его удаляют отдельно. Исходники, инкрементальные сборки и серверный кэш каждого worktree находятся отдельно в `~/gothic-ai/e2e/<имя worktree>/`. Для Codex-пути `…/worktrees/<имя>/<repo>` используется имя родительской папки; `RYZEN_WORKTREE` позволяет явно задать другое имя удалённой папки. `clean` удаляет только папку выбранного worktree, сохраняя общий кэш бинарников, данные игры и тулчейн.

Общий [`scripts/ryzen_game.py`](../scripts/ryzen_game.py) используется также в `perf.sh`, capture-скриптах, навигационных раннерах и личной игре. Он проверяет setup до создания папок прогона, замков и заявок `gq`; отсутствие отпечатков или INI даёт `Run scripts/ryzen.sh setup first`. В игру и `gothic-body-runner --assets <game-settings>` передаются те же отпечатки, импорт не запускается. Локальный `GOTHIC_DIR` остаётся на Mac; удалённые запуски используют `game-settings`. Явные `--assets` и `OPENGOTHIC_BASE*` сохраняют приоритет. Каталог сохранений `~/.local/share/gothic-ai/game/` к установке не относится и сохраняется.

`e2e` и `bench` разделяют подготовку и игру на две заявки через `scripts/gq --host "$RYZEN_HOST" run`. Подготовка e2e сверяет протокол, собирает движок и `storygraph`, выполняет `uv sync` сервера и нужных сценарию сервисов; для всех `errand*` также готовит `tts-service`. Подготовка bench только собирает движок. Эта заявка не занимает окно и видеопамять. Вторая запускает только игру. `pytest` остаётся одной заявкой без окна:

| Команда и этап | Имя заявки | Класс | Потоки | RAM | VRAM | Окно | `--max` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `e2e`: подготовка | `build e2e <сценарий>` | `quick` | `RYZEN_JOBS`, по умолчанию 12 | 12 ГБ | — | нет | 30 мин |
| `e2e`: игра | `e2e <сценарий>` | `quick` | 4 | 5 ГБ | 2 ГБ | да | 30 мин |
| `bench`: подготовка | `build bench <сценарий>` | `quick` | `RYZEN_JOBS`, по умолчанию 12 | 12 ГБ | — | нет | 30 мин |
| `bench`: игра | `bench <сценарий>` | `quick` по умолчанию | 4 | 5 ГБ | 4 ГБ | да | 30 мин |
| `pytest` | `pytest` | `quick` | 4 | 6 ГБ | — | нет | 20 мин |

В профиле `ryzen` ресурс окна имеет ёмкость 3. Заявка с `--display --display-shared` получает свободный слот 0–2, видимый в `gq status` и в окружении как `GQ_DISPLAY_SLOT`. После завершения или отмены слот освобождается. Старый `--display` без shared и явный `--display-exclusive` берут все слоты (`окно=все`): ждут завершения текущих и более ранних игр, перекрывая допуск следующих. Уже сохранённые заявки без поля shared тоже эксклюзивны. Приоритет `quiet` сохраняется. `ryzen.sh` подаёт shared только для e2e вне списка `e2e_display_exclusive`. `orders`, `calm` и `fight_reactions_bandits` вышли из списка 19 октября после тройных раундов и одиночных запусков. Bench остаётся эксклюзивным: его произвольное окно может перекрыть соседей, даже при изолированном туннеле. Старые клиенты, `body-*`, `nav-*` и `gq-job.sh` сохраняют прежнее поведение. Остальные профили по умолчанию сохраняют один слот.

`TEMPEST_WINDOW_SIZE=640x360` — размер окна e2e на Ryzen по умолчанию; явное значение сохраняется. `TEMPEST_WINDOW_POS=x,y` задаёт начальную позицию X11-окна. Без явной позиции обёртка берёт размер экрана из `xdpyinfo` и раскладывает окна по слотам с отступом от панели и зазорами под измеренные рамки и тени GNOME: на 1920×1080 это (100,100), (800,100), (100,560). Если стандартная сетка не помещается на экран, игра завершается с объяснением; нестандартный размер запускается эксклюзивно в позиции (0,0), если вызывающий не задал свою. Tempest соблюдает явный размер и при создании `Maximized`; без переменных поведение прежнее. `OPENGOTHIC_FPS_LOG=1` включает средний FPS представленных кадров раз в 10 с в `game.log` через существующий AppCadence, без включения режима бенча; в e2e эта переменная включена по умолчанию, `OPENGOTHIC_FPS_LOG=0` отключает вывод. Ryzen уже собирает его с `OPENGOTHIC_ENABLE_APP_CADENCE=ON`.

E2e с нестандартным размером или явно заданной позицией подаётся эксклюзивно: его окно может перекрыть стандартную сетку других слотов. Сценарии с боем, спутниками и движением по времени тоже идут эксклюзивно — список в `e2e_display_exclusive` в `scripts/ryzen.sh`. `fight_reactions_bandits` вышел из списка после исправления геометрии арены и гонки остановки Кавалорна: два тройных раунда дали 6/6 при 72,1–76,2 FPS, одиночный прошёл при 101,0 FPS; одиночный `flee` тоже прошёл. [Итоговые цифры](../reports/compute/2026-10-19-ryzen-three-windows/README.md#bandits-открытая-арена-и-окно-ответа), [механика сценария](npc-agent.md#как-работает-сейчас). Остальные бои (`fight_reactions_*`, `calm_*`, `neural*`, `wolf`, `rescue*`, `companion`, `crime_ally`) не проходили тройную приёмку и держатся в списке из осторожности. Сценарий выходит из списка, только пройдя все раунды тройного замера, как `orders` и `calm`. Если сценарий из общего слота упал странно по времени, сначала повтори его с `RYZEN_DISPLAY_EXCLUSIVE=1` — так он идёт один.

Тройной замер — `scripts/ryzen-round.sh TAG SCENARIO...`. Просто запустить три `scripts/ryzen.sh e2e` параллельно мало: пока в общей очереди ждёт quiet- или эксклюзивная заявка, общие игры допускаются по одной и не пересекаются. Поэтому скрипт берёт одну quiet-бронь общей очереди: 12 потоков, 15 ГБ RAM, 6 ГБ VRAM, все слоты окна. Внутри неё он запускает сценарии через частную очередь на Ryzen: три сразу, остальные по мере освобождения слотов. Сценарии из списка там делят слоты через `RYZEN_DISPLAY_EXCLUSIVE=0`. Один сценарий — одиночный прогон на тихой машине. Скрипт печатает проверки, слот и средний FPS каждой игры, логи пишет в `.ryzen/round/`. Bench оставляет свой размер, а обратный SSH-туннель исключает все девять портов таблицы. Игровые заявки e2e и bench объявляют 5 ГБ RAM, подготовка — 12 ГБ: при трёх играх в пуле 20 ГБ сборка ждёт памяти. Отдельному сценарию при необходимости можно поднять память в обёртке. Данные сервера `GOTHIC_AI_DATA=$state/data`, в том числе собранный `story.json`, сохраняются между прогонами под замком worktree. У разных worktree разные каталоги; память, трассы и Inworld-кэш остаются в каталоге прогона.

Быстрая проверка на Ryzen в управляющей SSH-сессии сначала ищет готовые бинарники по хэшу в общем кэше, затем проверяет сборки своего worktree по `source.sha256`. Для e2e она также проверяет готовность зависимостей через `uv sync --check --frozen`, без установки. Её stdout и stderr объединяются до служебной строки завершения, чтобы вывод `uv` не скрывал её от лаунчера. Если всё готово, заявка подготовки вообще не подаётся: остаётся только заявка с окном. Свежему Python-окружению по-прежнему нужна подготовка без окна, даже если бинарники найдены в кэше. Ошибка подготовки возвращает её код и хвост лога, игра не запускается. В игровой заявке сборок и `uv sync` нет; e2e передаёт `UV_NO_SYNC=1`, исключая неявную синхронизацию. Несовпадение бинарника с хэшем снимка завершает заявку понятной ошибкой.

`RYZEN_MAX` переопределяет `--max` каждой заявки. `RYZEN_BENCH_CLASS=quiet` сохраняет режим игры bench на тихой машине; подготовка всё равно идёт как `quick`. `RYZEN_LOCK_WAIT` (900 секунд по умолчанию) задаёт `--wait-max` игровой заявки; в режиме auto `scripts/bench.sh` задаёт 120 секунд. Подготовка не расходует это ожидание окна. Код 75 и строка «Ryzen занят» доходят до вызывающего: `bench.sh` может перейти на Mac, если игра ещё не запускалась. Сам `ryzen.sh` на Mac игру не запускает. Серверный `pytest` не занимает окно и порты e2e, поэтому может идти рядом с игрой другого worktree. Владелец заявки — имя worktree; заявки, их класс и занятые ресурсы видны в `scripts/gq status`.

`scripts/ryzen.sh e2e` повторяет прогон только при неожиданном SIGKILL игры до маркера `scenario <name>: checks started`. CLI пишет его один раз после готовности мира, прямо перед вызовом сценария; вся подготовка внутри сценария уже считается его началом. На каждое такое убийство выводится `Ryzen: game killed before checks at <время UTC>, run N/4`; после четвёртого подряд команда возвращает код 76 и перечисляет времена всех четырёх убийств. Это сбой стенда, не попытка проверки: задача останавливается с `blocked` и этими временами. SIGKILL после маркера и остальные исходы возвращаются без повтора. Настройки очереди и код 75 сохраняются. Проверки без настоящего Ryzen — `scripts/tests/test_ryzen.py`, `scripts/tests/test_e2e.py` и маркер в `server/tests/test_cli.py`.

Снимок исходников и сборку защищает отдельный замок `~/gothic-ai/e2e/<имя worktree>.lock`. Одна управляющая SSH-сессия держит его от заливки через обе заявки до конца сбора логов: снимок между подготовкой и игрой не меняется. При INT, TERM или обрыве SSH `gq` отменяет текущую заявку, а удалённый хранитель замка (`scripts/ryzen-lock.py`) ждёт её конечного состояния в очереди: завершение локального SSH ещё не означает остановку systemd-юнита. Ожидание замка ограничено `RYZEN_LOCK_WAIT`; `clean` берёт тот же замок. Вызовы одного worktree выполняются последовательно, а разные worktree могут работать рядом по правилам очереди. Общий `body-simulation.lock` держит сама `gq` для совместимости со старыми скриптами. `setup` заливает общие данные игры без машинного замка: `rsync` пишет временный файл и переименовывает его.

Обёртка `gq` наследует канал удержания замка: даже при SIGKILL запускающей оболочки снимок остаётся защищён до конца заявки. HD-текстуры bench копируются в `hd-textures/textures` внутри папки worktree. Для loopback `GOTHIC_AI_URL` обратный SSH-туннель открывается только после допуска заявки к окну, на той же управляющей SSH-сессии, и закрывается вместе с ней. Туннель получает отдельный удалённый порт (порты e2e всех трёх слотов исключены); адрес меняется только для этого bench, поэтому сбор логов после освобождения окна не мешает следующей игре.

Перед подачей заявки хранитель получает её уникальный `RYZEN_RUN_ID`. После EOF он проверяет завершение заявки, удерживая замок. Если после `drain` без `complete` заявка с этим идентификатором не появилась в `state.json` за 60 секунд, хранитель один раз пишет `no gq request registered for <run> in 60s; releasing` и освобождает замок; при EOF без `drain` отсчёт идёт от EOF. Уже замеченная заявка ждётся до конечного состояния без ограничения времени. Штатная ошибка проверки аргументов до подачи заявки освобождает замок без такого ожидания.

`e2e` принимает переменные `scripts/e2e.sh`: `SCENARIO`, `SAVE`, `LLM`, `TIMEOUT`, `E2E_MAX_FPS`, порты и настройки провайдеров. Локальные `SAVE` и явно заданный `VOICE_FILE` копируются отдельно. `LOG_DIR` относится к Mac: туда возвращаются логи, сейвы и трассы; без него создаётся временная папка и печатается её путь. Вывод обеих заявок, который стримит `gq run`, и время сборки, ожидания окна и игры попадают в `launcher.log` для e2e и `ryzen.log` в папке вывода bench. Файлы авторизации провайдеров с Mac не копируются; для живого LLM нужна авторизация на Ryzen либо переданные переменные API.

При повторах после SIGKILL первый запуск сохраняет логи и данные в корне `LOG_DIR`, следующие — в `LOG_DIR/run-2`–`run-4`. Каждый запуск оставляет `e2e.log`, `server.log`, `game.log` и свои данные; предыдущие логи не перезаписываются.

После успешного получения логов e2e и bench скрипт удаляет удалённые `runs/<RUN>` и `inputs/<RUN>`, включая завершившиеся с ошибкой прогоны. Если логи забрать не удалось, оба каталога сохраняются и печатается предупреждение. После pytest удаляется его `inputs/<RUN>`. Перед заливкой под замком worktree одной строкой выводятся свободное место на Ryzen и размеры отдельных папок `~/gothic-ai/e2e/*`. После влитого PR освободи состояние worktree через `scripts/ryzen.sh clean`.

Каждый вызов `e2e`, `bench` и `pytest` под замком своего worktree обновляет `~/gothic-ai/e2e/<имя worktree>/.last-used` и показывает свободное место. Удаление чужих сессий и `uv cache prune` из подготовки убраны: теперь действует единая политика [уборщика](#уборщик-диска). Обзор `scripts/ryzen.sh du` показывает размер, простой, пересобираемую часть и планируемое действие для каждой папки без изменений на диске.

Готовые Linux-бинарники общие для всех worktree: движок лежит в `~/gothic-ai/engine-cache/<digest>/Gothic2Notr`. Ключ — существующий `source_digest` дерева `OpenGothic/`: SHA-256 путей и содержимого файлов, включая незакоммиченные изменения и исключая каталоги `build`. При попадании `RYZEN_GAME_BIN` указывает прямо в кэш; своя папка `build` не создаётся. В логе появляется `Ryzen: engine from cache <первые 12 символов digest> (0s)`. Изменение только Python позволяет другому worktree использовать тот же движок.

При промахе configure и сборка идут в своей папке worktree как прежде, сохраняя возможность инкрементальной пересборки после правки движка. Если там уже есть актуальный бинарник, подготовка без окна публикует его без configure и сборки. Это также восстанавливает запись после вытеснения или `clean-cache`; для `storygraph` действует то же правило. Затем скрипт копирует весь каталог вывода `build/opengothic/`, включая файлы рядом с бинарником, во временный каталог кэша и публикует его одним атомарным переименованием. Копирование идёт без общего замка; короткий замок `~/gothic-ai/engine-cache.lock` защищает публикацию, выбор и очистку записи. Одновременная публикация одного хэша сохраняет одну готовую запись.

У `storygraph` свой кэш `~/gothic-ai/engine-cache/storygraph/<digest>/storygraph`. Его ключ учитывает `OpenGothic/ai_bridge/storygraph/`, `ai_bridge/textcodec.cpp`, `ai_bridge/textcodec.h`, `lib/ZenKit/` и `lib/rapidjson/include/`, также без `build`. Путь `OpenGothic/ai_bridge/storygraph/build/storygraph` в снимке ссылается на выбранную утилиту для сервера и нативных тестов. Перед e2e версия протокола сверяется между исходниками движка и сервера.

Перед запуском выбранная запись обновляет mtime под тем же замком. Автоматическая очистка оставляет до восьми записей движка и отдельно до восьми записей `storygraph`, удаляя сначала давно использованные. Записи моложе двух часов защищены, поэтому временно записей может быть больше восьми. `scripts/ryzen.sh clean-cache` вручную очищает оба раздела под общим замком, также сохраняя записи моложе двух часов; вывод показывает число удалённых и защищённых записей. Обычный `clean` кэш не трогает. Защита рассчитана на прогоны короче двух часов.

`RYZEN_JOBS` задаёт число процессов сборки для e2e и bench (по умолчанию 12); pytest использует 4 потока. SDK берётся из `~/gothic-ai/body-baseline/toolchain/vulkan-1.4.341.0` и проверяется до configure, чтобы отсутствие GLSL-компилятора не уничтожило `build.ninja`. Обёртку и кэш проверяют `cd scripts/tests && python3 -m unittest -q test_ryzen test_ryzen_lifetime test_ryzen_lock`; запуск готовых бинарников — сценарий `stages` на Ryzen.

Игра открывает окно через существующий пользовательский Xwayland: скрипт находит рабочие `DISPLAY` и `XAUTHORITY`, задаёт NVIDIA Vulkan ICD и отключает физический аудиовыход. Строка `GPU = …` из `game.log` выводится после e2e. При отсутствии доступного Xwayland скрипт завершает работу с объяснением. `e2e` и `pytest` возвращают исходный код завершения команды, кроме описанного выше кода 76 после четырёх убийств игры; логи e2e забираются и после ошибки. `e2e.sh` печатает код или сигнал завершения игры, `gq` добавляет доступные `memory_peak` и `oom_kill` cgroup в запись завершения заявки. Игры на Ryzen по имени (`pkill`/`killall Gothic2Notr`) не убивай: свою заявку останавливай через `scripts/gq cancel <id>`.

Игра e2e на Ryzen и Mac по умолчанию ограничена 30 FPS: `scripts/e2e.sh` пишет `[ENGINE] zMaxFps=30` в `Gothic.ini` каталога прогона, сохраняя настройки CharacterVirtual и записи TTS. `E2E_MAX_FPS=0` снимает этот лимит, `E2E_MAX_FPS=60` задаёт 60 FPS; `scripts/ryzen.sh` передаёт значение с Mac на Ryzen. Положительный `[PARAMETERS] FPS_Limit` общего `SystemPack.ini` имеет приоритет, о нём e2e предупреждает; общий файл не меняется. Bench и живая игра сохраняют прежние настройки. Проверки — `scripts/tests/test_e2e.py`, частые сценарии на Ryzen и `stages` на Mac; [приёмка](../reports/compute/2026-10-19-e2e-fps-cap/README.md).

### Уборщик диска

Новая версия пользовательского `gothic-janitor.timer` запускает [`scripts/ryzen_janitor.py`](../scripts/ryzen_janitor.py) ежечасно (`Persistent=true`, Linger уже включён). Сервис работает вне `gq` с `Nice=19`, `IOSchedulingClass=idle`; второй экземпляр сразу выходит по собственному замку. Корень задач `~/gothic-ai` может быть ссылкой на `/data/gothic-ai`; по ссылкам внутри него уборщик не ходит. Отдельно проверяются свободные байты файловой системы задач и `/`.

- После **2 дней простоя** задачи пересобираемые каталоги удаляются, а остальные данные переносятся со сверкой SHA-256. В `e2e/<сессия>/` и `codex-check/<задача>/` простой считается по сессии. Учитывается самое свежее изменение папки и её содержимого, в том числе `.last-used`; старая метка не скрывает свежие данные.
- Пересобираемое определяется явным списком имён в коде: `build*`, сборки утилит вроде `storygraph-build`, `.venv`/`venv`, `uv`-кэши, горячие кэши обучения и служебные кэши Python. Обход рекурсивный: сюда входят `e2e/<сессия>/build`, `e2e/<сессия>/storygraph-build` и `codex-check/<задача>/build`. Оно удаляется до переноса и на NAS не копируется. Общий `engine-cache` также пересобираем.
- **Аварийный режим:** если на файловой системе задач или `/` меньше **60 ГиБ**, уборщик сразу берёт кандидатов с **12 часами** простоя, от самых старых. После каждого действия место проверяется снова; проход заканчивается при **100 ГиБ** на испытывающей нехватку файловой системе либо при исчерпании кандидатов. Папки на другом диске не засчитываются в освобождение нужной файловой системы.
- **Защита:** `.keep` в задаче/сессии, в том числе во вложенной папке, сохраняет её целиком. Не трогаются `body*`, `nav-probe`, `bin`, `lib`, служебные `game`, `game-settings`, `play`, `gq`, `queue`, прочие скрытые каталоги корня и имена/glob из `~/gothic-ai/.janitor-keep`. Внутри `body*` и `nav-probe` ничего не удаляется и не переносится, включая аварийный режим. Любая папка с cwd, открытым или исполняемым файлом живого процесса (`/proc/*/cwd`, `/proc/*/fd`, `/proc/*/exe`) либо ссылкой из ожидающей, стартующей или работающей заявки `gq` пропускается, включая e2e. Уборщик берёт соседний e2e-lock неблокирующим flock и сохраняет lock-файл.
- Остаток задачи или сессии `nas_archive.move` копирует в новый путь под `/mnt/shared/gothic-ai/archive/` и удаляет локально только после сверки. Существующее назначение не перезаписывается; разрешён повтор собственной незаконченной попытки с маркером, в том числе после смены даты. Простой и занятость проверяются перед удалением и во время переноса. Собственные изменения mtime сохраняются в `~/gothic-ai/.janitor/attempts.json` и игнорируются только при точном совпадении; новая активность защищает задачу.
- Общий `~/.cache/uv` удаляется после того же срока простоя, если не занят и не защищён `.keep`. Прежней еженедельной безусловной очистки `uv cache clean` нет.
- В **`~/.cache/gothic-ai/base`** сохраняются `current` и отпечатки из его указателей, отпечатки с занятой `.use` и два самых свежих отпечатка. `.use` — файл flock: игра держит shared-блокировку, поэтому наличие незанятого файла не означает использование. Удаление берёт общий замок кэша и эксклюзивную `.use`. Остальные отпечатки удаляются после **2 дней** простоя при наличии копии в `/mnt/shared/gothic-ai/base`; аварийный режим этот срок не сокращает.

Без CIFS-маунта NAS переносы пропускаются, удаление пересобираемого продолжается. При ошибке папки проход продолжается, итоговый код ненулевой. Исчезнувшие дочерние записи пропускаются при подсчёте; исчезновение самой папки или возобновившаяся во время копирования задача считаются пропуском. Каждое действие пишет путь, байты и правило. Итоговая строка в журнале юнита и `~/gothic-ai/.janitor/last.json` содержат объёмы удаления и переноса, числа папок и причины пропусков. `run` выводит последнюю сводку и при ошибке сервиса, сохраняя ненулевой код.

```sh
scripts/ryzen.sh du
scripts/ryzen-janitor.sh run --dry-run
scripts/ryzen-janitor.sh status
# Only after the user approves the plan:
scripts/ryzen-janitor.sh install
scripts/ryzen-janitor.sh run
scripts/ryzen-janitor.sh uninstall
```

`du` выводит таблицу «папка — размер — простой — пересобираемое — действие». `run --dry-run` печатает действия, правила и байты без удаления и переноса. Обе команды передают текущий код worktree во временную папку Ryzen, выполняют только обзор и удаляют свою временную копию; установленный сервис не запускается и не обновляется. Новые версии уборщика и `gq` ожидают разрешения пользователя «ставь».

`install` атомарно заменяет `ryzen_janitor.py` и отдельную копию `nas_archive.py` под именем `ryzen_janitor_archive.py` в `~/gothic-ai/lib/`, ставит пользовательские `.service`/`.timer` и включает таймер без `sudo`. `uninstall` останавливает сервис и таймер и удаляет только их файлы; общий `lib/nas_archive.py` не меняется. `run` использует установленный сервис. Проверки затронутых правил находятся в `scripts/tests/test_ryzen_janitor.py`, проверки двух дисков очереди — в `scripts/tests/test_gq.py`, обёртки — в `scripts/tests/test_ryzen.py`.

При принудительной остановке внутри `rmtree` отдельного восстановления нет: частичная очистка может обновить mtime и отложить перенос на 2 дня; после закрытия проверенного архива повтор в тот же путь явно отклоняется до смены даты.

### Перенос результатов на NAS

Завершённую фазу переносят из `~/gothic-ai/<путь>` в `/mnt/shared/gothic-ai/<тот же путь>`. Это делает [`scripts/nas_archive.py`](../scripts/nas_archive.py), доступный как CLI и библиотечная функция `move(src, keep_local=False, dry_run=False)`, возвращающая число байт:

```sh
# On Ryzen, from a project checkout:
python3 scripts/nas_archive.py move "$HOME/gothic-ai/my-task/results" --dry-run
python3 scripts/nas_archive.py move "$HOME/gothic-ai/my-task/results" --keep-local
python3 scripts/nas_archive.py move "$HOME/gothic-ai/my-task/results"
# From Mac through the queue; DIR is an absolute path on Ryzen:
scripts/gq submit --class batch --threads 4 --mem 4G --max 30m --name phase \
  --archive /home/USER/gothic-ai/my-task/results -- python3 /absolute/path/to/phase.py
```

Корни на Ryzen задают `GOTHIC_LOCAL_ROOT` и `GOTHIC_NAS_ROOT`; SSH-обёртка не передаёт эти переменные с Mac. Источник вне локального корня или сам корень отклоняется. Для `gq run` и `gq submit` `--archive DIR` повторяется для нескольких папок и проверяется при подаче; папку может создать сама команда. `gq_job` передаёт эти аргументы в `submit`. После завершения команды с любым кодом `ExecStopPost` своей заявки переносит каждую папку, записывает исход и байты в журнал заявки и `gq logs`. Ошибка даёт предупреждение и сохраняет код команды. На время переноса обработчик завершения продлевает ожидание systemd; лимит команды и её 60-секундный срок остановки сохраняются. Отменённая заявка ничего не переносит. Если завершение восстанавливает `reconcile`, перенос пропускается: в журнал и `gq logs` записывается `skipped after recovery; local data kept (0 bytes)`, событие `archive` получает `outcome="skipped"`. Локальная папка остаётся для будущего уборщика. Без опции поведение очереди прежнее. Будущая установка `scripts/gq install` доставляет и библиотеку переноса; установленную очередь этот PR не обновляет.

Перед копией модуль обращается к NAS, чтобы поднять autofs, затем проверяет запись `cifs` для корня или предка в `/proc/mounts`: одного существующего каталога недостаточно. Только для герметичных проверок `GOTHIC_NAS_MOUNTS` задаёт другой файл маунтов. Копирование — rsync `--no-links` без файлов и каталогов `pytest-*` на любой глубине. Пути ссылок и их цели сохраняются в корневом `.symlinks.tsv` и выводятся; исходный файл с этим именем отклоняется, чтобы не затереть данные. Бит исполнения не сохраняется на CIFS.

После копии каждый обычный файл сверяется по SHA-256. Источник удаляется только после полного совпадения; при ошибке маунта, нехватке места, сбое копирования или сверки он сохраняется, команда возвращает ненулевой код с одной строкой причины. Rsync работает без `--checksum`: для надёжного повтора с совпадающими размером и mtime `--ignore-times` перезаписывает файлы без предварительного чтения NAS. Повторный `move` завершает перенос в ту же папку без дублирования; результат заново сверяется по SHA-256. `--keep-local` копирует и сверяет без удаления, `--dry-run` выводит пути и байты без копирования. Для уборщика `move` принимает `destination_relative` и `attempt_id` (CLI: `--destination-relative archive/<задача>-<YYYYMMDD> --attempt-id <id>`): путь задаётся относительно корня NAS, абсолютный путь и `..` отклоняются. Новое назначение создаётся эксклюзивно; существующее принимается только с маркером незавершённой попытки, совпадающими источником и id. После сверки маркер снимается перед локальным удалением, чтобы прерванная очистка не разрешала повторную запись в проверенный архив. Назначение без подходящего маркера отклоняется; такая попытка сбрасывается, позволяя выбрать новый путь с текущей датой на следующем запуске. Перед повторной копией из назначения с маркером этой попытки удаляются записи, отсутствующие в снимке источника; маркер попытки сохраняется, а корневая `.symlinks.tsv` сохраняется до перезаписи только при наличии ссылок в источнике; без ссылок устаревшая таблица удаляется. В этом режиме копируются и сверяются все оставшиеся файлы; исключение `pytest-*` относится только к прежнему режиму без нового назначения. Исключённые `pytest-*` удаляются вместе с исходной папкой после успешного переноса остальных данных. Пока фаза пишет результаты, архивировать её нельзя; сборки, `.venv` и `uv`-кэш остаются локально.

Проверки изолированы временными корнями и поддельным файлом маунтов: `scripts/tests/test_nas_archive.py`, `test_gq.py`, `test_gq_job.py`. Живой смоук использует отдельную случайную папку и временную копию модуля на Ryzen, после проверки удаляет свои данные с NAS.
