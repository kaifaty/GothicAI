# План реализации GRU слоя управления телом NPC

Статус: P30 по умолчанию ведёт бой в движке через `body_acquire` с `policy:"engine"` (v54, 28 октября 2026 года). Сервер и лаунчер выбирают этот путь по `hello.body_net`; TCP-сервис остановлен и выключен 28 октября, его поднимают вручную для опытов и сравнения. Пилот ведёт до четырёх NPC с одноручным оружием; для нескольких боёв — протокол движка ≥45 в `hello`. Развитие обучения — в [плане и журнале](#план-и-журнал).

## Как работает сейчас

### Вывод P30 на C++

Вывод P30 на C++ подключён к `BodyController`. `OpenGothic/common/game/bodypolicy.*`
загружает отдельный `.bodynet` v1, проверяет схему и веса, упаковывает и нормирует
184 входа из JSON-наблюдения, применяет маску и GRU-256. Неизменяемая сеть общая
для NPC; `BodyPolicyRuntime` хранит их память и повторяет гейты, сбросы, memory-only
и арбитраж NumPy-эталона. Плотные слои, sigmoid и GRU, а также чтение float32-тензоров
вынесены в `common/nets/smallnet.*`; навигация пока использует прежний код.

При старте движок один раз загружает файл из `OPENGOTHIC_BODY_NET`, по умолчанию
`~/.local/share/gothic-ai/body/nets/p30.bodynet`. Ошибка записывается с причиной,
игра продолжает работать без сети. `hello.body_net` сообщает загрузку, SHA-256
checkpoint и ошибку. `body_acquire` с `policy:"engine"` требует загруженную сеть
(`body_net_unavailable` при её отсутствии); без `policy` lease работает как прежде.
Каждая периодическая строка этого NPC поступает в `BodyPolicyRuntime` в том же JSON,
что и в `body_observations`. Веса общие, память GRU отдельная у каждого lease.
Строки, нужные только памяти, повторы и сброс после `observation_too_old` повторяют
правила серверного `BodyFight._row`. Команды проходят прежние проверки действия и
`FightAlgo::resolve` с `ttl_ms:100` от времени строки. Отказ политики завершает бой
на безопасной границе с `reason:"native_restored"` и
`release_reason:"policy_fallback:<reason>"`.
Раз в секунду и при запросе release сервер получает `body_policy` со счётчиками
решений, отказами по причинам и p50/p99 времени шага в микросекундах.
Необязательные `selected_actions` / `accepted_actions` считают выбранные сетью /
принятые движком действия по именам из `.bodynet`, `hidden_reset` — сбросы памяти
за интервал, включая новый lease. Без полей сервер получает пустые счётчики и 0;
дополнение совместимо с v54. Счётчики интервалов суммируются в `FightSummary`;
формат `neural-body end …` сохраняется; `engine_max_interval_p50_us` явно обозначает максимум
интервальных медиан. Сводка боя сохраняет максимумы интервальных p50/p99,
поскольку отдельные длительности шагов серверу не передаются.
`body_observations` продолжает идти. Сервер запрашивает `policy:"engine"` по умолчанию
и сохраняет `body_heartbeat`: локальные решения lease не продлевают. В этом режиме
нет `PolicyClient`, серверных `body_action` и сторожа таймаутов сервиса.

Предел застоя: P30 умеет бесконечно ждать пассивного противника (`wait_200` подряд
в шаге от героя). Если 4 с игрового времени (`BodyEnginePolicy::StallGameMs`) нет
ни замаха цели (`target.attack_anim`), ни потери HP у любой стороны, решение берётся
только из `approach`, `turn_to_target` и трёх ударов: из тех, что разрешает та же
маска, с наибольшим логитом самой сети. Удар, уже испробованный в этом застое, ждёт,
пока не будут испробованы остальные разрешённые удары. Собственный замах без урона
застой не снимает: правый удар физического клинка часто не достаёт с предельной
дальности. Если маска не разрешает ни одного из этих действий, выбор сети остаётся.
Урон любой стороне или замах цели снимает предел. Входы и память GRU не меняются.
Предел есть только в движке; запасной `service` его не применяет.

`--body-policy engine|service` (`GOTHIC_BODY_POLICY`, по умолчанию `engine`) выбирает
путь для текущего подключения. При `hello.body_net.loaded:true` используется движок;
без сети (в том числе без поля `body_net`) — сервис из `--body-url` / `GOTHIC_BODY_URL`,
если адрес задан, иначе родной ИИ. Причина из `hello.body_net.error` пишется один раз
для подключения. Явный `service` требует адрес. Юнит `gothic-body` на dev-ubuntu
остановлен и выключен 2026-10-28 по решению пользователя; сервис поднимают вручную
только для опытов и сравнения. `--no-neural-body` выключает пилот.
Лаунчер хранит `llm.body_policy` и необязательный `llm.body_net`: последний передаёт
игре `OPENGOTHIC_BODY_NET`; без него действует путь движка по умолчанию.

`check-bodypolicy` создаёт случайную NumPy-фикстуру из 1280 шагов и сравнивает входы
(1e-5), логиты и память (1e-4), действия, причины и сбросы (точно).
Маска только с `continue` проверяет `no_available_primitive`; отдельные записи
`arbitrate` проверяют отсутствующее состояние, возраст и несовпадение якоря,
блокировку и неверную маску. Сравнение якоря повторяет равенство Python для
чисел и булевых значений; сама маска по-прежнему требует булевые элементы.
Настоящие веса проверяет `gothic-bodypolicy-contract MODEL.bodynet GOLDEN.jsonl.gz`;
`--benchmark` добавляет время шага p50/p99 на одном ядре. `gothic-body-engine-test`
проверяет последовательность действий, новые счётчики сводки в сравнении с прямым
`BodyPolicyRuntime`, валидацию, причину fallback и предел временных отказов на фикстуре
`scripts/body_net.py fixture` без ассетов. `gothic-body-watch-test` проверяет ответ
acquire без сети, применение к настоящим NPC, watchdog владельца и возврат native.

### Сбор для обучения

PPO собирает дуэли в lockstep: [`scripts/body_rl_collect.py`](../scripts/body_rl_collect.py) и `gothic-body-runner`
с `--fork-reset`. Мир вне арены заморожен (`OPENGOTHIC_FREEZE_WORLD=1` и остальные флаги `TRAINING_ENV`);
каждый эпизод — fork загруженного мира. Среды берут следующую дуэль из общей очереди. Сэмплы идут из потоков
самой дуэли (зерно сэмплирования и seed дуэли), поэтому строки не зависят от числа воркеров.
Runner не копирует базу на хранилище: шаблону fork нужен один поток. На Ryzen 1024 дуэли на 24 воркерах `main`
28 октября — 165 с, около 4800 тиков/с и 240 решений/с; машина упирается в процессор. CPU тика — около 1,3 мс
runner и 0,6–0,9 мс Python на воркер. Как профилировать —
[`scripts/body_lockstep_cpu_profile.py`](../scripts/body_lockstep_cpu_profile.py),
разбор — [отчёт 28 октября](../reports/npc-body/2026-10-28-collect-speed/README.md).

### Боевой пилот

- Сервер ведёт до четырёх NPC сразу, каждый со своим lease, памятью GRU и сводкой боя; в запасном режиме `service` — ещё и TCP-соединением. Подходят свободные люди с одноручным оружием, которые уже сражаются с героем или его спутником; самих спутников пилот не ведёт. Лимит задаёт `--neural-body-max` (1–4, по умолчанию 4). Пятый кандидат остаётся родному ИИ до освобождения места.
- Движок передаёт наблюдения с частотой 20 Гц. P30 в движке (или удалённая политика в режиме `service`) выбирает следующий боевой примитив; анимации, движение, столкновения и урон исполняет движок.
- В realtime обычного моста `body_action` устаревает относительно последней отправленной провайдеру строки своего NPC; снятая, но ещё не отправленная строка её не устаревает, TTL сохраняет игровые и стенные часы исходной строки. Runner, арена, lockstep и gate используют прежнее правило.
- В режиме `service` после принятия действия пилот ждёт существующее событие `accepted` и пропускает строки более ранних `sim_step` только в память политики: следующая команда требует наблюдения шага принятия или новее, поэтому снятая до принятия строка не создаёт лишний `command_busy`. Одиночный таймаут ожидания 250 мс временный: следующая строка решается как обычно, `accept_wait_timeouts` сохраняется в сводке и `neural-body end`. При отправленных неподтверждённых командах отсутствие новых `accepted` дольше `LEASE_TIMEOUT_MS` (2 с) завершает бой с `acceptance_timeout`; без ожидающих команд тишина не завершает бой.
- Захват и возврат родному бою проходят на безопасной границе действия. Просроченные команды не исполняются; ошибка, разговор или конец одного боя освобождают только его NPC. Загрузка, смена сессии или мира, отключение моста и выключение пилота завершают все бои.
- При release незашищённые `approach`, `strafe`, `turn_to_target` и `jump_back` останавливаются не позднее следующего тика: переход беговой анимации сам по себе не удерживает lease. Защищённые сегменты атаки, блока и отскока, падение, попадание, воздух и остальные физические блокировки сохраняются.
- При дальнем режиме NPC и фактическом удалении героя от 30 м release и realtime watchdog возвращают native не позднее следующего тика, отменяя боевую позу и ожидания; физические реакции сохраняются для native, ближние защищённые сегменты доигрываются. Это проверяет `gothic-body-watch-test`; его диагностический `body_control_status` показывает режим симуляции, остаток сегмента, gates и `interruptible`, обычный wire status сохраняет прежнюю схему.
- Общая подписка `body_watch` содержит NPC всех идущих боёв, включая наблюдение и захват. Несколько боёв разрешены только после `hello` с протоколом ≥45. Если версия ниже или `hello` ещё нет, новый кандидат при идущем бое получает отказ `watch_busy`: запрос изменения подписки не отправляется, текущие бои сохраняются. Отказ пишется только в лог и счётчик `watch_busy` диспетчера; `summaries` и `last_summary` содержат лишь завершённые бои. Если движок с протоколом ≥45 всё же отказал в `body_watch`, причина нового боя — `watch_refused`. Повтор возможен после `REACQUIRE_INTERVAL`.
- `GameLink.body_watch` разрешает менять подписку при ожидающих заявках на захват, если все их NPC остаются в новом списке. При подтверждении с прежней generation очищает кэш свободных актёров, сохраняя строки актёров с lease и ожидающих захвата; это освобождает место в кэше для новых NPC.
- После подтверждённого release NPC убирается из подписки. Если очистка боя не уложилась в 2 с, диспетчер сохраняет невыпущенного владельца в `body_watch`, в том числе при старте новых боёв. Опрос `native_restored`/`body_control_status` продолжается каждые 150 мс; только подтверждённый `native` снимает удержание. Если с начала release прошло lease timeout + 3 с (сейчас 5 с), диспетчер снимает свой учёт, пишет лог и увеличивает `release_orphan_timeout`. Неудачное сжатие откладывается и повторяется отдельно; оно не завершает другие бои.
- Сводка и лог `neural-body end` сохраняют исходную причину в `end_trigger`, даже при `reason=finish_deadline`. Позднее подтверждение публикует новую неизменяемую сводку с `release_late_seconds` — временем от начала release до фактического подтверждения возврата; прежний снимок сводки не меняется.
- Поздний release после `target_changed` ставит повторный захват в очередь. После паузы `REACQUIRE_INTERVAL` диспетчер проверяет живую разрешённую цель и только затем снимает запрет прежней схватки. Для `target_lost`/`npc_unavailable` таймаут сироты тоже разрешает завершить учёт старой схватки при уходе NPC из радиуса или полного roster; подтверждение release в сводке при этом не подделывается. Ошибки политики и падение цели сохраняют прежний запрет повторного захвата.
- Активный собеседник может перейти к P30, когда roster уже показывает родной `ZS_ATTACK`
  с активностью `fight` или текущую аренду `body`. Сам статус собеседника не блокирует
  бой; настоящий `attach`, ванильный диалог и недоступное тело по-прежнему его блокируют.
- Причины `loading`, `session_changed`, `world_changed` и `disconnected` сохраняются,
  если после них приходит ошибка ожидающего RPC; неподтверждённая очистка по истечении
  общего дедлайна остаётся `finish_deadline`.
- После подтверждённого `npc_unavailable`/`target_lost` выход NPC из полного roster
  или радиуса 20 м завершает прежнюю схватку для диспетчера. Вернувшийся нападающий
  получает новый lease и память, даже если распорядок вне поля зрения не попал в roster.
  Ошибки политики и fallback по-прежнему не разрешают захватывать ту же схватку заново.
- После `hero_down`/`target_down` NPC остаётся в `_claimed_fights`, пока следующий
  roster не покажет `down` или распорядок вне `ZS_ATTACK`. Родные грабёж и отход в
  `fight/ZS_ATTACK`, в том числе события нападения, не создают новый бой и подписку.
  Это не отменяет повторный захват после бегства героя.
- До получения lease свежая строка с упавшим NPC или потерей цели завершает
  наблюдение и снимает подписку до истечения окна захвата. Падение цели до lease
  игнорируется: живой `NPC_GETTARGET` уже может указывать на другого, здорового NPC.
  `hero_down`/`target_down` принимаются только для `entity_id` цели подтверждённого
  lease после живой проверки и захвата. Посторонняя упавшая цель не ставит claim
  и не мешает прямому переключению NPC на героя без промежуточного распорядка.
  Новый живой бой может получить отдельный lease и `reset`.
- Если всё окно захвата занято только разговором или мягким действием, новый roster
  родного боя разрешает повтор через 2 с. Другие отказы, ошибки политики и fallback
  сохраняют запрет повторного захвата той же схватки.
- Обычный мост с v45 позволяет расширять и сокращать `body_watch` до четырёх NPC при прежней частоте, сохраняя всех NPC под lease или с заявкой на захват. Identity, lease, заявки и последовательность наблюдений оставшихся NPC продолжаются без сброса; без владельцев перенастройка по-прежнему выполняет полный сброс.
- После подвисания игры накопившиеся строки проходят по порядку только в память GRU; действовать может последняя строка не старше 100 игровых мс. Одиночный `observation_too_old` пропускается, после сброса памяти следующая строка начинает новый эпизод.
- Таймаут `body_events` под lease временно пропускает обработку строк, следующий опрос — через `EVENTS_INTERVAL`, heartbeat независим; более 2 с без успешного опроса по стенным часам, другая ошибка моста или пропажа lease дают `lease_lost`. При `loading`/`world_changed` таймаут пишется как info; сводка и `neural-body end` содержат `ownership_poll_timeouts` и `ownership_poll_max_gap_ms`.
- Подготовка P30 допускает 500 мс на TCP connect и начальный `reset` с одним повтором `reset` при таймауте; `step` сохраняет 100 мс. Потерянный ответ на захват проверяется до конца окна: lease из события или статуса продолжает бой, native без заявки допускает новый захват через `ACQUIRE_INTERVAL` даже до обновления roster; после `finish_deadline` неопределённую заявку автоматически очищает диспетчер, сохраняя подписку и место NPC до подтверждения. Сводка и `neural-body end` содержат `setup_timeouts` и `acquire_uncertain_recovered`.
- Есть отдельная арена и [раннер без окна](../OpenGothic/game/bodyrunner.cpp) для записи боёв, обучения и оценки; в обычной игре пилот работает в реальном времени.
- Записанные с `--keep-journals` дуэли снимает `scripts/body_replay_film.py`: `prepare` строит сцену, `render --size 1920x1080` на macOS использует Metal, звук боя без музыки и фоновых звуков и пишет `duel.mp4` + `duel.wav` (48 кГц). Jolt работает без фоновых потоков, как у runner; Linux сохраняет Xvfb/lavapipe. Для съёмки каждый дубль проверяется через `scripts/body_schedule_equivalence.py`: нужны `identical_commands=1`, `same_outcome=1`, ноль отклонённых команд и одинаковые HP и время боя. `same_outcome` сравнивает только причину завершения, поэтому HP и `elapsed_game_ms` проверяются отдельно. Небольшие численные различия физики Linux x86 и macOS arm64 допустимы; строгое совпадение наблюдений и координат не требуется ([числа](../reports/npc-body/2026-10-19-replay-mac/README.md)).
- `prepare --track-head` добавляет `track <primary> head` перед записью. `labels DIR --output actions.json` читает журналы повтора и строит данные для подписей: `fps`, `frames`, `size`, координаты головы `track` (пиксели, `null` вне кадра), HP обоих участников `hp`, действия `actions` с кадром, временем от начала ролика, именем из `gothic_body.schema` и `command_id`. Начало действия берётся из `started`, а не `accepted`; игровое время сопоставляется с кадрами `metrics.csv`. Linux-трек можно использовать поверх Mac-ролика после сверки числа кадров и игрового времени каждого кадра. [Сверка восьми дуэлей P30](../reports/npc-body/2026-10-19-replay-track/README.md).
- Живой бой на Mac снимает `scripts/body_live_capture.py`: сцены `live-takeover`, `live-group` (три бандита) и `live-passive` (герой без ударов). Это родное нападение в обычном мире и обычные `GameServer` + `BodyPilot`; ответы героя задаются клавишами игрока. Адрес P30 читается из `[llm].body_url` обычных настроек, сервис и веса не меняются. LLM/ASR/TTS должны быть `fake`, клиенты этих моделей не создаются. По умолчанию снимаются 25 с в 1920×1080/30 FPS с отдельным WAV 48 кГц, только звук игры (`SOUND=1 MUSIC=0 WORLD_SOUNDS=0`). Герою задаются бессмертие и 100000 HP, бандитам — 1800 HP. Перед запуском инструмент проверяет, что на Mac нет другой игры. [Запуск](../scripts/bench/README.md#live-p30-capture-on-mac).
- Инструментация живого боя включается только `bodylive on` (по умолчанию выключена): события `body_live_control` сохраняют решения контроллера, `body_live_sample` — HP каждого кадра. `track A,B,C head` пишет отдельные треки NPC. `scripts/body_live_film.py labels DIR --npc SYMBOL` выдаёт формат `fps`, `frames`, `size`, `track`, `hp`, `actions`; `actions` — принятые решения P30 (`accepted`), включая `continue` и команды, отменённые до начала исполнения. Кадр берётся из захвата движка, `t` — его время в видео; наличие решения не означает начало анимации. Экспорт сверяет все принятые решения сеанса с единственной строкой `neural-body end … decisions=` своего NPC, а в файл включает только решения внутри записи. В группе экспорт запускается отдельно для каждого бандита. Пороги `--min-decisions` и `--consecutive-wait` проверяют количество решений и подряд идущих `wait_200`. Ограничения: один lease на NPC за сеанс, полные журналы и метрики кадров; совместный режим с ареной или повтором запрещён.

При съёмке пилот запускается после подготовки NPC и события `rec`: команды постановки `fight` не могут отменить lease, выданный раньше начала записи.

**Модули:** [bodypilot.py](../server/src/gothic_ai/bodypilot.py), транспорт подписки и lease — [game.py](../server/src/gothic_ai/game.py), [BodyController](../OpenGothic/common/game/bodycontroller.cpp), [BodyObservations](../OpenGothic/common/game/bodyobservations.cpp), [body-service](../body-service/src/gothic_body/runtime.py).

**Веса:** движок загружает `.bodynet` по пути выше; checkpoint SHA-256 виден в `hello.body_net`. Запасной [сервис](../body-service/deploy/run.sh) на dev-ubuntu использует CPU и `BODY_CHECKPOINT`, по умолчанию `~/gothic-ai/body/models/working/best.pt`. Веса в git не входят.

**Как выключить:** `gothic-ai serve --no-neural-body`. В engine пилот создаётся и без URL; только явный service без `--body-url` / `GOTHIC_BODY_URL` не создаёт его; разбор флагов — в [cli.py](../server/src/gothic_ai/cli.py).
В `gothic-body serve-net` проверку возраста строк только для памяти возвращает `--no-allow-stale-memory-only`; обычный runtime, gate, арена и сбор сохраняют прежнюю проверку.

**Проверки:** `gothic-body-watch-test` проверяет изменение подписки под lease и с заявкой на захват; сценарии `neural`, `neural-companion` и `neural-group` в [scripts/e2e.sh](../scripts/e2e.sh) и [scenarios/companions.py](../server/src/gothic_ai/scenarios/companions.py). `neural-group` запускает три бандита с разными символами против пассивного героя и спутника-мечника: проверяет три одновременных lease, ≥10 решений и 0 fallback у каждого, release ≤2 с от наблюдаемого конца каждого боя, p99 шага движка ≤2000 мкс (в service — p95 сервиса ≤20 мс) и пустую подписку после боя; выводит отдельные сводки с отказами по причинам и временем шага. В engine URL не нужен, в service без `GOTHIC_BODY_URL` сценарии завершаются с кодом 2 до запуска игры. Модульные проверки — [test_bodypilot.py](../server/tests/test_bodypilot.py), [test_body_control.py](../server/tests/test_body_control.py), [test_body_observations.py](../server/tests/test_body_observations.py).

Переходы проверяют `neural-talk` (`companions.py`, `LLM=fake`) и `neural-load`
([neural_load.py](../server/src/gothic_ai/scenarios/neural_load.py)). Первый начинает с
отдельного не-бандита в [neural_knockout.py](../server/src/gothic_ai/scenarios/neural_knockout.py):
нападение после слов с `AR_NONE`, настоящий нокаут без смерти, распорядок NPC и подъём героя.
Затем бандит проходит нападение после слов, бегство героя и возвращение к распорядку вдали
от героя. При возвращении героя ожидается повторное нападение `GIL_BDT` или ответ в разговоре
и новое нападение; обе ветки проверяют новый lease. После ≥20 решений или 20 с повторного
боя герой убегает. `fight_end_clean` требует `target_lost`/`npc_unavailable`, release ≤2 с
и через 2 с отсутствие lease, `body` и подписки. Победа бандита и смерть героя в этом
отрезке не требуются; враждебность бандита не меняется.
Второй загружает мирный сейв при трёх активных lease,
проверяет три причины `loading`, очистку подписки и новый бой после загрузки. Строки
результата содержат числа решений, причины конца и время release; повторный бой проверяет
отдельное соединение и подтверждённый `reset` политики. После конца боя или загрузки
отдельно проверяются отсутствие lease и активности `body` через две секунды.
Проверка `body` читает roster независимо от локальных fight и lease: оставшаяся
активность у NPC проваливает release даже при уже очищенном клиентском состоянии.
В `neural-talk` звери около площадки убираются, а мечник после нокаута и подъёма героя
перемещается дальше 60 м. Проверки относятся к боям против героя; отказы
`target_not_allowed` при наблюдении чужих боёв в приёмку не входят. После 15 с без урона
цели сценарий один раз наносит обычный удар героя (`debug player_hit`), пишет
`stall_broken`, время и последние десять решений P30. Результат содержит число и сумму
застоев как диагностику качества политики. Только отдельный нокаут мечником требует
`hero_down` за следующие 30 с; повторный бой с бандитом заканчивается бегством по лимиту.
P30 и пилот этим обходом не меняются.

Длительную работу проверяет `neural-soak` (`neural_soak.py`, `neural_soak_capture.py`, `neural_soak_metrics.py`,
`LLM=fake`): по умолчанию `--body-policy engine` без `GOTHIC_BODY_URL`, новая игра
с живым миром, герой и спутник-мечник, волны из 3–4 бандитов
примерно раз в 90 с у Кавалорна и на открытой площадке под башней. После 75 с герой
и спутник уходят; выжившие и трупы убираются, четыре символа используются снова.
Перед каждой волной герой лечится и сохраняется с убранным оружием; достаёт его
после сохранения. Загрузка мирного слота 7 не создаёт угрозу соседнему собеседнику
во время восстановления графа. Смерть героя или спутника вызывает
загрузку этого сейва, со счётчиками `hero_death` и `companion_death` в результате.
Мёртвому спутнику команды не отправляются. Плановая загрузка сохраняет боевой снимок в слот 8 и откатывает мир
к мирному сейву перед волной в слоте 7, как `neural-load`. Проверяются очистка старого
мира и новый lease с чистой памятью (в service — отдельное соединение и `reset`). Между волнами NPC отвечает
через fake-модель. Мир, P30 и правила пилота не меняются.
Готовность героя к смене оружия проверяется повтором `debug player_weapon`, без
изменения общей подписки пилота. Прямые `body_watch` сценария работают только в контроле без пилота.
При смерти героя проверка допускает естественный `hero_down` старого боя перед
обработкой загрузки; при смерти спутника — `target_down` боя с целью `companion`.
Допускается и подтверждённый `native_restored` с `target_changed_or_lost` для известной
погибшей цели. Очистка проверяет старые объекты и поколения, сохраняя запрет на lease,
незавершённые захваты/release и `body` без lease; свежие пассивные наблюдения нового мира
разрешены. `load_check` сохраняет результаты отдельных подпроверок и найденные остатки.
Для плановой загрузки остаётся `loading`. Первая плановая загрузка
обязательно ждёт боя: предыдущая смерть героя не разрешает потратить эту отметку в паузе.
`GOTHIC_SOAK_SECONDS` задаёт длительность (по умолчанию 1800 с); в коротком прогоне
моменты плановых загрузок пропорционально сжаты. Сборщик каждые 10 с пишет
`$LOG_DIR/neural_soak.jsonl`, все сводки боёв сохраняет до вытеснения из deque пилота;
итог и пороги — `neural_soak_result.json`. Отдельно считает застоявшиеся интервалы
без урона, один `stall_broken` на бой, `wait_200` и число одновременных нападающих
на ту же цель. `FightSummary` в service содержит p50/p95/p99 сервиса; в engine —
число решений, отказы по причинам, p50/p99 шага, счётчики выбранных и принятых
действий и сбросов памяти из `body_policy`. Доля `WAIT_200` остаётся диагностикой;
доля принятых команд, чистая память повторного захвата, нулевые fallback, концы
боёв и release сохраняют прежние пороги. В engine проверяется p99 шага ≤20 мс;
в service — p95/p99 ≤20 мс.
`GOTHIC_BODY_POLICY=service` с `GOTHIC_BODY_URL` выбирает прежний сервисный путь
и его данные, без принудительного переключения сценария на service.
Знаменатель захвата — живые люди не дальше 2000 см с одноручным оружием в `ZS_ATTACK`,
чья цель — герой или спутник, при наличии свободного слота. `capture_result` сохраняет каждый
пропуск и исключение с причиной, окно захвата и отказы попыток.
Захват подходящего NPC подтверждает и сводка с lease своей волны, если бой успел
закончиться между опросами; задержка захвата — верхняя граница по времени обнаружения.
Подтверждённый поздний release после `finish_deadline` — отдельная диагностика;
`release_orphan_timeout` — сбой.
Освобождение считается от первого события падения или входа в завершение боя, до cleanup.
`release_seconds` и `release_late_seconds` больше 2 с проваливают `release_clean`, даже
если к моменту опроса lease уже исчез. Подтверждённый поздний release при этом не становится fallback.
Терминальный `acceptance_timeout` проваливает порог сбоев, в том числе когда очистка
заменила причину конца на `finish_deadline`; исходный `end_trigger` сохраняет сбой.
Одиночные таймауты `accept_wait_timeouts` с последующим подтверждением остаются диагностикой.
Полный запуск на Ryzen: `BENCH_CLASS=quiet RYZEN_MAX=40m SCENARIO=neural-soak
TIMEOUT=2400 scripts/ryzen.sh e2e`; URL в engine не нужен. Штатный bench пишет 25 с первой волны при поддержке обычного
игрового времени (`cadence normal`); запись не замораживает мир.
Попадание в общий кэш движка Ryzen сохраняет запись: для опубликованного runtime
не нужен собственный `CMakeCache.txt` в новом worktree.
Для сравнения памяти `GOTHIC_SOAK_CONTROL=1` выключает пилот (`--no-neural-body`),
сохраняя подготовку мира, волны, лечение, разговоры и загрузки после смерти героя.
Родной ИИ сам заканчивает бои; подписка `body_watch` остаётся пассивной.
В контрольном результате нет метрик и порогов пилота: остаются RSS, загрузки,
тик и диагностика моста. В обоих режимах каждые 10 с пишутся
`observation_wall_gap_max_ms` и `bridge_reply_wall_gap_max_ms` по monotonic часам
сервера, число сообщений и возраст последнего сообщения; незавершённая пауза
включается в максимум. Ответы моста — `Result`, `ActionResult`, `Pong`, `RoutineInfo`,
`Snapshot`, `NpcActResult`; промежуток включает и время, когда запросов/подписки нет,
поэтому сам по себе не доказывает остановку игры. Перед загрузкой и через 2,1 с
после готовности мира снимается дополнительный RSS; перед подготовкой волны и
после её очистки — тоже. Запуск контроля: обычная команда выше плюс `GOTHIC_SOAK_CONTROL=1`.
По решению пользователя от **19 октября 2026 года** порог RSS игры — прирост в последних
20 минутах, делённый на число загрузок сейва в том же окне, не выше контроля без P30
**182,8 МиБ/загрузку + 10% = 201,08 МиБ/загрузку**. В результате сохраняются измерение,
контроль, допуск и число загрузок. Старый порог игры ≤5% снят; для сервера остаётся ≤5%.
Приёмочный пользовательский прогон на `edc32749` — **done**, 19 октября 2026 года:
сбоев 0, захват 71/73, принято 98,4% команд, RSS игры 26,5 МиБ/загрузку.
[Отчёт, графики, метрики и видео](../reports/npc-body/2026-10-19-p30-group-soak/README.md).
Шаг 5 принят; живой бой у Кавалорна (шаг 6) остаётся открытым.

**Ограничения:** двуручное оружие, луки, магия, монстры и бой с посторонними NPC остаются родному ИИ. Для нескольких боёв нужен `hello` с протоколом ≥45; при старой или неизвестной версии новые кандидаты ждут завершения текущего боя. Нужна загруженная `.bodynet` либо доступный запасной сервис политики; веса в репозитории не хранятся. P30 ждёт пассивного противника: возможны серии `wait_200` до 4 с, дальше в движке действует предел застоя (выше); в `service` серии не ограничены. Однократный удар героя не гарантирует ответную атаку; это качество политики для длительного прогона, а не критерий перехода в повторном бою `neural-talk`.

## План и журнал

28 октября 2026 года: предел застоя P30. В `surrender_live` бандит под P30 иногда за 30 с
ни разу не бил стоящего героя. Стенд `neural-still` (подготовка сцены `surrender_live`
без модели, Ryzen, 11 загрузок) до правки: P30 держал тело в 9 прогонах и ударил в одном;
в 8 — 0 ударов за 30 с, из ~95 решений 71–78 `wait_200`. Дистанция стояла на 194 или 263 см
при дальности удара 190 см. Сеть детерминирована, поэтому сцена повторяется почти всегда.
Первый вариант предела (4 с без замаха и урона → только подход, поворот и удары) дал
удар в 17 из 20 при медиане 15,7 с. Причина задержки: `attack_right` (`T_1HATTACKR`)
промахнулся 37 из 37, магнит не нашёл контакта, а свой замах снимал застой. Итог: свой
замах застой не снимает, испробованный удар ждёт остальных. 20 загрузок: P30 ударил
в 19, медиана 6,2 с, максимум 7,5 с; в одном родной бой ударил до захвата, P30 потерял
цель вплотную через 1,25 с (`target_lost`). Промахи правого удара — задача физического
ближнего боя, не P30.

Ревью 28 октября 2026 года: мирный слот 7 сохраняется до обнажения оружия.
Прежний порядок существовал в `main` с 19 октября: после загрузки вооружённый
герой вызывал предбоевой watch собеседника одновременно с восстановлением NPC
и графа. Поиск символа имеет прежний предел 250 мс; пороги soak и обработка
настоящих ошибок не менялись. Бой, включая native control, начинается вооружённым.

28 октября 2026 года: `neural-soak` переведён на engine по умолчанию без URL.
Совместимое дополнение v54 `body_policy` передаёт выбранные и принятые действия
и сбросы памяти за интервал; `FightSummary` и пороги soak используют эти данные
с прежними числовыми порогами. Явный service с URL и родной контроль сохранены.
Юнит `gothic-body` на dev-ubuntu остановлен и выключен 2026-10-28 по решению
пользователя; его запускают вручную только для опытов и сравнения.

Ревью 28 октября 2026 года: повторяемые отказы действий в `body_policy` остаются
в полной карте причин, но не увеличивают `FightSummary.fallbacks`, как в service.
Конец по `policy_fallback:*` учитывается и без финальной сводки; максимум
интервальных медиан явно называется `engine_max_interval_p50_us`. Сценарий
`memprobe` принудительно выключает пилот, чтобы измерять родные бои.

28 октября 2026 года: сервер и лаунчер переведены на `engine` по умолчанию.
Выбор делается по `hello.body_net` текущего подключения; при отсутствии сети
используется заданный TCP-сервис либо родной ИИ. Пилот поддерживает heartbeat,
цели и release без серверных действий. Сводки `body_policy` учитываются только
для своего lease; `policy_fallback:*` завершает бой как отказ политики.
E2e `neural`, `neural-companion`, `neural-group`, `neural-talk`, `neural-load`
работают без URL в engine; `neural-soak` оставлен сервисным, потому что его
пороги отдельных действий и подтверждений не представлены в `body_policy`.

28 октября 2026 года: вывод P30 подключён к движку за явным `body_acquire.policy:"engine"`
(v54). Добавлены однократная загрузка `.bodynet`, состояние сети в `hello`, память на lease,
общий путь применения примитивов и сводки `body_policy`. Серверный выбор этого режима,
лаунчер и включение по умолчанию остаются следующей задачей.

запрашивает release, а передача native выполняется на следующей границе симуляции,

## Общие правила интерфейса

### Источник решения и исполнитель

`native`, `scripted` и `neural` выбирают следующий примитив в одной точке и используют одинаковый набор действий, mask и исполнитель. Программный `scripted` provider нужен для тестирования API; он не является нейросетью.

Сейчас родной `FightAlgo` выбирает инструкции, а `Npc::implAttack` может сначала повернуть NPC вместо удара, отложить начало или превратить ожидание в отскок. Перед обучением разделяем **намерение**, **нормализованный примитив**, **принятие** и **фактическое начало**. Преобразования оформляем в общем resolver, а не оставляем только внутри пути native AI. При записи фиксируем все эти стадии. Refactor сохраняет порядок native очереди/комбо, `nextFromQueue`/`consumeAction`, задержки и число RNG calls. Нормализованный примитив не проходит второе смысловое преобразование только в neural пути. [FightAlgo](../OpenGothic/common/game/fightalgo.cpp), [боевое исполнение](../OpenGothic/common/world/objects/npc.cpp).

Запрос частого примитива не идёт через нынешний `NpcController::action`: этот путь предназначен для длинных действий и может очищать очередь. GRU подменяет источник следующего боевого решения, сохраняя исполнение текущей анимации. [NpcController](../OpenGothic/ai_bridge/npccontroller.cpp).

### Идентификаторы и время

| Поле | Правило |
|---|---|
| `session_epoch`, `world_epoch` | Меняются при соответствующем reconnect/load/world change; сообщения прежней эпохи недействительны |
| `entity_id` | Уникальный runtime ID в мире; script symbol хранится отдельно. Два NPC одного вида не делят ID |
| `control_generation` | Меняется при смене владельца, reset и восстановлении после неопределённого состояния сервиса |
| `observation_seq` | Возрастает в рамках generation; повторный запрос не обновляет hidden state дважды |
| `goal_version` | Версия структурированной задачи; действие старой задачи не применяется |
| `t_game_ms`, `dt_game_ms` | Время и интервал игры; единицы и фаза снимка зафиксированы |
| `valid_for_ms` | Максимальный возраст наблюдения для команды, проверяется движком по сохранённому локальному времени его создания |
| `command_id`, `decision_id` | Связывают выбор, подтверждение и исполнение; дубликат не запускает действие повторно |

`tickCount` игры сохраняется и загружается, может идти назад и зависит от масштаба игрового времени. Он не является общим monotonic clock для сервера и Mac. TTL по игровому времени, watchdog по локальному `steady_clock` движка и monotonic измерения каждого сервиса задаются раздельно. Нельзя сравнивать абсолютные monotonic timestamps разных машин. [GameSession](../OpenGothic/common/game/gamesession.cpp).

В обычной игре и realtime evaluation движок проверяет актуальность в игровой шкале и по локальному возрасту снимка. Пауза не создаёт новые решения; при возобновлении запрашивается свежий снимок и инвалидируются ожидавшие команды. Load всегда начинает новое поколение управления.

Для headless training с самого начала вводится lockstep: runner выдаёт наблюдение и ждёт action, пока simulated time не продвигается. CPU/GPU ожидание не расходует окно защиты и не становится игровым штрафом; отдельный wall watchdog прерывает зависший job как infrastructure failure. Если нужно моделировать задержку реакции, она задаётся явно в игровых substeps и записывается в manifest. Нельзя ускорять игру увеличением `timeMul` или просто растягивать TTL. Realtime evaluation проверяет тот же actor с реальными deadlines; качество ускоренного обучения не заменяет её.

### Предлагаемые сообщения

Названия и поля уточняются на этапе 1; номер новой версии протокола выбирается при реализации с учётом остальных изменений проекта.

| Сообщение | Назначение |
|---|---|
| `body_watch` | Подписка на компактные наблюдения с частотой и лимитом акторов; сама по себе не захватывает тело |
| `body_observations` | Пакет наблюдений, masks, `can_decide`, текущий примитив и последний фактический результат |
| `body_control` | Явная смена владельца и lease; ответ содержит generation |
| `body_action` | Один примитив для конкретного актуального наблюдения и задачи |
| `body_action_result` | `accepted`, `rejected`, `started`, `completed` или `cancelled`; reason и effective primitive |
| `body_event` | Замах, попадание, завершение lock, потеря цели, смерть; ограниченная по частоте доставка |

`accepted` означает, что арбитр принял команду; это не синоним `started` или нанесённого урона. Перед `started` повторно проверяются возраст, goal/generation, owner и допустимость. Устаревшая ожидающая команда получает `cancelled` с причиной, а не запускается после lock. У каждого отказа есть причина: stale, expired, invalid mask, owner changed, target gone или несовместимое состояние. Очередь следующего решения ограничена одним элементом; нескончаемый backlog недопустим.

Runner использует общую симуляцию настоящего движка. До refactor графические ресурсы создавались при старте, `World` обязательно создавал view, а simulation/animation updates были связаны с `MainWindow::render`. CPU ресурсы и функции мира теперь отделены от GPU allocation и presentation. [Старт игры](../OpenGothic/game/main.cpp), [Resources](../OpenGothic/common/resources.cpp), [World](../OpenGothic/common/world/world.cpp), [MainWindow](../OpenGothic/common/mainwindow.cpp).

**Выполненные работы:**

1. Выделить общий simulation step для обычной игры и runner с прежним порядком script/world tick, animation update, root motion, animation tags, hit/block/damage events и восприятий. Один вызов `GameSession::tick` недостаточен: обновление анимаций отдельно, а animation tags участвуют в нанесении урона.
2. Разделить CPU загрузку скелетов, анимаций, meshes для collision/hit geometry и weapon attachments от текстур, shaders и GPU buffers. Выключение картинки не должно выключить позу, root motion или хитбоксы.
3. Добавить headless world/view/audio adapters. Убрать playback и визуальные эффекты, сохранив игровые события звука, perceptions, callbacks и необходимые длительности. Нельзя менять условия боя отсутствием аудиоустройства.
4. Задать arena focus и активных участников с той же семантикой AI LOD, что в reference арене. Отсутствие героя/камеры не должно переводить бойцов в `AiFar` и отключать восприятия.
5. Сделать минимальный env API: `reset(scenario, seed)`, `advance(substeps/until_decision)`, `status`, `close`, и место подключения будущего `step(actions, substeps)` на этапе 4. Мелкие simulation substeps отделены от policy period; первое значение и порядок фаз берутся из reference. До готовности body API работает native AI в scripted сценариях.
6. Реализовать lockstep и realtime режимы на одной симуляции. Lockstep не ждёт wall clock между substeps и останавливает продвижение мира на ожидание policy; realtime воспроизводит нормальную скорость и таймауты. В обоих режимах сохраняется одинаковая игровая механика.
7. Подготовить user-local Linux build/toolchain, пути к игровым assets и save/setup, собственные каталоги runtime и CPU/RAM/threads/disk budgets. Игровые данные пользователя не входят в Git. Зависимости и сервисы размещаются в `~/gothic-ai/`; системные пакеты и конфигурация Docker не меняются.

**Связь с обучением:** runner, recorder, collector и `body-service` работают на одной машине. Начать с localhost/Unix socket IPC с той же feature/action schema и resolver, без ChatGPT, ASR/TTS и Mac gateway в training loop. Сервис этих моделей продолжает работать независимо; shared host resources всё равно учитываются.

**Готовность:**

- Бинарник на `dev-ubuntu` запускается без DISPLAY/Wayland и графического backend, не создаёт graphics device и не занимает renderer VRAM. Нет зависимости от запущенной игры или процесса на Mac.
- Native reference и headless используют одинаковые assets, настройки, seeds и общий simulation step. Trace сравнивается также с записью до refactor: примитивы/consume, animation hit/block timings, HP/урон, root motion, collisions и terminal outcome. При фиксированном setup существенных расхождений нет; допуски чисел установлены до оценки. Reference получают выбранным на этапе 1 способом на сервере. Parity masks добавляется на этапе 4, когда общий resolver/API готов.
- Тест отдельно подтверждает, что CPU animation update и события урона продолжают работать; бой не превращается в вызовы AI без исполняемой механики.
- Участники арены сохраняют ожидаемые восприятия и AI LOD независимо от наличия камеры. Невидимость и audio perceptions проверяются по событиям, а не по картинке.
- Lockstep даёт одинаковый игровой trace при разной wall задержке ответа policy, если simulated delay одинаков. Realtime задержки фиксируются отдельно; операционный watchdog не выдаётся за terminal поражение.
- Reset не оставляет старых targets, queues, effects, leases и event/reward state; 100 коротких последовательных эпизодов не показывают необъяснимого роста RSS, файлов, threads или зависаний.
- Отчёт содержит CPU/RAM, actual substeps/s и transitions/s, reset latency и влияние на текущие сервисы. Ускорение сверх realtime измерено либо явно указано, что runner пока не обеспечивает его; конкретный множитель не обещается.

**Первый запуск — один runner и одна симуляция за раз.** Пул процессов/несколько арен не входят в этот этап и не запускаются автоматически; это отдельное последующее решение с учётом правил проекта и измеренного запаса сервера.

**Код:** новый CMake target/entry point, общий simulation driver и CPU/headless adapters в `OpenGothic`; scripts сборки/запуска на сервере. Проверка — одна серия `body_headless_parity` со scripted/native эпизодами на `dev-ubuntu`. Перед следующими этапами headless и обычный build должны собираться, а существующие игровое исполнение и save/load сохраняться.

Первая схема содержит относительную позицию/скорость цели, расстояние и угол, HP, оружие и навык, native flags собственного действия и наблюдаемой атаки, interruptibility, предыдущий результат, native goal и `dt`. Дальность оружия и фазовые методы берутся из исполнителя. `availability_mask[12]` имеет информационную семантику; `can_decide/control_allowed/action_mask_valid=false` до lease и общего resolver этапа 4. `native_decision_eligible` отдельно отражает read-only gates. Полноценные LLM goals и execution IDs также относятся к этапу 4.

Добавлены 16 Landscape/Object лучей, лимиты четыре NPC, 256 строк очереди, 32 pending events на actor и 4096 live runtime IDs. Текущие сведения о невидимой цели равны `null`; сохраняются последнее известное положение и возраст. Debug oracle хранится отдельно. Явные fixture teleports и первая видимость после пропуска инвалидируют derivative velocity.

Периодические и событийные данные объединены одной последовательностью. Снимки имеют фазу `post_simulation_post_animation` после обновления всего мира и poses, перед benchmark mutations. Очередь ограничена, потери маркируются. Network memory будущей policy может обновляться при `can_decide=false`; внешние команды в этом этапе не исполняются.

**Готовность:**

- 10 минут пассивного наблюдения без захвата тела: корректные ID, последовательности, единицы, masks; нет NaN и неограниченных буферов.
- В normal realtime сценарии p95 интервала снимков не больше 100 мс при заданной частоте; пропуски и frame quantization отражены в отчёте.
- Событие замаха/попадания попадает в поток не позднее следующего доступного sample tick; предел измерен в игровых кадрах.
- Для четырёх активных NPC добавленная работа simulation thread — целевой p95 до 2 мс, падение headless substeps/s до 5%; влияние на realtime шаг измерено относительно baseline. Эти начальные budgets зафиксированы в контракте этапа 1, измеряются после готовности headless; клиентский frame time дополнительно проверяется при интеграции. Если лучи дороже, уменьшаем их бюджет и повторяем этот же сценарий.
- Подписка выключается без изменения поведения native AI; невидимые цели не дают актуальных privileged features actor.

**Выполнен 13 октября 2026 года.** [API и runtime](npc-body-api.md), [отчёт](../reports/npc-body/2026-10-13-body-api/validation-notes.md), [37 независимых проверок](../reports/npc-body/2026-10-13-body-api/body-api.md). **Сделать:** общий resolver/mask и source selector рядом с `FightAlgo`/`Npc::implAttack`; отдельный body controller в bridge. Сначала команды задаёт scripted provider.

Арбитр допускает одного владельца. Native AI, soft `npc_act`, управление в разговоре и новая policy не должны одновременно выбирать движение или чистить очереди друг друга. Владение разрешается по `body_control`, ограничениям сценария и цели. Сюжетный/native takeover завершает neural generation.

Mask описывает реально допустимые примитивы. Исполнитель повторно валидирует их на текущем состоянии. Команды во время неразрешённого lock не прерывают удар. В lockstep wall watchdog завершает/помечает эпизод как infrastructure failure с финальным наблюдением при возможности; коллектор не продолжает его как обычную дуэль после сбоя policy.

**Готовность:**

- Scripted provider запускает каждый примитив первой версии; trace связывает выбор, принятие, начало и завершение.
- Native и scripted используют тот же resolver и executor. Seeded primitive/queue traces до и после refactor подтверждают порядок, consume и RNG calls; с recording и API, выключенными для управления, baseline сохраняется в пределах исходной вариативности.
- Проверены duplicate, out-of-order, stale goal/generation, просрочка, неизвестная цель, смерть, load, disconnect и pause/resume. Ни один такой запрос не запускает действие повторно и не создаёт второго владельца.
- После потери provider нет вечного freeze: в realtime watchdog возвращает native на следующей допустимой границе, максимум — установленный timeout плюс оставшийся непрерываемый primitive; в lockstep завершает аварийный эпизод. Значения и режим видны в trace. Команда, принятая до lock, но утратившая актуальность к запуску, не получает `started`.
- Подключение body mode не обходит weapon/animation/collision checks и не заменяет `npc_act` частыми длинными командами.

**Проверка:** pure protocol/arbiter тесты с fake; один `body_api` e2e на серверном runner со scripted последовательностью и fault injection. Resolver и masks общие для env API и bridge. Изменения существующих [bodies.py](../server/src/gothic_ai/bodies.py), [npccontroller.cpp](../OpenGothic/ai_bridge/npccontroller.cpp) и [npcobserver.cpp](../OpenGothic/ai_bridge/npcobserver.cpp) проверяются на конфликт владельцев.

| Manifest | Schema, build/commit, hashes assets/save/setup, scenario, seeds, action/feature versions, teacher/model, simulation mode/dt/delay profile, условия и split group |
| Наблюдение | Epoch/generation/entity/seq, фаза снимка, `t`, `dt`, признаки, mask, `can_decide`, goal/style |
| Решение | Источник, decision/command ID, native intent при наличии, normalized chosen action, принятая команда |
| Исполнение | `started/completed/rejected/cancelled`, effective primitive, причина, игровые timestamps |
| Переход | Следующее наблюдение, события урона/цели, длительность, terminal/truncation/infrastructure flags |

Native teacher логируется в общей точке выбора. Текущая анимация не считается новым действием на каждом кадре. Lock ticks сохраняются для памяти, но имеют `decision_valid=false` и не заполняют весь BC loss классом `continue`. Если выбранный intent был преобразован resolver, expert label относится к нормализованному действию; исходный intent остаётся для диагностики.

Начать с 10–20 полных дуэлей и защитных микроэпизодов. Далее объём определяет покрытие: по каждому действию и существенному условию есть успешные и неуспешные примеры, включая стену, потерю цели и плохую дистанцию. Целевой минимальный набор для первого диагностического BC — не менее 20 настоящих decision labels каждого включённого класса; это проверка покрытия, а не гарантия достаточного обучения.

Splits — целые группы эпизодов, например 70/15/15. Обе стороны одной дуэли и связанные повторы одного setup остаются в одном split. Отдельный OOD набор — новые начальные положения/геометрия/противник. Normalization и class weights вычисляются только по train; test не участвует в выборе checkpoint.

**Готовность:** validator проходит все файлы; нет silent gaps, дублирования решений, смешения эпизодов, labels вне recorded mask или события будущего в признаках. Число решений, подтверждений и завершений сверяется, незавершённые помечены. Есть coverage report, manifest splits, список недостаточно представленных состояний и загрузчик ordered sequences с reset/burn-in.

Replay здесь проверяет журнал и связи, а не обещает точно воспроизвести мир без симуляции. Запись не блокирует game thread и не меняет выбор native AI.

**Хранение:** configs, manifests и сводки — в Git; сырые trajectories и checkpoints — `~/gothic-ai/body/data/` на сервере. На Mac возвращаются небольшие manifests/отчёты и при необходимости выбранные записи для анализа, без зеркала всего датасета. В Git не коммитить веса, игровые assets/saves и большие сырые журналы.

## Этап 7 Сервис и behavioral cloning

Реализация: [workflow](npc-body-bc.md), [body-service](../body-service/README.md), [remote launcher](../scripts/body-bc-remote.sh). Результаты: [validation notes](../reports/npc-body/2026-10-14-bc/validation-notes.md), [независимый audit](../reports/npc-body/2026-10-14-bc/body-bc.json). `implementation_ready=true`, `checkpoint_ready=false`: численные и runtime инварианты пройдены; дуэли требуют разбора. Сохранены шесть training runs и eval-selected веса GRU/MLP на сервере.

**Сделать:** отдельный пакет `body-service/` с `serve`, сборкой dataset, BC training и evaluation; отдельный `uv` environment в `~/gothic-ai/body/`. Сервис не загружает языковую модель.

Actor: self/goal/geometry features → MLP → GRU-256 → masked categorical primitive head. Для первой дуэли target фиксирован. При нескольких целях сохранять per-entity embeddings и использовать scorer по каждой сущности; одного pooling для выбора ID недостаточно. Critic понадобится на этапе PPO.

Сравнение: GRU и MLP со стеком 4–8 наблюдений, одинаковые features/actions/BC dataset. Первые sequence chunks — 32–64 наблюдения с prefix/burn-in; terminal/reset очищает память. Supervised loss применяется к expert decision opportunities, а locked наблюдения участвуют в обновлении памяти.

Сервис хранит состояние по epoch/entity/generation, обрабатывает наблюдение один раз и кеширует ответ для retry. На первого NPC — один последовательный запрос в работе. Gateway имеет bounded latest-observation mailbox, сообщает gap/`dt`; после timeout с неизвестным исходом начинает новую generation. Старый ответ не меняет новое состояние. Checkpoint фиксирован на весь эпизод.

Recorder дополнительно отмечает, какие наблюдения действительно обработала модель. BC и runtime используют одну sampling/coalescing семантику: `gap/dt` не восстанавливает потерянную историю. Для первой версии unexpected gap вызывает явный reset поколения/fallback; healthy нагрузка должна обрабатываться без таких пропусков. Позже устойчивость к drops обучается на таком же режиме пропусков с отдельной оценкой.

**Готовность реализации:** step и sequence forward согласуются, resets работают, недопустимые logits замаскированы, normalizer фиксирован и версия schema проверяется. Маленький overfit на выбранных траекториях доказывает работоспособность pipeline. Все model forward проверки выполняются на `dev-ubuntu`.

**Готовность первого BC checkpoint:** есть held-out per-action precision/recall, confusion matrix, whole-episode результаты в арене и сравнение с native/MLP. Замкнутый цикл проходит все задачи без softlock. Для допуска к дальнейшему обучению первичная task success не ниже native более чем на 15 процентных пунктов в диагностическом наборе; это предварительный gate, без заявления о статистической неуступчивости. При провале сначала проверить labels/features, затем расширить demonstrations.

**Ресурсный gate:** свежий `nvidia-smi`, measured CPU/GPU runtime и достаточный запас под training batch/optimizer/activations. Выбрать CPU или GPU **сервера** по замеру. Сервисы ASR/TTS/Strands продолжают выполнять свои задачи; Docker и продовые контейнеры не изменяются. Если обучение не помещается, уменьшить batch/длину, использовать CPU сервера для малого эксперимента либо отложить GPU training до доступного бюджета; дефицит ресурсов фиксируется до запуска.

- На defense микроэпизодах измеряется наблюдаемый замах → фактическое начало допустимого блока/отскока, включая sampling, RPC и игровой тик. Там, где защита разрешена, этот путь должен помещаться в измеренное на этапе 1 боевое окно. Быстрая arbitration с опоздавшим блоком gate не проходит.
- При дубликатах, задержке, пропуске и reconnect нет повторного hidden update, второго владельца или применения команды старой generation.
- Нет зависания, бесконечного отхода, удара через стену и циклического переключения примитивов; failures записаны отдельными эпизодами.
- При совместной фиксированной нагрузке деградация p95 выбранных метрик ASR/TTS/Strands не больше начального бюджета 10%; измеряется относительно baseline этого же запуска, не исторических чисел.

**Исправление поведения:** добавить targeted demonstrations на посещённых learner состояниях. DAgger использовать только при наличии teacher oracle без побочных эффектов. `FightAlgo` stateful и использует RNG: простой второй вызов teacher может изменить настоящий бой. Нужен clone состояния/RNG или независимый наблюдающий scripted oracle. Gate oracle — запрос разметки не изменяет game trace. Если его нет, DAgger откладывается, PPO остаётся следующим возможным этапом.

## Этап 9 Сильнее учителя: обучение с подкреплением

Подражание поднимает сеть максимум до уровня родного ИИ вместе с его ошибками: например, он достаёт оружие, когда его уже бьют. Чтобы NPC стал умнее, сеть дообучается на награде в той же headless арене настоящего движка. Что выучено в арене, работает в игре без переноса между симулятором и движком. Отправная точка — BC-веса этапа 8 (gate v16).

**Рабочая модель этапа 9 — P30** (`edcb77c3…`, первый прогон PPO с self-play) вместо BC gate v16, по решению пользователя 17 октября 2026 года после процедуры gate и realtime-дуэлей. От неё считаются следующие сравнения и прогоны. Веса с критиком и записью происхождения лежат в `~/gothic-ai/body/models/p30` на Ryzen и dev-ubuntu, ссылка `~/gothic-ai/body/models/working` указывает на рабочую модель. ### 9.3 Recurrent PPO

**Первый прогон (16 октября 2026 года), dev-ubuntu.** PPO от R3m: критик-MLP по признакам и

был собран под SSE2, и обход дерева в лучах шёл через программные заглушки. Правка: опция CMake `OPENGOTHIC_JOLT_X86=x86-64-v3`
(AVX2, F16C, BMI1, LZCNT, без FMA). Сборка runner (`body-api-remote.sh`) включает её, если хост это
умеет; по умолчанию остаётся `portable`. Jolt собран с `CROSS_PLATFORM_DETERMINISTIC`, поэтому
результат тот же: 128 из 128 lockstep-эпизодов совпали с прежним runner бит в бит, native-off совпал с
native-base-v1, native-эпизоды gate совпали с v5 в 95 из 95. Код Jolt на шаг — 6,1 мс вместо 8,4 (у
Bullet было 7,7), шаг — 22,9 мс CPU вместо 25,3 (до слияния 21,7). На 64 + 64 отложенных
дуэлях P30 окно p5 после первой секунды — 8,1 мс (было 4,8–5,1, до слияния 9,4–10,0). Отклонены
2 команды из 2188 (было 100 из 2361), тик в тик с lockstep — 62 из 64 открытых и 63 из 64 у стены.
По процедуре gate (`stage9-rt-eval-v6`) P30 проходит все пороги, включая нагрузку 4 NPC: доля
нейронного управления 0,985 (на v5 — 0,918). [Отчёт](../reports/npc-body/2026-10-18-runner-step-jolt/README.md).

**Скорость сбора после физики ударов (28 октября 2026 года).** Сбор 1024 дуэлей на 24 воркерах Ryzen занимал
166 с, втрое медленнее октябрьского. Шаг runner почти не подорожал: 1,38 мс CPU на тик против 1,33.
Дуэли стали в 2–2,5 раза длиннее: из-за физических попаданий и равновесия P30 промахивается в 33–40 % ударов
против 1,8 %. Python на тик подорожал вдвое, потому что бои сети против сети удлинились сильнее всего.
Воркеры простаивали, потому что дуэли раздавались заранее поровну. Правки:
- общая очередь дуэлей и сэмплы из потоков самой дуэли;
- `Cloth::setEnabled` больше не пересчитывает все полотнища мира каждый тик (0,16 мс на тик, и в игре тоже);
- замороженный мир не обновляет якоря возврата NPC вне арены (0,14 мс).

На тех же дуэлях сбор ускорился с 201,5 до 165,0 с. Lockstep-журналы до и после совпали в 64 эпизодах
из 64, итоги не зависят от числа воркеров. Runner больше не копирует базу на хранилище, и `--fork-reset`
работает с пустым хранилищем. Тик в тик с realtime lockstep на `main` уже не совпадает: realtime-шаг в первую секунду
боя вырос до 29,5 мс из 33, и первая команда опаздывает на тик. На 16 дуэлях P30 одинаково с правками и без них.
Совпало тик в тик 0 пар, исход — 15 из 16. [Отчёт](../reports/npc-body/2026-10-28-collect-speed/README.md).

**Сделать:** actor/critic, masked distribution, synchronous rollout collector и recurrent updater поверх параллельных runner из 9.1. Старт с весов 9.2 или BC; KL-штраф к BC-политике удерживает поведение «готическим». Противники: сначала родной ИИ, затем пул собственных прошлых версий (self-play) и смешанные противники, чтобы сеть не училась только на слабостях родного ИИ. Оценка всегда против отложенных противников и на свежих seed.

**Расписание решений.** Lockstep-сбор принимает решения в те же моменты, что realtime: это проверено (`scripts/body_schedule_equivalence.py`, см. 9.2). Проверку повторять при любом изменении коллектора, runtime или runner. Сбои realtime (команда, опоздавшая на тик) до слияния с main были редкими — 1 на 3,5 тыс. решений; после слияния их стало около 4 %, в основном в первую секунду боя, а с Jolt на x86-64-v3 они снова редки — 2 на 2,2 тыс. (см. выше). Их можно добавлять при сборе. Финальный отбор весов — realtime-оценкой драйвером gate; в оценку входят дуэли у стены (`near_wall`).

**Правила сбора** (из исходного плана): один frozen checkpoint собирает batch в lockstep, обновление происходит после сбора; новые веса включаются между эпизодами. Перед новым on-policy batch завершить текущие эпизоды старой версии и сбросить управление/hidden state; лишние эпизоды входят в прежний batch. Не смешивать незавершённый rollout старых весов с новым behavior policy. Начать с коротких задач дистанции и защиты, затем native дуэли. Увеличивать rollout/сложность после стабильного малого эксперимента, без автоматического запуска нескольких игр.

В rollout сохранять sampled action, его log-probability, value, mask, behavior-policy version, начальный hidden state фрагмента, rewards и terminal semantics. **Фактическое native fallback действие не подставляется вместо sampled action в PPO ratio.** Rejection/delay либо моделируется как часть среды с исходным action, либо affected fragment исключается из actor update по явно заданному правилу.

GAE не пересекает resets. Смерть/terminal success не bootstrap; при time-limit truncation value берётся из финального наблюдения до reset. Смену владельца, crash и потерю связи не выдавать за обычное terminal поражение; для первой версии такие rollout fragments отдельно маркировать и не использовать в actor update. Переменный `dt` учитывать в rewards/discounting либо собирать на фиксированной сетке с отдельным признаком lock, не смешивая два режима молча.

Награды: исход задачи, нормализованный HP урон, полезная защита при надёжном событии, timeout/stuck cost. Не награждать попытку атаки или каждый прожитый тик так, чтобы выгодно было бесконечно стоять/убегать. Отдельные проверки — block spam, infinite kite, wall attack, animation exploits, нарушение цели и границы арены.

**Готовность механики:** no-update ratio около 1, masks совпадают при sampling и recomputation, sequence/reset/value targets проходят содержательные тесты; небольшой цикл rollout → update → новый эпизод заканчивается без утечки состояния. Все numerical/model тесты — на сервере.

**Готовность качества:** сравнение native, BC GRU, PPO GRU и MLP на общей серверной evaluation конфигурации; итоговый release набор проверяется в realtime headless режиме с зафиксированным delay profile. Для debug достаточно 5–10 парных seeds на сценарий; screening checkpoint — 20–30. Для release начать со 100 парных seeds на каждый основной сценарий и показать 95% интервалы; при недостаточной точности расширить по заранее выбранной цели. Отдельно показывать lockstep throughput и realtime качество, не смешивать их.

**Общий release gate для BC или PPO:** нижняя граница интервала разницы task success с native выше −10 процентных пунктов на основных задачах; пройдены stability/latency/coverage/OOD критерии и проверки exploits. Этот gate применяется и до PPO.

**Дополнительный gate продвижения PPO checkpoint:** хотя бы одна заранее выбранная основная метрика улучшена относительно BC без ухудшения остальных сверх бюджета; эффект и интервалы показаны в отчёте. Если PPO не улучшает BC, сохраняем лучший BC и разбираем среду/награды — завершение PPO job не доказывает готовность PPO policy.

Для содержательного архитектурного/алгоритмического сравнения — три training seeds при доступном бюджете. Каждая on-policy модель собирает собственные rollouts; фиксируются сценарии и interaction budget, а не общий PPO dataset. Стиль и читаемость поведения оцениваются отдельно от win rate.

### 9.4 Новые действия и ситуации

Сейчас сеть включается, когда меч уже в руке и бой идёт. Тактика «достать оружие заранее» недоступна, пока нет таких действий и эпизодов, начинающихся до боя.

**Сделать по очереди, каждый пункт с тестами и gate как на этапе 8:**

1. Достать, убрать и сменить оружие; эпизод начинается с подхода противника.
2. Лук и арбалет: выстрел и смена на ближнее оружие при сближении. Учитель есть: родной ИИ лучников и ArcherAi проекта.
3. Задачи на память в ближнем бою: цель ушла из поля зрения и вернулась, два противника, бой у стены или обрыва, волк с другим ритмом атак.
4. Зелья и предметы в бою. Если родной ИИ так не делает, учителя нет: только награда (9.2–9.3). Отдельно решить баланс: кто пьёт, сколько зелий, ограничения характера.

Препятствия и лазанье остаются на этапе 11.

### 9.5 Сравнение архитектур

MLP, GRU и Mamba (state-space) с одинаковым бюджетом параметров и тремя training seed на задачах 9.4, где нужна память. На задачах этапа 8 все три дают 20/20, поэтому сравнение там ничего не различает. Победитель определяется по качеству, задержке шага и стабильности обучения.

### Сила и характер

Слишком сильный NPC не всегда хорош для игры. Сила политики регулируется: температура, KL к BC, черты характера (трус, берсерк) как часть задачи, уровни сложности. Стиль и читаемость поведения оцениваются отдельно от процента побед, по видео.

2. **Пилот тела на сервере — сделано 17 октября 2026 года**
   ([bodypilot.py](../server/src/gothic_ai/bodypilot.py)). Один человек с одноручным мечом против
   героя, вне разговора и attached, не спутник: `body_watch`, свежее периодическое наблюдение,
   попытка `body_acquire` в realtime. Цель-герой подтверждается существующим `story_eval`
   (`NPC_GETTARGET` и `NPC_ISPLAYER`), watch остаётся `[npc]`.
   Roster с `fight`/`ZS_ATTACK` также запускает наблюдение: одиночному нападающему NPC
   не нужны боевые события героя или свидетели. Повторные roster не перезапускают попытку.
   До lease `control_allowed` не требуется; безопасную границу проверяет движок. Пилот передаёт
   `await_boundary_ms=1500`, ограничивая заявку оставшейся частью окна захвата в 5 секунд,
   и ждёт ownership-события. Истёкшие заявки повторяет не чаще 150 мс; принятие заявки
   ещё не означает выдачу lease. После подтверждённого захвата устанавливает TCP-соединение
   и делает `reset`, затем все свои периодические строки без перепаковки идут в TCP-сервис.
   Решения передаются в `body_action` с TTL 100 мс. Отдельная задача шлёт
   heartbeat каждые 250 мс от момента отправки; lease timeout — 2000 мс. Ответы политики и
   `body_events` не задерживают продление. Roster с `activity: "body"` отмечает NPC занятым
   для остальных потребителей сервера, пока пилот держит его lease.
   Захват посреди родного `ZS_ATTACK` допускается на безопасной границе: только помеченные
   действия самого боевого цикла (`Attack`, `Wait`, `GoToNpc`, `TurnToNpc`) и переход к той же
   цели. При захвате они очищаются; реплики, сюжетная очередь, чужая цель и физические
   блокировки дают отдельные причины отказа. Пустая очередь арены сохраняет прежний путь захвата.
   TCP-соединение и `reset` готовятся сразу после acquire, под работающим heartbeat.
   **Доработка 18 октября:** отложенная заявка исполняется на первой безопасной границе
   внутри NPC tick, без изменения частоты опроса; до этой границы работает родной бой.
   Истечение окна, смена цели, падение, разговор, release, disconnect, пауза и загрузка
   отменяют заявку с причиной. ID заявки связывает receipt и ownership-событие с фактическим
   seq захвата; отмена по ID закрывает гонку с выдачей lease и потерей ответа.
   Сводка содержит число заявок/захватов и p50/max времени от отправки до подтверждения lease.
   Отказы `stale_observation`, `expired`, `expired_wall`, `command_busy`, `target_invalid`,
   `masked` и `locked` пропускают строку: живое состояние изменилось после наблюдения.
   Десять таких отказов подряд, включая смешанную серию, завершают бой; принятое действие
   сбрасывает серию, строка без действия её сохраняет. Ошибки lease/identity, протокола,
   инфраструктуры и смена оружия завершают бой сразу. Сводка сохраняет счётчик отказов
   по каждой причине, общую серию `transient_rejections_consecutive` и p50/p95 стадий
   «приём пакета → запрос политики → ответ → отправка действия», без времени ACK моста.
   **Подвисания игры (18 октября):** из пачки под lease все строки, кроме последней, идут с `memory_only: true`; последняя старше 100 игровых мс — тоже. Номера и порядок сохраняются; `serve-net` по умолчанию разрешает старые строки только для памяти, обычный runtime — нет (`--no-allow-stale-memory-only` возвращает проверку).
   `observation_too_old` входит в общую серию временных отказов до десяти; при `process.hidden_reset` перед следующей строкой выполняется `reset`. Сводка хранит строки только для памяти, отказы по возрасту, сбросы памяти и максимальные число строк/отставание пачки.
   Пилот запрашивает `include_capabilities` при `reset`, новый сервис объявляет `memory_only_step`; со старым остаётся прежний формат `step`, а пилот подавляет действия накопившихся строк сам.
   Ответ `step` ожидается 100 мс; после таймаута строка пропускается без действия.
   Бой завершается после пяти таймаутов подряд или секунды без ответа при ожидаемом `step`,
   даже если новые наблюдения не приходят. Своевременный ответ, включая строку без действия,
   сбрасывает серию таймаутов. Поздний ответ со старым ID подтверждает связь, но не выдаёт
   действие, не отвечает за новый запрос и не сбрасывает серию. Сводка хранит число таймаутов,
   серию, p95 ожидания до таймаута и длительность отсутствия ответа. Прежняя метрика сервиса
   включает ожидания запросов, завершившихся таймаутом; её порог не менялся.
   Невидимость цели под lease сама не завершает бой: движок получает время на свой поворот
   к цели. `present/current_valid=false` завершают бой только после 1000 мс подряд по времени
   наблюдений; валидная строка сбрасывает отсчёт. Скрытый HP не считается падением.
   Смена ненулевого ID цели, падения и смена оружия остаются немедленными причинами конца.
   Только событие своего lease `native_restored` с `release_reason=target_visibility_lost`
   отображается в `target_lost`. До acquire по-прежнему нужна видимая валидная цель.
   Сводка и лог сохраняют последний и максимальный интервалы невидимости в игровых мс
   и wall-секундах, причину release и последние 10 решений с seq, временем, действием
   и результатом отправки. Игровой интервал при native release фиксируется `t_game_ms`
   события; wall-интервал считается от обработки первой невидимой строки до получения события.
   При завершении, смене цели или владельца, разговоре, загрузке, разрыве, fallback, ошибке,
   исчерпании бюджета таймаутов или пяти минутах боя: `body_release`, `end_episode`, очистка watch. В логах —
   причина конца, решения, fallback и задержки p50/p95. Тесты с фальшивым мостом и TCP-сервисом
   проверяют захват, команды, фильтрацию строк, ограничения NPC и возврат скриптам.

   **Исходные ограничения.**
   - До шага 2 пилот вёл один `self.npc` и не начинал новый бой, пока у моста был любой lease.
   - До v45 мост менял `body_watch` только без владельцев тела и при этом сбрасывал наблюдения.

   **Шаги.**
   1. **Подписка растёт под lease (движок, протокол).** `body_watch` принимает новый список, если
      все NPC под lease или с заявкой на захват остаются в нём. Их epochs, `observation_seq` и
      lease не меняются, новые NPC получают поток с ближайшего тика. Убрать можно только свободного
      NPC; смена частоты при владельцах отклоняется. Протокол v45 (19 октября): обычный мост
      сохраняет identity, lease и заявки при смене списка; без владельцев остаётся полный сброс.
      Проверка: тест моста или общего контроллера показывает:
      lease A живёт, watch [A, B] принят, A продолжает получать строки и действия, B захватывается;
      сценарий `neural` зелёный на Ryzen.
   2. **Пилот ведёт несколько боёв (сервер) — готово, 19 октября 2026 года.** `BodyPilot` — диспетчер. Каждый бой —
      отдельный объект: свой lease, своё TCP-соединение к сервису (отдельный эпизод и память GRU),
      heartbeat, таймауты и сводка. Общие — подписка, roster и выбор кандидатов. Лимит —
      `--neural-body-max`, по умолчанию 4. Конец одного боя не трогает остальные; загрузка,
      отключение и выключенный пилот завершают все. Готово, когда `test_bodypilot.py` с фальшивым
      мостом и сервисом проходит: три боя сразу, независимый конец, рост подписки, отказ пятому;
      прежние тесты зелёные.

      Реализация: у боя отдельные heartbeat, watchdog, окно захвата, очередь наблюдений, серии
      отказов и таймаутов. Пакеты наблюдений раздаются по NPC; переполнение завершает только
      его бой. Диспетчер хранит общую подписку и выбор кандидатов; `handles(npc)` учитывает
      также наблюдение и захват. `last_summary` сохраняет последнюю сводку, `summaries` —
      последние 32. Для нескольких боёв нужен `hello` с протоколом ≥45; при старой или неизвестной
      версии новый кандидат получает `watch_busy` без изменения подписки; отказ отражается только в логе и счётчике, не в сводках боёв. Отказ `body_watch`
      от движка с протоколом ≥45 остаётся `watch_refused`. В обоих случаях действующие lease
      и соединения сохраняются, повтор разрешается после `REACQUIRE_INTERVAL`.

## Этап 11 Навигация и несколько целей

Этот этап расширяет готовый melee слой, не блокирует первую версию.

Добавить waypoint candidates и локальную геометрию; goal `move/follow/protect/retreat`, несколько видимых сущностей и target scorer с сохранёнными embeddings. Штатный графовый поиск остаётся в движке. Policy выбирает локальную позицию/обход/восстановление после застревания; длительное retreat получает полноценный исполнитель вместо одного jumpback.

Сначала отдельные навыки и сценарии: открытый маршрут, угол, узкий проход, движущийся NPC, потеря/недостижимость цели. Затем сочетать с боем, проверяя, что navigation training не разрушает уже обученный duel skill. Если общая GRU ухудшает навыки, использовать task heads или отдельные небольшие policy.

**Готовность:** на held-out маршрутах success не хуже native сверх заранее установленного допуска; stuck/collision rate и длина/время пути имеют отдельные метрики. В тупике NPC прекращает бесконечную команду и сообщает наверх `goal_unreachable`. Изменение цели и target IDs не повреждает hidden state, сопровождение соблюдает дистанцию, OOD сцены покрыты отчётом.

## Структура реализации и артефактов

Новые пути ниже — предлагаемые места, окончательные имена выбираются перед кодом соответствующего этапа.

| Область | Место |
|---|---|
| Headless engine | Новый `gothic-body-runner` CMake target/entry point, общий simulation driver, CPU resource/view/audio adapters |
| Headless env и collector | Новые env/runner modules в `body-service/`, localhost/Unix socket IPC, общие scenario/setup configs |
| Body observation/controller | Новые `OpenGothic/ai_bridge/bodyobservation.{h,cpp}`, `bodycontroller.{h,cpp}` |
| Общий primitive resolver | Рядом с `common/game/fightalgo` и `Npc::implAttack`; регистрация в сборке движка |
| Gateway/body loop | Новый `server/src/gothic_ai/body/`; транспорт через существующий `GameLink`, координация с `Bodies`/talk/planner |
| Remote inference/training | Новый пакет `body-service/`; `schema`, `dataset`, `model`, `bc`, `ppo`, `serve`, deploy scripts |
| Dataset/evaluation configs | Новый `evals/npc-body/` с README, manifests, seeds, scenario matrix и отчётами покрытия |

Checkpoint bundle включает веса, feature/action schema, train normalizer, model config и версии dataset/кода. Env manifest дополнительно фиксирует engine/asset hashes, phase order, simulation substep и delay profile. Gateway не импортирует PyTorch и не загружает веса на Mac. Веса и shared training buffers не должны занимать место в рабочем репозитории игры.

## Порядок проверок и расход ресурсов

Во время реализации после правки — pytest только изменённого модуля и **один** соответствующий e2e/bench сценарий, с вариантами внутри него. Body/headless симуляции и model проверки — на `dev-ubuntu`; локальные тесты используют fake и небольшие данные. Перед PR — полный pytest и регрессия общих e2e один раз: слой затрагивает движок, protocol/game и управление разговором. Обычная игра на Mac нужна для короткой интеграционной проверки, не для training/evaluation серий.

Перед обычной игрой проверить `pgrep -fl Gothic2Notr`; перед headless запуском на сервере проверить также наличие `gothic-body-runner` и runner job/lease. Если симуляция занята другой сессией, дождаться её. Одна игра/runner за раз, pytest и e2e последовательно. Большие evaluation серии выполняются для выбранного checkpoint, не после каждого изменения файла.

Перед runner/training/inference сверить CPU/RAM/threads/disk и GPU бюджеты. Исторический снимок с примерно 2 GiB свободной VRAM не гарантирует доступность сейчас. Headless освобождает renderer VRAM, но всё равно конкурирует за CPU/RAM; выставить измеренные лимиты и не занимать все ядра сервера. ASR/TTS/Strands и продовые контейнеры не останавливать ради прохождения gate; GPU training не запускается фоном без известного бюджета. Для модели используются отдельные venv и user units; конфигурацию Docker и системные пакеты не менять.
