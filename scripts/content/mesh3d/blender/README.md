# Обработка мешей пилота 3D

Ручной офлайн-конвейер для [пилота генераторов](../../../../reports/content/2026-10-3d-generators/README.md). Игра его сама не запускает. Концепты и генерация — отдельные шаги.

## Модель по концепту

Основной путь этапа 2 с 2026-10-20: модель строится по своему концепту `image_gen`, генераторы 3D не используются ([бочка](../../../../reports/content/2026-10-barrel-from-concept/README.md)).

```sh
B=/Applications/Blender.app/Contents/MacOS/Blender
$B -b --factory-startup -P scripts/content/mesh3d/blender/barrel.py -- \
  scripts/content/mesh3d/blender/barrel.json /absolute/output/barrel
$B -b --factory-startup -P scripts/content/mesh3d/blender/compare.py -- /absolute/compare.json
uv run --with numpy --with pillow python scripts/content/mesh3d/iron_material.py \
  /absolute/maps/own_prop_iron_band --target R G B
```

Своя текстура на предмет:

```sh
$B -b --factory-startup -P scripts/content/mesh3d/blender/bake_atlas.py -- \
  scripts/content/mesh3d/blender/barrel-atlas.json /absolute/output/barrel-atlas
uv run --no-project --with numpy --with pillow python scripts/content/mesh3d/pack_prop.py \
  --bake /absolute/output/barrel-atlas --visual NW_HARBOUR_BARREL_01 --name mesh3d-barrel-atlas \
  --output ~/.local/share/gothic-ai/content-staging/mesh3d-barrel-atlas
```

`bake_atlas.py` даёт модели новую развёртку-атлас и запекает в неё плиточные материалы этапа 1. Сверху добавляются тон каждой детали, тёмные щели по краям досок, светлые стёртые кромки, выгоревший верх, мокрый низ и AO. Затем каждая зона растягивается по контрасту и возвращается к своему замеренному среднему цвету. Среднее считается по всем текселям зоны; `measure_ao` в настройках задаёт зоне порог запечённого AO, и тогда среднее берётся только по открытым наружу граням, без изнанки досок, стыков и концов под брусками. Усиление получает вся зона. Пути `glb` и `maps_dir` в настройках — внутри `content-staging`. В GLB остаётся одна UV, атлас, и материалы атласа с группами звука. `pack_prop.py` упаковывает атлас в DDS один раз и даёт каждому материалу GLB свой ключ `materials.json` на эти файлы.

Износ по модели, как у кровель из частей ([путь](../../../../docs/remaster-pipeline.md#материал-из-модели)), включается ключами настройки. Без них предмет печётся как раньше, бит в бит:
- `crevice` — грязь или мох (по цвету) в стыках между деталями, по короткому AO на 2 см;
- `streaks` — потёки вниз от деталей выше. Из каждого текселя луч идёт вверх вдоль поверхности, по пути воды, и находит обруч или край над ним: под железом ржавчина, под другой деталью грязь. Потёки затухают на `length` метрах и идут столбиками шириной около `column`;
- `wet_roughness` — мокрый низ глаже, до этой шероховатости; ржавчина и грязь матовые.
- `metal_scale` — множитель металличности зон из `metal`. Ржавое и грязное железо почти не металл, а у металла нет рассеянного света: в тени обручи бочки при 0,67 выходили чёрными полосами, хотя у оригинала они светлее клёпок. У бочки — 0.

Износ кладётся до того, как зона приводится к своему среднему цвету, как и AO. Маски пишутся рядом с атласом (`atlas-crevice.png`, `atlas-rust.png`, `atlas-drip.png`, `atlas-wet.png`).

Включены пока только у бочки порта (`barrel-atlas.json`), [проверка в игре](../../../../reports/content/2026-10-barrel-from-concept/README.md#износ-по-модели-и-обручи).

Рельеф плитки запекается ослабленным: фильтр этапа 1 (`bakeoff.filtered_maps`) растягивает рельеф любой плитки на полный диапазон, и в игре дерево выглядело выдавленной имитацией, а ткань — твёрдой и искрящейся. Сила карты нормалей плитки — по материалу зоны: ткань, ковёр и мешковина ×0,12, свои процедурные стекло, воск и кость ×1, всё остальное ×0,25; `tile_normal` в настройках задаёт её для зоны. У ткани, верёвки и меха нет светлых стёртых кромок (`edge_wear`, по умолчанию 0,7 маски кромок). Обе величины пишутся в `metrics.json` по зонам. [Замеры и игровое сравнение](../../../../reports/content/2026-10-prop-relief/README.md).

Ящик и замер оригинала. Плитки ящиков сначала собирает `market_tiles.py --spec scripts/content/mesh3d/blender/crate-tiles.json`, атлас пишется в набор рынка:

```sh
ST=~/.local/share/gothic-ai/content-staging/market-set
$B -b --factory-startup -P scripts/content/mesh3d/blender/crate.py -- \
  scripts/content/mesh3d/blender/crate.json $ST/build/crate
$B -b --factory-startup -P scripts/content/mesh3d/blender/bake_atlas.py -- \
  scripts/content/mesh3d/blender/crate-atlas.json $ST/build/crate/atlas
# C++20 против ZenKit, как target-measures.cpp: позиции в NEWWORLD.ZEN и средний цвет текселей меша
c++ -std=c++20 -O2 -DZKNO_REM=1 -D_ZK_WITH_MMAP=1 -IOpenGothic/lib/ZenKit/include -I<zenkit build>/include \
  scripts/content/mesh3d/prop-survey.cpp <zenkit build>/libzenkit.a <zenkit build>/vendor/libsquish/libsquish.a -o prop-survey
./prop-survey "<Gothic II>" NW_HARBOUR_CRATE_01.MRM
```

Стол и лавка строятся так же: `table.py` + `table.json`, `bench.py` + `bench.json`, атласы — `table-atlas.json` и `bench-atlas.json`. Общие детали лежат в `parts.py`: доска, брусок-ножка с сужением, камень, Г-уголок, полоса, гвоздь и экспорт с номерами деталей. Ящик собран тем же модулем, GLB от этого не изменился. Зоны цели можно переопределить в настройках (`zones`): у лавки опоры каменные, как у оригинала, с группой `STONE`.

Сундук — модель MOB с двумя вложениями: `chest.py` + `chest.json`, атлас — `chest-atlas.json`. Цель записана в настройках (`goal`), потому что этого сундука нет в наборе пилота. `finish_nodes` из `parts.py` пишет каждый набор деталей отдельным узлом GLB с именем вложения (`BIP01 CHEST_BIG_0` — корпус, `BIP01 CHEST_BIG_1` — крышка); `finish` — тот же путь с одним узлом. Крышка строится целиком перед осью петли (`hinge` — начало узла крышки в bind pose) и выше неё, поэтому при повороте не входит в корпус; запас скрипт пишет в `metrics.json`. Грани внутри закрытого сундука получают свою зону `INNER` со своей целью цвета. С настройкой `nodes` `bake_atlas.py` запекает узлы в общий атлас и снова делит их по именам. [Отчёт](../../../../reports/content/2026-10-chest-from-concept/README.md).

`../barrel-material-measures.cpp` — зональный замер бочки по её текстуре `NW_CITY_BARREL_01` (бок, днища, строки обручей). Собирается так же, как `prop-survey.cpp`, и даёт цели `barrel-atlas.json`. Плитки дерева всех четырёх предметов — материалы `mesh3d-barrel-wood-stave` и `mesh3d-barrel-wood-head` в реестре.

`crate.py` и `crate_pile.py` с 21 октября 2026 года строят ящики порта по замыслу из [отчёта](../../../../reports/content/2026-10-crates-redesign/README.md). Общий ящик — `harbour_crate.py`:
- на торцах угловые стойки поверх горизонтальных досок и верёвочная ручка между ними;
- на длинных гранях горизонтальные доски разной ширины и одна вертикальная планка посередине;
- крышка из досок вдоль ящика, тёмный короб за щелями в своей зоне `OWN_PROP_WOOD_INNER` со своей целью;
- износ геометрией: разная ширина и небольшой наклон досок, доски чуть выступают или утоплены, одна сломана с дырой на короб, одна доска крышки сдвинута.

Доски и бруски меряются по открытым текселям (`measure_ao` 0,5), цель — цвет оригинала в кадре: [отчёт](../../../../reports/content/2026-10-crates-redesign/README.md#цвет-по-видимым-граням). Металла нет, кроме гвоздей одиночного ящика. Шляпки гвоздей трёхгранные и утоплены в дерево на 1 мм, без основания; это единственные открытые рёбра, их число — в `metrics.json`. Шляпки касаются bbox цели. Каждая деталь пишет свой номер в атрибут `_part`, и `bake_atlas.py` тонирует по нему. Плитка дерева — `own_prop_wood_crate`, четыре доски на плитку; бесшовна только вдоль волокна (`axes: v`): иначе сшивка сдвигает стыки досок с четвертей, и каждая доска модели ловит полосу соседней. Прежний ящик пилота с рамкой на каждой грани и Г-уголками — в истории git и [отчёте пилота](../../../../reports/content/2026-10-crate-from-concept/README.md). `prop-survey.cpp` выводит только числа: где стоят копии визуала (для кадра стенда) и средний цвет текселей, которые использует меш, с делением на «дерево» и «серое» по R/G.

`barrel.py` снимает профиль с альфы вида спереди (`front` — путь внутри `content-sources`), остальные части берёт из `barrel.json`: число клёпок, положение и высоту обручей, стык, венец, доски крышки. Пишет `model.glb` и `metrics.json`. `compare.py` рендерит GLB с одним светом и камерой по списку видов, материалы `ours` берёт из `maps_dir/<ключ>/`. `iron_material.py` делает бесшовное кованое железо со средним цветом замера.

### Вывернутые грани

`parts.py` в конце сборки пересчитывает нормали всех граней (`recalc_face_normals`). У детали — открытой оболочки он может выбрать не ту сторону. Cycles освещает обе стороны грани, поэтому в Blender такая деталь выглядит верно, а в игре видна изнанкой и выходит чёрной; так было со свечой рынка (#343). `"backfaces": true` в настройках `compare.py` заливает изнанку каждой грани плоским пурпурным цветом. Деталь, у которой видна изнанка, становится пурпурной с любого вида.

`"fit": "extent"` (в настройках или у предмета) вписывает в `target_height` самую длинную сторону bbox, а не высоту: длинный прилавок и плоский ковёр не вылезают из кадра.

```sh
cat > /absolute/backfaces.json <<'EOF'
{"out_dir": "/absolute/out", "size": 512, "samples": 16, "target_height": 1.0, "fit": "extent",
 "maps_dir": "/absolute/none", "scales": {}, "backfaces": true,
 "views": [{"name": "fl", "elevation": 18, "azimuth": 35, "distance": 3.0},
           {"name": "bl", "elevation": 18, "azimuth": 145, "distance": 3.0},
           {"name": "top", "elevation": 70, "azimuth": 20, "distance": 3.0}],
 "items": [{"name": "candle", "glb": "/absolute/candle/atlas/model.glb", "materials": "own"}]}
EOF
$B -b --factory-startup -P scripts/content/mesh3d/blender/compare.py -- /absolute/backfaces.json
```

Пурпур помечает только то, что видит камера. Отражённые лучи его не несут: иначе две совпадающие грани (шейка и кольцо ручки свечи) красили бы друг друга. Пурпур на виде — не всегда ошибка. Одностороннюю деталь (задник у стены, подложку щита) видно изнанкой только оттуда, куда в игре не заглянуть. Ошибка — пурпур на стороне, которую видит игрок.

Чинить такую деталь надо в её `<item>.py`:
- замкнуть оболочку: скрытая крышка, как у свечи, концов каната и ушей волка; у замкнутой оболочки пересчёт не ошибается;
- деталь, которая задумана односторонней (клёпка группы бочек, кисть бахромы ковра, подложка щита), строить с верным обходом граней и брать номер через `P.new_part(wound=True)`. Её грани не попадают в пересчёт нормалей, и обход остаётся таким, как его задал скрипт. Шляпки гвоздей `parts.py` обходит наружу сам.

Ещё один источник изнанки — вогнутый многоугольник. Общая триангуляция может положить треугольник поверх вогнутого угла, и он смотрит назад. Так было с передней гранью доски таблички волка; теперь её грани собраны веером от центра.

Тест «нормаль от центра детали» для этого не годится: у открытой полосы и одиночной грани нет внутренней стороны, и знак теста ничего не значит. Проверка 2026-10-21 прошла по всем 19 предметам рынка и пяти предметам пилота. Изнанку нашли у семи предметов рынка, у пилота её нет; разбор — в журнале [`docs/own-content.md`](../../../../docs/own-content.md).

### Совпадающие грани

Чёрные клинья на рендере без пурпура — другая ошибка: две детали заходят друг в друга, и их грани лежат в одной плоскости. Cycles затеняет такое место чёрным, в игре оно мерцает (z-fighting). Так было у сундука: соседние сегменты обода крышки перекрываются в стыке, и их торцы совпадали. Лечится сдвигом одной из граней на 1–3 мм: у сундука каждый второй сегмент уже на 3 мм с обеих сторон (`rim_step`), а доски стенок кончаются у стоек, а не заходят в них.

`coplanar.py` находит такие места без рендера. Ему нужен GLB сборщика `<item>.py`, а не GLB атласа: номер детали есть только в первом (атрибут `_part`). У модели без `_part` (`barrel.py`) деталью считается связный кусок.

```sh
$B -b --factory-startup -P scripts/content/mesh3d/blender/coplanar.py -- \
  /absolute/build/cart/model.glb /absolute/build/bench/model.glb --json /absolute/coplanar.json
```

Пара — два треугольника разных деталей в одной плоскости (ближе 0,1 мм), которые перекрываются больше чем на 0,1 мм².
- Нормали смотрят в разные стороны: детали касаются гранью. Этих граней не видно, править нечего.
- Нормали смотрят в одну сторону: грани рисуются на одной глубине. Скрипт берёт точки в 0,3 мм перед перекрытием:
  - `hidden: inside …` — каждая точка внутри другой замкнутой детали: конец доски в стойке, грань под соседней деталью;
  - `hidden: ground` — точки ниже самой нижней точки модели, это дно на земле. У настенного предмета низ виден, такое решай сам;
  - `look` — всё остальное. Видно ли это игроку, решаешь по координатам `lo`/`hi` и нормали. Так бывает с гранью внутри закрытого сундука, с задником у стены или с верхом бруса под столешницей прилавка, который виден только в щель 5 мм.

Скрипт печатает пары `look`, а с `--all` ещё скрытые и касания. Перед правкой стоит снять крупный план места в Cycles: перекрытие выходит чёрным. Сдвиг 0,5 мм по замыслу (бока досок крышки сундука и торцы сегментов обода) скрипт уже не считает совпадением. Проверка 2026-10-21 прошла по всем 19 предметам рынка и пяти предметам пилота; разбор — в журнале [`docs/own-content.md`](../../../../docs/own-content.md).

## Установка и запуск

Blender **5.2.2 LTS** (та же линейка 5.2, что на Mac) устанавливается официальным портативным архивом с закреплённым SHA-256 в `~/gothic-ai/mesh3d/blender` на Ryzen. Установщик сначала показывает `df -h ~` и требует 23 ГиБ до распаковки, чтобы сохранить порог очереди 20 ГиБ. `run-ryzen.sh` копирует только Python-файлы этого модуля в свою папку и запускает `blender -b -P` через `gq batch`: 6 потоков, 8 ГиБ RAM, без GPU. Workbench использует Mesa llvmpipe без окна.

```sh
ssh ryzen bash < scripts/content/mesh3d/blender/install.sh
# Входы предварительно копируются в собственную папку на Ryzen.
sh scripts/content/mesh3d/blender/run-ryzen.sh postprocess \
  --raw /absolute/input/raw.npz --target /absolute/mesh3d-pilot.json \
  --id barrel --out /absolute/output/barrel
sh scripts/content/mesh3d/blender/run-ryzen.sh parametric \
  --target /absolute/mesh3d-pilot.json --id barrel --out /absolute/output/control
sh scripts/content/mesh3d/blender/run-ryzen.sh sheet \
  --variants /absolute/variants.json --out /absolute/output/barrel.png
sh scripts/content/mesh3d/check-blender.sh
sh scripts/content/mesh3d/blender/run-ryzen.sh synthetic --out /absolute/output/synthetic
```

Все пути аргументов раннера — абсолютные пути на Ryzen. Результаты и архивы не добавляются в git.

## Вход и обработка

`raw.npz`: `vertices (N,3)` f32, `faces (M,3)` i32, линейный `color (N,3)` f32, необязательные `metallic (N,)` и `roughness (N,)`. Рядом `meta.json`: `{"up_axis":"+Z","meters_per_unit":1.0}`; поддерживаются все шесть знаковых осей вверх.

Цель — отдельный объект, массив целей либо `{"targets":[...]}` с полями `id`, `visual`, `kind`, `bbox_min`, `bbox_max`, `budget_tris`, `zones:[{key,group,role}]`. Для нескольких целей нужен `--id`. `kind` описывает тип игрового ресурса, например `static_mrm`, и не выбирает UV. Необязательный `uv_projection` явно задаёт `cylinder` или `box`; без него анализируются горизонтальные сечения меша. Бочка `id=barrel`, `kind=static_mrm` из PR #312 получает цилиндр по форме.

`postprocess.py` выравнивает горизонтальный OBB и bbox, сливает близкие вершины, убирает мелкие компоненты, вложенные замкнутые оболочки и внутренние грани неманифолдных стыков, закрывает только короткие контуры дыр. Границы материалов упрощаются отдельно и защищаются от Collapse; затем идут Collapse в бюджет и Planar 5°. У тела вращения Planar применяется к крышкам и плоским участкам, сохраняя треугольники кривого бока. После триангуляции внутренние диагонали переставляются для улучшения формы треугольников, сохраняя границы материалов и острые углы. Металличность >0,5 задаёт METAL, без неё используется тёмный нейтральный кластер OKLab. Дерево распределяется по 1–3 кластерам с соседним сглаживанием. UV измеряются в метрах, жёсткие рёбра 30° расщепляются.

UV назначаются связным участкам: общие рёбра пропускают заливку при угле нормалей меньше 20°. Крышки и дно получают плоскую XZ-проекцию, бок тела вращения — цилиндрическую, остальные участки — box по своему OBB. У участка общие проекция, начало и масштаб; цилиндр делится по меридианам, чтобы шов лежал на границе участков. U — интеграл `sqrt(R² + R'²)` по среднему горизонтальному профилю R(θ): веса площади, 32 периодических бина и сглаживание `[1,4,6,4,1]/16`. Узкий участок использует покрытый угловой интервал с той же плотностью бинов, минимум три. Перед построением V радиус нормируется на R(θ), чтобы неравномерная выборка эллипса не создавала ложный наклон меридиана. Затем радиус усредняется в 33 бинах высоты, интерполируется и сглаживается ядром `[1,2,1]/4` с линейным продолжением краёв. Накопленная длина отрезков профиля задаёт `V(h) = ∫ sqrt(1 + r'(h)²) dh`. Угловой зависимости V и индивидуальных поправок треугольников нет.

Выход: `model.glb`, `collision.glb` с отдельными выпуклыми оболочками компонент, `metrics.json`, `scene.blend`. GLB — метры, glTF +Y вверх; отражение X и сантиметры остаются загрузчику игры. Имена материалов равны ключам зон, `extras.group` сохраняется. Цвета зон служат диагностикой; текстура генератора не запекается. Метрики содержат бюджет, топологию до расщепления нормалей, доли зон по площади, проекцию UV, число участков и скачков UV на внутренних рёбрах, время.

`parametric.py` строит контроль по `id=barrel` или `id=crate`/`box`: отдельные выпуклые клёпки, три обруча и крышки либо доски, рёбра и уголки. Общий обработчик задаёт bbox, зоны, UV и экспорт. Контроль сохраняет собственные `raw.npz` и `meta.json`.

## Листы сравнения

`sheet.py` принимает JSON с `title` и массивом `variants`. Строка варианта: `label` (модель × концепт × сид), `concept` (PNG), `raw`, `meta`, `result` (папка результата). Пути внутри JSON считаются от него; для параметрического контроля достаточно `label` и `result`. Все варианты предмета, включая контроль, подаются одним массивом.

Пять колонок: концепт, сырой цвет вершин, зоны, UV-шахматка 10 см, каркас. Подписи берутся из `metrics.json`; отсутствующий концепт отмечается явно.

Портретные листы вписываются по ширине камеры. Проверка пяти строк на Ryzen через `gq batch`: 1848×2250, границы камеры совпали с холстом, заголовок и подписи не обрезаны.

Масштаб проверяется раздельно по направлениям U и V, в метрах на единицу UV, по каждой невырожденной грани. Для цилиндра V вдоль оси — ±5%, U на среднем сечении — ±5%, а по всей поверхности — не более ±15%. Для box оба направления — ±5%. Среднее сечение независимо восстанавливается по вершинам и весам площади в 64 угловых бинах; U измеряется вдоль его горизонтальной касательной, без примеси V. Проверяются минимум и максимум U по угловым бинам каждого участка, а также исходные экстремумы U/V всех граней. Плоские крышки, торцы их досок и радиальные грани толщины клёпок проверяются как плоская проекция. Приёмка использует сохранённый тип проекции каждого участка. На общих рёбрах внутри участка проверяется совпадение UV с допуском 1e-5; это проверяется также на полной исходной синтетической бочке до упрощения.

Цвета сами по себе не различают тёмное дерево и железо надёжно. Несколько METAL-зон допустимы, но всё железо получает первый ключ METAL: атрибуты metallic и color не различают role. Без WOOD допускается одна другая неметаллическая зона. Чистка не выполняет булеву реконструкцию произвольных самопересечений. OBB не знает лицевую сторону предмета. Выпуклая оболочка компоненты заполняет её вогнутости. Качество генератора выбирается на реальных вариантах пилота.
