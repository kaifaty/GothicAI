# Codex → Claude Code: how Codex can message, ask, report to or read a supervising Claude Code session (state as of 2026-10-15)

Scope: mechanisms by which OpenAI Codex (codex-cli 0.162.1, the Codex desktop app / ChatGPT.app) can push progress reports or questions into an already running Claude Code session (CLI or the Claude desktop app's Code tab), plus the inbound channels Claude Code itself offers. Items marked "Local check" were verified on this machine on 2026-10-15 with Claude Code 2.1.296 and codex-cli 0.162.1. They are first-hand observations, not published sources.

Short catalogue (details and sources below):

## Q1. `claude mcp serve` and the Claude Agent SDK: can Codex add Claude Code as an MCP server or call it via a skill/plugin, and does that reach an already running session?

### Takeaway
`claude mcp serve` is a stdio server that the client launches, so Codex always gets a fresh Claude Code process, never the running session. As of v2.1.296, though, that fresh process exposes `ListAgents` and `SendMessage`. Through cross-session messaging, Codex can therefore list your live Claude Code sessions, including Claude Desktop sessions, and send a plain-text message into one of them. The Agent SDK, `claude -p` and `claude --resume` from a non-TTY process also start new processes. They don't inject into the live desktop session.

### Cited Findings
- `claude mcp serve` starts Claude as a stdio MCP server. It "only exposes Claude Code's tools to your MCP client", and the client is responsible for confirming tool calls. Example client config: `{"command":"claude","args":["mcp","serve"]}`. If a Bash result carries `backgroundOutputPath`, nothing notifies the client when the command finishes (needs v2.1.295+) — [Claude Code docs: MCP](https://code.claude.com/docs/en/mcp)
- Codex registers MCP servers in `~/.codex/config.toml` under `[mcp_servers.<id>]`, with `command`, `args`, `env`, `cwd`, `startup_timeout_sec` (default 10 s), `tool_timeout_sec` (default 60 s), `enabled_tools`/`disabled_tools`, and per-tool `approval_mode` (`auto | prompt | writes | approve`) — [Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference) (developers.openai.com/codex/config-reference now 308-redirects there)
- A March 2026 guide (updated 2026-10-15) gives the Codex-side config `[mcp_servers.claude-code] command = "claude" args = ["mcp","serve"]`. It says each client connection spawns a new Claude Code process with no shared state, so an external Codex cannot continue an existing session, and Claude's own MCP servers are not passed through. Its tool list (View/GrepTool/dispatch_agent era) is outdated — [Daniel Vaughan, "Claude Code ↔ Codex CLI: Bidirectional MCP Integration"](https://codex.danielvaughan.com/2026/03/26/claude-code-codex-bidirectional-mcp/)
- Local check (Claude Code 2.1.296, 2026-10-15): a JSON-RPC probe of `claude mcp serve` returned `serverInfo {name: "claude/tengu", version: "2.1.296"}`, capability `tools` only, and 27 tools: Agent, Bash, Read, Edit, Write, NotebookEdit, WebFetch, WebSearch, TaskStop, Skill, Artifact*, EnterWorktree, ExitWorktree, **SendMessage, ListAgents**, Workflow, CronCreate/Delete/List, ScheduleWakeup, Monitor, PushNotification, ToolSearch, and a few others. Calling `ListAgents` from that process (with the messaging env vars unset, so nothing was inherited) returned "Peer sessions (24)", listing the user's live "Claude Desktop session" rows with names, `[ref]` ids and idle/busy status. The `SendMessage` schema takes `to` (a name or `name [ref]` from ListAgents), `message` (plain text, first line shown as the preview), `summary`, and `notify_when_idle`. Delivery was NOT tested, to avoid injecting into the user's live sessions. The serve process bound its own `/tmp/cc-socks/<pid>.sock` but wrote no `~/.claude/sessions/<pid>.json` registry entry. The cross-session docs describe the same tools: `ListAgents` lists "your other local sessions … A session appears only when it binds an inbox socket", and `SendMessage` delivers to them — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging); [Tools reference](https://code.claude.com/docs/en/tools-reference)
- Background-session resume: for a session running in agent view, `claude --resume <session> "prompt"` (or `claude -p --resume …` typed at a terminal) sends the prompt as its next turn and attaches (v2.1.285+). With piped or redirected input/output, configuration flags (`--model`, `--settings`, `--permission-mode`), output flags (`--output-format json`) or `--max-turns`, Claude Code "sends nothing and exits with status 1". Prompts starting with `/` or `!` are never sent — [Manage sessions](https://code.claude.com/docs/en/sessions)
- Resuming the same session in two terminals without forking makes "messages from both interleave into one transcript" — [Manage sessions](https://code.claude.com/docs/en/sessions)
- Agent view CLI for scripting: `claude agents --json [--all] [--cwd]` returns `state` (working/blocked/done/failed/stopped), `status` (busy/waiting/idle) and `waitingFor`. Other commands: `claude attach|logs|stop|respawn|rm`, `claude --bg "<prompt>"` (new session), `claude daemon status|logs|stop`. The docs warn that `~/.claude/jobs/<id>/state.json` is not a stable interface. No `claude send`/`reply` command is documented — [Agent view](https://code.claude.com/docs/en/agent-view)
- The Agent SDK runs Claude Code programmatically from the CLI, Python or TypeScript. `--bare` skips hooks, plugins, MCP and CLAUDE.md, and is "recommended … for scripted and SDK calls" — [Run Claude Code programmatically](https://code.claude.com/docs/en/headless)
- A `claude -p` session binds an inbox socket like an interactive one, so a long-running `-p` worker can receive messages. Bare mode doesn't bind one — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)

### Inferences
- The most practical documented path from the Codex desktop app (not launched by Claude) to the live supervisor is: add `claude mcp serve` to `~/.codex/config.toml`, restrict it with `enabled_tools = ["ListAgents","SendMessage"]` so Codex can't use Claude's Bash/Edit tools, and have a Codex skill or AGENTS.md rule call `SendMessage` with `to = "<supervisor session name>"` at milestones and questions. It is cheap: no model call happens in the serve process, because `SendMessage` is a harness tool. This is untested end to end, so it needs one delivery check.
- Replies are the weak point. The receiving Claude replies to the sender's address, which is the short-lived `mcp serve` process's socket. Codex's MCP client has no way to surface it. Answers from the supervisor to Codex need another channel: the supervisor writing to a file Codex watches, Codex's own `codex app-server`/MCP interface, or a resumed Codex thread (covered in claude_to_codex.md).
- `claude -p --resume <supervisor-id>` from Codex is not a way to talk to the live desktop session. Codex runs commands without a TTY and with captured output, so for background sessions the command exits 1. For desktop sessions it would fork or interleave the transcript in a separate process that the live session never sees.

### Gaps
- No primary doc states that `claude mcp serve` exposes `SendMessage`/`ListAgents`, or how the serve process is classified for inbound controls (prompting vs bypass). This is only observed locally on 2.1.296, so it could change.
- Not verified: whether a message sent from `claude mcp serve` actually arrives in a Claude Desktop session, and whether the receiver's reply reaches anything.

## Q2. Codex plugins, skills or MCP servers (community or OpenAI) that call Claude Code: "ask claude", "claude review", second-opinion tools

### Takeaway
Several exist, and they all spawn new Claude Code runs (`claude -p`, `claude --bg`, or the Agent SDK) for reviews and second opinions. None of them reports into an existing supervisor session. OpenAI's official plugin goes the other way (Codex inside Claude Code). For Codex → Claude, I found nothing official from OpenAI or Anthropic.

### Cited Findings
- **yanchuk/claude-plugin-codex**: a Codex plugin that "lets Codex consult local Claude Code". Install with `codex plugin marketplace add yanchuk/claude-plugin-codex`, then install "Claude" in the plugin directory and run `$claude setup`. Commands: `review`, `adversarial-review`, `advise`, `do`, `rescue` (read-only unless `--write`), and `monitor`/`status`/`result`/`cancel` for background jobs. It runs the local `claude` CLI through a Node companion with `--output-format json`. Background mode uses `claude --bg`, `claude agents`, `claude logs`, `claude attach` and `claude stop`. MCP is off by default. Foreground `advise`/`rescue` times out after 2 minutes and falls back to a background job. Status: Alpha, verified with Codex CLI 0.130.0. 22 stars. It describes itself as the inverse of `openai/codex-plugin-cc` — [GitHub: yanchuk/claude-plugin-codex](https://github.com/yanchuk/claude-plugin-codex)
- **@leo000001/claude-code-mcp** (repo xihuai18/claude-code-mcp): an MCP server wrapping `@anthropic-ai/claude-agent-sdk`, with async tools `claude_code` (start, returns a sessionId), `claude_code_reply`, `claude_code_check` (poll events, answer permission requests with allow/deny/allow_for_session; auto-deny after 60 s) and `claude_code_session`. In-memory sessions expire after 30 minutes idle. Disk resume is opt-in (`CLAUDE_CODE_MCP_ALLOW_DISK_RESUME=1` plus a secret). Codex install: `codex mcp add claude-code -- npx -y @leo000001/claude-code-mcp`. 20 stars — [GitHub: xihuai18/claude-code-mcp](https://github.com/xihuai18/claude-code-mcp)
- **@steipete/claude-code-mcp**: a single `claude_code` tool that runs a child Claude Code in one-shot mode, by default with `--dangerously-skip-permissions`. It has `sessionId` resume and 1.3k stars. **Archived 2026-05-15**, and the README points to native `claude mcp serve` instead. It "can only pass flags to the child Claude Code process it starts" — [GitHub: steipete/claude-code-mcp](https://github.com/steipete/claude-code-mcp)
- thomaswitt/mcp-agents: a bidirectional MCP server (Claude → `codex`/`codex-reply`, Codex → `claude_code`). Its blocking `claude_code` tool is meant for small prompts — [Glama: mcp-agents](https://images.glama.ai/mcp/servers/thomaswitt/mcp-agents) (listing only, README not read)
- OpenAI's `codex-plugin-cc` is the official Claude Code plugin for running Codex from Claude Code, the opposite direction — [Daniel Vaughan, codex-plugin-cc](https://codex.danielvaughan.com/2026/04/12/codex-plugin-cc-cross-provider-bridge/); [yanchuk README](https://github.com/yanchuk/claude-plugin-codex)
- Codex plugin infrastructure in config: `plugins.<name>@<marketplace>.enabled`, plugin-bundled MCP servers (`plugins.<p>.mcp_servers.<s>.*`), `marketplaces.<name>.source`, and `skills.config[].path` pointing at a folder with `SKILL.md` — [Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference). Local check: `codex features list` on 0.162.1 shows `plugins stable true`, `hooks stable true`, `plugin_hooks removed false`, and `remote_control removed false`.

### Inferences
- These tools are useful for "Codex asks Claude for a second opinion", where a fresh Claude instance answers inside Codex's turn. They do not let the supervising Claude session see Codex's progress. They also bill a separate Claude run per call. hcom's README notes that Claude `-p` print mode uses separate Agent SDK credits ([hcom](https://github.com/aannoo/hcom)).
- A thin Codex plugin for "report to supervisor" could reuse this packaging (skill + bundled MCP server) but point the bundled MCP server at `claude mcp serve` limited to `SendMessage`/`ListAgents` (Q1), or at a small script posting to the inbox socket (Q3).

### Gaps
- I did not find a published Codex plugin that specifically messages an existing Claude Code session through `SendMessage` or channels. The closest are the hook-based `codex-claude-notify` (Q4) and the hubs (Q3/H).

## Q3. Claude Code's inbound channels as of 2026: how another process can push a message into a running session, and which of these a Codex plugin could use

### Takeaway
Claude Code now has several documented inbound paths into a live session:
1. **Cross-session messaging over a per-session inbox socket.** Explicitly meant for "a script or hook to post into a session". It works in Desktop sessions too, and needs no flags.
2. **Channels.** MCP servers that push `notifications/claude/channel`. Research preview, CLI started with a flag.
3. **Mods.** Plugin code with timers and `$.prompt.submit`.
4. **`Monitor` / `asyncRewake` hooks.** The supervisor watches something Codex writes.
5. **Remote Control and Desktop "work across sessions".** Human or Claude-only surfaces, with no third-party API.

For a Codex plugin, (1) is the best fit: through `claude mcp serve`'s `SendMessage`, or by writing to the socket directly.

### Cited Findings
**Cross-session messaging / inbox socket (GA)**
- Requires Claude Code v2.1.224+ on macOS/Linux and is on by default. The receiving Claude reads a message between tool calls during an active turn. When idle, "Claude Code starts a new turn with the message." A message can't approve permission prompts or change config, and `/commands` in it aren't run. It arrives as a dim preview `› Message from @name: …` — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- Each session binds an inbox socket (a Unix domain socket on macOS/Linux, restricted to the OS user). The path is shown in `/status` as `Peer address`, and exported to hooks and Bash as `CLAUDE_CODE_MESSAGING_SOCKET`, with a per-session `CLAUDE_CODE_MESSAGING_TOKEN`. On macOS/Linux, a script may send `{"type":"auth","token":"<token>"}` as the first line (optional on macOS). A connection that hasn't sent a complete line within 30 s is closed. The docs say this section is for "when you want a script or hook to post into a session" — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging); [Env vars](https://code.claude.com/docs/en/env-vars)
- Inbound controls: `crossSessionInbound` = `accept | hold | refuse`, settable in any settings file. With no value set, a prompting receiver delivers messages unless the sender identifies as bypass, and a bypass receiver holds them. "A session in the VS Code extension or the Desktop app can't show the dialog". Held messages expire after `dialogExpiry` (default 5 min). Own-child messages (from the session's hooks or Bash children) are delivered by default. On macOS, process evidence works only while the poster is alive, otherwise the token is used. A sandboxed Bash needs `sandbox.network.allowUnixSockets`. Limits: plain text, about 1M characters, at most 50 queued accepted messages, and per-sender rate limits — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)
- Wire format (undocumented on the docs page): the 2.1.296 binary contains this `--debug` hint: `[uds-messaging] Inject messages (auth line … here): { echo '{"type":"auth","token":"'"$CLAUDE_CODE_MESSAGING_TOKEN"'"}'; echo '{"type":"user","message":{"role":"user","content":"hello"}}'; } | socat - UNIX-CONNECT:<socket>`, and also suggests `printf '%s\n' "$out" | nc -U "$CLAUDE_CODE_MESSAGING_SOCKET"`. So it is newline-delimited SDK-style `{"type":"user",…}` JSON. Local check: strings from `~/.local/share/claude/versions/2.1.296`. Treat it as an internal, version-sensitive interface.
- Local check: this Claude Desktop session (`CLAUDE_CODE_ENTRYPOINT=claude-desktop`) exports `CLAUDE_CODE_MESSAGING_SOCKET=/tmp/cc-socks/<pid>.sock`. `~/.claude/sessions/<pid>.json` holds per-session records with `sessionId`, `cwd`, `name`, `kind: interactive`, `entrypoint: claude-desktop`, `status: idle|busy`, `messagingSocketPath` and `peerProtocol: 1`, so an external process could look up the supervisor's socket by name or cwd. This registry is not documented as a stable interface.
- Desktop app: Claude can list, read and message other Code-tab sessions ("work across sessions"). That surface sees only Desktop-run sessions, and a message to a busy session is held until its current work finishes. It "can't deliver messages into" unattended scheduled-task runs. It respects `crossSessionInbound`. Cross-session messaging separately reaches terminal sessions too — [Desktop docs](https://code.claude.com/docs/en/desktop)
- `SendMessage` with `notify_when_idle` gives one notice when another local session next goes idle or exits (v2.1.236+, expires after 12 h) — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)

**Channels (research preview)**
- A channel is an MCP server that "pushes events into your running Claude Code session". It declares `capabilities.experimental['claude/channel']: {}`, emits `notifications/claude/channel` with `{content, meta}`, and the event arrives as `<channel source="…" k="v">body</channel>`. There is no acknowledgement. Queued events are delivered together on the next turn. It can be two-way through a `reply` tool, and optionally relay permission prompts (`claude/channel/permission`, `notifications/claude/channel/permission_request` / `…/permission` with `behavior: allow|deny`) — [Channels reference](https://code.claude.com/docs/en/channels-reference)
- Requirements: claude.ai or Console auth (not Bedrock/Vertex/Foundry). Enabled per session with `claude --channels plugin:<name>@<marketplace>`, and only Anthropic-allowlisted plugins (Telegram, Discord, iMessage, fakechat) are accepted. Custom channels need `--dangerously-load-development-channels server:<name>`, which shows a confirmation dialog, and the dev flag "is ignored" in `-p` or through the Agent SDK. Pro/Max users without an org skip the org checks. On the v2 MCP runtime, a server negotiating protocol 2026-07-28 isn't registered as a channel (workaround `MCP_PROTOCOL_NEGOTIATION=legacy`) — [Channels](https://code.claude.com/docs/en/channels); [Channels reference](https://code.claude.com/docs/en/channels-reference); [MCP](https://code.claude.com/docs/en/mcp)
- The webhook example listens on `127.0.0.1:8788`, so any local process (a Codex hook, `curl`) can POST into the session — [Channels reference](https://code.claude.com/docs/en/channels-reference)

**Mods (plugin code inside the session)**
- A mod can run timers (`$.clock.every/after`), read files (`$.fs`), fetch HTTP (`$.http.fetch`), run processes, and start a turn with `$.prompt.submit({text})` ("waits until the session is idle and then starts a new turn"). It can send through `$.session.send({to:{sessionId}, text})` and observe incoming messages with `session.receive` (`e.origin.kind` e.g. `peer`), which can consume them. It has no inbound socket or server of its own — [Mods API](https://code.claude.com/docs/en/plugins/mods/api)

**Supervisor-side watchers**
- `Monitor` "runs a command in the background and feeds each output line back to Claude … Can also open a WebSocket and treat each incoming message as an event" — [Tools reference](https://code.claude.com/docs/en/tools-reference)
- Hook option `asyncRewake: true` runs a hook in the background and "wakes Claude on exit code 2", showing stderr/stdout as a system reminder — [Hooks](https://code.claude.com/docs/en/hooks)
- `codex-claude-bridge` v0.3.0 dropped its earlier channel- and MCP-based designs for a shared `talkto.md` file plus a watch command. "Claude uses Monitor for this", so the watch exit wakes Claude. 61 stars — [GitHub: abhishekgahlot2/codex-claude-bridge](https://github.com/abhishekgahlot2/codex-claude-bridge)

**Not usable by Codex directly**
- Remote Control: the local session makes outbound HTTPS only, "never opens inbound ports", and messages are routed from claude.ai or the mobile app. No third-party send API is documented — [Remote Control](https://code.claude.com/docs/en/remote-control)
- Deep links `claude-cli://open?q=…` open a NEW terminal session with a pre-filled prompt — [Deep links](https://code.claude.com/docs/en/deep-links)

### Inferences
- For a Codex desktop app → Claude Desktop supervisor on macOS, the realistic options are: (a) Codex MCP server `claude mcp serve` → `SendMessage` (documented tools, no undocumented format); (b) a Codex hook or MCP tool that finds the supervisor's socket in `~/.claude/sessions/*.json` and writes the NDJSON `{"type":"user",…}` line (undocumented, version-sensitive); (c) Codex appends to a file and the supervisor runs `Monitor` on it. Channels are a poor fit for a Desktop supervisor, because Desktop starts sessions itself and offers no documented way to pass `--channels` or the dev flag.
- If the supervisor runs in Bypass permissions mode, messages from a non-child process (the Codex desktop app) are held. Desktop can't show the dialog, so they are dropped after 5 minutes. Set `"crossSessionInbound": "accept"` in the supervisor project's `.claude/settings.local.json`, or in user settings (which affects every session).
- Delivery while the supervisor is busy is between tool calls, and when idle it starts a turn. That gives real push semantics, so the supervisor stops polling Codex logs, but each delivered message costs a turn's usage.

### Gaps
- Not found: official documentation of the inbox socket message schema beyond the auth line, and whether the `~/.claude/sessions/*.json` registry is supported.
- Not documented: whether mods and `--channels` work in Claude Desktop Code-tab sessions.
- Not verified: whether the Codex shell sandbox (seatbelt, workspace-write) blocks `connect()` to `/tmp/cc-socks/*.sock`. MCP servers and hooks may run outside that sandbox, but I found no source confirming it.

## Q4. Codex hooks / `notify`: can they ping Claude Code when a Codex turn ends? Examples in the wild

### Takeaway
Yes. Codex has a top-level `notify` command (the legacy path, fired only for `agent-turn-complete`, with the JSON passed as argv) and, since spring 2026, stable lifecycle hooks enabled by default. Hooks include `Stop` (gets `last_assistant_message`, `turn_id`), `PermissionRequest`, `UserPromptSubmit`, `SessionStart/End` and others, and must be trusted once in `/hooks`. A ready-made example, `vshuraeff/codex-claude-notify`, posts each finished Codex turn into the Claude Code session that launched Codex, through the inbox socket. It depends on Codex inheriting the socket env vars, so it does not work for the independent Codex desktop app without a socket-lookup change.

### Cited Findings
- `notify = ["python3", "/path/notify.py"]` fires "currently only" for `agent-turn-complete`. The payload is a single JSON argv argument with `type`, `thread-id`, `turn-id`, `cwd`, `input-messages` and `last-assistant-message` — [Codex advanced config](https://learn.chatgpt.com/docs/config-file/config-advanced)
- A 2026 change added a top-level `client` field to the (now "legacy") notify payload: `codex-tui` for the TUI, or the app-server's `clientInfo.name`, so hooks can tell Codex App completions from terminal ones. This implies notify also fires for app-server clients such as the desktop app — [mirror of openai/codex docs/config.md](https://forge.lthn.ai/core/core-agent-ide/src/commit/1afbbc11c3e2452cd61a4b102eb96b60e45f2de0/docs/config.md) (mirror, not the primary repo)
- `notify` must be a root-level key placed before any `[table]` header. The external notify fires only for `agent-turn-complete`, not `approval-requested`. Approvals are covered by `tui.notifications = ["agent-turn-complete","approval-requested"]` — [Daniel Vaughan, notification pipeline](https://codex.danielvaughan.com/2026/04/13/codex-cli-notification-pipeline-osc9-hooks-alerts/); [Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference)
- Hooks: events `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `UserPromptSubmit`, `SubagentStart/Stop`, `Stop`, `Interrupt`, `SessionStart`, `SessionEnd`. Config lives in `~/.codex/hooks.json`, `~/.codex/config.toml [hooks]`, the repo `.codex/…`, plugin-bundled hooks, or managed `requirements.toml`. "Hooks are enabled by default" (`[features] hooks = false` disables them). Non-managed hooks "must be reviewed and trusted" in `/hooks`, and trust is keyed to the hook's hash. `Stop` input adds `turn_id`, `stop_hook_active` and `last_assistant_message`. `Stop` output `{"decision":"block","reason":…}` makes the reason a continuation prompt. `async: true` hooks can't block — [Codex hooks docs](https://learn.chatgpt.com/docs/hooks)
- Hook handler types: command and MCP-tool hooks are supported, while prompt/agent handlers are parsed but skipped. There is also `additionalContextLimit` (default 2500) — [Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference). Local check: `codex features list` on 0.162.1 reports `hooks stable true`.

### Inferences
- For the target setup (Codex desktop app plus a Claude Desktop supervisor), the simplest robust bridge is a Codex `Stop` hook, an MCP-tool hook, or `notify`, calling a ~30-line script. The script would find the supervisor's inbox socket (via a known name in `~/.claude/sessions/*.json`, or a path the supervisor writes to a known file at start) and send `last_assistant_message` as a `{"type":"user",…}` NDJSON line. Alternatively, a Codex MCP-tool hook could call `claude mcp serve`'s `SendMessage`. This is `codex-claude-notify` with socket discovery added instead of env inheritance. Use the `client` field / `CODEX_CLAUDE_NOTIFY_SOURCES` idea to filter which Codex surfaces report.
- If the supervisor launches Codex itself (`codex exec` or a TUI from its Bash tool), `codex-claude-notify` works as-is, and messages count as own-child. That makes them more trusted: delivered by default even when the supervisor is in bypass mode, verified by the token on macOS once the poster has exited.
- `Stop` fires per turn, so it reports progress at turn ends only. Mid-turn questions need Codex to call a tool (an MCP `SendMessage`) deliberately, which can be instructed through AGENTS.md or a skill.
