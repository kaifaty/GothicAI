# Per-character and per-user adapters on one base LLM ("one model, many pluggable characters") — fact sheet as of 2026-11-04

Method note for the report writer: pages were read through a fetch tool that summarises pages with a small model, so numbers are quoted as returned; where a number comes only from a search-result summary (not the paper's own table) it is marked "secondary". Almost every quality number below is the authors' own result, usually judged by an LLM (GPT-3.5). I found no independent replication of any per-character-adapter result.

## 1. Role-play with per-character training (Character-LLM, Neeko, RoleLLM, OpenCharacter, persona vectors, 2025–2026 work): what was tried, and how it compares with in-context persona prompting

### Takeaway
Per-character fine-tuning (full-model or LoRA) reaches about the same LLM-judged quality as persona prompting of a stronger hosted model (GPT-3.5) and clearly beats prompting the same small base model, at a few MB of trainable parameters per character in the LoRA case. Differences between the best fine-tuned systems and GPT-3.5-with-a-prompt are small (<= 0.15 on a 7-point scale) and there is no independent evaluation or significance testing that I could see.

### Cited Findings
**Character-LLM (Shao et al., EMNLP 2023) — one full model per character**
- Each character gets its own LLaMA-7B fine-tuned only on that character's data. Nine characters, ~1.4K–2.2K scenes each (average ~1.6K), ~754K words per character on average. The extracted text does not say whether it is full or parameter-efficient fine-tuning. Training: 10 epochs, lr 2e-5, batch 64, ~1 hour per agent on 8×A100-80GB. — [Character-LLM paper](https://arxiv.org/html/2310.10158v2)
- Evaluation: 1,307 interview questions (857 single-turn, 450 multi-turn), GPT-3.5 judge on a 7-point scale over memorization, values, personality, hallucination, stability. Baselines (Alpaca-7B, Vicuna-7B, ChatGPT) were prompted with a character description. The text reports no exact numbers (only Figure 4); it says Character-LLMs beat same-size baselines "by a large margin" on personality, memorization, hallucination, stability and performed comparably to ChatGPT; "values" was a weak point. — [Character-LLM paper](https://arxiv.org/html/2310.10158v2)
- "Protective experiences" (<100 scenes per character) teach the agent to refuse out-of-era questions; an agent trained without them answered a request to write Python anyway. The authors conclude these scenes are needed to reduce character hallucination. — [Character-LLM paper](https://arxiv.org/html/2310.10158v2)
- Authors' stated limitations: only LLaMA-7B tested, LLM judges rather than humans, profiles only from Wikipedia. Authors also note world knowledge can leak into the character's memories and cause hallucinations (secondary summary of the same paper). — [Character-LLM paper](https://arxiv.org/html/2310.10158v2), [search summary](https://arxiv.org/pdf/2310.10158)
- Released weights for nine characters (as Llama-1 weight diffs) — [GitHub trainable-agents](https://github.com/choosewhatulike/trainable-agents)

**Neeko (Yu et al., EMNLP 2024) — dynamic LoRA, many characters, one base**
- Architecture: each character owns a non-overlapping slice of the LoRA matrices (per-character partial rank p, total rank M×p); a gating network scores characters from a global role-embedding matrix built from character profiles (DeBERTa-V3 init) and activates the top block; paper reports 100% correct role selection for trained roles. Backbone LLaMA-2-7B (ChatGLM also tested); one A100. — [Neeko paper](https://arxiv.org/html/2402.13717)
- Two ways to add an unseen character: Fusion (weighted sum of existing LoRA blocks, no new data) and Expansion (new block + gate, previous parameters frozen, needs role data). — [Neeko paper](https://arxiv.org/html/2402.13717)
- Setup: Character-LLM-Data, 9 characters (8 for pre-tuning, 1 held out for incremental learning); 857 single-turn + 450 multi-turn dialogues; GPT-3.5 judge on 7-point scale; human study on knowledge metrics only (3 graduate students, 82 snippets, 328 responses). — [Neeko paper](https://arxiv.org/html/2402.13717)
- Table 1 average score (authors' numbers): Neeko-ChatGLM 5.74; LoRA-ChatGLM 5.65; Character-LLM 5.62; Neeko-LLaMA2 5.61; GPT-3.5 in-context (ICL) 5.59; single shared LoRA-LLaMA2 5.54; GPT-3.5 RAG 5.48; LLaMA-2-chat ICL 5.35; LLaMA-2-chat RAG 5.29. Margins among the top fine-tuned methods are small. — [Neeko paper](https://arxiv.org/html/2402.13717)
- Trainable parameters: Neeko-LLaMA2 17M total (all characters' blocks + gate), 2.3M activated per query; single LoRA-LLaMA2 4.2M. Training cost (Table 5): Character-LLM 107.84 GB / 48.55 h; Neeko 13.55 GB / 2.01 h; single LoRA 13.49 GB / 1.72 h. — [Neeko paper](https://arxiv.org/html/2402.13717)
- Unseen character (Table 2): Neeko-Expansion 5.62; Neeko-Fusion 5.57; ICL (LLaMA-chat) 5.53; single LoRA 5.48 (authors blame catastrophic forgetting); RAG 5.40. Fusion needs no data but lowers the "Character Utterance" score. Multi-role transfer (Table 4): Neeko 5.87; LoRA 5.83; ICL 5.67; RAG 5.28. — [Neeko paper](https://arxiv.org/html/2402.13717)
- Human knowledge ratings: Neeko-Expansion highest on virtual, real and hallucination-avoidance knowledge (4.72, 4.77, 4.77); humans scored lower than the LLM judge but ranked systems the same. — [Neeko paper](https://arxiv.org/html/2402.13717)
- Authors' limitations: role embeddings come from profile text only (imprecise, gating errors can accumulate); human evaluation covers knowledge only. — [Neeko paper](https://arxiv.org/html/2402.13717)
- Code/data: [github.com/weiyifan1023/Neeko](https://github.com/weiyifan1023/Neeko) (link as stated in secondary summaries — [Moonlight review](https://themoonlight.io/review/neeko-leveraging-dynamic-lora-for-efficient-multi-character-role-playing-agent))

**RoleLLM / RoCIT (Wang et al. 2023) and OpenCharacter (Wang et al. 2025) — one model, many characters, profile as input**
- RoleLLM: 100 roles, RoleBench with 168,093 samples; role-conditioned instruction tuning (RoCIT) yields RoleLLaMA (English) and RoleGLM (Chinese) which the abstract says achieve "comparable results with RoleGPT (using GPT-4)". Authors' claim; benchmark tables not retrieved. — [RoleLLM abstract](https://arxiv.org/abs/2310.00746)
- OpenCharacter (arXiv 2501.15427, submitted 26 Jan 2025, v2 18 Feb 2025): synthetic character profiles from Persona Hub personas, two ways to make character-aligned responses (rewriting vs generation), SFT of LLaMA-3-8B; abstract claims the best model achieves performance "comparable to GPT-4o models on role-playing dialogue"; synthetic characters and dialogues released. Abstract page gives no benchmark names or numbers. — [OpenCharacter abstract](https://arxiv.org/abs/2501.15427)

**Persona / steering vectors (no weights trained per character)**
- Persona vectors (Chen, Arditi, Sleight, Evans, Lindsey; Anthropic Fellows, Aug 2025): a trait vector is the difference of activations between trait-exhibiting and non-exhibiting responses, extracted automatically from a trait name + description. Models: Qwen2.5-7B-Instruct and Llama-3.1-8B-Instruct. Traits: evil, sycophancy, hallucination (also politeness, apathy, humor, optimism). Injecting the vector causally shifts behaviour; inference-time steering against a vector degrades general capability (MMLU chart); "preventative" steering during training showed little-to-no MMLU degradation. Page gives no correlation numbers. — [Anthropic: persona vectors](https://www.anthropic.com/research/persona-vectors), paper [arXiv 2507.21509](https://arxiv.org/pdf/2507.21509)
- PERSONA (ICLR 2026, arXiv 2602.15669, 17 Feb 2026): training-free personality control by orthogonal trait vectors and vector algebra (scale = intensity, add = compose, subtract = suppress; Persona-Flow composes dynamically). Authors report PersonalityBench mean 9.60 vs SFT upper bound 9.61 and win rates up to 91% on their own Persona-Evolve benchmark. It targets personality traits, not named characters with biographies. — [PERSONA abstract](https://arxiv.org/abs/2602.15669)
- "Assistant Axis x Character Training" dataset card (Butanium): ~310,176 steered responses testing how steering along an "assistant axis" (default assistant vs role-play direction, coefficients -10..+10) interacts with eleven character-training LoRA adapters ("maius" adapters from OpenCharacterTraining constitutions) on Qwen2.5-7B-Instruct, Llama-3.1-8B-Instruct and Gemma-3-4B-it. The card reports no quantitative findings; it only suggests positive coefficients pull toward neutral assistant tone and negative toward role-play tone. — [dataset card](https://huggingface.co/datasets/Butanium/assistant-axis-constitution-steering/blob/main/README.md)
- Another 2026 paper (CAVI, arXiv 2605.09443, 10 May 2026) uses training-free steering to keep multimodal role-play agents in character; abstract reports no numbers. — [CAVI abstract](https://arxiv.org/abs/2605.09443)

**Prompting vs fine-tuning, surveys**
- A 2025 multi-turn survey states prompting alone can keep a persona consistent without parameter updates, and that fine-tuning on persona-rich dialogue (PIPPA) helps small models stay in character (secondary summary). A personalisation survey notes persona prompting can cause "character hallucination" (knowledge or behaviour misaligned with the persona). — [search summary of arXiv 2504.04717](https://arxiv.org/pdf/2504.04717), [Personalization of LLMs: a survey](https://arxiv.org/pdf/2411.00027) (claim from search summary, not verified in the paper text)

### Inferences
- The strongest direct evidence for "adapter vs prompt" is Neeko Table 1: a 7B base prompted in context scores 5.35 and with a LoRA 5.61 (+0.26 on 7 points), roughly equal to prompted GPT-3.5 (5.59). So the adapter lifts a small base to the prompted-large-model level; it does not clearly beat a strong prompt on a strong base. Our base (Gemma 12B with a ~5.5k-character persona prompt + 24 real sample lines) is stronger and its prompt richer than the plain ICL baselines in these papers, so the expected gain is smaller than +0.26 and is unmeasured.
- The usual selling point of fine-tuning in these papers (fewer prompt tokens, "brittleness and token overhead" per [Fixed-Persona SLMs](https://arxiv.org/html/2511.10277)) is largely neutralised when the persona prompt sits in a warm per-NPC KV cache; I found no paper that compares adapters against a cached prompt.
- Neeko's gate is unnecessary in a game: the NPC identity is known, so an adapter id can be chosen deterministically.
- Out-of-character knowledge is handled in Character-LLM by explicit training data ("protective experiences"), not by the adapter mechanism itself; a per-NPC adapter does not automatically make the NPC ignorant of what the base model knows.

### Gaps
- No independent (third-party) evaluation of per-character adapters vs persona prompting with human judges; every number above is authors' own, mostly GPT-3.5-judged.
- ChatHaruhi and CharacterGLM were not retrieved (not researched within budget); Character-LLM paper's Figure 4 numbers not available as text.
- No 2025–2026 paper found that trains per-character LoRAs and measures consistency against prompting on a 7B–14B model with a long prompt and a prompt cache. OpenCharacter's mechanism for supplying the profile (prompt vs weights) is not stated in the abstract I read.
- Persona-vector/steering work is shown on 7–8B models and traits, not on named characters; nothing found on steering vectors per NPC on Gemma.

## 2. What the pluggable parts actually capture: voice/style, persona, knowledge, episodic memory — compared with prompting and retrieval

### Takeaway
Weights learn style, persona and behaviour patterns well; they learn new facts slowly and with a hallucination cost, and LoRA specifically learns less than full fine-tuning. For memories that change during play, the one NPC-specific design I found keeps persona in the fine-tuned weights and memory in swappable retrieval stores outside the weights.

### Cited Findings
- Fine-tuning examples that introduce new facts are "learned significantly slower" than examples consistent with existing knowledge, and once learned they "linearly increase the model's tendency to hallucinate"; authors argue knowledge is acquired in pre-training and fine-tuning teaches the model to use it. (Gekhman et al., EMNLP 2024, closed-book QA setup.) — [arXiv 2405.05904](https://arxiv.org/abs/2405.05904)
- "LoRA Learns Less and Forgets Less" (Biderman et al., TMLR 2024): in programming and math (instruction tuning ~100K pairs; continued pre-training 20B tokens) LoRA at standard low ranks "substantially underperforms" full fine-tuning, but better preserves performance outside the target domain; full fine-tuning learns weight perturbations with rank 10–100× higher than typical LoRA configs. — [arXiv 2405.09673](https://arxiv.org/abs/2405.09673)
- A 2025 study (arXiv 2502.14502, secondary summary): LoRA on Llama-3.1-8B with varying amounts of new facts worked best with a mix of known and new facts; more new facts degraded existing world knowledge. — [arXiv 2502.14502](https://export.arxiv.org/pdf/2502.14502) (as summarised in a search result; not read directly)
- A 2025 comparison of RAG, LoRA and DoRA on accuracy and hallucination exists; the retrieved excerpt suggests LoRA+RAG works best but I did not see its results. — [arXiv 2502.10497](https://arxiv.org/pdf/2502.10497)
- Fixed-Persona SLMs with Modular Memory (Braas & Esterle, arXiv 2511.10277, Nov 2025): persona fine-tuned with LoRA ("not injected at runtime"), memory kept outside the weights in two ChromaDB vector stores per NPC (conversation memory, world knowledge) that can be swapped at runtime. Seven models (DistilGPT-2, TinyLlama-1.1B-Chat, Mistral-7B-Instruct variants) on an RTX 2070 Super 8 GB: factual consistency (100 responses, OpenChat-3.6 judge) OliverS (Mistral-7B) 93%, CasperS (TinyLlama) 55%, CasperL 39%, JackS (DistilGPT-2) 16%; context retention (30 multi-turn tests) OliverS 100%, CasperS 63.3%; world-knowledge retrieval OliverS 100%; memory-store swap 0.012–0.027 s, retrieval <0.042 s at 1,000 entries, store size 3.9–9.0 MB. Limits: one persona (merchant), one run, small test sets (30–100 items), single LLM judge, no comparison with prompting, "larger datasets underperformed smaller ones" (merchant persona: ~115 curated pairs vs ~564 synthetic). — [Fixed-Persona SLMs, HTML](https://arxiv.org/html/2511.10277)
- OPPU (see Q3) puts user history into the weights and finds it more robust than retrieval when history is irrelevant to the query (behaviour shift), but RAG+OPPU and profile+OPPU were best overall. — [OPPU paper](https://arxiv.org/html/2402.04401v3)
- Neeko: a single shared LoRA across incrementally added characters forgets (authors' attribution); per-character blocks avoid that. — [Neeko paper](https://arxiv.org/html/2402.13717)

### Inferences
- "Per-character memory layers" in the weights is supported for voice, persona and stable biography (what Character-LLM/Neeko train on), but there is no evidence in this literature for training episodic memories (what happened yesterday in the game) into a LoRA reliably; the facts-in-weights literature points the opposite way (slow learning, hallucination growth, forgetting).
- The only NPC-specific architecture found (Braas & Esterle) agrees with this split: weights = persona, retrieval store = memory. It is also very small-scale evidence (one persona, one run).
- Retraining a LoRA "in the background" after each game event would be an unverified use; OPPU-style evidence is for user history in bulk, not per-event updates.

### Gaps
- No paper found that measures episodic memory (events after training) stored in a LoRA vs retrieval for a conversational agent.
- The 2502.10497 and 2502.14502 results were seen only via summaries/snippets.
- Whether LoRA trained on a handful of lines (e.g., our 24 sample lines per NPC) captures voice better than putting those lines in the prompt was not tested in any source found; the data scale in the papers is 10²–10³ scenes per character (Character-LLM ~1.6K scenes; Fixed-Persona ~115–564 pairs).

## 3. Per-user adapters (personalisation): OPPU, PLoRA, Per-Pcs, hypernetworks; results vs RAG and both combined; retraining as history grows

### Takeaway
One-PEFT-Per-User beats retrieval/profile baselines modestly (single-digit points in the cells I have) and the best results come from combining the adapter with retrieval or profiles; training cost grows linearly with history and there is no published retraining-cadence study. Newer work tries to remove per-user training altogether (hypernetwork generating the LoRA; sharing LoRA "pieces").

### Cited Findings
- OPPU (Tan et al., EMNLP 2024): per-user LoRA on a frozen base; Llama-2-7B base, LoRA rank 8 on W_q and W_v; seven public LaMP tasks (LaMP-6 excluded, private); 100 test users with the longest histories; baselines: non-personalised, BM25 RAG (k=1,2,4), profile-augmented PAG (profiles generated by Vicuna-7B). When history does not fit the task format, the model is trained on right-shifted history (next-token prediction). — [OPPU paper](https://arxiv.org/html/2402.04401v3)
- Table 1 cells (k=1): LaMP-1 accuracy RAG .659, RAG+OPPU .675, PAG .755, PAG+OPPU .797; LaMP-2M accuracy RAG .587, RAG+OPPU .626, PAG .587, PAG+OPPU .648; LaMP-5 ROUGE-1 RAG .505, RAG+OPPU .522, PAG .516, PAG+OPPU .525. Averaged across tasks: RAG+OPPU about +1.93% relative over OPPU-less non-retrieval and +2.48% over retrieval without OPPU; profiles+OPPU about +4.56% and +7.18% on the corresponding comparisons. — [OPPU paper](https://arxiv.org/html/2402.04401v3)
- Abstract-level headline (secondary summary of the abstract): state of the art on all seven public LaMP tasks; about +17.4% average relative MAE improvement on LaMP-3 and about +11.9% accuracy on LaMP-2M over baselines; per-user update typically <1% of base parameters. — [OPPU on arXiv](https://arxiv.org/html/2402.04401v3) (figures as reported by [secondary summary](https://deep-paper.org/en/paper/2402.04401))
- Behaviour shift: with the 100 history items most similar to the query removed, retrieval-only methods fell back toward non-personalised performance, OPPU stayed more robust (exact cell values not extractable). As k grows, the gap between retrieval-only and retrieval+OPPU narrows. — [OPPU paper](https://arxiv.org/html/2402.04401v3)
- Cost: training time grows linearly with the number of history items; training 100 personal modules sequentially on 3 NVIDIA A6000 GPUs took ~12 minutes to 12 hours depending on history length. Paper does not discuss retraining cost when new history arrives or per-module storage. Limitations: one task per user; user interests change over time, and selecting relevant history is left to future work. — [OPPU paper](https://arxiv.org/html/2402.04401v3)
- Code: [github.com/TamSiuhin/OPPU](https://github.com/TamSiuhin/OPPU) (includes OPPU+RAG workflow, per secondary summary) — [search summary](https://arxiv.org/pdf/2402.04401.pdf)
- PLoRA (Zhang et al., AAAI 2024): plug-and-play personalised LoRA for human-centred text understanding (classification-focused, not LaMP generation); personalised dropout + mutual-information objective for cold-start users; claims gains in full, few-shot and zero-shot settings with fewer trainable parameters on four benchmarks. — [AAAI page](https://ojs.aaai.org/index.php/AAAI/article/view/29931)
- Personalized Pieces / Per-Pcs (Tan et al., 2024): users share their PEFT modules; a target user's model is assembled at "piece" level guided by the user's history; authors report it beats non-personalised and PEFT-retrieval baselines and comes close to OPPU with far less compute and storage; one task per user. — [arXiv 2406.10471](https://arxiv.org/pdf/2406.10471)
- Profile-to-PEFT (arXiv 2510.16282, Oct 2025): a hypernetwork maps an encoded user profile directly to a full set of LoRA parameters in one forward pass, removing per-user training at deployment; claims instant adaptation, generalisation to unseen users, privacy-preserving local deployment, and better results than prompt-based personalisation and OPPU with substantially lower deployment compute. Abstract gives no numbers; evaluated on LaMP, LongLaMP, Personal Reddit per a secondary summary. — [P2P abstract](https://arxiv.org/abs/2510.16282), [secondary summary](https://www.arxiv.org/pdf/2510.16282)

### Inferences
- From the cells above, OPPU's absolute gain over same-k RAG is about +0.016 (LaMP-1), +0.039 (LaMP-2M), +0.017 (LaMP-5 ROUGE-1): real but small, and it shrinks as more history fits in the prompt. This is the closest published analogue to "per-NPC adapter plus a retrieval layer": adapter + retrieval beats either alone by a few percent.
- Per-user data scale in OPPU is hundreds-to-thousands of history items; our NPCs have a ~5.5k-character persona and 24 lines, orders of magnitude less. The result transfers to "adapter learns patterns from large personal history", not obviously to "adapter learns a character from a card".
- The hypernetwork direction (P2P) is the published answer to "train in the background for every new entity", but it needs a hypernetwork trained on many entities (users), and nothing found applies it to fictional characters.

### Gaps
- HYDRA: searched; nothing found under that name — could not verify it exists as described.
- No source on how often a per-user adapter must be retrained as history grows; the only data point is linear training time and the open "interests change" limitation.
- Per-task OPPU numbers for all seven LaMP tasks and the behaviour-shift table were not extractable.
- LongLaMP results for adapters (and the P2P quantitative results) not retrieved.

## 4. Mixtures and composition: LoRA routing/mixtures (LoraHub, MoLE, X-LoRA), merging character adapters, interference

### Takeaway
Composition works but is lossy: naive arithmetic merging can erase the identity of individual adapters, learned gates (MoLE, X-LoRA, Neeko) help, and LoraHub-style composition does not beat in-context learning overall. For named NPCs with fixed identities, the safe pattern in the literature is one non-overlapping adapter per character selected, not blended.

### Cited Findings
- MoLE (Wu et al., ICLR 2024, arXiv 2404.13628): states direct arithmetic merging "can erode the pre-trained model's generative abilities or the distinct identity of each LoRA"; treats each layer of trained LoRAs as an expert with a learnable gate; reports it beats arithmetic merging on LoRA fusion in NLP and vision-language experiments. No numbers in the abstract. — [MoLE abstract](https://arxiv.org/abs/2404.13628)
- LoraHub (Huang et al., 2023): gradient-free composition of existing LoRA modules from a few examples of a new task, evaluated on Big-Bench Hard; the abstract says it does not surpass in-context learning overall but gives a performance-efficiency trade-off (far fewer tokens per example at inference) and a better upper bound than ICL when paired with different demonstrations. — [LoraHub abstract](https://arxiv.org/abs/2307.13269)
- X-LoRA (Buehler & Buehler, 2024): gating from hidden states mixes frozen LoRA adapters layer-wise and token-wise; applicable to any LLM without changing its structure; demonstrated on biomaterials/protein/molecular tasks (no numbers in abstract). Project docs: base and all adapters frozen, only the gate trained. — [X-LoRA abstract](https://arxiv.org/abs/2402.07148), [project summary](https://www.sourcepulse.org/projects/1844419)
- Neeko: non-overlapping per-character LoRA blocks + gate; Fusion (weighted sum of blocks for an unseen character) scored 5.57 vs Expansion (new block) 5.62 and vs a single shared LoRA 5.48 on an unseen character; Fusion lowers Character Utterance. — [Neeko paper](https://arxiv.org/html/2402.13717)
- Merging a LoRA into a 4-bit base can degrade results significantly (blog experiments), a reason to keep adapters separate on quantised bases. — [Kaitchup](https://kaitchup.substack.com/p/dont-merge-your-lora-adapter-into) (blog, not peer reviewed)
- A 2026 survey of model merging says Mixture-of-Experts-style merging preserves specialised capabilities by keeping distinct expert pathways and counters destructive interference. — [Model Merging survey, arXiv 2603.09938](https://arxiv.org/pdf/2603.09938) (via search snippet)
- Steering-vector alternative for composition: PERSONA reports trait vectors behave as roughly orthogonal directions that can be added and subtracted without training. — [PERSONA abstract](https://arxiv.org/abs/2602.15669)

### Inferences
- A "shared Gothic world" adapter plus per-character adapters (stack of two LoRAs at scales 1.0 each) is a natural design, but I found no paper measuring interference between a shared adapter and a character adapter; llama.cpp can stack several adapters (see Q6) so it could be tested cheaply.
- Blending two characters' adapters (e.g., to make a third NPC) is the Fusion case: measurably worse on voice than a dedicated block in Neeko.

### Gaps
- No numeric interference results for merging/stacking character adapters; MoLE/LoraHub/X-LoRA experiments are on task adapters, not persona adapters.
- Original tables for MoLE/X-LoRA not read (abstract-only).

## 5. Serving many adapters at once: S-LoRA, Punica, LoRAX, vLLM multi-LoRA

### Takeaway
Server-side stacks batch requests for different adapters in one pass with small per-token overhead (Punica reports +2 ms/token) and can serve thousands of adapters (S-LoRA), as long as the active working set fits in GPU memory. These systems are built for high concurrency on datacenter GPUs; our scale (dozens of adapters, few concurrent requests) is far below where they matter.

### Cited Findings
- Punica (MLSys 2024): new CUDA kernel (SGMV) batches GPU operations for different LoRA models so one GPU keeps a single copy of the base model; authors report 12× higher throughput than state-of-the-art LLM serving systems on a fixed-size cluster "while only adding 2ms latency per token". — [Punica abstract](https://arxiv.org/pdf/2310.18547)
- S-LoRA: keeps all adapters in main memory and fetches the ones needed by running queries into GPU memory; Unified Paging (one pool for adapter weights and KV cache), custom CUDA kernels for heterogeneous batching, tensor-parallel strategy; up to 4× throughput over vLLM with naive LoRA support and HuggingFace PEFT; serves "thousands" of adapters on one or multiple GPUs ("several orders of magnitude" more adapters). — [S-LoRA abstract](https://arxiv.org/abs/2311.03285)
- LoRAX (Predibase): packs requests for different adapters in one batch, adapters swapped through a tiered cache (GPU/CPU/disk), credits Punica's SGMV kernel; claims near-constant latency/throughput with number of concurrent adapters. Vendor claim. — [Predibase blog](https://predibase.com/blog/lorax-the-open-source-framework-for-serving-100s-of-fine-tuned-llms-in)
- vLLM multi-LoRA: enabled with `--enable-lora` and `--lora-modules name=path`; settings `max_loras` (adapters resident on GPU at once), `max_cpu_loras` (cached in CPU RAM), `max_lora_rank` (must be >= highest adapter rank; default 16 per Cloudera docs; oversizing wastes memory). Sources disagree on the `max_cpu_loras` default (Cloudera: None; DJL docs and a blog: equals `max_loras`); `max_loras` default 1 per a blog. vLLM's multi-LoRA path uses Punica kernels. — [vLLM LoRA docs](https://docs.vllm.ai/en/latest/models/lora.html), [Cloudera docs](https://docs.cloudera.com/machine-learning/1.5.5/ai-inference/topics/ml-model-endpoint-vllm-adapter-configuration.html), [DJL docs](https://docs.djl.ai/master/docs/serving/serving/docs/adapters.html), [particula.tech blog](https://particula.tech/blog/vllm-multi-lora-serving), [Compress then Serve](https://arxiv.org/html/2407.00066v4)
- "Compress then Serve": when adapters are numerous they must be loaded/offloaded from GPU memory repeatedly, which degrades throughput; with >1000 LoRAs, compressing them raises throughput by 1.6× and keeps ~80% of single-LoRA throughput. — [arXiv 2407.00066](https://arxiv.org/html/2407.00066v4)
- Vendor blog (Pioneer): adapter count matters less than whether the active working set fits in GPU slots; a 25-slot LRU cache hit a cliff when the working set exceeded it; moving to SGMV batching gave 44× throughput on one L4 for that workload. — [Pioneer](https://pioneer.ai/blog/the-33rd-adapter-problem-how-we-got-44x-more-throughput-from-one-l4) (vendor, not independent)

### Inferences
- Our 3090 setup with a few dozen adapters can keep every adapter resident; paging (S-LoRA, `max_cpu_loras`) is not needed. The relevant question is not adapter count but per-request latency and cache behaviour (Q6).
- If cross-adapter batching ever mattered (many NPCs speaking at once), vLLM/LoRAX-type servers do it; llama.cpp does not (Q6).

### Gaps
- No independent head-to-head of vLLM vs LoRAX vs S-LoRA overhead for tens of adapters; vLLM docs page returned HTTP 429 on direct fetch, so the docs were seen via search results/third-party mirrors only.
- No numbers found for adapter-switch latency inside vLLM at small adapter counts.

## 6. llama.cpp specifics: several LoRAs in llama-server, per-request `lora`, quantised GGUF base, Gemma family, interaction with the per-slot prompt (KV) cache, latency and VRAM overhead

### Takeaway
llama-server can load many LoRA GGUFs at start and choose their scales per request (`lora` field, merged Jan 2025); it applies adapters at runtime on top of a quantised base, and Gemma 4 E2B adapters have been run this way. The critical interaction: in the current source, a request whose LoRA config differs from the slot's last config clears that slot's whole prompt cache (except for activated-LoRA cases), so a per-NPC slot keeps its warm cache only if it always sees the same LoRA config; requests with different configs are also never batched together.

### Cited Findings
**Interface**
- Flags: `--lora FNAME` (comma-separated for several), `--lora-scaled FNAME:SCALE,...`, `--lora-init-without-apply` ("load LoRA adapters without applying them (apply later via POST /lora-adapters)"). By default adapters load at scale 1; `--lora-init-without-apply` starts all at 0. — [llama.cpp server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)
- `GET /lora-adapters` lists adapters with `id`, `path`, `scale`; `POST /lora-adapters` sets the global scale (0 or omit to disable). The global value "will be overwritten by the `lora` field for each request". — [server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)
- Per-request: `lora` is "a list of LoRA adapters to be applied to this specific request"; each object needs `id` and `scale`; "if a LoRA adapter is not specified in the list, its scale will default to 0.0". Example from the PR: `[{"id": 0, "scale": 0.5}, {"id": 1, "scale": 1.1}]`; works on `/completions` and `/v1/chat/completions`. — [server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md), [PR #10994](https://github.com/ggml-org/llama.cpp/pull/10994)
- PR #10994 "server : allow using LoRA adapters per-request": opened by ngxson 27 Dec 2024, approved by ggerganov and merged 2 Jan 2025; fixes issue #10377. — [PR #10994](https://github.com/ggml-org/llama.cpp/pull/10994)
- Docs warning: "requests with different LoRA configurations will not be batched together, which may result in performance degradation." The server README says nothing about prompt-cache invalidation. — [server README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)

**Slot / KV cache behaviour (from current master source, read 2026-11-04)**
- `server_slot::can_batch_with` requires `are_lora_equal(lora, other_slot.lora)`; `are_lora_equal` compares each adapter's scale and pointer, not the path. — [server-context.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/server-context.cpp), [server-common.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/server-common.cpp)
- In `launch_slot_with_task`: `if (!are_lora_equal(task_loras, slot.lora)) { if (lora_should_clear_cache(slot.lora, task_loras)) { slot.prompt.clear(); } slot.lora = task_loras; }`. When a request has no `lora` field the slot is set to the server defaults (`slot.lora = params_base.lora_adapters`). — [server-context.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/server-context.cpp)
- `lora_should_clear_cache(current, next)` returns `!(enabled_ids(current).empty() || all_alora(current)) || !all_alora(next)`. In plain terms: the cache is kept only when moving between activated-LoRA (aLoRA) configurations, or from "no LoRA" to aLoRA; standard LoRA to a different config, any config to "no LoRA", and aLoRA to standard all clear it. — [server-common.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/server-common.cpp)
- `get_available_slot` picks a slot by longest-common-prefix similarity (with LRU fallback) and does not check LoRA; the clear decision is applied afterward at task launch. — [server-context.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/server-context.cpp)
- Reading caveat: the fetch tool read only the first ~100K of ~306K characters of server-context.cpp; function definitions came from server-common.cpp; a different tool-summarised reading, not a compiled test. A PR test commit named "test: force disable cache prompt" hints that LoRA tests ran without prompt caching. — [PR #10994](https://github.com/ggml-org/llama.cpp/pull/10994)

**Quantised bases, Gemma, conversion**
- Adapters are separate GGUF files, produced by `convert_lora_to_gguf.py` from a Hugging Face PEFT adapter (needs base model config) or via the hosted GGUF-my-LoRA space; applied at runtime with `--lora`/`--lora-scaled` next to the base GGUF. — [GGUF-my-LoRA discussion](https://github.com/ggml-org/llama.cpp/discussions/10123), [search summary of converter](https://cdn04132025.gitlink.org.cn/replica/llama.cpp/src/branch/master/convert_lora_to_gguf.py)
- Gemma 4 evidence: a community adapter "Gemopus-v1-e2b" is a LoRA on `google/gemma-4-E2B-it`; its card runs `llama-server --model gemma-4-E2B-it-Q4_K_M.gguf --lora Gemopus-v1-e2b-lora.gguf --ctx-size 4096`, i.e., an adapter GGUF on top of a Q4_K_M base; architecture listed as `gemma4`; the card documents no llama.cpp limitations. This is one community example, not official documentation, and it is the E2B size, not 12B. — [Gemopus-v1-e2b card](https://huggingface.co/Hashhasapi/Gemopus-v1-e2b)
- Pitfall reported for Gemma 3: a LoRA that included vision-tower tensors failed GGUF conversion (secondary, from a Japanese article seen via search); fallback suggested by a Gemma 4 guide is to merge the LoRA into the base and convert the merged model. — [zenn.dev article](https://zenn.dev/akakagerengoku/articles/5561bf474b59fa), [Gemma 4 QLoRA guide](https://gemma4.dev/guides/gemma-4-unsloth-qlora)
- Historical note (2023, llama.cpp PR #820): applying LoRA directly to a quantised model can hurt quality; suggested `--lora-base` with an f16 model so deltas are applied before quantisation. Old advice; current behaviour for runtime adapters not verified. — [PR #820](https://github.com/ggerganov/llama.cpp/pull/820)

**Overhead**
- One anecdotal measurement on a model card: a rank-256 F16 adapter (3.48 GB file, `adapter.lora.alpha` = 512) on a Q4_K_M base (~15.7 GB) on an RTX 5090 ran at ~50 tok/s with the adapter vs ~78 tok/s without (about 35% slower), and ~19 GB total memory with the adapter loaded. The card's title and the model named in the text do not match (MiniMax-H3 vs Qwen3.6-27B), so treat as a rough, uncontrolled data point. — [HF model card](https://huggingface.co/ivanfromm/MiniMax-H3-Prompt-Rewriter-LoRA-GGUF)
- Training-time adapter size reference points: OPPU rank 8 on W_q/W_v for a 7B base, <1% of base parameters per user (secondary); Neeko 17M parameters total for 8 characters on LLaMA-2-7B. — [OPPU](https://arxiv.org/html/2402.04401v3), [Neeko](https://arxiv.org/html/2402.13717)

### Inferences
- Per-NPC slots with a fixed per-slot `lora` config keep warm caches (config equal -> no clear), but only if every request to that slot always sends the same config; omitting `lora` on one request (slot reset to defaults) or toggling an adapter off for a "narrator" call clears that slot's cache. Because slot choice ignores LoRA, pinning each NPC to its slot with `id_slot` matters (not verified in sources I read).
- Because the KV values are computed with the adapter applied, a cache built under one adapter is not valid under another; the code reflects this by clearing. So "switching characters inside one slot" costs a full re-evaluation of the prompt, which is exactly what the warmed per-NPC slot avoids today.
- Concurrent lines from different NPCs would not be batched together if their `lora` configs differ; with one slot per NPC and several NPCs talking at once the server will serialise decode steps across configs (per README warning), a throughput, not a correctness, issue.
- Adapter overhead on Q4 bases is a per-token compute cost proportional to rank × targeted modules; the single 35% data point is for rank 256 on a 27B-class model. A rank-8–16 adapter should cost much less, but no measurement exists in my sources for Gemma 12B on a 3090.
- With `--lora-init-without-apply` or scale 0 default plus per-request `lora`, dozens of adapters can be resident; VRAM cost ≈ adapter file sizes (F16), unmeasured here.

### Gaps
- No direct test of Gemma 4 12B (or any Gemma 4 size beyond E2B) with several adapters in llama-server; no official statement of Gemma 4 LoRA support in llama.cpp release notes.
- No measurement of LoRA latency overhead at rank 8–32 for a 12B quantised model, nor of VRAM per loaded adapter in llama.cpp.
- Source behaviour should be confirmed by a short experiment (send the same prompt with lora config A, then B, then A; watch `cache_n` / `prompt_n` in the response); I did not run one.
- Whether `/slots/{id}` save/restore (slot state files) keys on LoRA config was not examined.

## 7. Games and products: shipped games or middleware that fine-tune per character or per archetype

### Takeaway
I found no shipped game or middleware that publicly documents a separate fine-tuned adapter per named NPC. Public NPC products describe per-character configuration (backstory, knowledge base, style) plus a shared model; fine-tuning, where mentioned, is at the shared-model or companion level. The only per-NPC fine-tuning I found is an academic paper.

### Cited Findings
- Ubisoft NEO NPC (GDC 2024, with Inworld and NVIDIA Audio2Face): narrative team authored two NPCs (Bloom and Iron), each with its own background story, knowledge base and conversational style; it is a prototype and Ubisoft said it had no plans to bring it into its pipeline in the near future (per press coverage). — [HotHardware](https://hothardware.com/news/ubisoft-unveils-a-generative-ai-prototype-for-npcs), [GamesBeat](https://gamesbeat.com/ubisoft-neo-npcs-nvidia-inworldai-gdc/), [Ubisoft press release (PDF)](https://staticctf.ubisoft.com/8aefmxkxpxwl/Mw2s4KjssknqHHh1VIf8V/720296810ecc3deae51778a219732c7f/PRESS_RELEASE_GDC_UbisoftUnveilsNEONPC_190324.pdf)

### Inferences
- Industry practice visible from public material is "shared model + per-character configuration/knowledge + retrieval", the same shape as our current persona prompt; per-character weights appear in research, not in shipped products I could verify.
- Small SLMs (2B) are shipped for a single scoped companion with domain training (Krafton); that supports domain/archetype fine-tuning (e.g., "Gothic speech style" shared adapter) more than per-NPC adapters.
