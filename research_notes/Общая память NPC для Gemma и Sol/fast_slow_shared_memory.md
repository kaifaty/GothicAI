# Shared memory between a fast small model and a slow large model (and between many agents) — fact sheet as of 2026-11-04

Reading guide. Tags used below: **[author]** = number or claim reported by the paper/project's own authors on their own benchmark; **[indep]** = measurement by someone other than the method's authors (rare; flagged where it exists); **[docs]** = vendor documentation (describes behaviour, not measured results); **[anecdote]** = GitHub issue, forum or blog post; **[secondary]** = only seen via a third-party summary, not verified in the primary source. Pages were read through a summarising fetch tool, so exact table values are worth re-checking in the paper before they go into a design decision. Nearly every quantitative result in this area is author-reported; independent replications were not found for any architecture below.

Context: NPC = small local model (Gemma, one RTX 3090, seconds) + big hosted model ("Sol", several seconds, decisions). Goal: one shared memory per NPC.

---

## 1. How do dual-process (fast/slow) agents share memory or state? (Talker-Reasoner, SwiftSage, DPT-Agent, DUMA and others)

### Takeaway
In the best-documented designs the **slow model is the writer and the fast model is the reader**: Talker-Reasoner has the Reasoner write a structured "belief state" to memory that the Talker reads at every turn without waiting; DPT-Agent has System 2 write a natural-language belief plus guidelines that periodically regenerate System 1's code policy. The reverse flow (fast model writes, slow model consolidates) exists too (DUMA stores slow-mind answers in the fast mind's dialogue memory; SwiftSage feeds a rolling action history to both), but no paper in this group measures latency or staleness cleanly: Talker-Reasoner reports no numbers at all.

### Cited Findings

**Talker-Reasoner (Google DeepMind, 2024)**
- The Reasoner "generates the next belief state" and writes it to memory; the Talker reads the latest belief from memory every time it responds, together with the interaction history and the newest user utterance. Memory is the main channel between the two. — [arXiv 2410.08328 (HTML)](https://arxiv.org/html/2410.08328) [author]
- Default is asynchronous: the Talker does not wait for the Reasoner and "uses the latest available belief state" to minimise latency, so it "might operate with a delayed view of the world". Exception: in the sleep-coaching app's "planning" phase the Talker waits ("in the planning coaching phase the Talker waits, otherwise it does not"); the paper calls this System 2 overruling System 1. — [arXiv 2410.08328](https://arxiv.org/html/2410.08328) [author]
- In the sleep-coaching case study the Reasoner runs every turn: it infers which of three coaching phases the user is in (understanding, goal-setting, coaching-plan), routes to one of three phase-specific chain-of-thought Reasoners, updates a belief JSON/XML schema (fields such as sleep concern, goals, habits, barriers, sleep environment) and, in the planning phase, retrieves resources (e.g. videos). Both Talker and the mini-Reasoners are Gemini 1.5 Flash. — [arXiv 2410.08328](https://arxiv.org/html/2410.08328) [author]
- Failure mode named by the authors: a "snap judgement" Talker answering from an outdated belief when the Reasoner has not yet extracted the correct phase or fetched resources. Stated limitations: Talker may act on an outdated view of the world; limited capacity for complex planning. Future work lists: Talker deciding when to invoke System 2, multiple Reasoners writing to different parts of memory. — [arXiv 2410.08328](https://arxiv.org/html/2410.08328) [author]
- **No quantitative results and no latency measurements**: the evaluation is one example conversation and one feedback-adaptation example; "decreased latency" is claimed, not measured. — [arXiv 2410.08328](https://arxiv.org/html/2410.08328) [author]

**SwiftSage (Lin et al., 2023)**
- Swift = small encoder-decoder LM fine-tuned on an oracle agent's action trajectories (fast, intuitive); Sage = GPT-4 prompted for subgoal planning and grounding. — [arXiv 2305.17390 abstract](https://arxiv.org/abs/2305.17390) [author]
- Shared state is the environment text plus a sliding window of the last 10 actions with observations and rewards, current room, inventory, visited rooms; Sage additionally sees condensed history and objects from previously visited rooms; subgoals live only in Sage's planning output (Swift does not track them). — [arXiv 2305.17390 (HTML v2)](https://arxiv.org/html/2305.17390v2) [author]
- Control hand-over is rule-based, not model-judged: Sage is invoked on (1) five consecutive zero-reward steps, (2) an invalid Swift action, (3) a "critical" decision such as a final answer, (4) an exception in the observation. Sage fills an **action buffer** (about five actions per Sage call); the agent executes the buffer and returns to Swift when it is empty; two consecutive failures abort the buffer. — [arXiv 2305.17390 (HTML v2)](https://arxiv.org/html/2305.17390v2) [author]
- ScienceWorld (30 tasks) overall score with GPT-4: SwiftSage 84.68, Reflexion 45.34, ReAct 36.43, SayCan 33.82, Swift-only 49.22; with GPT-3.5-turbo SwiftSage 62.22 vs ReAct 19.76. Tokens per action: SwiftSage 757 vs SayCan 1,856, ReAct 1,971, Reflexion 2,983. The paper notes Reflexion may run up to four rounds while others run one, so the comparison is not perfectly fair. — [arXiv 2305.17390 (HTML v2)](https://arxiv.org/html/2305.17390v2) [author]

**DPT-Agent (ACL 2025 Main; real-time human-AI Overcooked)**
- System 1 = finite-state machine + code-as-policy, runs autonomously without waiting for the LLM (one game timestep = 0.25 s). System 2 = Theory-of-Mind module + asynchronous reflection. System 2 writes a natural-language **belief about the human** and a **behaviour guideline**; a code-as-policy generator (run periodically "and when necessary") reads recent (state, action, reward) history + latest belief + guidelines and emits executable code that rewrites the FSM logic. There is no separate shared memory store: a history buffer feeds both systems. — [arXiv 2502.11882 (HTML v1)](https://arxiv.org/html/2502.11882v1) [author]
- Results [author]: with rule-based partners, mean score ReAct 19.77, Reflexion 20.39, DPT-Agent w/o ToM 39.44, DPT-Agent 43.06. Human study (68 valid data points from 71 students; GPT-4o-mini for all frameworks): Map 1 ReAct 99.03, Reflexion 97.78, w/o ToM 103.19, DPT-Agent 111.53; Map 2 119.67 (Reflexion) vs 160.63 (DPT-Agent). On Map 2 the w/o-ToM variant was ranked above the full agent in subjective cooperation/preference rankings. System 1 vs System 2 latency in seconds is only in a figure/appendix, not in the text read. — [arXiv 2502.11882](https://arxiv.org/html/2502.11882v1) [author]
- Independent replication not found; the project page repeats the authors' claims. — [GitHub/GitCode mirror](https://gitcode.com/meituan-longcat/DPT-Agent)

**DUMA (dual-mind conversational agent, 2023)**
- Fast Mind talks to users and keeps a "Dialogue Memory" made of its own exchanges plus the results Slow Mind returns; Slow Mind never talks to users, receives the conversation as query-answer pairs structured by Fast Mind, and its output goes back into Fast Mind's dialogue memory ("DUMA only needs to think deeply once" for a repeated situation). Fast Mind decides via an `Invoke` True/False flag. Models: Baichuan-13B-Chat (fast) and ChatGLM2-6B (slow), i.e. here the "slow" model is **not larger**. Manual evaluation, 80 dialogue groups per system, scores 0–2; DUMA beats ChatGPT-ReAct on all six metrics (e.g. House Expertise 1.550 vs 0.733); column mapping of the table was inferred by the fetch tool, no latency reported; authors caution results are from a Chinese real-estate domain. — [arXiv 2310.18075 (HTML)](https://arxiv.org/html/2310.18075) [author]

**Background "slow thinker" that pre-fills what the fast talker reads (2025–2026)**
- VoiceAgentRAG (arXiv 2603.02206): background Slow Thinker (LLM) predicts 3–5 likely follow-up topics per user utterance, retrieves chunks and writes them into an in-memory FAISS semantic cache; foreground Fast Talker only **reads** the cache (similarity threshold 0.40) and falls back to the vector DB on a miss (then also writes). Min 0.5 s between predictions; entries expire after 300 s TTL; max 2,000 entries, LRU eviction; near-duplicates (>0.95) are updated, not added; the authors say TTL gives "eventual consistency but not immediate coherence". Results [author, one synthetic KB of 12 documents/76 chunks, 200 queries, GPT-4o-mini]: hit rate 75% overall (58% turns 1–4, 86% turns 5–9), cache lookup 0.35 ms vs 110.4 ms for remote Qdrant; but LLM generation (500–8000 ms) dominates end-to-end latency, and with a local FAISS store (~0.1 ms) the speedup is negligible. — [arXiv 2603.02206](https://arxiv.org/html/2603.02206v1) [author]
- PMFR "Prepared mind, fast response" (arXiv 2510.08175): the only shared state is the knowledge base K_t; a Lightweight Response Generator only reads it, an Asynchronous Knowledge Refinement Agent (background threads: search, evidence reasoning, summary+cache) writes K_{t+1}; a Knowledge Adequacy Evaluator gates when the background agent runs; cached summaries carry provenance and confidence scores. TopiOCQA zero-shot: PMFR GEval-C 0.613 / GEval-RC 0.645, mean latency 1.09 s (P95 1.81 s) vs ReAct with a 235B backbone 0.620 / 0.845, 23.38 s (P95 49.44 s) — 95.3% lower mean latency, but a visible drop in the GEval-RC (consistency/relevance-type) score that the headline claim does not mention. The paper does not discuss staleness explicitly. — [arXiv 2510.08175](https://arxiv.org/html/2510.08175) [author]
- SALMONN-duo (arXiv 2609.34247): always-on fast voice frontend + asynchronous slow LLM backend; frontend learns when to delegate (knowledge-boundary-aware training reduces unnecessary System 2 calls; cost-aware RL on a custom τ-Voice benchmark). Only the abstract was read; shared-state mechanism and numbers not available. — [arXiv 2609.34247 abstract](https://arxiv.org/abs/2609.34247) [author]

**Large planner / small executor with a shared cache (agents, games)**
- Agentic Plan Caching (arXiv 2506.14852): large planner (GPT-4o) runs only on cache **misses**; after a successful run, a rule-based filter plus GPT-4o-mini strips context-specific details and stores a plan *template* keyed by an extracted intent keyword; on a hit a small planner (Llama-3.1-8B) adapts the template and the actor (Llama-3.1-8B) executes. Reported: 50.31% average cost reduction, 27.28% average latency reduction, 96.61% of accuracy-optimal performance retained; hit rate 46% at 100 entries on FinanceBench; cache-entry generation adds ~3.99 s; fuzzy (embedding) matching raised hit rate but lowered accuracy (83% at >80% similarity vs 77% at >60%); heterogeneous tasks (GAIA) had few hits; the paper does not discuss stale templates. — [arXiv 2506.14852 (HTML v2)](https://arxiv.org/html/2506.14852v2), [abstract](https://arxiv.org/abs/2506.14852) [author]
- AgenticCache (arXiv 2604.24039): agents query a runtime cache of frequent plan transitions; a background updater asynchronously calls the LLM to "validate and refine" entries. Over 4 multi-agent embodied benchmarks, 3 models, 12 configurations: success +22%, simulation latency −65%, tokens −50%. Mechanics of sharing and staleness detection are not in the abstract. — [arXiv 2604.24039 abstract](https://arxiv.org/abs/2604.24039) [author]
- A hobbyist Minecraft bot with a large-model strategy layer (~90 s per cycle) and a small-model tactical layer (a few seconds) reports that all-large is too slow and all-small loses long-term planning. — [note.com write-up](https://note.com/daily_hack_lab/n/nd390ad70bc69?hl=en) [anecdote]

### Inferences
- The consistent pattern across Talker-Reasoner, DPT-Agent, PMFR, VoiceAgentRAG and Plan Caching is **single-writer-per-field**: the slow side produces *beliefs/guidelines/templates/knowledge*, the fast side only reads (and at most appends raw dialogue). That structure is what makes them conflict-free without locks.
- None of these papers uses an LLM-vs-LLM pair as lopsided as Gemma-on-3090 vs a hosted frontier model; DUMA's slow mind is smaller, and Talker-Reasoner uses the same Flash model for both. So "bigger slow model → better memory" is an assumption in this literature, not a demonstrated result.
- The Talker-Reasoner "wait only in the planning phase" rule is the cleanest published precedent for a policy of "fast model answers from the last-known belief, except for decision-critical turns where it blocks on the slow model". SwiftSage's four rule-based triggers (stuck / invalid / critical / unexpected) give a concrete trigger list to copy.
- Reported latency gains are all from removing a slow call from the critical path (PMFR 1.09 s vs 23.38 s; VoiceAgentRAG notes generation dominates), so the gain depends on how often the fast path is allowed to answer without the slow result.

### Gaps
- No paper found that measures *staleness cost* (how often the fast model's answer is wrong because the belief is one turn old) in Talker-Reasoner-style designs; the only numbers are cache hit rates (VoiceAgentRAG) and task scores.
- No dual-process LLM design found that is evaluated specifically on **NPC dialogue in a shipped or realistic game**; DPT-Agent (Overcooked) and DUMA (real-estate sales dialogue) are the nearest. The 2025 "LLM-NPC" papers surfaced (e.g. arXiv 2511.10277 below) use a single model per NPC.
- DPT-Agent latency figures (appendix/figure) and SALMONN-duo's mechanism/numbers were not readable in the fetched text.

## 2. Asynchronous memory consolidation by a stronger or background model (Letta sleep-time, sleep-time compute, LangMem, others)

### Takeaway
There is solid vendor documentation (Letta, LangMem) and one research paper (Sleep-time Compute) for the pattern "fast agent talks, a background agent edits its memory". Letta's *own* blog recommends exactly your split — a fast cheap model as primary agent, a larger slower model as the sleep-time agent that alone edits the shared memory blocks. Measured evidence is thin: the sleep-time paper's numbers are on reasoning benchmarks (not dialogue memory) and are author-reported; its benefit depends on how predictable the future query is.

### Cited Findings
- Sleep-time Compute (Letta + UC Berkeley, Apr 2025): the model reasons offline over a context before the query arrives. Reported [author]: ~5x less test-time compute for the same accuracy on Stateful GSM-Symbolic and Stateful AIME; scaling sleep-time compute raises accuracy by up to 13% (GSM-Symbolic) and 18% (AIME); with multiple related queries per context the average cost per query falls 2.5x; benefit is "well correlated with how predictable the user's query is". The abstract gives no cost for the offline step itself. — [arXiv 2504.13171](https://arxiv.org/abs/2504.13171)
- Letta sleep-time architecture [docs/blog]: enabling it creates two agents. The **primary agent** talks to the user, calls tools and searches recall/archival memory but **does not edit its own core memory**; the **sleep-time agent** has tools to edit both its own and the primary agent's in-context memory blocks, asynchronously. The blog suggests a fast model (e.g. gpt-4o-mini) for the primary agent and a larger, slower one (gpt-4.1 / Sonnet 3.7) for the sleep-time agent "since it is less latency-constrained"; higher frequency costs more tokens. The primary reads the blocks whenever it needs, without waiting for sleep-time processing. The blog gives no benchmark figures of its own. — [Letta blog: sleep-time compute](https://www.letta.com/blog/sleep-time-compute)
- Letta defaults [docs, via package docs/search snippet]: the sleep-time agent triggers every N steps (default 5, `sleeptime_agent_frequency`); the two agents run as a multi-agent group; a memory block can be attached to several agents ("shared blocks"). — [Letta package docs summarised by search](https://docs.letta.com/guides/agents/architectures/sleeptime/index.md) (page itself returned 404 when fetched directly; treat as [secondary]); [PyPI letta-nightly page](https://pypi.org/project/letta-nightly/0.13.0.dev20251030104218/)
- Letta has since moved on: current docs describe "dreaming" — background subagents that review recent conversations, consolidate lessons and update memory without interrupting the main agent; trigger is a configurable number of completed steps or context compaction; an optional "agent reviews before applying" pass has a second background conversation review proposed updates. Memory is a **git-backed filesystem (MemFS)**: every memory edit is a commit; files at the memory root are always loaded into the system prompt, subdirectories stay out of context until needed (indexed by `MEMORY.md`); memory subagents "use git worktrees so they can update memory concurrently without blocking the main agent"; multiple cloud agents can attach the same shared memory repository. Docs do not say which model runs dreaming subagents or how merge conflicts are resolved. — [Letta: Memory & dreaming](https://docs.letta.com/configuration/memory), [Letta: MemFS](https://docs.letta.com/concepts/memfs) [docs]
- LangMem (LangChain): two creation modes — **hot path** (agent saves notes deliberately via tools; immediate but adds latency) vs **background / "subconscious"** (extracted after the conversation or after inactivity; no response latency but updates delayed). A memory manager extracts, inserts, updates, removes and consolidates memories ("reconcile new information with previous beliefs"). Memory types: semantic (collection or single-document "profile"), episodic (situation, reasoning, outcome), procedural (prompt updates). — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/) [docs]
- LangMem's `ReflectionExecutor` **debounces**: each thread has a queue of pending memory tasks; if new messages arrive before the delay expires the pending task is cancelled and rescheduled with the new messages; it runs only after a full quiet delay, so each run sees the whole conversation. Docs list the problems with per-message processing: redundant work, incomplete context mid-conversation, unnecessary token consumption. Demo delay 0.5 s; guide suggests 30–60 minutes in practice. — [LangMem delayed processing](https://langchain-ai.github.io/langmem/guides/delayed_processing) [docs]. A community report says pending tasks in the local executor are lost on application restart. — [LangChain forum](https://forum.langchain.com/t/discussion-a-recovery-mechanism-for-langmems-localreflectionexecutor-to-survive-application-restarts/1588) [anecdote]
- Generative Agents (Park et al., 2023) is the classic game-world precedent for *periodic consolidation*: reflection fires when the summed importance scores of recent events exceed 150, about 2–3 times per simulated day, each over the 100 most recent memory records; retrieval score = recency (decay 0.995/game hour) + importance (LLM-rated 1–10 at write time) + relevance (cosine), weights 1 each, min-max normalised. Ablation (TrueSkill μ, higher = more believable): full 29.89, no reflection 26.88, no reflection+planning 25.64, no observation/reflection/planning 21.21. Hallucination: 6 of 453 awareness responses (1.3%) in the end-to-end run. — [ar5iv: Generative Agents](https://ar5iv.labs.arxiv.org/html/2304.03442) [author]
- A-MEM-style notes show a *write-time* consolidation variant: the LLM writes keywords/tags/context for each new note, then proposes links to the top-10 nearest notes and may rewrite ("evolve") those neighbours' context/tags. — [A-MEM, arXiv 2502.12110](https://arxiv.org/html/2502.12110) [author]

### Inferences
- Letta's recommended split (fast primary, big sleep-time editor, primary has read-only access to the blocks) maps directly onto "Sol consolidates, Gemma reads". The git-commit-per-edit design is a ready model for a per-NPC memory with an audit trail and rollback.
- Debouncing until a conversation goes quiet (LangMem) is the natural trigger for Sol's consolidation pass in a game: end of a dialogue, NPC leaves the player's vicinity, or a quest event, rather than every utterance. Letta's "every N steps" is the alternative.
- Sleep-time compute pays off when future queries are predictable from the context; NPC dialogue about a quest or a known character is more predictable than open chat, so precomputed "answer cards" (what this NPC would say about topic X) are a plausible fit — but no source tests that.

### Gaps
- No measurement found of consolidation *quality* when a large model writes and a small model reads (e.g. LoCoMo with big-writer/small-reader). The closest are Plan Caching (large planner → small adapter; Section 1) and Letta's recommendation, which is guidance, not data.
- Letta docs do not state which model runs dreaming subagents, nor how git merge conflicts are resolved.
- Letta's benchmark claims for MemFS vs earlier memory blocks were not found in this pass.

## 3. Small-model-friendly memory formats; what small open models can reliably read and write

### Takeaway
Small models (≤8B) can *use* short structured memory well, but *writing/updating* it is where they break: malformed JSON, silently dropped facts, over-adding, collapsing several facts into one entry. Evidence is mostly bug reports and a handful of papers; the one controlled study that tried a 3B model as the memory writer (Intrinsic Memory Agents) found it "poor on every benchmark". Trained small writers (RL/SFT, 0.6B–7B) do much better and are the best-documented route.

### Cited Findings
- **Failures in the wild [anecdote].** Mem0 `Memory.add()` silently discards all extracted facts when a non-OpenAI model (Qwen3 via Cerebras/Ollama) returns malformed JSON — no retry, little logging. — [mem0 issue #4540](https://github.com/mem0ai/mem0/issues/4540). Similar parse failures reported with Gemini ([#3918](https://github.com/mem0ai/mem0/issues/3918)) and Mistral returning empty results ([#4061](https://github.com/mem0ai/mem0/issues/4061)); an older Ollama issue found the default update prompt not robust enough and strict JSON-mode forcing caused problems ([#2758](https://github.com/mem0ai/mem0/issues/2758)). One user's audit of 10,134 Mem0 entries reported 97.8% "junk", with the update step biased toward ADD/UPDATE and rarely choosing NONE — single deployment, not a controlled benchmark. — [mem0 issue #4573](https://github.com/mem0ai/mem0/issues/4573)
- **Competitor-paper numbers on Mem0 [author, interested party].** Fortunate Recall (proposes its own FR-Bank) reports Mem0 default vs Mem0 with a gpt-4.1-mini extractor: lifecycle-benchmark pass 61% → 67.1%, stale 27% → 21.5%, correct 18.6% → 27.3%, confabulation 32.2% → 25.4%; on a "selective forgetting" test Mem0 and Memory-R1 both scored 2.5% end-to-end correct. The JSON-parse failure appendix was not readable. — [arXiv 2609.10413 (HTML)](https://arxiv.org/html/2609.10413)
- **Intrinsic Memory Agents (small-model evidence) [author].** Per-agent memory is rewritten after each turn by a separate LLM call (inputs: role, previous memory, latest output) into a JSON template. Main benchmarks (ALFWorld, FEVER, PDDL) used **Gemma3:12b via Ollama**; "Llama3.1:3b was tried first but gave poor results across all frameworks". Templates compared: manual strict JSON schema (weakest, sensitive to construction), generic free-form (best overall), LLM-generated. PDDL: generic 0.260, LLM-generated 0.254 vs empty-memory baseline 0.224 — a small margin; token cost ~352k per run vs ~52k for the empty baseline (the paper calls it a worthwhile trade). The headline 38.6%/15.5% gains do not clearly match the tables (comparison basis unclear). Llama-3.2-3B was used for a case study. — [arXiv 2508.08997 (HTML v2)](https://arxiv.org/html/2508.08997v2)
- **A-MEM with tiny models [author].** Qwen2.5-1.5B/3B and Llama-3.2-1B/3B run locally via Ollama with LiteLLM structured output; A-MEM beat LoCoMo/ReadAgent/MemoryBank/MemGPT baselines in most categories (e.g. Llama-3.2-3B temporal F1 26.38 vs best baseline 4.37 as read by the fetch tool; column labels in the extracted table are OCR-garbled, so treat per-category assignments as uncertain); about 1,100–1,400 tokens per question vs ~16,900 for LoCoMo/MemGPT baselines; ~1.1 s per memory operation with local Llama-3.2-1B vs ~5.4 s with GPT-4o-mini. Absolute F1 values remain low (single digits to ~28). — [arXiv 2502.12110 (HTML)](https://arxiv.org/html/2502.12110)
- **Trained small memory writers.** Mem-α: RL-trained memory construction with core/semantic/episodic memory and tool-validity + content-quality rewards; trained on ≤30k-token sequences, generalised to >400k tokens (13x). Secondary summaries put Qwen3-4B at 0.389 average before RL and 0.642 after, and describe the untrained 4B as failing to update core memory and collapsing several semantic facts into one entry. — [arXiv 2509.25911 abstract](https://arxiv.org/abs/2509.25911) [author]; the 4B numbers and failure description come from [Moonlight review](https://www.themoonlight.io/review/mem-learning-memory-construction-via-reinforcement-learning) [secondary]. Memory-R1: Memory Manager with ADD/UPDATE/DELETE/NOOP + Answer Agent, trained with PPO/GRPO from 152 training QA pairs, reported to work across 3B–14B models on LoCoMo, MSC, LongMemEval. — [arXiv 2508.19828](https://arxiv.org/abs/2508.19828) [author]. A critique notes both Memory-R1 agents are full 7B LLMs doing per-turn generation. — [search summary of MemRouter/related](https://arxiv.org/pdf/2605.00356) [secondary]
- **Small specialist for memory-adjacent extraction.** MemPrivacy: on-device 0.6B–4B models detect privacy spans and replace them with typed placeholders before text reaches a cloud memory system (mapping kept locally; cloud "never directly observes the original sensitive values"). F1: 0.6B-SFT 83.09%/92.08% (two datasets), 4B-RL 85.97%/94.48% vs Gemini-3.1-Pro 78.41%/92.18%; latency 0.43–0.70 s (PersonaMem-v2) and 1.6–2.1 s (privacy-dense set) vs ~29–33 s for Gemini-3.1-Pro; masking PL2–PL4 cost 0.71–1.60% memory accuracy, irreversible masking up to 41.87 points on Mem0. — [arXiv 2605.09530 (HTML)](https://arxiv.org/html/2605.09530) [author]
- **NPC-specific small-model memory.** "Fixed-Persona SLMs with Modular Memory" (Nov 2025): LoRA-tuned DistilGPT-2 / TinyLlama-1.1B / Mistral-7B merchant personas; per-NPC ChromaDB stores for *conversation memory* and *world knowledge* (both queried by cosine similarity, top-k added to the prompt; each turn appended to conversation memory; how world-knowledge entries are written is not stated); retrieval <0.042 s even with 1,000 entries; memory swap 0.012–0.027 s; Mistral-7B variant 93% factual accuracy, 100% context retention, TTFT 0.11 s, total 5.49 s, ~4.2 GB VRAM on RTX 2070 Super; TinyLlama 55% factuality; DistilGPT-2 16% factuality / 6.7% context retention. LLM-judged, 30–100 samples, one persona, not integrated in a game. — [arXiv 2511.10277 (HTML)](https://arxiv.org/html/2511.10277) [author]
- **Structured-output tooling.** JSONSchemaBench (10K real-world schemas; Guidance, Outlines, llama.cpp, XGrammar, OpenAI, Gemini) frames compliance as a measurable property of the decoding framework; one version reports constrained decoding improves downstream task performance by up to 4%. No Gemma-specific validity rate was found. — [arXiv 2501.10868](https://arxiv.org/html/2501.10868v3) [author]
- A practitioner guide (Apr 2026) recommends Qwen3-8B FP8 as the summariser/extractor for self-hosted Mem0/Zep/Letta and a larger model only when 8B extraction produces noisy memories in multi-entity domains. — [Spheron blog](https://www.spheron.network/blog/agent-memory-gpu-cloud-mem0-zep-guide/) [anecdote/vendor blog]

### Inferences
- Failure is concentrated in the **update/merge step** (deciding between ADD / UPDATE / DELETE / NONE and emitting valid JSON), not in reading. A design where the small model writes only *append-only, tiny, schema-light notes* and the big model owns merge/dedupe/contradiction avoids exactly the step small models fail at.
- Constrained decoding (GBNF / JSON-schema) on the local runtime removes the malformed-JSON class of failure at the source; it does not fix semantic errors (over-adding, collapsing facts). For Gemma on a 3090 this is a free guard, but no benchmark of semantic quality under constraint was found.
- Intrinsic Memory Agents' result that a *free-form* template beat the manual strict schema, and the A-MEM design of short LLM-written keywords/tags/context, both point toward short natural-language lines with a few mandatory fields rather than deep nested schemas for small writers. This is an inference from two small experiments, not an established rule.
- The 4B/0.6B trained-specialist results (Mem-α, MemPrivacy) suggest that if Gemma's raw note-writing is poor, a narrow SFT/RL pass on Sol-written gold memories is the proven fix; no source tests distilling a *frontier* model's memory writing into Gemma specifically.

### Gaps
- No published failure *rates* (percent malformed / percent wrong update) for Gemma 3/4, Llama or Qwen ≤30B as memory writers under a standard protocol; only anecdotes and one "poor results" statement for a 3B model.
- Mem-α 4B numbers (0.389 → 0.642) were confirmed only via a secondary summary; the arXiv abstract lacks them.
- The Fortunate Recall paper's Mem0 JSON-error appendix (Appendix O) was not read.
- No source found on distilling memory-*writing* skill from a large model into a small one other than RL-from-reward approaches (Memory-R1, Mem-α).

## 4. Multi-agent shared memory: G-Memory, Collaborative Memory, Intrinsic Memory, blackboards, MemoryOS, provenance and permissions

### Takeaway
Published multi-agent memory systems mostly give each agent a private store plus a shared layer, and enforce read-side filtering (role, permission graph) rather than solving write conflicts; conflict resolution is absent in Collaborative Memory and implemented only as an extra "conflict-resolver" agent in the blackboard design. Provenance is explicit in Collaborative Memory (immutable creator/agents/resources/time) and in a gossip-graph prototype ("who told you"), which is the closest thing to what gossiping NPCs need.

### Cited Findings
- **G-Memory (arXiv 2506.07398) [author].** Three graph tiers: *interaction graph* (per-query utterances: which agent said what), *query graph* (past queries with Resolved/Failed status, linked by semantic similarity), *insight graph* (LLM-distilled generalisable insights linked to supporting queries). Read: embedding retrieval of top-k similar queries + 1 hop → upward traversal to insights → downward traversal where an LLM ranks queries and sparsifies interaction graphs → **role-specific injection** per agent. Write: after a task, store the interaction graph, add a query node with links, have an LLM generate a new insight, link it to insights used and update supporting-query sets. Invoked once at the start of each query. Results: up to +20.89 points on ALFWorld (MacNet, Qwen-2.5-14b, 58.21 → 79.10), up to +10.12 on HotpotQA (AutoGen, 24.49 → 34.61); on PDDL +10.32% at ~1.4×10⁶ tokens vs MetaGPT-M +4.07% at ~2.2×10⁶; best with 1-hop expansion and k∈{1,2}. Limitations: three domains/five benchmarks; a compromised LLM could make memory amplify wrong reasoning. — [arXiv 2506.07398 (HTML)](https://arxiv.org/html/2506.07398)
- **Collaborative Memory (arXiv 2505.18279) [author].** Two tiers: private memory (visible only to the originating user) and shared memory (cross-user). Access control = two time-indexed bipartite graphs (user→agent, agent→resource) that change over time. Read policy: a fragment is visible only if its contributing agents are accessible to the user *and* its resources accessible to the agent. Write policies are separate for private and shared writes and can be LLM prompts: the private prompt extracts user-relevant key-value memories; the shared prompt strips user-specific details. Provenance: each fragment records creation time, contributing user, contributing agents and resources accessed, described as immutable (supports retrospective permission checks). The paper **does not** describe how conflicting fragments or concurrent writes are resolved. Results: MultiHop-RAG scenario (609 articles, 2,556 queries, 5 users, 6 agents) accuracy >0.90 with resource usage down up to 61% at 50% query overlap; dynamic-access scenario showed accuracy rising as access was granted and falling as revoked. Limitations: moderate user/agent counts, synthetic queries, resource calls used as a latency proxy. — [arXiv 2505.18279 (HTML)](https://arxiv.org/html/2505.18279)
- **Intrinsic Memory Agents [author].** Each agent has its own memory, rewritten after it speaks; the only channel between agents is the shared conversation history (the paper does not describe agents reading each other's memories); it notes agents' interpretations of shared context diverge over time. — [arXiv 2508.08997 (HTML v2)](https://arxiv.org/html/2508.08997v2)
- **Blackboard, LbMAS (arXiv 2507.01701) [author].** One blackboard with a *public* space (all agents read/write) and *private* spaces for debates/verification; agents communicate only via it; an LLM control unit picks which agents act each round; special agents include a **conflict-resolver** (finds contradictory messages, names the agents, they debate privately and repost) and a **cleaner** (removes redundant messages); terminates when the decider answers or after 4 rounds. Models: Llama-3.1-70B and Qwen-2.5-72B. Average over six benchmarks: LbMAS 81.68 vs Chateval 80.56, CoT(Qwen) 80.09, CoT(Llama) 74.60; CoT(Qwen) beat it on MATH (76.40 vs 72.60). The text's "+4.33% / +5.02%" claims do not match the table averages. MATH tokens ≈4.72M; without the control unit ≈13.9M. — [arXiv 2507.01701 (HTML)](https://arxiv.org/html/2507.01701)
- **Blackboard for information discovery (arXiv 2510.01285) [author, via search snippet].** A central agent posts requests to a blackboard and subordinate agents decide themselves whether to respond; reported 13–57% relative improvement in end-to-end task success over RAG and a master-slave baseline. — [arXiv 2510.01285](https://arxiv.org/abs/2510.01285v2) [secondary snippet]
- **MemoryOS (EMNLP 2025).** Three tiers — short-term, mid-term, long-term personal memory; short→mid by dialogue-chain FIFO, mid→long by segmented-page organisation; reported +48.36% F1 and +46.18% BLEU-1 average on LoCoMo with GPT-4o-mini [author]. No multi-agent / shared-memory mode was found in the paper or abstract. — [ACL Anthology](https://aclanthology.org/2025.emnlp-main.1318), [arXiv 2506.06326](https://arxiv.org/html/2506.06326v1)
- **Mem0 scoping [docs].** Memories are scoped by `user_id`, `agent_id`, `app_id`, `run_id`; a filter with only `user_id` returns only records whose other scope fields are null (a common mistake: a memory saved with no `agent_id` is invisible to a later agent-scoped search). Mem0's agent-to-agent example uses one shared store keyed by `user_id`. No official guidance on contradictory writes from two agents was found. — [Mem0 entity-scoped memory](https://docs.mem0.ai/platform/features/entity-scoped-memory), [Mem0 A2A article](https://mem0.ai/library/agent-memory/how-memory-works-in-agent-to-agent-protocols)
- **LangMem namespaces [docs].** Hierarchical namespaces such as `("acme_corp", "{user_id}", "code_assistant")` filled at runtime from config. — [LangMem conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- **Consistency as an open problem.** A March 2026 position paper (UC San Diego) frames multi-agent memory as a computer-architecture problem — shared vs distributed memory, a three-layer hierarchy (I/O, cache, memory), a missing *agent cache sharing protocol* and *memory access protocol* — and calls memory **consistency** the most pressing open challenge. — [arXiv 2603.10062](https://arxiv.org/abs/2603.10062) [position paper, no experiments]; commentary: [Moonlight review](https://www.themoonlight.io/review/multi-agent-memory-from-a-computer-architecture-perspective-visions-and-challenges-ahead) [secondary]. A claim that a March 2026 "Artifact Coherence System" applied MESI to agents rests on one secondary source and was not verified. — [same review](https://www.themoonlight.io/review/multi-agent-memory-from-a-computer-architecture-perspective-visions-and-challenges-ahead)
- **Gossip / private knowledge / provenance.**
  - Generative Agents' information diffusion over two simulated days: Sam's candidacy known by 1 agent (4%) → 8 (32%); Isabella's party 1 (4%) → 13 (52%); embellishment observed (an agent added an announcement that was never discussed) — [ar5iv](https://ar5iv.labs.arxiv.org/html/2304.03442) [author].
  - In a 15-agent relay experiment, LLM agents "tend to expand on the original information rather than shorten it" — a warning for distortion along gossip chains — [arXiv 2405.14744](https://arxiv.org/pdf/2405.14744) [author, via search summary].
  - Rumour-spreading simulation with LLM agents gives each agent a persona and a per-rumour belief score updated by the LLM each round; network structure and personas change reach; a critic notes no grounding against behaviour — [arXiv 2502.01450](https://arxiv.org/pdf/2502.01450) [author].
  - `gossip-graph` (hackathon prototype): NPCs store memories, rumours and trust links in a FalkorDB graph; a "who told you" query traces the provenance path of a belief; corrections supersede old beliefs rather than deleting them; a debunked rumour cannot spread again — [GitHub: yubaraj2000/gossip-graph](https://github.com/yubaraj2000/gossip-graph) [anecdote/prototype].
  - "Revisiting Gossip Protocols" proposes cryptographic provenance on gossip payloads so receivers can judge claim origin — [arXiv 2508.01531](https://arxiv.org/html/2508.01531v1) [vision paper, no experiments].

### Inferences
- For NPCs that each know different things, the Collaborative Memory pattern (private tier + shared tier, immutable provenance on every fragment, read-side filtering by who may see what) fits directly; its weakness (no conflict handling) is the part that has to be added — blackboard-style conflict-resolver/cleaner passes or supersede-don't-delete semantics (gossip-graph) are the available templates.
- Because the engine's code can own ground truth (as the project already does for quests), the "shared" tier can be split into *world facts owned by code* (read-only to all models) and *beliefs owned per NPC* (what that NPC thinks, with source = who told them / witnessed / inferred). The literature has the second but rarely the first.
- G-Memory's role-specific injection and `k∈{1,2}`, 1-hop result suggest keeping retrieval narrow; it also notes up to 10x more tokens for multi-agent trajectories, so each NPC's injected memory should stay small.
- Gossip chains with small models risk expansion/embellishment (Generative Agents; relay experiment); storing the *original* statement plus its source, and passing the stored text verbatim rather than re-narrating it, avoids compounding drift. This is an inference, not a tested result.

### Gaps
- No evaluation found of private-vs-shared memory with **conflicting beliefs** (two agents holding contradictory facts) in any of G-Memory, Collaborative Memory or Intrinsic Memory Agents; Collaborative Memory explicitly leaves concurrency unexplored.
- MemoryOS multi-agent mode: not found (may not exist).
- Rest of the Collaborative Memory paper (last ~45k characters) and G-Memory (last ~9.5k) were not read.
- No peer-reviewed study of per-NPC belief provenance in a shipped/realistic game; gossip-graph is an unreviewed hackathon prototype.

## 5. Prompt-caching and latency tricks when injecting memory into a fast model's prompt

### Takeaway
Every provider and local engine caches by **exact token prefix**, so the working pattern is: stable prefix (persona, rules, slowly changing consolidated memory) first, volatile material (timestamps, retrieved notes, latest user turn) last, and updates to memory either appended or batched into infrequent rewrites. Measured benefits are large for cost (45–80%) and modest for latency (≈10–31% TTFT), and full-context caching can backfire. For Gemma on llama.cpp/vLLM, sliding-window attention complicates prefix reuse and has to be tested on the exact build.

### Cited Findings
- **Anthropic [docs].** Cache covers the prompt prefix in the order tools → system → messages, up to a `cache_control` breakpoint; a hit needs a 100% identical prefix; lookup checks at most 20 blocks back from each breakpoint; put the breakpoint on the last block that is identical across requests, not on timestamps or the incoming user message; up to 4 explicit breakpoints or one automatic breakpoint; default TTL 5 min (refreshed free on each hit), 1 h optional; write multiplier 1.25x (5 min) / 2x (1 h), read 0.1x of base input price (some models cheaper); a cache entry is only available after the first response begins, so parallel requests do not hit it; minimum cacheable length varies by model (512 to 4,096 tokens). Changing tool definitions invalidates everything; toggling images or `tool_choice` invalidates system/messages. — [Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- **OpenAI [docs].** A hit requires the entire prefix up to a breakpoint to match, so a change before a breakpoint prevents reuse of everything after it; stable content (instructions, tools, reference) first and dynamic content (timestamps, user data) last; on the newest models an explicit breakpoint after the static portion is advised; minimum 1,024 visible input tokens; reads discounted up to 95% (0.1x of input rate on the newest generation, 0.05x on two named variants including "Sol"); write premium 1.25x for 30-minute lifetime and 2.5x for 12 h on the newest models, none on earlier ones; default retention 30 min (earlier models: in-memory 5–10 min up to 1 h, or 24 h extended); `prompt_cache_key` helps routing (aim ~15 requests/min per key on older models); docs say a hit "isn't guaranteed to lower latency". Detail as summarised by a fetch tool from the docs page. — [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)
- **Independent measurement** (PwC authors, not a vendor): across OpenAI, Anthropic and Google models on a multi-turn research agent (10,000-token system prompt, 40 sessions per condition per model, >500 total), caching cut cost 27.8–81.4% and changed TTFT by −8.8% to +30.9% depending on model and strategy. Examples (cost / TTFT): GPT-5.2 system-prompt-only 81.4% / 10.5%; Claude Sonnet 4.5 78.5% / 22.9%; Gemini 2.5 Pro full-context 38.3% / 6.0% but excluding tool results 27.8% / −2.9%; GPT-4o full-context 47.8% / **−8.8%** (a regression) vs system-prompt-only 45.9% / 30.9%. Recommendation: dynamic information, if necessary, at the end of the system prompt; embedding timestamps, session IDs or user-specific data in the system prompt, or changing tool definitions, breaks the cache. Paper's abstract (13–31% TTFT, 41–80% cost) does not match its own tables (Gemini 6.1% TTFT, 27.8% cost). — [arXiv 2601.06007 (HTML v2)](https://arxiv.org/html/2601.06007v2)
- **llama.cpp server [docs].** `cache_prompt` (default true) reuses the KV cache of a previous request so only the differing suffix is processed (may not be bit-for-bit deterministic); `--cache-reuse N` / `n_cache_reuse` tries to reuse chunks ≥N tokens via KV shifting (default 0 = off); `-np` parallel slots; `--slot-prompt-similarity` (default 0.10) picks the slot whose cached prompt best matches the request; `id_slot` pins a request to a slot (use one slot per NPC to keep that NPC's prefix warm); `-cram` RAM prompt cache (default 8192 MiB) and `--cache-idle-slots` save idle slots; `--slot-save-path` for slot save/restore to disk; `GET /slots` for monitoring. — [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- **Gemma and sliding-window attention.** Gemma 3 mixes sliding-window and full-attention layers (vLLM docs: Gemma-3-27b has 52 sliding-window and 10 full-attention layers). vLLM's hybrid KV cache manager caches each layer group independently; a prefix hit on a sliding-window group only needs the last `sliding_window_size − 1` tokens, and the cached prefix is the intersection across groups; the docs note some memory waste "not perfect". — [vLLM hybrid KV cache manager](https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager/) [docs]. For llama.cpp, `--swa-full` switches to a full-size SWA cache (default false), and users report frequent forced full-prompt re-processing with SWA models (Gemma 3 iSWA was added in llama.cpp PR #13194); a 2026 thread has conflicting reports on whether recent builds fixed it for Qwen3.5/Gemma 4. — [llama.cpp completion README](https://git.mitjafelicijan.com/r/llmnpc/blob/llama.cpp/tools/completion/README.md), [Reddit thread snapshot](https://reddit.sentinel-team.org/posts/1sd6b1l/snapshots/2026-04-09T16%3A11%3A00.655487Z) [anecdote]
- **Where else latency is saved by memory design.** Local small-model memory operations: ~1.1 s per A-MEM operation with Llama-3.2-1B on one GPU vs 5.4 s with GPT-4o-mini ([arXiv 2502.12110](https://arxiv.org/html/2502.12110)); NPC memory retrieval <0.042 s for 1,000 entries and memory-DB swap 12–27 ms ([arXiv 2511.10277](https://arxiv.org/html/2511.10277)); remote vector retrieval ~110 ms vs 0.35 ms cache lookup, but generation of 0.5–8 s dominates ([arXiv 2603.02206](https://arxiv.org/html/2603.02206v1)). Letta's MemFS keeps only the root files in the system prompt and leaves subdirectories out of context until needed, i.e. a small always-loaded index plus on-demand detail ([Letta MemFS](https://docs.letta.com/concepts/memfs)).

### Inferences
- A concrete layout that fits all the sources: **[static persona+rules] [per-NPC consolidated memory written by Sol, changes rarely] [recent episodic notes, append-only] [retrieved items + current turn]**. Sol's rewrite of the consolidated block is the only operation that invalidates the cache, so batching it (end of dialogue / debounced) keeps it rare; appended notes only add to the suffix (full-prefix reuse in llama.cpp for the unchanged part).
- One llama.cpp slot per NPC (`id_slot`) plus `cache_prompt` is the lowest-effort way to keep each NPC's prefix warm on one 3090, constrained by VRAM for N slots; slot save/restore to disk can park inactive NPCs. Whether Gemma's SWA breaks this on the project's exact llama.cpp/vLLM build is an empirical question to test first, since sources disagree.
- For the hosted big model, the cache only matters if Sol is called repeatedly with the same long prefix within TTL (5–30 min); one-off consolidation calls per NPC may not hit it. The PwC measurement says to cache only the stable system part and keep volatile tool/memory results out of the cached region.
- Latency wins from memory systems are small next to generation time: moving a slow call off the critical path (Section 1) matters more than shaving retrieval milliseconds.

### Gaps
- No measurement found of KV-prefix-cache behaviour for **Gemma 3/4 specifically** under llama.cpp `cache_prompt`/`--cache-reuse` with an appended-memory pattern (only anecdotes about SWA re-processing).
- OpenAI doc details for the newest model generation were read through a summarising fetch; verify TTL and pricing for the actual model ("Sol") before relying on them.
- No source found on "delta updates" of memory in a prompt beyond append-vs-rewrite reasoning (no named technique for patch-style memory edits); the closest published mechanisms are Letta's commit-per-edit MemFS and LangMem's collection-vs-profile split (Section 2).

## 6. Cross-cutting: who writes what, and how designs avoid conflicts and staleness

### Takeaway
Across all sources, conflict avoidance comes from (a) **ownership** (one writer per memory region), (b) **time separation** (background/debounced writes, batch at idle), (c) **versioning** (git commits, supersede-don't-delete), and (d) **read-side TTLs/gates** for staleness — not from locking or merging. Where a design lets many writers hit one store, the papers either leave consistency open (Collaborative Memory, position paper) or add an extra LLM "resolver" (LbMAS).

### Cited Findings
Summary table of who-writes/who-reads, built from sources cited above:

| System | Slow/strong writer | Fast/weak side | Staleness / conflict handling |
|---|---|---|---|
| Talker-Reasoner | Reasoner writes belief state each turn | Talker reads latest belief; waits only in planning phase | Accepts delayed view; named "snap judgement" failure ([2410.08328](https://arxiv.org/html/2410.08328)) |
| SwiftSage | Sage writes action buffer + subgoals | Swift acts when buffer empty; shared 10-step window | Rule-based hand-over; abort buffer after 2 failures ([2305.17390](https://arxiv.org/html/2305.17390v2)) |
| DPT-Agent | System 2 writes belief + guidelines; generator rewrites FSM code | FSM runs on game state, never waits | Periodic "and when necessary" regeneration ([2502.11882](https://arxiv.org/html/2502.11882v1)) |
| DUMA | Slow Mind answer returned to Fast Mind's dialogue memory | Fast Mind reads; decides `Invoke` | Reuse instead of re-thinking ([2310.18075](https://arxiv.org/html/2310.18075)) |
| Letta sleep-time | Sleep-time agent edits primary's memory blocks | Primary reads, cannot edit core memory | Every N steps; git commits + worktrees in MemFS ([blog](https://www.letta.com/blog/sleep-time-compute), [MemFS](https://docs.letta.com/concepts/memfs)) |
| LangMem | Background manager extracts/consolidates | Agent reads; may also write on hot path | Debounce: cancel and reschedule pending task ([guide](https://langchain-ai.github.io/langmem/guides/delayed_processing)) |
| VoiceAgentRAG | Slow Thinker prefetches into cache | Fast Talker reads cache only | 300 s TTL, LRU, similarity dedupe; "eventual consistency" ([2603.02206](https://arxiv.org/html/2603.02206v1)) |
| PMFR | Async agent writes knowledge base | Generator reads only | Adequacy gate triggers refresh; provenance+confidence on cached summaries ([2510.08175](https://arxiv.org/html/2510.08175)) |
| Plan Caching | Big planner on miss; lightweight LLM filters template | Small planner adapts template | Disable caching when hit rate stays low; stale templates not discussed ([2506.14852](https://arxiv.org/html/2506.14852v2)) |
| G-Memory | LLM writes insights after each task | Agents read role-filtered subsets | Memory invoked at query start; no concurrent-write handling described ([2506.07398](https://arxiv.org/html/2506.07398)) |
| Collaborative Memory | Private/shared write policies (LLM prompts) | Read filtered by permission graphs | Provenance immutable; conflicts/concurrency not handled ([2505.18279](https://arxiv.org/html/2505.18279)) |
| LbMAS blackboard | All agents write public board; conflict-resolver agent | Control unit picks who reads/acts | Conflict-resolver + cleaner, max 4 rounds ([2507.01701](https://arxiv.org/html/2507.01701)) |

Other findings:
- Letta MemFS makes every memory edit a git commit and lets subagents work in separate worktrees, with versioning described as the conflict-resolution mechanism (merge process unspecified). — [Letta MemFS](https://docs.letta.com/concepts/memfs) [docs]
- A debunked-rumour rule in `gossip-graph` (corrections supersede old beliefs, the debunked rumour cannot spread again) is an explicit staleness/contradiction rule at the belief level. — [gossip-graph](https://github.com/yubaraj2000/gossip-graph) [prototype]
- The only published *quantified* staleness trade-offs in this set are VoiceAgentRAG's TTL/hit-rate numbers and Plan Caching's fuzzy-match accuracy drop (83% → 77% as the similarity threshold loosens); wrong prefetch predictions waste work and stale cache entries persist if the KB changes mid-conversation. — [2603.02206](https://arxiv.org/html/2603.02206v1), [2506.14852](https://arxiv.org/html/2506.14852v2)

### Inferences
- Mapping to the Gemma/Sol question (inference, not a tested recommendation):
  1. *Should the big model write and the small one only read?* The strongest-documented pattern is yes for **consolidated** memory (Letta, Talker-Reasoner, DPT-Agent, PMFR). Sol should own merge, dedupe, contradiction resolution, summaries and decisions.
  2. *Can the small model write fast episodic notes that the big one later consolidates?* Not documented as a named architecture, but it is consistent with every constraint found: it is append-only (no conflict), the writer is the one that sees the raw turn (no extra latency), small-model failure is concentrated in update/merge rather than short extraction, and DUMA/Generative Agents/LangMem all store raw dialogue first and consolidate later. Risks: small-model note quality (Section 3) and embellishment (Generative Agents; relay experiment). Mitigations visible in the sources: constrained decoding, short free-form notes, provenance tag on each note, Sol treating notes as evidence not truth.
  3. *Consistency:* give each memory region one writer (Gemma → `notes` append-only; Sol → `beliefs/profile/summary`; engine code → `world facts`), version Sol's rewrites (commit-per-edit), and tag every item with source (witnessed / told by X / inferred) and timestamp; let the fast path read the last committed version and accept a one-turn delay except for decision-critical turns (Talker-Reasoner's planning-phase wait; SwiftSage's "critical" trigger).
- The literature gives almost no quantitative support for any particular NPC-scale choice (all benchmarks are task-completion or QA, not conversational believability), so any design should be validated with the project's own scoring.

### Gaps
- No independent (non-author) evaluation of any architecture here; staleness effect on dialogue quality is unmeasured everywhere.
- No source compares "small model writes episodic notes + large model consolidates" against "large model writes everything" head to head.
- Ownership split by memory region (as proposed above) is the report-writer's synthesis, not a published design.
