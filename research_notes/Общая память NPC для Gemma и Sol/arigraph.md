# AriGraph (Anokhin et al., AIRI/Skoltech): memory architecture for LLM agents, in depth

Research date: 2026-11-04. Primary sources read in full: arXiv v1, v2 and v3 HTML of 2407.04363, the IJCAI-25 PDF (text extracted), the whole released repository (cloned at HEAD `e884b76`, 2024-09-10, code and the `logs/` folder). Independent work was read from arXiv HTML and GitHub. Where a number comes from my own processing of the repo logs, it is labelled "computed from logs". Items I could not verify are in Gaps sections.

Short version of identity: AriGraph = "Ariadne's Graph", a per-agent memory graph with (a) a semantic triplet graph and (b) episodic vertices (raw observations) linked to the triplets they produced. The paper's agent that uses it is called Ariadne (memory + planner + ReAct-style action selector). Versions: arXiv v1 5 Jul 2024, v2 9 Sep 2024, v3 15 May 2025 ([arXiv abs](https://arxiv.org/abs/2407.04363)); published in IJCAI-25 main track, pp. 12-20, DOI 10.24963/ijcai.2025/2 ([IJCAI-25](https://www.ijcai.org/proceedings/2025/0002), [OpenAlex record](https://openalex.org/W4414360988)).

## 1. Exact architecture: semantic memory, episodic memory, outdated-triplet replacement, planner/decision module, exploration memory

### Takeaway
The graph is G=(Vs,Es,Ve,Ee): triplets as semantic edges, one episodic vertex per observation, and an "episodic edge" that ties an observation to all triplets extracted from it. Every new observation costs 2 memory LLM calls (extract triplets, then check which existing incident triplets are outdated); deletion is destructive and local to the entities named in the new observation. Planner, action selector and an exploration flag are separate LLM calls. The "exploration memory" is not a store, only rule-based reading of exit triplets.

### Cited Findings
- Formal definition: G=(Vs,Es,Ve,Ee). Vs = semantic vertices (objects); Es = semantic edges (v, rel, u), i.e. triplets; Ve = episodic vertices, each one is the full observation text of step t (v_e^t = o_t); Ee = episodic edges e_e^t = (v_e^t, Es^t) which "connect all semantic triplets extracted from o_t with each other and the episodic vertex", described as the relation "happened at the same time". A footnote admits episodic edges are strictly hyperedges. — [arXiv v3](https://arxiv.org/html/2407.04363v3)
- Construction loop per step: (1) LLM extracts triplets from o_t as new vertices/edges; (2) all existing semantic edges incident to the new vertices (E_s^rel) are collected; (3) outdated edges among them are detected by comparison with the new triplets and removed; (4) new vertices/edges are added; (5) the episodic vertex with o_t and the episodic edge to all new triplets is added. — [arXiv v3](https://arxiv.org/html/2407.04363v3)
- Extraction prompt (repo `prompt_extraction_current`): output format `subject, relation, object; ...`; triplet "not more than 7 words"; only concrete knowledge, assumptions must be phrased as hypotheses; subject/object must be atomic, relation may be long; split "John, position, engineer in Google" into two triplets; if the observation says you take an item emit only `item, is in, inventory`; do not emit `you, are in, location`; include triplets about the contents of notes/books that were read; the prompt also receives `{example}` = triplets retrieved at the previous step, as format/style examples. Temperature 0.001. — [prompts.py](https://github.com/AIRI-Institute/AriGraph/blob/main/prompts/prompts.py), [contriever_graph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/graphs/contriever_graph.py)
- Outdated-triplet prompt (`prompt_refining_items`): gets "existing triplets" (those touching the entities of the new triplets) and "new triplets"; must answer only `[[outdated -> actual], ...]`; strongly conservative wording: replace only on semantic duplication / conflicting information about the same aspect of the same entity, "it is better to leave a triplet than to replace the one that has important information", "Do not state that triplet needs to be replaced if you are not sure!!!"; few-shot examples (item moved from floor/kitchen to inventory is replaced; `apple, to be, cooked` vs `apple, is on, table` is not). Temperature 0.001. — [prompts.py](https://github.com/AIRI-Institute/AriGraph/blob/main/prompts/prompts.py)
- Code-level guards around replacement that the paper does not describe: candidate "existing" triplets containing any of `west, east, south, north, associated with, used for, to be` are filtered out before the LLM sees them; `delete_triplets` never deletes a triplet whose both endpoints are known location names; location adjacency triplets (`A is north of B`, plus the inverse) are appended by a rule from the movement action, not by the LLM. Location names come from the environment's own `env.curr_location`. — [contriever_graph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/graphs/contriever_graph.py), [pipeline_arigraph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/pipeline_arigraph.py), [parent_graph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/graphs/parent_graph.py)
- Entity handling: no canonicalisation or entity resolution; `clear_triplet` only lowercases and strips punctuation (and maps "I" to inventory, "P" to player). Duplicates are suppressed only by exact-string equality of the triplet. — [utils.py](https://github.com/AIRI-Institute/AriGraph/blob/main/utils/utils.py)
- Storage in the released code is not a graph database: triplets are a Python list `[subj, obj, {"label": rel}]` plus a dict of string -> embedding; the episodic memory is a dict `observation text -> [list of triplet strings, embedding]`. "Episodic edge" = the list of triplet strings stored with the observation. — [contriever_graph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/graphs/contriever_graph.py)
- Ariadne agent: working memory = final goal, current observation, recent history, retrieved semantic + episodic knowledge, plan. Planner outputs a plan of sub-goals each with a short description/reason and also evaluates the outcome of the action at t-1; a separate ReAct-style decision module states its reason, then picks one action from the valid-action list. Planning and decision are separate LLM calls "to let LLMs focus on distinct cognitive processes". The agent's action space is extended with "go to location" commands that route over spatial relations stored in the semantic graph. — [arXiv v3](https://arxiv.org/html/2407.04363v3)
- Planner and action prompts (repo): planner returns JSON `{main_goal, plan_steps:[{sub_goal_i, reason}], your_emotion:{...}}`; sub-goals may not be reordered or reworded until completed or confirmed irrelevant, only the "reason" text tracks progress; action selector returns JSON `{reason_for_action, action_to_take}`, prioritises main goal, then sub-goals in order, but prefers sub-goals solvable by one action. — [system_prompts.py](https://github.com/AIRI-Institute/AriGraph/blob/main/prompts/system_prompts.py)
- Released pipeline settings: last `n_prev=5` observation/action pairs in the prompt, `topk_episodic=2`, `max_steps=150`; planner and action selector use `gpt-4-0125-preview`, the entity-extraction and exploration-flag agents use the variable `model` (default `gpt-4o`). — [pipeline_arigraph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/pipeline_arigraph.py)
- Exploration (paper App. B): an auxiliary LLM call says whether the current plan needs exploration; if yes, the prompts of the graph agent make it extract triplets like `kitchen, has an unexplored exit, south` and spatial links like `hall, east of, kitchen`; "simple graph-based methods" then list unexplored exits per room and add them to working memory. Algorithm 3 relies on "expert knowledge about what elements of the semantic graph can represent locations and exits". Code: `find_unexplored_exits` is string/keyword matching over triplets (`has exit`, `exit/lead/entr/path` plus compass words). — [arXiv v3](https://arxiv.org/html/2407.04363v3), [utils.py](https://github.com/AIRI-Institute/AriGraph/blob/main/utils/utils.py)
- The repo also contains an unpublished `Hypergraph` variant (entities, "thesis" hyperedges, events), and alternative "thesis" extraction/refining prompts that store whole-sentence facts plus entity lists; the later PersonalAI paper builds on this. — [hypergraph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/graphs/hypergraph.py), [prompts.py](https://github.com/AIRI-Institute/AriGraph/blob/main/prompts/prompts.py)
- Version differences in the architecture description: v1 compared against full history, summarisation and a Generative-Agents-style RAG; v1 reported on TextWorld only. v2 added the multi-hop QA table and the "hardest" Treasure Hunt. v3 added NetHack, separate Simulacra and Reflexion baselines, the token-usage table, ablation rows and the "Graph quality" discussion. — [v1](https://arxiv.org/html/2407.04363v1), [v2](https://arxiv.org/html/2407.04363v2), [v3](https://arxiv.org/html/2407.04363v3)

### Inferences
- The "update" is a single LLM call over a 1-hop neighbourhood. There are no timestamps or validity intervals on triplets, so history of a changed fact survives only inside the old episodic text. Contrast: Zep/Graphiti keeps `t_valid/t_invalid` and invalidates edges by marking them rather than deleting ([Zep paper](https://arxiv.org/html/2501.13956)).
- The agent code is heavily tuned to a single-agent text game (inventory, compass exits, rooms, `you` triplets, `env.curr_location`). Reusing it for NPC dialogue/world knowledge means rewriting prompts and the location/exit rules; the memory core (extract, refine, embed, BFS, episodic scoring) is small and portable.
- The episodic memory is just "raw text of past turns with a pointer list"; any memory that stores raw turns and the structured facts derived from them has the same shape.

### Gaps
- The Appendix E prompts of the paper did not render in the arXiv HTML; I used the repo prompts, which may differ from the paper's. Whether the IJCAI PDF contains the prompts: not checked (its text contains no token-usage table).
- The paper gives no per-step or per-observation count of extracted triplets. (Only my log counts, below.)

## 2. Retrieval: semantic search + graph BFS (depth/width), episodic scoring formula, what goes into the prompt

### Takeaway
Semantic retrieval is embedding top-w over triplet strings, expanded breadth-first for d hops through the vertices of the found triplets. Episodic retrieval ranks past observations by how many of the retrieved triplets they produced (normalised, log-weighted); the released code adds an embedding-similarity term the paper's formula does not show. In the released TextWorld code the numbers are: top-6 triplets per hop, similarity threshold 0.75, depth chosen per entity by an LLM (1 or 2), 2 episodic observations. The working-memory prompt is about 6,000 prompt tokens per step according to the paper.

### Cited Findings
- Algorithm 1 (Memory Graph Search): inputs a set of queries Q and parameters k (number of episodic vertices), d (semantic search depth), w (width). For every query a semantic search returns triplets; the union of triplets is then used for an episodic search that returns k episodic vertices. — [arXiv v3](https://arxiv.org/html/2407.04363v3)
- Algorithm 2 (SemanticSearch) is "close to BFS": a queue starts with the query q with D[q]=0; while the queue is not empty, pop q'; skip if D[q'] >= d; `EmbedAndRetrieve` returns the top-w edges most similar to q' (dot product of embeddings); for each retrieved edge both incident vertices are enqueued with distance D[q']+1; all retrieved edges are the result. Because the query for `EmbedAndRetrieve` is usually a vertex name, it mostly returns edges incident to that vertex, "but also has ability to retrieve edges connected to vertices that are semantically close" (example: "grill" vs "grilling"). — [arXiv v3, App. A](https://arxiv.org/html/2407.04363v3)
- The paper never states the values of d, w, k. — [arXiv v3](https://arxiv.org/html/2407.04363v3)
- Values in the released code (TextWorld pipeline): per-query `max_depth` = the score the LLM assigns to the entity (1 or 2), `topk=6` triplets per hop, `post_retrieve_threshold=0.75` (hits below the score are dropped, so top-k and threshold are combined), `topk_episodic=2`. QA script uses scores 1-3 and the same `topk_episodic=2`. — [pipeline_arigraph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/pipeline_arigraph.py), [retriever_search_drafts.py](https://github.com/AIRI-Institute/AriGraph/blob/main/utils/retriever_search_drafts.py), [parent_agent.py](https://github.com/AIRI-Institute/AriGraph/blob/main/agents/parent_agent.py), [musique_test_big.py](https://github.com/AIRI-Institute/AriGraph/blob/main/musique_test_big.py)
- Where the query entities come from: one extra LLM call (`item_processing_scores`) reads the observation, inventory and plan and returns a JSON dict `{entity: score}` with "a relevance score from 1 to 2", excluding compass exits; the score becomes the BFS depth for that entity. This extra call is not mentioned in the paper's method section. — [parent_agent.py](https://github.com/AIRI-Institute/AriGraph/blob/main/agents/parent_agent.py)
- Episodic scoring, paper Eq. (1): rel(v_e^i) = n_i / max(N_i,1) * log(max(N_i,1)), where n_i = number of input (retrieved) triplets incident to episodic edge e_i, N_i = total number of triplets incident to e_i; the log term "prevents high scores for low information observations"; the text says a "log2(N_i) scaling" is applied (formula writes log); observations with exactly one triplet get zero weight; the k top vertices (observations) are returned. — [arXiv v3](https://arxiv.org/html/2407.04363v3)
- Code version of episodic scoring (`find_top_episodic_emb`, `top_k_obs`): (a) structural score n/N*ln(N) (natural log), divided by the maximum over all stored observations; (b) plus an embedding similarity between the current plan (or the question in QA) and each stored observation, divided by its maximum; final score = sum of the two, top-k (k=2), observations already in the 5-step history are dropped. In `update()` the "input triplets" are the subgraph retrieved at the previous step; in `retrieve()` (QA) they are the current subgraph. — [utils.py](https://github.com/AIRI-Institute/AriGraph/blob/main/utils/utils.py), [contriever_graph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/graphs/contriever_graph.py)
- Embedding models: paper says Contriever (Izacard et al. 2022) for games, replaced by BGE-M3 for multi-hop QA ("better fit for general text encoding"). Released code uses `facebook/mcontriever` (multilingual Contriever) loaded on CPU in the game pipeline (`retriever_device="cpu"`) and `cuda` in the QA script; no BGE-M3 appears anywhere in the repo. — [arXiv v3](https://arxiv.org/html/2407.04363v3), [contriever.py](https://github.com/AIRI-Institute/AriGraph/blob/main/utils/contriever.py), [pipeline_arigraph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/pipeline_arigraph.py), [musique_test_big.py](https://github.com/AIRI-Institute/AriGraph/blob/main/musique_test_big.py)
- Efficiency detail of the released retriever: the BFS calls `retriever.search(triplets_as_strings, q, ...)`, and `Retriever.search` re-embeds all key strings on every call (the stored `triplets_emb` dict is not used for the BFS), so each hop of each query embeds the whole triplet list. — [retriever_search_drafts.py](https://github.com/AIRI-Institute/AriGraph/blob/main/utils/retriever_search_drafts.py), [contriever.py](https://github.com/AIRI-Institute/AriGraph/blob/main/utils/contriever.py)
- What is put into the prompt (planner and action selector get the same blocks): 1 main goal; 2 history of the last 5 observations+actions; 3 current observation (plus inventory); 4 "information from the memory module" = the retrieved triplets (minus triplets that are new this step); 5 the 2 most relevant episodic observations; 6 current/previous plan; 7 (optional) unexplored exits; action selector also gets the valid-action list (plus `go to <known location>`). — [pipeline_arigraph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/pipeline_arigraph.py)
- Token size of the prompts: Table 3 of the paper gives 6,000 prompt tokens and 500 completion tokens per step for Ariadne (text games), versus RAG 4,000/350, Summary 3,800/350, Full history 14,000/350 at step 150, Simulacra 7,500/400, Reflexion 5,800/350. — [arXiv v3, App. D](https://arxiv.org/html/2407.04363v3)
- Retrieved subgraph size, computed from logs: in the Cooking-hardest log the "Length of subgraph" line over 245 steps has median 56 triplets and maximum 84. — [cook_hardest_arigraph.txt](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/cook_hardest_arigraph.txt)
- QA mode: the question is the plan-equivalent; entities of the question (LLM call, scores 1-3) are searched in the graph built from all paragraphs of that item; the final prompt gives "Relevant facts from your memory" (triplets) and "Relevant texts from your memory" (the top-2 episodic paragraphs), and asks for CoT + "Direct answer". — [musique_test_big.py](https://github.com/AIRI-Institute/AriGraph/blob/main/musique_test_big.py)

### Inferences
- The paper's Eq. 1 uses natural vs base-2 log inconsistently, but this does not matter in the released code, because the score is divided by its maximum over all stored observations (a constant factor cancels). (My reading of the code.)
- Retrieval quality depends on a hand-set threshold 0.75 for Contriever dot-product scores: a different encoder (such as BGE-M3 or a small multilingual embedder for Russian-language NPC text) needs its own threshold. The independent reproduction in the repo issue ([issue #3](https://github.com/AIRI-Institute/AriGraph/issues/3)) swapped in BGE-M3 and still got the README numbers, so the encoder alone does not explain the v3 gain.
- Everything that matters for latency in the retrieval path is O(|triplets|) per query-hop in the released code; a real implementation would cache embeddings and use an ANN index.

### Gaps
- Exact d, w, k used for the paper's reported numbers are not stated; the repo values (6 / 0.75 / 2) are from the pipeline file for TextWorld at HEAD and may differ from the numbers used in v3/IJCAI runs, especially for QA after the "slight prompt adjustments" (see Issue #3 under question 6).

## 3. Cost: LLM calls per step, tokens, latency, embeddings

### Takeaway
Paper: no call count, no latency, no dollars; only tokens per step (about 6,000 prompt / 500 completion) and per QA task (11,000 / 2,500, "more than 10x cheaper than GraphRAG" at 115,000 / 20,000). Code: 6 sequential GPT-4-class calls per game step (3 memory-specific). Logs: roughly $0.06-0.10 per step at GPT-4-turbo prices and about 47-87 s median wall-clock per step. Embeddings are a local Contriever on CPU.

### Cited Findings
- Paper Table 3 (tokens): text games per step - Ariadne 6,000 prompt / 500 completion; RAG 4,000/350; Summary 3,800/350; Full history (at step 150) 14,000/350; Simulacra 7,500/400; Reflexion 5,800/350. QA per task - AriGraph 11,000/2,500; GraphRAG 115,000/20,000. Text: AriGraph "more then 10x cheaper" than GraphRAG. No dollars, no latency, no number of LLM calls. — [arXiv v3, App. D](https://arxiv.org/html/2407.04363v3)
- LLM calls per game step in the released pipeline: (1) `item_processing_scores` (entities + depth), (2) triplet extraction, (3) outdated-triplet detection, (4) exploration flag (`need_exp=True`), (5) planner, (6) action selector, all sequential; calls 5 and 6 on `gpt-4-0125-preview`. The graph-update path is calls 2-3; the retrieval query path is call 1. — [pipeline_arigraph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/pipeline_arigraph.py), [contriever_graph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/graphs/contriever_graph.py)
- QA mode calls: per paragraph one extraction call only (`update_without_retrieve` has the outdated-triplet step commented out, so QA runs without update/deletion); per question one entity call and one answer call. — [contriever_graph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/graphs/contriever_graph.py), [musique_test_big.py](https://github.com/AIRI-Institute/AriGraph/blob/main/musique_test_big.py)
- Cost accounting in code: `cost = completion_tokens*3/100000 + prompt_tokens*1/100000` per call, i.e. $30 per 1M output and $10 per 1M input tokens (GPT-4-Turbo list price). — [parent_agent.py](https://github.com/AIRI-Institute/AriGraph/blob/main/agents/parent_agent.py)
- Cost from the shipped logs (computed from logs): Treasure Hunt solved in 36 game steps = $2.30 total ($0.064 mean per step; counters show 122,922 prompt / 12,830 completion tokens, but these counters include only the planner and action calls); Treasure Hunt hard $2.86; Cooking $2.18; Cooking hard $2.57; later logs print "step amount" with a mean of about $0.09 per step (Cooking hardest) and about $0.10 per step (Cleaning). — [hunt_arigraph.txt](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/hunt_arigraph.txt), [hunt_hard](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/hunt_hard_arigraph.txt), [cook](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/cook_arigraph.txt), [cook_hard](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/cook_hard_arigraph.txt), [cook_hardest](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/cook_hardest_arigraph.txt), [clean](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/clean_arigraph.txt)
- Latency (not in the paper; computed from logs): per-step wall-clock "step time" - Cooking hardest median 65.5 s (mean 69.8 s, max 300.9 s); Cleaning median 87.3 s (mean 88.8 s, max 169.9 s); Treasure-hunt without exploration median 47.2 s; Cleaning without episodic median 50.2 s. These include 5-6 sequential API calls to GPT-4-class models and CPU embedding, with no breakdown. — [cook_hardest](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/cook_hardest_arigraph.txt), [clean](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/clean_arigraph.txt), [hunt_arigraph_without_exploration](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/hunt_arigraph_without_exploration.txt), [clean_arigraph_without_episodic](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/clean_arigraph_without_episodic.txt)
- Embeddings: Contriever/mContriever, local, CPU in the game pipeline; `Retriever.embed` embeds the full triplet list on every search call (see question 2). In the QA paper-version BGE-M3. — [arXiv v3](https://arxiv.org/html/2407.04363v3), [contriever.py](https://github.com/AIRI-Institute/AriGraph/blob/main/utils/contriever.py)
- Independent cost numbers for graph construction (MuSiQue, per paragraph, Wikontic's Table 5): AriGraph about 11,000 prompt + 2,500 completion tokens (the same figures as AriGraph's own Table 3), Wikontic 12,687 + 881; Wikontic claims about 3x fewer output tokens. — [Wikontic](https://arxiv.org/html/2512.00590v2)
- AriGraph-derived PersonalAI (extraction + update on Ollama/vLLM, no deletion): memory construction speed 0.85-2.47 contexts (550-650 characters each) per minute, depending on model and dataset; mean 1.48/min for Qwen2.5 7B, 1.19 DeepSeek-R1 7B, 1.71 Llama3.1 8B (local Ollama), 1.86 GPT-4o-mini, 0.92 DeepSeek V3; whole-dataset builds 23.5-90 hours. — [PersonalAI](https://arxiv.org/html/2506.17001v5)

### Inferences
- For an NPC with ~1 observation per game event, the memory-specific cost of AriGraph is 2 LLM calls to write + 1 call to build the retrieval query, per observation. That is 3 calls of about 1-3k tokens each; the large costs in the paper's setting come from planner/action prompts, which an NPC architecture would replace with its own dialogue/decision prompts.
- Per-step latency of 47-87 s in the shipped logs is not an architectural property alone (GPT-4 API latency 2020s-era, 5-6 serial calls, re-embedding the graph on CPU); no measurement separates these parts.

### Gaps
- Number of LLM calls and latency are not reported in the paper; my counts come from the code at HEAD, which may not be what produced all v3 numbers (see the repo-version mismatch in question 6).
- The logs' counters appear to reset per attempt and the log files contain several attempts, so only per-step statistics are used above.

## 4. Models tested; small/open-model evidence (<=30B)

### Takeaway
The paper used GPT-4 Turbo (`gpt-4-0125-preview`) for TextWorld, GPT-4o for NetHack, GPT-4 / GPT-4o-mini for QA; the only open model was LLaMA-3-70B, which was clearly worse. The paper has no experiment with a model of 30B or less. Independent work with 7-27B models exists but only in derived pipelines or on different tasks, and shows large drops at 7B and mixed results at 17-27B.

### Cited Findings
- TextWorld backbone: `gpt-4-0125-preview` for AriGraph and all LLM baselines. NetHack: GPT-4o for all agents. QA: GPT-4 and GPT-4o-mini (v3/IJCAI); v2/README additionally GPT-3.5, LLaMA-3-70B and "LLaMA-3-70B + GPT-4". — [arXiv v3](https://arxiv.org/html/2407.04363v3), [arXiv v2](https://arxiv.org/html/2407.04363v2), [README](https://github.com/AIRI-Institute/AriGraph)
- LLaMA-3-70B in code: `Undi95/Meta-Llama-3-70B-Instruct-hf`, bf16, `max_new_tokens=2048`, temperature 0.2, top_p 0.9. — [llama_agent.py](https://github.com/AIRI-Institute/AriGraph/blob/main/agents/llama_agent.py), [contriever_graph.py](https://github.com/AIRI-Institute/AriGraph/blob/main/graphs/contriever_graph.py)
- TextWorld, normalised score, LLaMA-3-70B vs GPT-4 backbone: Treasure Hunt 0.47 vs 1.0; Cooking 0.67 vs 1.0; Cleaning 0.50 vs 0.79. — [arXiv v3, Table 4](https://arxiv.org/html/2407.04363v3)
- QA with weaker models (v2 table, still in README): MuSiQue EM/F1 - GPT-3.5 14.5/23.3, GPT-4o-mini 23.0/35.1, LLaMA-3-70B 27.0/36.7, LLaMA-3-70B+GPT-4 28.5/36.4, GPT-4 37.0/47.4; HotpotQA EM/F1 - GPT-4o-mini 50.9/60.3, LLaMA-3-70B 43.0/51.8, GPT-4 59.5/69.9. — [arXiv v2](https://arxiv.org/html/2407.04363v2), [README](https://github.com/AIRI-Institute/AriGraph)
- Authors' graph-quality finding: "the growth rate of the graph decreases with the increase in quality of LLM backbone" (stronger LLM = fewer spurious additions/updates); they did not measure graph correctness because direct comparison with a true graph is "extremely challenging". — [arXiv v3, App. C](https://arxiv.org/html/2407.04363v3)
- Independent, PersonalAI (AriGraph-derived memorize + QA pipeline, Skoltech/AIRI/Sber; Qwen2.5 7B, DeepSeek-R1 7B, Llama3.1 8B vs GPT-4o-mini and DeepSeek V3; same LLM does extraction and answering; the outdated-knowledge stage was disabled in the experiments): best LLM-as-judge scores (judge = Qwen2.5 7B) - Qwen2.5 7B 0.22 (DiaASQ), 0.24 (HotpotQA), 0.34 (TriviaQA); DeepSeek-R1 7B 0.12 / 0.19 / 0.27; Llama3.1 8B 0.19 / 0.47 / 0.66; GPT-4o-mini 0.50 / 0.77 (TriviaQA not run); DeepSeek V3 0.47 / 0.76 / 0.87. The paper's own "mean" row gives 0.27 / 0.19 / 0.44 / 0.77 / 0.70 for the five models (the 0.77 for GPT-4o-mini does not equal the mean of its two listed cells, 0.635). Extraction parse-error rates: Qwen2.5 7B and Llama3.1 8B 0.02%, DeepSeek-R1 7B 0.29%, GPT-4o-mini 9.87%, DeepSeek V3 31.21%. For 7B/8B models, the best retrieval configs excluded episodic or object vertices (BeamSearch), while 74-84% of the worst configs excluded thesis vertices. — [PersonalAI](https://arxiv.org/html/2506.17001v5)
- Independent, "The Trap of Trajectory" (May 2026): AriGraph evaluated next to A-Mem, Mem0 and G-Memory with three open LLMs - Llama-4-Maverick-17B, Qwen3.6-27B, Mistral-Small-3.2-24B - on ALFWorld, ScienceWorld, LoCoMo and WebShop questions built to contain spurious correlations. The paper's finding: every memory system raises accuracy on clean inputs over no-memory but also raises the share of spurious-pattern reasoning; graph memories (G-Memory, AriGraph) show extra inflation of one spurious type (T1) on long-form LoCoMo. My extraction of the (flattened) Table 1 suggests AriGraph's original-task accuracy on ALFWorld of about 72 (Llama-4), 86 (Qwen3.6-27B), 61 (Mistral) with spurious ratios of roughly 40-90%; row alignment of that table was not verifiable, treat the numbers as indicative only. — [Trap of Trajectory](https://arxiv.org/html/2605.09330v1)
- Independent, student project `AriGraph_Hoodwinked`: AriGraph and a simpler "RelGraph" in a multi-player deception game (Hoodwinked) with Llama 3.1 8B-Instruct as primary model; authors report the 8B model could not remember complex game instructions without heavy prompt engineering and could not rate other players zero-shot without explicit reasoning, and expect larger models to help. No quantitative AriGraph-vs-baseline result was in the README. — [AriGraph_Hoodwinked](https://github.com/sonyamat/AriGraph_Hoodwinked)
- Independent replication attempt (`yamakoshi-lab`, 2026): authors state that the paper's backbones (Llama-3-70B and `gpt-4-0125-preview`) were confirmed unobtainable in practice, so TextWorld was re-run with Llama-3.1-70B via DeepInfra to check the architecture; no result table in the repo (work in progress). — [Arigraph-Replication-experiment](https://github.com/yamakoshi-lab/Arigraph-Replication-experiment) (see PHASES.md)
- Synapse (ACL Findings 2026) notes, about its own and similar graph-memory methods, that graph topology is tied to the extraction quality of the LLM and "smaller local models may struggle with consistent entity extraction, potentially leading to error propagation" (speculation about the class of methods; no experiment). — [Synapse](https://arxiv.org/html/2601.02744)

### Inferences
- The only controlled evidence in the original work is a 70B-vs-GPT-4 gap of roughly half the score on TextWorld (0.47-0.67 vs 1.0 on easy tasks) and 10-17 EM points on QA. Everything below 70B is extrapolation from derived or different pipelines.
- The two failure modes visible for 7-8B models in PersonalAI are low answer accuracy and (for DeepSeek V3, GPT-4o-mini) output-format parsing errors, while the small Qwen/Llama models almost never broke the parsing format. So format-following is probably not the bottleneck for 7-8B models; extraction coverage/precision and downstream reasoning are. This is an inference; PersonalAI did not isolate extraction quality.
- Nothing found tests Gemma-class models (2B-27B) on AriGraph's extract + replace prompts. The "replace" prompt is the most demanding (it requires conservative judgement about which stored triplets are made false by a new one), and no paper reports its precision/recall for any model.

### Gaps
- No paper reports triplet-extraction or outdated-detection accuracy for any model (the AriGraph authors skip graph-quality metrics).
- No source with Gemma, Qwen3-8B/14B or similar run through AriGraph's own prompts on TextWorld.
- The Trap of Trajectory table numbers: could not parse reliably.

## 5. Benchmarks and numbers (TextWorld, NetHack, multi-hop QA, baselines, humans)

### Takeaway
On custom TextWorld games with GPT-4 Turbo, AriGraph reaches normalised scores 1.0 on Treasure Hunt (all three sizes) and on Cooking and Cooking hard, 0.65 on Cooking hardest, and 0.79 on Cleaning, versus 0.05-0.52 for full-history/summary/RAG; but all agent numbers are the mean of the best 3 of 5 runs, and Reflexion (multi-trial) is close on two tasks. NetHack: with only room observations, AriGraph (593) is near NetPlay with a level-wide memory oracle (675). QA: competitive but below HOLMES; the numbers changed between v2 and v3.

### Inferences
- Best-3-of-5 averaging favours AriGraph and every other LLM agent equally in principle, but variance matters: single-run failure rate is not reported. For a production NPC, mean over all runs and worst-case behaviour are the more relevant numbers.
- The TextWorld tasks reward exactly what the graph is good at: remembering room layout, object locations and recipes in a closed, deterministic text world with explicit exits. The NPC use case differs (open dialogue, social facts, beliefs, time).
- The strong baseline Reflexion (0.93 / 1.0 on TH and Cooking) shows that multi-trial reflection also solves these tasks; AriGraph's edge is single-trial learning, scaling to harder versions, and Cleaning.

### Gaps
- Meaning of "-" cells in Table 4 (not run versus failed) is not explained in the text.
- Figures with step-wise curves and RL numbers are not readable in text form.
- Number of human volunteers is not stated in the paper text I read.
- IJCAI version: only Tables 1-2 and the text sections were cross-checked; the extracted text had no Table 3 and no appendix, so I assume the token table is arXiv-only.

## 7. Limitations and failure modes (stated by the authors, found by others, and visible in the logs)

### Takeaway
The authors list only future work (multimodal observations, procedural memory, better graph search) and have no limitations section. Independent and log evidence shows: dependence on strong LLMs for extraction/update, no canonicalisation (duplicate and inverse triplets, junk like "you, scored, one point"), partial updates that leave contradictory stale triplets, a benefit from episodic memory that reverses where facts change, un-measured graph quality, expert-coded game rules, and poor reproducibility of the later numbers.

### Cited Findings
- Authors' stated limits/future work: "our approach can be further enhanced by incorporating multi-modal observations, procedural memories, and more sophisticated graph search methods". No limitations section. — [arXiv v3](https://arxiv.org/html/2407.04363v3)
- Authors' own caveats in the body: graph quality was not measured (comparison to a true graph is "extremely challenging" and extra facts are not always harmful); exit/location detection uses expert-written rules; LLM-vs-RL environments "not 100% identical"; the Cooking observation was enriched with appliance rules because the task is otherwise "unbeatable for LLM-agents and human players". — [arXiv v3, App. B, C, F](https://arxiv.org/html/2407.04363v3)
- Graph growth: the number of triplets saturates after exploration; it grows moderately on the harder games and the growth rate falls with a better LLM (Fig. 5-6; no raw numbers). — [arXiv v3](https://arxiv.org/html/2407.04363v3)
- Graph size in the shipped logs (computed from logs): final graphs of about 78 triplets (Treasure Hunt, 36 steps), 108 (hunt hard), 93-98 (Cooking), 115-124 (Cooking hard); retrieved subgraph up to 84 triplets per step in Cooking hardest. The outdated-detection call returned at least one replacement pair in about 33-48% of the logged steps (hunt 38/115, hunt hard 53/141, cook 34/89, cook hard 57/118, cook hardest 118/245, clean 172/450; rough count of non-empty "Outdated triplets" lines). — [logs](https://github.com/AIRI-Institute/AriGraph/tree/main/logs)
- Concrete noise/duplication visible in `hunt_arigraph.txt`: step 1 extracts both `room a, contains, golden locker` and `golden locker, is in, room a` (and the same pair for key 1); step 2 extracts `you, scored, one point` as a fact. — [hunt_arigraph.txt](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/hunt_arigraph.txt)
- Partial-update contradiction visible in the same log: after picking up the key the outdated step replaces `key 1, is in, room a` and `key 1, is on, floor` with `key 1, is in, inventory`, but `room a, contains, key 1` stays in the graph next to `key 1, is in, inventory`. — [hunt_arigraph.txt](https://github.com/AIRI-Institute/AriGraph/blob/main/logs/hunt_arigraph.txt)
- Episodic memory can mislead after state changes (Cleaning) - see question 5. — [arXiv v1](https://arxiv.org/html/2407.04363v1), [arXiv v3](https://arxiv.org/html/2407.04363v3)
- Wikontic's critique/table: AriGraph has neither ontology grounding nor explicit entity canonicalisation; in its comparison AriGraph graphs have lower answer coverage (79.9% vs about 96%), Table 2 gives AriGraph 228.0 entities/115.6 relations and average degree 3.9 on MuSiQue (units not defined in extracted text). Wikontic does not claim that AriGraph duplicates entities specifically; the duplicate-surface-forms problem is described for open IE in general. — [Wikontic](https://arxiv.org/html/2512.00590v2)
- PersonalAI (built on AriGraph) reports for its extension: results vary strongly with model scale and with which vertex types may be traversed (up to 24% LLM-judge swing for BeamSearch under different traversal constraints), build time is long, storage 80-90 GB per graph with Milvus vs 4-6 GB with Qdrant, and the outdated-knowledge stage was switched off in experiments "because of the experiments scope". — [PersonalAI](https://arxiv.org/html/2506.17001v5)
- The Trap of Trajectory: graph-based memories including AriGraph inherit and amplify spurious correlations (repeated co-occurrence accumulates into heavier edges) and a single spurious retrieval keeps affecting later decisions. — [Trap of Trajectory](https://arxiv.org/html/2605.09330v1)
- Synapse's argument against AriGraph-style retrieval: it fails when the first vector search misses the relevant subgraph ("bad seed"); on LoCoMo multi-hop AriGraph scores 28.5 F1 vs 35.7 for Synapse. — [Synapse](https://arxiv.org/html/2601.02744)
- Reproducibility problems: the GPT-4 Turbo preview model and the specific LLaMA-3-70B variant are no longer obtainable (per the replication project); QA numbers in the repo differ from the published ones and the reproduction of the published ones failed in issue #3. — [Arigraph-Replication-experiment PHASES.md](https://github.com/yamakoshi-lab/Arigraph-Replication-experiment), [issue #3](https://github.com/AIRI-Institute/AriGraph/issues/3)

### Inferences
- Likely failure modes for a long-lived NPC memory built on this design: (1) fact duplication/near-duplication through paraphrase and inverse relations (nothing merges entities), (2) stale contradictions because the replacement LLM sees only triplets sharing exact vertex strings, (3) conservative prompt = missed deletions; a small model will be less reliable at this judgement, (4) loss of time information, (5) graph growth without any forgetting (no decay, no merge/summarise) over days of game time, (6) embedding threshold drift.
- Because the game results come from a deterministic closed world with GPT-4, they say little about false/contradicting facts told by other characters (belief vs truth), which matters for the project's deception design. AriGraph has no source/belief tagging on triplets.

### Gaps
- No paper measures precision/recall of AriGraph's deletions or counts duplicate entities; the failure modes above come from logs I inspected (a few steps), not from systematic measurement.
- I did not find a systematic third-party critique paper focused on AriGraph itself.

## 8. Follow-up and related work citing AriGraph (2024-2026), including games/NPCs and multi-agent

### Takeaway
Citations are growing (OpenAlex lists 33 citing works for the IJCAI record on 2026-11-04; Semantic Scholar/Google Scholar could not be queried, so the arXiv version surely has more). Direct follow-ups come from the same group (PersonalAI, Wikontic); most others cite it as a graph-memory example or as a baseline (Synapse, Trap of Trajectory). No shipped game or NPC system built on AriGraph was found; the nearest are a student multi-player-game port and a small NPC event-gating paper that only cites it.

### Cited Findings
- Counts: OpenAlex `cited_by_count` 34 and 33 listed citing works for W4414360988 (the IJCAI record). — [OpenAlex work](https://openalex.org/W4414360988), [citing list](https://api.openalex.org/works?filter=cites:W4414360988&per-page=100)

### Inferences
- Memory systems that kept the same idea (episodic + semantic layers, graph traversal) became production-oriented in other lines of work (Zep/Graphiti: temporal validity, entity resolution), while AriGraph remains the cheap, simple reference design. Good starting concepts for the NPC memory, not a drop-in.
- Absence of a games/NPC deployment in peer-reviewed work means there is no evidence of AriGraph (or its triplet-update step) working with persona dialogue, deception or tens of NPCs.

## 9. Fit for a shared per-NPC memory used by a small local model (Gemma) and a large hosted model (Sol)

### Takeaway
AriGraph's reusable core is small: per-observation triplet extraction, a conservative replacement pass, an embedding-based triplet index with BFS expansion and an episodic score based on triplet overlap. Its published evidence is GPT-4-class and deterministic single-agent text games; evidence for ≤30B models is weak and indirect. Treat it as a design reference and prototype by measurement on our own NPC logs, not as an off-the-shelf component.

### Cited Findings
- All claims in this section are inferences from the cited material above; sources: [arXiv v3](https://arxiv.org/html/2407.04363v3), [repo](https://github.com/AIRI-Institute/AriGraph), [PersonalAI](https://arxiv.org/html/2506.17001v5), [Trap of Trajectory](https://arxiv.org/html/2605.09330v1), [Zep paper](https://arxiv.org/html/2501.13956).

### Inferences
- What transfers: (a) the two-layer shape (raw event text + extracted facts pointing to it), cheap to store and shareable between two models; (b) the episodic scoring idea (rank past events by how many currently relevant facts they produced); (c) a pure-code BFS with a similarity threshold, which costs no LLM tokens.
- What does not transfer or needs redesign: deletion-by-LLM without timestamps (use validity intervals/supersession links instead, as Zep does); game-specific prompts and location rules; the planner/action calls; lowercase-string entity identity (NPC names, aliases and ASR-mangled names need an alias table); no belief/source field (needed for lies and rumours).
- Division of labour hint from the cost structure: write path (extract + replace) is 2 calls per event with 1-3k tokens each and tolerant of latency, so it could run asynchronously on either model; the query-entity call (1 call per step) is what sits on the response path, and it could be replaced by a code-side entity matcher over the NPC's alias table. Whether Gemma-class models can do extraction/replacement well is unmeasured (see question 4 gaps); a measurement on our own transcripts with the repo's `prompt_extraction_current` and `prompt_refining_items` would be the quickest test.
- Metrics worth adding if prototyped, since the paper has none: extraction precision/recall against hand-labelled events, duplicate rate, stale-fact rate after a state change, and the share of replacement calls that delete a still-true fact.

### Gaps
- No evidence on Russian-language text, multi-character dialogue, time-stamped facts, or tens of simultaneously active agents with AriGraph-style memory.
