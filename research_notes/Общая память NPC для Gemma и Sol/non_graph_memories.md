# Non-graph memory architectures for LLM agents (state of the art as of 2026-11-04): stream/scored memories, tiered self-editing memories, reflection, summarisation hierarchies, forgetting, background consolidation, structured state

Legend used in every "Cited Findings" bullet. [author] = number or claim reported by the system's own authors. [vendor] = measured by a company about its own or a competitor's product. [indep] = measured by a party that does not sell the system. [secondary] = blog, forum or search-summary, not a primary source. Where two sources disagree, both are listed in the same bullet. "Inferences" are mine, not from any source. I read the relevant passages of the cited arXiv papers in extracted full text (PDF) unless a bullet says "abstract only" or "via search summary". Several 2026 preprints (ForgetEval, Weighted Memory Tree, FadeMem) are single-team, not peer-reviewed as far as I could see.

## 1. Scored memory streams, reflection and planning: Generative Agents and the cheaper descendants (Lyfe Agents, Affordable Generative Agents)

### Takeaway
Generative Agents store every observation as a timestamped natural-language record and retrieve by a sum of recency + LLM-rated importance + embedding relevance; reflection (LLM-written higher-level records that cite their evidence) is triggered when accumulated importance crosses a threshold. The public code differs from the paper's constants. The architecture is expensive (thousands of dollars for 25 agents x 2 days), and the cheap descendants save cost mainly by cutting LLM calls and compressing retrieved text, with quality evidence that is thin (qualitative interviews, one murder-mystery scenario).

### Cited Findings
- Retrieval score = alpha_recency*recency + alpha_importance*importance + alpha_relevance*relevance, each min-max scaled to [0,1]; "in our implementation all alphas are set to 1"; the top-ranked memories that fit the context window go into the prompt — [Park et al. 2023 (paper)](https://arxiv.org/abs/2304.03442) [author]
- Recency in the paper: exponential decay over sandbox game hours since the memory was last retrieved, decay factor 0.995. Importance: the LLM is asked for an integer 1-10 ("1 purely mundane... 10 extremely poignant"), generated once when the memory object is created. Relevance: cosine similarity between the memory embedding and the embedding of a query memory — [Park et al. 2023](https://arxiv.org/abs/2304.03442) [author]
- The public code differs from the paper: `new_retrieve` uses `gw = [0.5, 3, 2]` (recency 0.5, relevance 3, importance 2; `[1,1,1]` and `[1,2,1]` are commented-out alternatives), min-max normalisation per component, and `n_count=30` (top 30 per focal point) — [retrieve.py](https://github.com/joonspk-research/generative_agents/blob/main/reverie/backend_server/persona/cognitive_modules/retrieve.py) [author code]
- In the code `recency_decay = 0.99` (not 0.995), and `extract_recency` computes `recency_decay ** i` over the *rank index* of nodes sorted by `last_accessed`, not over game hours. As summarised by the fetch tool, the list is sorted ascending so the oldest-accessed node gets the largest value; I did not execute the code, so treat this as "appears inverted, verify before reusing" — [retrieve.py](https://github.com/joonspk-research/generative_agents/blob/main/reverie/backend_server/persona/cognitive_modules/retrieve.py), [scratch.py](https://github.com/joonspk-research/generative_agents/blob/main/reverie/backend_server/persona/memory_structures/scratch.py) [author code]
- Reflection trigger: sum of importance scores of the latest perceived events exceeds 150 (`importance_trigger_max = 150` in the code); agents reflected "roughly two or three times a day" — [paper](https://arxiv.org/abs/2304.03442), [scratch.py](https://github.com/joonspk-research/generative_agents/blob/main/reverie/backend_server/persona/memory_structures/scratch.py) [author]
- Reflection procedure: feed the 100 most recent memory records to the LLM and ask for the 3 most salient high-level questions; use each question as a retrieval query (reflections themselves are retrievable); then ask for 5 high-level insights with citations "(because of 1, 5, 3)"; store each insight as a memory with pointers to the cited records, giving a reflection tree — [paper](https://arxiv.org/abs/2304.03442) [author]
- Ablation (TrueSkill, crowd-ranked believability of interview answers): full architecture mu=29.89 (sigma 0.72); no reflection 26.88; no reflection and no planning 25.64; human crowdworker 22.95; no memory/planning/reflection 21.21. Reflection therefore adds about 3 points (about 4 sigma units of the listed sigmas) on top of memory+planning. The evaluation is a snapshot of 25 agents over 2 simulated days with interviews as the probe — [paper](https://arxiv.org/abs/2304.03442) [author]
- Cost: "simulate 25 agents for two days, costing thousands of dollars in token credits and taking multiple days"; the authors name parallelisation or purpose-built models as future work — [paper](https://arxiv.org/abs/2304.03442) [author]
- Failure modes reported by the authors: failing to retrieve the right memory (an agent says he has not followed the election though he heard about it), retrieving an incomplete fragment, and embellishing recalled facts — [paper](https://arxiv.org/abs/2304.03442) [author]
- Lyfe Agents (MIT/LyfeAL): Summarize-and-Forget memory has working memory (about 4-5 items) feeding a self-monitoring summary, `recentmem` and `longmem`; when recentmem reaches capacity its items are clustered by embedding similarity and each cluster is summarised by an LLM before moving to longmem. Forgetting: when a new memory arrives, existing memories whose cosine similarity to it exceeds a threshold theta are deleted as redundant. The authors argue clustering before summarising keeps the summary semantically close to its parts so similarity search still finds it — [Lyfe Agents](https://arxiv.org/abs/2310.02172) [author]
- Lyfe Agents ablation (murder-mystery scenario, 3/6/9 agents): a plain single memory list with no forgetting and no summarisation consistently scores below the full system; ablating self-monitoring or SaF "dramatically lowers" performance. I could not extract the numeric values (they are in figures) — [Lyfe Agents](https://arxiv.org/abs/2310.02172) [author]
- Lyfe's cost claim, about $0.5 per agent per human hour on GPT-3.5 versus about $25 for Park et al., is the authors' own estimate: they *assumed* Park et al. spent $2,000 for 25 agents x 2 game days and *assumed* a 10x game-speed factor. The "10-100x cheaper" claim rests on that assumption — [Lyfe Agents, appendix F](https://arxiv.org/abs/2310.02172) [author estimate]
- Lyfe's self-monitoring summary is updated by an LLM call "asynchronously" with action selection and carries a narrative summary of recent events weighted by novelty and goal relevance; without it agents "frequently forgot their ongoing tasks" — [Lyfe Agents](https://arxiv.org/abs/2310.02172) [author]
- Affordable Generative Agents (Tencent, TMLR 2024): "Social Memory" is a per-interlocutor record with Summary Events, Relationship (e.g. acquaintances) and Feeling (e.g. friendly), updated by an LLM after each conversation. It replaces 30-45 retrieved events (about 2,000 tokens) in each conversation prompt with about 100 tokens — [AGA](https://arxiv.org/abs/2402.02053) [author]
- AGA token use relative to the Generative Agents baseline (GPT-3.5-Turbo, 3-person town, 2 game days): Lifestyle Policy only 40.2%, Social Memory only 58.6%, full AGA 31.1%; in a 25-person town 42.7% (25.41M -> 10.86M tokens). Total tokens 4.525M (baseline) vs 1.420M (AGA) with GPT-3.5 — [AGA](https://arxiv.org/abs/2402.02053) [author]
- AGA quality evidence is qualitative: the same interview questions as Park et al., plus counts of agents who learned about the election/party (baseline 8 and 13; AGA 4-12 and 12-17 over repeated runs) — [AGA](https://arxiv.org/abs/2402.02053) [author]

### Inferences
- The retrieval score is cheap and reusable (one embedding per record plus a stored importance integer), but the constants are not portable: the paper and the public code disagree, no source isolates the contribution of the importance term, and the code's recency is rank-based rather than time-based. For a game, define recency in game-time or visit-count explicitly and tune weights on your own probes.
- Per reflection the paper's procedure costs about 4 LLM calls (1 for questions, 3 for insights) plus an importance call per stored memory — this count is my arithmetic from the described procedure, not a published number. With two or three reflections per agent-day that is a batch job, which fits a slow "Sol" model better than the fast Gemma path.
- The strongest reusable idea from AGA is not summarisation but a typed per-pair record (relationship, feeling, summary events) that is overwritten, not appended — it is the first-found example of schema-based memory beating a growing stream on cost.

### Gaps
- No independent replication or ablation of the retrieval weights (recency vs importance vs relevance) was found; the one search for it returned only secondary summaries.
- Lyfe's ablation magnitudes and AGA's quality-vs-baseline numbers are only in figures/qualitative text I could not extract.
- No public measurement of how often LLM importance scores cluster at certain values (a commonly voiced worry); I found nothing citable.

## 2. Tiered self-editing memory: MemGPT / Letta (core memory blocks, recall and archival memory, memory tools)

### Takeaway
MemGPT treats the prompt as RAM: a read-only system prompt, a small writable "working context" (later "core memory blocks"), and a rolling FIFO message queue with a recursive summary at the head, backed by a recall store (all messages) and an archival store (arbitrary text). The model edits and pages memory through function calls and is nudged by a memory-pressure warning. On the authors' own recall test it lifts GPT-4 from 32.1% to 92.5%, but later head-to-head comparisons on other benchmarks are contested and show that weaker or non-agentic memory managers often lose to plain full context.

### Cited Findings
- Main context = system instructions (read-only) + working context (fixed-size read/write text, writable only via function calls; holds persona and key facts) + FIFO queue whose first slot is a system message containing a recursive summary of evicted messages — [MemGPT](https://arxiv.org/abs/2310.08560) [author]
- Eviction policy: at a "warning token count" (example 70% of the window) the queue manager inserts a memory-pressure system message so the model can save important items to working context or archival storage; at a "flush token count" (example 100%) it evicts a chunk (example 50% of the window), writes a new recursive summary from the old summary plus evicted messages, and keeps the evicted messages forever in recall storage — [MemGPT](https://arxiv.org/abs/2310.08560) [author]
- The model's output is parsed as function calls; `request_heartbeat=true` lets it chain calls (multi-step retrieval); retrieval is paginated ("Showing 3 of 124 results (page 1/13)") so a search cannot overflow the window — [MemGPT](https://arxiv.org/abs/2310.08560) [author]
- Deep Memory Retrieval (a new task built by the authors; the baselines see only a lossy summary of the five previous conversations while MemGPT can search the full history): accuracy GPT-3.5 Turbo 38.7% -> 66.9% with MemGPT, GPT-4 32.1% -> 92.5%, GPT-4 Turbo 35.3% -> 93.4% — [MemGPT](https://arxiv.org/abs/2310.08560) [author]
- Letta "memory blocks": each block has a label, a value (string), a size limit and an optional description; stored separately with a `block_id`; agents edit them through memory tools, developers through API; blocks can be shared by several agents (shared knowledge, sleep-time compute, team memory). Default limits are not stated. The Letta blog contains no benchmark numbers — [Letta: memory blocks](https://www.letta.com/blog/memory-blocks) [vendor]
- Letta's shared-memory docs warn that `memory_rethink` does full-block rewrites with last-writer-wins semantics and recommend a single owner agent (or the sleep-time agent) for heavy edits while others append with `memory_insert` — [Letta shared memory](https://docs.letta.com/v1-sdk/memory/shared-memory) [vendor, as relayed by a search summary]
- Letta's filesystem experiment: the LoCoMo conversation placed in a file, agent given `grep`, `search_files`, `open`, `close`, GPT-4o mini, tool rules forcing it to start with `search_files` and to end with `answer_question`: 74.0% accuracy against 68.5% that Mem0 published for its best graph variant. Letta states it could not backfill LoCoMo into MemGPT without major refactoring, that Mem0's figures are "controversial", and that LoCoMo "may not be very meaningful" because it tests retrieval, not agentic memory. The agent rewrites queries itself ("How does Calvin stay motivated when faced with setbacks?" -> "Calvin motivation setbacks") and searches iteratively — [Letta: benchmarking agent memory](https://www.letta.com/blog/benchmarking-ai-agent-memory) [vendor]
- Letta Leaderboard (May 2025; the repo is now archived and folded into Letta-Evals): tests core-memory read, archival read and write (including conflicting facts to force core-memory updates), graded by a GPT-4.1 judge with a penalty for extraneous memory operations — [Letta leaderboard](https://www.letta.com/blog/letta-leaderboard) [vendor, via search summary]
- An independent benchmark of agent memory (MemoryAgentBench, ICLR 2026) evaluated MemGPT: average Accurate-Retrieval score 34.3 (vs 58.1 for GPT-4o 128K long-context and 60.5 for BM25 RAG), Long-Range-Understanding average 22.4, conflict-resolution (FactConsolidation) 28.0 single-hop and 3.0 multi-hop — [MemoryAgentBench](https://arxiv.org/abs/2507.05257) [indep]
- In the MemGPT paper the gap between models is large: GPT-3.5 reaches 66.9% on DMR versus 92.5% for GPT-4, i.e. the self-editing loop depends on the underlying model's function-calling reliability — [MemGPT](https://arxiv.org/abs/2310.08560) [author]. A secondhand forum comment says Llama-2-70B variants "consistently" produced wrong function arguments or invented functions; I found no benchmark of 7-8B models on MemGPT-style tool use — [HN-style summary via search](https://brianlovin.com/hn/37901902) [secondary]

### Inferences
- The tier split (small always-in-prompt block, bounded queue, searchable store) is the reusable core. For two models sharing one memory, "core block" = what Gemma sees every turn; "archival/recall" = what Sol (or a retrieval step) fetches.
- Self-editing by the *fast* model is the risky part: it needs reliable tool calls on every turn and extra heartbeat round-trips, and the only evidence on weaker models is that quality drops with model strength (GPT-3.5 vs GPT-4; MemoryAgentBench MemGPT numbers). Assigning writes to the slow model (Sol) and keeping the Gemma path read-only matches the evidence better.
- Letta's own advice (single owner for rewrites, others append) is a concurrency rule you will need once two models write to the same NPC memory.

### Gaps
- No current (2026) measurement of MemGPT/Letta core-memory editing with a small local model (Gemma class) was found.
- Letta's published default block limits and the exact prompt/tool schema were not retrievable from the pages I could fetch.
- The Mem0-vs-Letta LoCoMo dispute is unresolved (see section 9); Letta has not (to my knowledge from the sources read) re-run its filesystem test against Mem0's newer pipeline.

## 3. Background / sleep-time consolidation: Letta sleep-time agents, "sleep-time compute", LangMem background manager, Letta Code "dreaming"

### Takeaway
Sleep-time designs move memory rewriting off the response path: a second agent, often a bigger or cheaper model, edits the shared memory blocks while the primary agent answers. The only controlled measurements (Letta/Berkeley paper) are on stateful math and a coding-agent task, not on dialogue memory: roughly 5x less test-time compute for equal accuracy, and 2.5x lower per-query cost only when several related queries share one context. There is no published measurement of sleep-time agents improving conversational memory quality.

### Cited Findings
- Letta sleep-time architecture: creating a sleep-time agent creates two agents; the primary agent talks, can search recall and archival memory, but "is not provided with tools to edit its core memory"; the sleep-time agent holds the core-memory editing tools and can manage both agents' memory blocks asynchronously, so the primary agent can read without waiting. Different models are possible: the blog suggests a fast model (gpt-4o-mini) for the primary agent and a larger slower one (gpt-4.1 or Sonnet 3.7) for sleep time. Higher frequency "uses more tokens" but gives more time to revise the "learned context" — [Letta: sleep-time compute](https://www.letta.com/blog/sleep-time-compute) [vendor]
- Trigger: sleep-time agent runs every N steps, default 5 (`sleeptime_agent_frequency`); docs label sleep-time agents experimental/unstable — [Letta docs (search-result excerpt)](https://docs.letta.com/guides/agents/architectures/sleeptime) [vendor, secondary excerpt]. A Jan-2026 forum guide says "every 5 messages" and recommends Claude Sonnet 4.5 or GPT-4o for the primary and Claude Haiku 4.5 for the sleep agent because memory work "doesn't need expensive model" — [Letta forum](https://forum.letta.com/t/sleeptime-agents-for-memory-consolidation-best-practices-guide/154) [secondary, community]
- Forum guide tool set: both agents get `memory_insert` and `memory_replace`; the sleep agent additionally gets `memory_rethink` (whole-block rewrite) "most valuable on sleeptime"; suggested cadence: dedupe every run (search before insert), light consolidation at session end, full reorganisation weekly, hierarchical roll-ups monthly when archival passes a threshold; suggested expiry: session context 30 days unless referenced 3+ times, decisions/preferences never, debug 14 days unless tagged root-cause, TODOs 90 days; "Reference count matters more than age"; "Don't over-consolidate - you lose granularity"; no measurements, no cost figures — [Letta forum](https://forum.letta.com/t/sleeptime-agents-for-memory-consolidation-best-practices-guide/154) [secondary, community]
- Current Letta docs at the sleeptime URL describe a related Letta Code feature, "dreaming": background subagents review recent conversations, consolidate lessons and update memory without interrupting work; they run after a set number of completed steps or when the context window is compacted; an optional "agent reviews before applying" step has a second background conversation review proposed updates (more tokens); updates go to MemFS, a git-backed memory filesystem shared across the agent's conversations — [Letta docs](https://docs.letta.com/guides/agents/architectures/sleeptime) [vendor, via fetch summary]
- Sleep-time compute paper (Letta + UC Berkeley): given context c but no query, S(c)->c' re-represents c (infers likely questions, pre-computes results); at test time T_b(q, c') uses a much smaller budget b << B. Implemented by prompting the model with two functions, `rethink_memory` (replace the entire current context with a new string; allowed up to 10 times) and `finish_rethinking` — [Sleep-time Compute](https://arxiv.org/abs/2504.13171) [author]
- Results: same accuracy with about 5x fewer test-time tokens on Stateful GSM-Symbolic (GPT-4o-mini, GPT-4o; P1 5,000 and P2 2,500 examples) and Stateful AIME (60 questions; o3-mini, Claude 3.7 Sonnet extended thinking, DeepSeek-R1; o1 showed "limited gains"); scaling sleep-time compute adds up to +13% (GSM) and +18% (AIME); with 10 related queries per context the average cost per query falls 2.5x under the assumption that a test-time token costs 10x a sleep-time token; with few queries per context sleep-time is less favourable in total cost — [Sleep-time Compute](https://arxiv.org/abs/2504.13171) [author]
- Limits reported by the authors: at high test-time budgets the test-time-only baseline slightly wins (hypothesis: extra material distracts); gain correlates with how predictable the query is from the context (binned by Llama2-70B log-probability); in the SWE-Features agent case study (file-set F1 for feature PRs) up to about 1.5x fewer test-time tokens at low budget, worse precision at high budget because the sleep-time agent tends to edit more files — [Sleep-time Compute](https://arxiv.org/abs/2504.13171) [author]
- LangMem (LangChain): memory formed in the "hot path" adds "perceptible latency", while "background" formation has no response latency but delayed updates and is "recommended for higher recall". `ReflectionExecutor.submit(..., after_seconds=delay)` debounces: it keeps a pending-task queue per thread, cancels older tasks when new messages arrive and runs only after the delay; the docs' example delay is 0.5 s "for demonstration" and say "in practice would choose longer (30-60 min)" — [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/), [LangMem delayed processing](https://langchain-ai.github.io/langmem/guides/delayed_processing/) [vendor]
- Mem0's extraction step also uses an asynchronously refreshed conversation summary so extraction is not blocked — [Mem0](https://arxiv.org/abs/2504.19413) [author]; Lyfe's self-monitor likewise runs asynchronously from action selection — [Lyfe Agents](https://arxiv.org/abs/2310.02172) [author]

### Inferences
- The sleep-time paper is evidence for *pre-computing derived context for predictable questions*, not for "background agent keeps memory clean". Its `rethink_memory` is a full rewrite, which is exactly the monolithic-rewrite pattern that section 6 shows can collapse (ACE) — so a Sol-side "sleep" pass should emit deltas against a structured store rather than rewrite a prose document.
- For an NPC, player questions in a given scene are fairly predictable from scene context (who is present, active quests), which is the condition under which the paper found sleep-time work pays off; the per-query amortisation argument also favours doing Sol's pass once per game-time interval/dialogue end, not per utterance.
- LangMem's debounce-and-cancel pattern maps well to dialogue: run consolidation only after a conversation goes quiet.

### Gaps
- No quantitative evaluation of Letta sleep-time agents on conversational or multi-session memory quality was found (blog and forum give none; the paper uses math/SWE tasks).
- The "every 5 steps" vs "every 5 messages" wording is inconsistent between sources; I could not fetch the original Letta docs page text that states the default and I did not confirm `memory_rethink` is default-enabled in the current SDK.
- Cost in dollars of a Letta sleep-time agent per user-hour is not published.

## 4. Summary-based and derived memories: MemoryBank, Reflexion, Think-in-Memory, RAPTOR, ReadAgent, SeCom, RMM, MemoryOS

### Takeaway
These systems store LLM-derived text instead of (or on top of) raw logs. The independent measurements are consistent on one point: replacing raw turns with summaries or extracted facts usually loses answerable detail (LongMemEval, SeCom's baselines, MemoryAgentBench), while keeping raw text and using summaries/facts as extra retrieval keys, or keeping a pointer back to the original (ReadAgent look-up), recovers or exceeds raw-text performance. Evidence for MemoryBank, TiM and MemoryOS comes from author-built small evaluations.

### Cited Findings
- MemoryBank (AAAI 2024): stores timestamped dialogues, a daily event summary, a global event summary, and daily-then-global user-personality summaries; retrieval by embedding + FAISS — [MemoryBank](https://arxiv.org/abs/2305.10250) [author]
- MemoryBank forgetting: retention R = e^(-t/S); S is a discrete strength initialised to 1 when an item is first mentioned; each time the item is recalled S += 1 and t is reset to 0; the paper calls this "exploratory and highly simplified" — [MemoryBank](https://arxiv.org/abs/2305.10250) [author]
- MemoryBank evaluation: a 10-day memory store from 15 ChatGPT-simulated users, 194 hand-written probe questions (97 English, 97 Chinese), human scoring; SiliconFriend (ChatGPT) English: retrieval accuracy 0.763, correctness 0.716, coherence 0.912; Chinese 0.711 / 0.655 / 0.675; open-source ChatGLM/BELLE variants have higher retrieval accuracy (0.809-0.856) but lower correctness (0.418-0.603). I found no experiment isolating the forgetting mechanism, and a 10-day store would barely exercise it — [MemoryBank](https://arxiv.org/abs/2305.10250) [author]
- Reflexion: an episodic buffer of the agent's own verbal self-reflections after failed trials, bounded to a maximum Omega of 1-3 stored experiences "to adhere to max context LLM limitations"; reported gains: +22% on ALFWorld (12 iterative steps), +20% on HotPotQA, up to +11% on HumanEval, 91% pass@1 on HumanEval — [Reflexion](https://arxiv.org/abs/2303.11366) [author]
- Think-in-Memory (Ant Group): after answering, the LLM writes "inductive thoughts" as relation triples in text (e.g. "(China, Capital, Beijing). The capital of China is Beijing."), stored in an LSH hash table (similar thoughts share a bucket); retrieval = LSH bucket then pairwise cosine within the bucket; organisation ops are Insert, Forget (prompt: "remove the counterfactual thoughts or contradictory thoughts") and Merge (prompt: merge thoughts with the same entity, e.g. "John works as an actor, a director, and a writer") — [TiM](https://arxiv.org/abs/2311.08719) [author]
- TiM results vs MemoryBank's SiliconFriend (ChatGLM): English correctness 0.438 -> 0.450, coherence 0.680 -> 0.735; Chinese correctness 0.418 -> 0.605, coherence 0.428 -> 0.665; Top-5 thoughts recalled; retrieval-time table with memory length 140 — [TiM](https://arxiv.org/abs/2311.08719) [author]
- RAPTOR: recursively embeds, clusters (GMM after UMAP, soft clusters), and LLM-summarises chunks into a tree; retrieval over all layers ("collapsed tree"); QuALITY 82.6% with GPT-4 (reported as +20% absolute over previous best); about 4% of summaries contained minor hallucinations which did not propagate; searching all layers beat searching only one layer — [RAPTOR](https://arxiv.org/abs/2401.18059) [author]
- The same RAPTOR retriever performed poorly in an incremental agent-memory benchmark: Accurate-Retrieval average 36.8 vs 60.5 for BM25 and 58.1 for GPT-4o long-context; Long-Range-Understanding average 27.9 (summarisation sub-task 13.4) and FactConsolidation average 7.5 — [MemoryAgentBench](https://arxiv.org/abs/2507.05257) [indep]
- ReadAgent (Google DeepMind): paginate into episodes, compress each page into a "gist", and let the model look up original pages on demand. On QuALITY gists alone (85.53% compression) score 77.52% vs 85.83% for the full raw text; ReadAgent with look-up of 1-6 pages scores 86.91% (parallel) / 87.17% (sequential); effective context extended 3.5-20x; look-up of up to 2 pages gives about 3.5x more tokens in context at 72.17% compression — [ReadAgent](https://arxiv.org/abs/2402.09727) [author]
- SeCom (ICLR 2025): segment-level memory (topically coherent segments, LLM segmentation) plus LLMLingua-2 compression as denoising. LoCoMo GPT4Score: SeCom (BM25, GPT-4 segmentation) 71.57; turn-level BM25 65.58; session-level BM25 63.16; MemoChat 65.10; recursive-summary RecurSum 56.25 (about 400 tokens); SumMem 53.87; full history 54.15 (13,330 tokens); no history 24.86. On Long-MT-Bench+ SeCom 86.67-88.81 vs full history 63.85. Summarisation baselines and full history lose to retrieval over raw units — [SeCom](https://arxiv.org/abs/2502.05589) [author, GPT-4 judge]
- LongMemEval's reader experiments: decomposing sessions into rounds improves GPT-4o reading; replacing sessions/rounds by extracted summaries or facts "negatively impacts QA performance due to information loss" (exception: multi-session reasoning improves with fact decomposition); using summaries/facts as *keys* appended to the original value (document expansion) improves recall@k by 9.4% and final accuracy by 5.4% on average — [LongMemEval](https://arxiv.org/abs/2410.10813) [indep]
- RMM (Reflective Memory Management, Google/UNC): "Prospective reflection" summarises dialogue into topic-based memories; "Retrospective reflection" refines the retriever online by RL from the evidence the LLM cites; reports more than 10% accuracy gain over a no-memory-management baseline on LongMemEval — [RMM](https://arxiv.org/abs/2503.08026) [author]
- MemoryOS: short-term FIFO of dialogue chains -> mid-term segmented pages with a heat score, Heat = alpha*N_visit + beta*L_interaction + gamma*R_recency; segments above a threshold (tau = 5) are promoted to long-term personal memory; claims average +49.11% F1 and +46.18% BLEU-1 on LoCoMo (GPT-4o-mini) over baselines — [MemoryOS](https://arxiv.org/abs/2506.06326) [author]
- A-MEM (Zettelkasten-style linked notes with "memory evolution" that rewrites older notes' attributes when related notes arrive) is a note network and so borders on graph memory; Mem0's re-run of A-Mem scored J=48.38 (2,520 memory tokens) on LoCoMo — [A-MEM](https://arxiv.org/abs/2502.12110) [author]; [Mem0](https://arxiv.org/abs/2504.19413) [vendor]

### Inferences
- The robust pattern is "summary as index, raw as source of truth": keep the original episode text (or at least the original utterance) addressable from every summary/fact, and use LLM-derived text to improve *retrieval keys*, as LongMemEval and ReadAgent show. For a game this means keeping the event log and treating the NPC's "what I think happened" notes as a view, not the store.
- MemoryBank's forgetting law is the simplest form of "usage-reinforced strength" (+1 per recall, reset t). It is cheap and deterministic but unevaluated; the better-evidenced usage-based pruning is in section 5.
- TiM's forget and merge prompts are a concrete template for a closing step: group by entity, drop contradicted thoughts, merge same-entity thoughts. They were only evaluated on small dialogue sets.

### Gaps
- No ablation of MemoryBank's forgetting term, nor of TiM's forget/merge operations versus insert-only, was found.
- ReadAgent, RAPTOR, MemWalker are document-reading designs; I found no dialogue/NPC evaluation of them apart from MemoryAgentBench's negative RAPTOR result.
- The MemoryOS and RMM gains are author-reported on LoCoMo/LongMemEval; I found no independent replication.

## 5. Forgetting, decay, merging and bloat control: what works, with evidence on retrieval quality versus memory size

### Takeaway
Usage-based or utility-based pruning can shrink an agent memory by roughly 63-77% with small accuracy change (sometimes a gain) when the quality signal is good, but it hurts when the evaluator is noisy; pure time-decay laws (Ebbinghaus) are popular but have almost no ablation evidence. The strongest independent evidence on "size vs quality" is about *context length*: accuracy falls as the amount of text in the prompt grows, and focused retrieval beats stuffing the whole history, yet plain full context still beats most memory systems on short (26K-token) conversations.

### Cited Findings
- Survey taxonomy of forgetting: time-based (creation time, decay; MemGPT FIFO eviction), frequency-based (LFU/LRU, MemOS uses LRU with archiving), and importance-driven (composite of time, frequency and semantic value; TiM and MemTool use an LLM to judge importance). It notes that heuristics such as LRU "may eliminate long-tail knowledge" and that many systems avoid deleting when storage is cheap — [Memory in the Age of AI Agents](https://arxiv.org/abs/2512.13564) [secondary survey]
- Experience-following study (addition and deletion policies on four agents): periodic deletion by retrieval frequency (delete a record whose retrievals in a window are <= alpha) with a coarse evaluator reduced memory 3,511 -> 1,012 records (RegAgent, performance 63.18 -> 60.88), 1,447 -> 338 (EHRAgent, 25.91 -> 26.65), 1,161 -> 426 (AgentDriver, 36.92 -> 36.38) and 1,030 -> 355 (CIC-IoT, 74.00 -> 78.10). History-based deletion (remove records whose mean downstream utility over >= n retrievals is below beta) with a strict evaluator improved EHRAgent 38.67 -> 42.06 and CIC-IoT 85.40 -> 89.60, but with a coarse GPT-4o-mini evaluator it helped one agent and hurt another. The paper also finds "experience-following": a retrieved record that resembles the query produces a similar output, so errors in stored records propagate — [How Memory Management Impacts LLM Agents](https://arxiv.org/abs/2505.16067) [indep]
- Lyfe Agents' redundancy-forgetting (delete older memories whose embedding similarity to a new one exceeds theta) plus cluster-then-summarise outperformed a single unbounded list in their scenario — [Lyfe Agents](https://arxiv.org/abs/2310.02172) [author]
- FadeMem: two-layer memory with exponential (Ebbinghaus-style) decay modulated by semantic relevance, access frequency and temporal pattern, plus LLM-guided conflict resolution and fusion; abstract states 45% storage reduction; a secondary summary adds 82.1% critical-fact retention at 55.0% storage on LTI-Bench and 77.2% RP@10 on MSC (numbers not verified against the paper body; v2 posted Feb 2026) — [FadeMem](https://arxiv.org/abs/2601.18642) [author, preprint; extra numbers secondary]
- Weighted Memory Tree (Aug 2026 preprint, tool-using agent on GAIA-Text, includes Gemma 4 E4B): each memory has a retention score updated by events (action success 0.75, failure 0.30) and decays by rho^min(m, M) only when it was eligible but not selected, so "elapsed time alone does not affect retention"; finished tasks are folded into summaries with full traces kept. Accuracy / prompt tokens (M) - Gemma 4 E4B: no memory 14.17; linear history 24.41 / 65.27; full WMT 33.07 / 37.85; Qwen3-8B 20.47 / 43.67 -> 33.86 / 32.48; Llama-3.1-8B 9.45 / 73.96 -> 17.32 / 51.17. Decay constants rho, M are not given — [Weighted Memory Tree](https://arxiv.org/abs/2608.20631) [author, preprint]
- Context length hurts independently of difficulty: across 18 LLMs (incl. Qwen3-8B) performance "grows increasingly unreliable as input length grows"; on a LongMemEval subset (306 prompts) every model did better with a focused prompt (about 300 tokens) than with the full history (about 113K tokens); even one distractor lowers accuracy, and four lower it more — [Chroma: Context Rot](https://www.trychroma.com/research/context-rot) [indep, vendor-run benchmark of other vendors' models]
- LongMemEval: GPT-4o reading only the evidence sessions scores 0.870 but 0.606 when given the whole ~115K-token history (30.3% drop); Llama 3.1 70B 0.744 -> 0.334; Llama 3.1 8B 0.710 -> 0.454 — [LongMemEval](https://arxiv.org/abs/2410.10813) [indep]
- On LoCoMo (about 26K tokens per conversation in Mem0's run) the full-context baseline J=72.90 beats every memory system tested (Mem0 66.88, Zep 65.99, OpenAI memory 52.90, LangMem 58.10, A-Mem 48.38; best RAG about 61), but at total p95 latency 17.1 s vs 1.44 s for Mem0 and 26,031 vs 1,764 memory tokens — [Mem0](https://arxiv.org/abs/2504.19413) [vendor]
- MemoryAgentBench: RAG agents are best at accurate retrieval; long-context agents are best at test-time learning and long-range understanding; no method masters all four competencies (accurate retrieval, test-time learning, long-range understanding, selective forgetting) — [MemoryAgentBench](https://arxiv.org/abs/2507.05257) [indep]
- Anthropic's memory-tool docs recommend operator-side controls: track and cap memory file size, cap characters returned by `view` (the tool truncates text views of files over 16,000 characters), and "periodically delete memory files that haven't been accessed in a long time" — [Claude memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) [vendor]
- Letta forum expiry rules (reference-count promotion, TTL by type) and "don't over-consolidate" are the only concrete numbers from a memory-agent vendor community, with no measurement — [Letta forum](https://forum.letta.com/t/sleeptime-agents-for-memory-consolidation-best-practices-guide/154) [secondary]

### Inferences
- Of the forgetting rules, the best-supported are (a) redundancy removal by similarity threshold (Lyfe), (b) usage-count pruning over a window (periodic deletion, bounded memory M <= alpha*(t - t')*K), and (c) utility feedback from later use (history-based deletion) — the last needs a trustworthy signal, which for an NPC could be "was this note cited/used in a reply that the player did not contradict".
- Time decay is best used as a *ranking* factor (as in Generative Agents) and not as the delete trigger unless the item type is known to be ephemeral; WMT's choice to decay only items that were eligible but not selected is a game-friendly variant because NPCs offscreen should not "forget" merely because game time passed.
- Because accuracy degrades with prompt length and distractors even for strong models, a hard token budget per NPC prompt (a few hundred focused tokens) is better supported than "bigger memory in context", and matters more for a small local model than for Sol.

### Gaps
- No head-to-head study of Ebbinghaus-style decay vs recency-weighted retrieval vs LRU on the same benchmark was found.
- No source measures retrieval precision as a function of store size (number of records) at fixed query set; the closest evidence is context-length degradation and the deletion study.
- FadeMem's extra figures and WMT's decay constants could not be verified in the paper body.

## 6. Stale facts, contradictions and rewrite collapse: how memories get closed or updated (relevant to the pilot's "mind document bloats; patches leave stale items")

### Takeaway
Three failure modes are documented: monolithic LLM rewrites collapse a context (ACE: 18,282 -> 122 tokens in one step), insert-only memories keep stale items alive and let old and new facts both surface, and LLM-judged update operations are fragile. Independent benchmarks show that almost every current memory system does badly at superseding facts (multi-hop <= 28%). What works best in the evidence is itemised records with ids and counters, deterministic merge logic, and an LLM invoked at the moment of mutation.

### Cited Findings
- Context collapse (ACE, ICLR 2026): when an LLM fully rewrites the accumulated context at each step, at step 60 the context had 18,282 tokens and accuracy 66.7; at the next step it collapsed to 122 tokens with accuracy 57.1, below the 63.7 no-adaptation baseline (observed on AppWorld with Dynamic Cheatsheet). The authors also describe "brevity bias" (optimisation drifts to short generic prompts) — [ACE](https://arxiv.org/abs/2510.04618) [author]
- ACE's remedy: the context is a set of itemised bullets, each with metadata (unique id, counters of how often it was marked helpful or harmful) and content; a Reflector proposes small delta bullets, a Curator merges them by lightweight non-LLM logic, existing bullets are updated in place (counters) and new ids are appended; a de-duplication step compares bullets by embeddings, run after each delta or lazily when the window is full. Results: +10.6% on agent benchmarks, +8.6% on finance, adaptation latency down 86.9% on average (AppWorld offline: 82.3% lower latency and 75.1% fewer rollouts than GEPA) — [ACE](https://arxiv.org/abs/2510.04618) [author]
- Dynamic Cheatsheet keeps a self-curated text memory of "concise, transferable snippets rather than entire transcripts"; e.g. GPT-4o on Game of 24 rose from about 10% to 99% after discovering and reusing a Python solution — [Dynamic Cheatsheet](https://arxiv.org/abs/2504.07952) [author]
- Mem0's update phase: for each extracted candidate fact it retrieves the top-s similar stored memories and asks the LLM (function call) to choose ADD, UPDATE, DELETE (contradicted by new information) or NOOP; extraction uses a conversation summary plus a recent-message window; GPT-4o-mini does extraction and update — [Mem0](https://arxiv.org/abs/2504.19413) [vendor]
- Memory-R1 trains a Memory Manager with RL (PPO/GRPO) to pick ADD/UPDATE/DELETE/NOOP; with 152 training QA pairs it beat baselines across 3B-14B models; with LLaMA-3.1-8B on LoCoMo it reports relative gains over Mem0 of 28% F1, 34% BLEU-1, 30% LLM-judge. Its motivating example: a prompted manager sees "adopted a second dog" as a contradiction and does DELETE+ADD, erasing the first fact, where the trained manager does one UPDATE — [Memory-R1 abstract](https://arxiv.org/abs/2508.19828), [HTML v5 (via search summary)](https://arxiv.org/html/2508.19828v5) [author, ACL 2026]
- ForgetEval (single-author June 2026 preprint; 385 adversarial cases, deterministic substring scoring): defines supersede (new fact replaces old), release (retire a TTL/one-time fact), purge (hard delete). Deterministic methods score 95%+ on lexical/temporal cases but 0-5% on identifier variants; an LLM at write time fixes canonicalisation (100%) but scores 0% on prefix-collision and compound-fact deletion; an LLM hook at mutation time reaches 91.7-93.2% overall (about 2.3 s and about $0.17 per 385 cases). Overall: reference deterministic store 63.4% -> 91.7% with the hook; Mem0 v2.0.2 with its LLM router (infer=True) 43.6% (0% on prefix collision and paraphrase supersession); Letta 65.5% of evaluable cases; A-Mem 70.6% evaluable; Graphiti 7.0% — [ForgetEval](https://arxiv.org/abs/2606.15903) [indep, preprint, synthetic]
- MemoryAgentBench FactConsolidation (facts overwritten over a ~262K-token stream): single-hop / multi-hop accuracy: GPT-4o 128K 60.0 / 5.0; GPT-5-mini 78.0 / 28.0; BM25 RAG 48.0 / 3.0; Mem0 18.0 / 2.0; Zep 7.0 / 3.0; MemGPT 28.0 / 3.0; MIRIX 14.0 / 2.0. The authors state "all methods fail on the multi-hop situation (at most 28%)" and that selective forgetting "poses a significant challenge to all memory mechanisms" — [MemoryAgentBench](https://arxiv.org/abs/2507.05257) [indep]
- LongMemEval's online test: on 97 questions over 3-6 session histories, ChatGPT's memory and Coze (both GPT-4o) lose 37% and 64% relative accuracy versus reading the same history offline; "ChatGPT tended to overwrite crucial information as the chat continues, while Coze often failed to record indirectly provided user information" — [LongMemEval](https://arxiv.org/abs/2410.10813) [indep]
- LangMem's framing: a "profile" is one document that holds current state and is updated in place (suits "only the latest state matters"); a "collection" is unbounded records where over-extraction hurts precision and under-extraction hurts recall, and memory systems must reconcile new information by "deleting/invalidating" or "updating/consolidating" — [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/) [vendor]
- TiM's Forget prompt (drop counterfactual or contradictory thoughts within a hash bucket) and Merge prompt (same-entity thoughts) are an LLM-based closing step applied inside a similarity group rather than over the whole store — [TiM](https://arxiv.org/abs/2311.08719) [author]
- Error propagation: because agents "follow" retrieved experiences, inaccurate stored records compound; the study recommends regulating experience quality in the store and using later task outcomes as free quality labels — [How Memory Management Impacts LLM Agents](https://arxiv.org/abs/2505.16067) [indep]
- Letta (forum): "Reference count matters more than age"; dedupe by searching before every insert — [Letta forum](https://forum.letta.com/t/sleeptime-agents-for-memory-consolidation-best-practices-guide/154) [secondary]

### Inferences
- The pilot's two findings match the literature: a growing free-text "mind" is the free-text-rewrite pattern that collapses or bloats, and patch-only updates behave like the insert-only stores that ForgetEval and MemoryAgentBench show cannot retire superseded facts. Evidence points to making "open/closed/superseded-by" a first-class field (status, supersedes id, expiry) so closing is a deterministic state change, not something an LLM must remember to rewrite.
- A two-stage close fits the evidence: a deterministic key (entity + slot, or id) catches lexical/temporal supersession (ForgetEval: 95%+), and an LLM is called only when a new record collides with an existing one in the same entity group (the "mutation-time hook", about 2.3 s per call in the study — acceptable for Sol, too slow for the Gemma reply path).
- ACE's helpful/harmful counters suggest a cheap per-item utility signal: increment when a record is cited in a reply the player accepts, decrement when contradicted; that feeds the history-based deletion from section 5.

### Gaps
- No source evaluates conflict-closing in an NPC/dialogue game setting; ForgetEval is synthetic and its author-built templates may favour his own design.
- The Memory-R1 dog example and numbers come through a search-engine summary of the paper, not from my own reading of the body text.
- ACE's gains are for strategy "playbooks", not episodic facts about people; transfer to NPC knowledge is untested.

## 7. Structured state alternatives: schema-based memory, typed records, "memory as a database", file-based memory; when they beat free text or graphs

### Takeaway
Typed, keyed records (profiles, per-pair relationship records, SQL rows) are the best-evidenced answer when the data is entity-centric and needs updates or exact arithmetic: they bound size, make supersession deterministic and cut prompt tokens (AGA 2,000 -> 100). Free-text archives remain better for open-ended recall of what was actually said, and LLM-written SQL has only a small synthetic evaluation. No source shows structured memory beating graphs head-to-head; the one data point (Mem0 vs Mem0g) shows small gains for the graph variant, mainly on temporal questions.

### Cited Findings
- ChatDB: an LLM generates SQL to insert/update/delete/select in a database used as "symbolic memory", with a "chain-of-memory" that decomposes a question into several SQL steps; supports rollback to any timestamp. Evaluated on a synthetic Fruit Shop set (70 records, 50 questions: 15 easy, 35 hard); the paper says ChatGPT, which sees the records in its prompt, fails on hard multi-hop/calculation questions while ChatDB answers them with "notably high" accuracy (exact accuracy figures were not extractable from the text I read) — [ChatDB](https://arxiv.org/abs/2306.03901) [author]
- AGA Social Memory is a per-interlocutor typed record (Relationship, Feeling, Summary Events) updated after each conversation; it cut the conversation-prompt memory from about 2,000 to about 100 tokens and let agents correctly track relationship change (Klaus no longer mistakes the cafe owner for a student) — [AGA](https://arxiv.org/abs/2402.02053) [author]
- LangMem lets a semantic "profile" be a schema'd single document updated in place, versus a "collection" of records; procedural memory is stored as updated prompt rules; episodic memory as a collection with full interaction context — [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/) [vendor]
- MIRIX: six typed stores (Core, Episodic, Semantic, Procedural, Resource, Knowledge Vault) each with its own manager agent plus a meta-manager; the authors report 85.38% on LoCoMo (+8.0% over the best existing method). In the independent MemoryAgentBench, MIRIX with its default model had Accurate-Retrieval average 47.5 and with GPT-4.1-mini 63.0, versus 71.8 for GPT-4.1-mini used as plain long-context agent — [MIRIX](https://arxiv.org/abs/2507.07957) [author]; [MemoryAgentBench](https://arxiv.org/abs/2507.05257) [indep]
- Mem0 (flat fact list, no graph) vs Mem0g (adds entity-relation graph) on LoCoMo: overall J 66.88 vs 68.44; Mem0g better on temporal and open-domain questions, Mem0 better or equal on single/multi-hop; token cost 1,764 vs 3,616; Zep (graph) 65.99 — [Mem0](https://arxiv.org/abs/2504.19413) [vendor]
- LongMemEval's reading experiments: presenting retrieved memory items in a structured JSON format combined with Chain-of-Note reading "consistently benefits" reader LLMs; without Chain-of-Note, JSON does not consistently beat natural language. Time-aware indexing (index by event date, LLM extracts a time range from the query) raises recall by 11.3% (round-level) or 6.8% (session-level) — [LongMemEval](https://arxiv.org/abs/2410.10813) [indep]
- ForgetEval: deterministic keyed stores handle lexical and temporal supersession at 95%+ but fail on identifier variants (<=5%) and cross-lingual keys (0%); an LLM at write time canonicalises identifiers (100%) — i.e. typed keys need LLM-assisted canonicalisation — [ForgetEval](https://arxiv.org/abs/2606.15903) [indep, preprint]
- Anthropic's memory tool is file-based: the model uses `view`, `create`, `str_replace`, `insert`, `delete`, `rename` on a `/memories` directory; the docs suggest XML-structured files in examples and a prompt line "keep its content up-to-date, coherent and organized. You can rename or delete files that are no longer relevant. Do not create new files unless necessary"; the memory root cannot be deleted/renamed; the API auto-prompts the model to view memory first — [Claude memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) [vendor]
- Survey view: "token-level" memory (explicit records, flat/planar/hierarchical) is the dominant realisation, alongside parametric and latent; functions are factual, experiential and working memory — [Memory in the Age of AI Agents](https://arxiv.org/abs/2512.13564) [secondary survey]

### Inferences
- NPC world state is mostly entity-centric (person X, relation to player, open promises, known facts, last seen) with a long tail of free-text episodes. The evidence supports a hybrid: typed/keyed slots for state that must be correct and closeable (promises, debts, locations, relationship, quest flags), plus an append-only text episode log searchable by embedding for "what did the hero say"; free text should not carry state that needs closing.
- SQL-by-LLM is attractive for exactness but rests on one small synthetic evaluation; a safer variant is to let the models emit *typed JSON deltas* validated against a schema and applied by game code (code owns truth), which keeps the benefits of ChatDB (rollback, exact queries) without trusting generated SQL.
- Graphs are out of scope here, but the only direct comparison found (Mem0 vs Mem0g) gives +1.6 J points for the graph variant at 2x the tokens, mainly temporal — which suggests timestamps and `valid_from/valid_to` fields in a flat typed store may capture most of that gain.

### Gaps
- No head-to-head evidence of typed-slot memory vs free-text vs graph on the same dialogue benchmark with the same model was found.
- ChatDB's accuracy numbers were not recoverable from the text; its dataset is tiny and synthetic.
- No source evaluates schema-based memory specifically for NPC/game state.

## 8. Industry user-facing memories: Claude's memory tool and context editing, ChatGPT memory, LangMem, Mem0

### Takeaway
Production memories are deliberately simple: a short list of saved facts plus recent-chat summaries injected into the prompt (ChatGPT), or a file directory the model edits itself (Claude's memory tool), with caps, expiry and user deletion handled by the operator. Vendors publish few quantitative results, and the one independent test (LongMemEval) found ChatGPT's memory overwriting crucial information.

### Cited Findings
- Claude memory tool: client-side; the application implements storage under `/memories`; six commands (`view`, `create`, `str_replace`, `insert`, `delete`, `rename`); the API adds a system instruction to view the memory directory first and warns "ASSUME INTERRUPTION: Your context window might be reset at any moment"; recommended companions are context editing (clears stale tool results) and compaction (server-side summary); operator duties: path validation, size caps, expiry of unused files, stripping sensitive data — [Claude memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) [vendor]
- Anthropic's internal agentic-search evaluation: context editing alone +29%; memory tool combined with context editing +39% over baseline; a 100-turn web-search evaluation saw 84% lower token consumption — the post attributes the 84% to context editing, while The Decoder's coverage ties it to the combined setup — [Anthropic: context management](https://claude.com/blog/context-management) [vendor internal eval]; [The Decoder](https://the-decoder.com/anthropic-claims-context-engineering-beats-prompt-engineering-when-managing-ai-agents/) [secondary, disagrees on attribution]
- ChatGPT memory as reverse-engineered by one user (not official): layers = system/developer instructions, session metadata, user memory (author's account held 33 short facts, injected as a block into every prompt), recent-conversation summaries (about 15, each with timestamp, title and snippets of the *user's* messages only), the current session; the author inferred no vector database or RAG; session messages are trimmed first when the token budget is hit; deletion is conversational. Another write-up claims a vector space indexed by summaries, so the architecture is disputed — [Gupta](https://manthanguptaa.in/posts/chatgpt_memory) [secondary]
- OpenAI's FAQ (as relayed by a search summary): saved memories are what the user asked ChatGPT to remember; a log of deleted saved memories may be kept up to 30 days for safety and debugging, and the FAQ mentions avoiding a "memory full" state; deleting a chat does not remove memories saved from it; ChatGPT can update, combine or remove saved memories when asked — [OpenAI Memory FAQ](https://help.openai.com/en/articles/8590148-memory-faq) [vendor, via search summary]
- LongMemEval measured ChatGPT and Coze memory (GPT-4o) on short 3-6 session histories and found 37% and 64% relative drops vs offline reading, with ChatGPT overwriting crucial information — [LongMemEval](https://arxiv.org/abs/2410.10813) [indep]
- LangMem: three memory types (semantic facts as profile or collection, episodic experiences, procedural rules), hot-path vs background formation, and a memory manager that extracts, updates, removes outdated and consolidates memories; in Mem0's benchmark LangMem scored J=58.10 with a p95 search latency of 59.82 s and p95 total 60.40 s — [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/) [vendor]; [Mem0](https://arxiv.org/abs/2504.19413) [vendor-run on a competitor's product]
- Mem0 (production memory layer): reports J=66.88 on LoCoMo with 1,764 memory tokens and p95 total latency 1.44 s, a 91% lower p95 latency and more than 90% token saving versus full context (J=72.90, 26,031 tokens, 17.1 s) — [Mem0](https://arxiv.org/abs/2504.19413) [vendor]; Zep's blog critique disputes Mem0's LoCoMo claims — [Zep blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/) [competitor]

### Inferences
- Industry practice converges on: small, always-injected, human-editable memory + on-demand file/record lookup + operator-side caps and TTL. That is cheap to run for hundreds of NPCs and easy to debug, which matters more than benchmark gains here.
- The reported ChatGPT behaviours (overwriting facts, only user-side messages in summaries) are warnings for a per-NPC store: keep NPC-side statements and promises as first-class items because "what I told the hero" is what NPC deceit/consistency depends on.

### Gaps
- OpenAI has not published its memory architecture; everything about ChatGPT's internals is reverse-engineered and partially contradictory.
- The OpenAI FAQ and the 100-200 fact "memory full" number come only via search summaries; I did not read the FAQ page itself.
- I found no independent measurement of Claude's memory tool in isolation (Anthropic's 39% number is internal and combined with context editing).

## 9. How good is the evidence? Benchmarks, head-to-head numbers and their validity problems

### Takeaway
Most published headline numbers are author-run on LoCoMo, with LLM judges, different answer models and disputed baselines; the independent suites (LongMemEval, MemoryAgentBench, ForgetEval) show a much harsher picture: long-context reading is a strong baseline, retrieval systems lose on updates and holistic understanding, and no system dominates. Treat any single-benchmark ranking, especially from a vendor, as weak.

### Cited Findings
- LoCoMo (ACL 2024): dialogues of up to 35 sessions, 300 turns and "9K tokens on avg"; long-context LLMs and RAG "lag behind human levels (by 56%)", especially on temporal reasoning — [LoCoMo](https://arxiv.org/abs/2402.17753) [author]. Mem0's run reports about 26,000 tokens per conversation, which conflicts with the 9K average — [Mem0](https://arxiv.org/abs/2504.19413) [vendor]
- LoCoMo answer-key problems: a community audit reports 99 of 1,540 questions (6.4%) have wrong golden answers (ceiling 93.57%) and that the LLM judge accepts up to about 63% of intentionally wrong answers; authors are not neutral and it is not peer-reviewed — [dial481/locomo-audit](https://github.com/dial481/locomo-audit) [secondary, community]
- Vendor claims conflict: Mem0 claims 26% relative improvement in LLM-judge score over OpenAI memory and J=66.88; Letta claims 74.0% with a filesystem and GPT-4o-mini; Zep disputes Mem0's numbers; Mem0's own table has full context at 72.90 above all memory systems — [Mem0](https://arxiv.org/abs/2504.19413), [Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory), [Zep](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/) [vendor claims]
- LongMemEval (ICLR 2025): 500 questions over five abilities (information extraction, multi-session reasoning, temporal reasoning, knowledge updates, abstention); S version about 115K tokens, M version 500 sessions about 1.5M tokens; commercial assistants and long-context LLMs lose about 30% accuracy on sustained interactions — [LongMemEval](https://arxiv.org/abs/2410.10813) [indep]
- MemoryAgentBench (ICLR 2026): four competencies; results across long-context agents, BM25/embedding RAG, structure-augmented RAG (RAPTOR, GraphRAG, HippoRAG-v2, MemoRAG, Mem0, Cognee, Zep) and agentic memory (Self-RAG, MemGPT, MIRIX). Overall averages: GPT-5-mini 128K long-context 60.6; GPT-4o 48.8; BM25 41.5; HippoRAG-v2 41.6; MemGPT 28.3; Mem0 21.1; Zep 24.0 — [MemoryAgentBench](https://arxiv.org/abs/2507.05257) [indep]
- Surveys call evaluation the open problem: static recall benchmarks vs multi-session agentic tests, "continual consolidation, causally grounded retrieval, trustworthy reflection, learned forgetting" are listed as open — [Memory for Autonomous LLM Agents](https://arxiv.org/abs/2603.07670) [secondary survey, abstract only]
- Park et al.'s own evaluation is a 2-day, 25-agent crowd ranking of interview answers with TrueSkill, and Lyfe's/AGA's cost claims rely on estimates or the same style of interview — [Park et al. 2023](https://arxiv.org/abs/2304.03442), [Lyfe Agents](https://arxiv.org/abs/2310.02172), [AGA](https://arxiv.org/abs/2402.02053) [author]

### Inferences
- None of these benchmarks tests what the NPC project needs: multi-day persistence of promises, lies and relationships, with a fast model reading and a slow model writing. Use them only for mechanism ideas; the project's own scripted probes (open promise closed? stale fact still quoted? lie remembered with who believes it?) are the real evaluation.
- Since full-context reading beats memory systems on short histories (Mem0's table, MemoryAgentBench), the break-even for an NPC memory is not conversation length of a few thousand tokens but multi-session accumulation, latency (Gemma 3090 reply path) and prompt-token cost.

### Gaps
- No benchmark with NPC/game semantics (deception, belief per character) turned up in this scope; the other researchers' notes may cover it.
- I could not verify the community LoCoMo audit independently.

## 10. Which mechanisms are reusable for one memory per NPC, read by a fast local model (Gemma) and written by a slow hosted model (Sol)

### Takeaway
The evidence supports splitting by role, not by model size: a small always-in-prompt structured "core" per NPC that code can validate and close deterministically, an append-only episode log with embedding retrieval for fast lookups, and slow-model passes that emit schema-validated deltas, reflection and summaries as retrieval aids rather than as the source of truth. Most of the specific numbers below are borrowed from other domains (QA, agent benchmarks) and need NPC-specific probes.

### Cited Findings
- Cost asymmetry across models is built into the designs: Letta suggests a small fast model for the conversational agent and a larger one for the sleep-time agent (blog) or a cheap one (forum) — [Letta blog](https://www.letta.com/blog/sleep-time-compute), [Letta forum](https://forum.letta.com/t/sleeptime-agents-for-memory-consolidation-best-practices-guide/154) [vendor / secondary]
- The only Gemma-class data point found: on GAIA-Text with Gemma 4 E4B as the frozen agent model, a retention-scored tree memory raised accuracy from 24.41 (linear history) to 33.07 and cut prompt tokens from 65.27M to 37.85M; no-memory was 14.17. It is a tool-use benchmark, not conversation — [Weighted Memory Tree](https://arxiv.org/abs/2608.20631) [author, preprint]
- Weak models are the weak link in self-editing memory: MemGPT's DMR accuracy was 66.9% on GPT-3.5 vs 92.5% on GPT-4; the model that selects UPDATE vs DELETE matters (Memory-R1 trains 3B-14B managers with RL to reach reliable behaviour) — [MemGPT](https://arxiv.org/abs/2310.08560), [Memory-R1](https://arxiv.org/abs/2508.19828) [author]
- Mem0's extraction and update run on GPT-4o-mini via function calling, with p50 total latency 0.708 s and p95 1.44 s per question — a fast-model-sized extraction pipeline — [Mem0](https://arxiv.org/abs/2504.19413) [vendor]
- Prompt-size effects: focused prompts of a few hundred tokens beat full-history prompts for all 18 tested models (including Qwen3-8B), and summarisation-only memories (RecurSum about 400 tokens) underperform retrieval of raw units on LoCoMo (56.25 vs 65.58) — [Chroma: Context Rot](https://www.trychroma.com/research/context-rot), [SeCom](https://arxiv.org/abs/2502.05589) [indep / author]
- Concurrent writers are a known hazard: Letta recommends one owner for block rewrites and appends from others because simultaneous `memory_rethink` leads to lost updates — [Letta shared memory](https://docs.letta.com/v1-sdk/memory/shared-memory) [vendor, via search summary]

### Inferences
Proposed design drawn from the evidence above (my synthesis, not tested):
- Per NPC, three layers. (1) Core card, about 300-800 tokens, rendered from typed records and rebuilt by code each turn: identity/persona (read-only), relationship to hero, open commitments (id, text, status open/closed/superseded, due), current beliefs about hero (with source and certainty), last-seen facts. (2) Episode log, append-only, raw utterance/event text with game-time, speaker, importance integer (Generative Agents style) and embeddings; retrieval score recency + importance + relevance with explicit weights tuned on probes. (3) Derived notes (Sol reflections, summaries, relationship updates) that always carry pointers to the episode ids they were derived from (as in Park's reflection trees, ReadAgent look-up and TiM thoughts).
- Write path: Gemma never edits memory (avoids fragile tool calls on the hot path); it may emit a cheap "candidate event" line per turn. Sol, asynchronously ("sleep-time", after a dialogue ends or on game-time interval, debounced as in LangMem), receives the delta since its last pass plus the affected core records, and returns schema-validated JSON deltas (add / update / close / supersede with ids) that game code applies. This follows ACE (itemised deltas, deterministic merge, counters) rather than whole-document rewrites (collapse) and Mem0/ForgetEval (LLM only at the mutation point).
- Closing every turn: make closing a code rule over fields, not an instruction to an LLM: a commitment record has `status`, `closed_by`, `valid_to`; a new record with the same (entity, slot) key supersedes the old one; unresolved collisions go to Sol's next pass (mutation-time hook). This addresses the pilot's stale-items problem by construction.
- Forgetting/size control: rank by recency+importance+relevance; prune episodes with a usage-window rule (not retrieved for N game-days and low importance) after Sol has folded them into a derived note; dedupe by embedding similarity threshold (Lyfe); promote by reference count (Letta forum, MemoryOS heat). Keep records tied to open commitments or lies exempt from pruning. Do not use wall-clock time for NPC offscreen decay; use game-time or interaction counts (WMT).
- What to measure before adopting any of this: probe sets for (a) closed promise not re-quoted, (b) superseded fact not mentioned, (c) lie remembered with who was told, (d) retrieval within a 300-token Gemma budget, (e) Sol delta correctness rate, using the failure types from ForgetEval as templates.

### Gaps
- No source evaluates any of these designs on NPC dialogue with a split small/large model; every number above is from a different task family.
- Latency/cost figures for Gemma on a single RTX 3090 and for Sol subscription calls are outside this scope.
- The effect of letting the fast model write at all (vs read-only) has not been measured by any source I found.
