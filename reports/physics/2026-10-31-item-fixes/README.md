# Item physics fixes — 2026-10-31

Статус: **needs_decision**. Проверки физики, оружия и p95 завершены. Лимит загрузки NEWWORLD **+5% не выполнен**: парные медианы на Mac дают **+33,10%**. Нужен выбор: сохранить принятый механизм с явно зафиксированным превышением либо отдельно разрешить новый подход к загрузке, например кэш готовой статичной коллизии. Нового загрузочного механизма сверх принятых исправлений в этой ветке нет.

Первый ход закончился по лимиту времени. Второй ход остановил **сторож повторов**, а не пользователь: три ожидаемых результата `pgrep` с кодом 1 и пустым выводом он принял за одинаковый сбой. Это не падение физики. Далее занятость проверялась только командой `pgrep -fl '[G]othic2Notr' || echo absent` при `LC_ALL=C`; при занятой игре ожидали, чужие процессы не останавливали.

База — чистая `main` на `a42e36086`. Данные Mac и Ryzen ниже разделены. Код трёх принятых исправлений сохранён; в продолжении добавлены диагностика возврата и исправления подготовки стенда. Мебель, `convexparts`, `movable-vobs.csv`, `item_hulls`, P30, навигация, урон/окна/комбо и `docs/physics.md` не менялись.

## Итоговый item-wake ON / OFF

Два свежих процесса с текущим `scripts/bench/item-wake.bench`, `ITEM_HULLS=1`, `STATIC_COLLISION_SPLIT=1`. Все **18 контрольных точек** имеют `pass=true`, оба процесса завершились с кодом 0 и `[bench] done`.

| Фаза | ON: сдвинулись >5 см / новые тела | OFF: сдвинулись >5 см / новые тела | Возвраты ON / OFF |
|---|---|---|---|
| ragdoll | 2 / 4 | 0 / 0 | 0 / 0 |
| debris | 1 / 4 | 0 / 0 | 0 / 0 |
| item | 1 / 4 | 0 / 0 | 0 / 0 |
| arrow | 1 / 1 | 0 / 0 | 0 / 0 |
| sword | 3 / 3 | 0 / 0 | 0 / 0 |
| pile-far | 0 / 0 | 0 / 0 | 0 / 0 |
| event-ragdoll | 2 / 7 | 0 / 0 | 0 / 0 |
| event-debris | 3 / 6 | 0 / 0 | 0 / 0 |
| pile (`report_only`) | 11 / 26 | 0 / 0 | 0 / 0 |

Вне критериев исправления: диагностическая ON-фаза `pile` отметила 1 `floor_fall`, максимальное проникновение bounds 9,796875 см, `below_world=0`, возвратов 0; эта искусственная фаза остаётся `report_only`. В остальных восьми фазах падений 0; в OFF падений 0 во всех девяти фазах. Это не исправляли.

Подготовка оружия выбирает опору **лучами по реальной столешнице**, проверяет след предмета и переходит к следующему имеющемуся столу при отсутствии опоры. Яблоко стоит на `DT_TABLE_V2.3DS`, три кружки — на `OC_TABLE_V3.3DS`; нормали выбранных поверхностей `(0,1,0)` записаны в `item_wake_table`.

Для меча сохраняются исходные корень/направление NPC, после завершения первого запроса анимации выполняется отдельный сухой взмах. Самая плоская достаточно быстрая поза выбирается внутри кадров `[2,6)` (80–240 мс), **внутри существующего физического окна 0–400 мс**. Само окно не меняется. Стол расположен у входного угла: он не перекрывает сухую траекторию и не заставляет NPC подняться на столешницу. `item_wake_sword_path` подтверждает фактическое пересечение всех трёх bounds.

На оружейной фазе меча стенд временно отключает `npccharacter` и восстанавливает его после checkpoint. Это исключает независимый прежний путь `MoveAlgo::tickCharacterVirtual`, создающий тела ближайших Item даже при `item_wake=0`; проверка OFF остаётся строгой — и смещение, и число новых тел равны нулю. Маршруты NPC проверялись отдельно с `NPC_CHARACTER_VIRTUAL=1`. Код этого прежнего пробуждения не менялся.

## Парная загрузка NEWWORLD — только Mac

На Ryzen следующая тихая заявка получила оценку ожидания 7206 с (>30 минут) из-за другой задачи; отменили только свою заявку и перешли на Mac. Все загрузки ниже выполнены на одной машине, с одной базой и одинаковыми начальными флагами, по одной игре, без параллельной сборки. После двух первых запусков стороны чередовались main/ветка.

Результат: **+861,23804 мс / +33,10397%**, предел +5% не выполнен. Ранний одиночный Ryzen-замер `2964,885 → 3108,827 мс` (+4,85%) не используется как приёмочное доказательство: это другая машина и не серия 3 + 3.

Временные таймеры локализовали цену крупного статичного меша: `352641 → 1565364` треугольника, деление `221,640 мс`, native-построение `821,735 мс`, всего `1082,311 мс`. Проба существующего Jolt `FavorBuildSpeed` только для разделённых мешей и резервирования буферов дала `154,914 / 643,749 / 834,288 мс`, но одиночная загрузка всё ещё заняла `3342,671 мс`. Это диагностическая проба, не второй приёмочный набор 3 + 3. Она **не оставлена**: `physicvbo.cpp` возвращён точно к принятому коду, временные таймеры удалены. Новый кэш или параллельное построение без отдельного решения не добавлялись.
