# Дальний бой NPC — калибровка

Калибровка v1, 2026-11-02. **Приёмка не прошла; требуется решение о дальнейшем подходе.** Выбранный по обучающим парам вариант Б проверен один раз на 60 отложенных дуэлях. Он лучше `uncalibrated`, но хуже постоянной модели; не проходят таймауты и потери HP. `server/src/gothic_ai/gamedata/far_fight.json` оставлен без изменений с `source: "uncalibrated"`.

Текущий результат — [v2: измеренные части, приёмка не пройдена](#v2--измеренные-части-приёмка-не-пройдена-2026-11-02). Ниже сначала сохранён отчёт v1; его поиск коэффициентов заменён оценкой частей в том же `far_fight_fit.py`.

## Данные и восстановление бойцов

Прогон `far-fight-run`, все пять частей `duels-000`–`duels-004`: **240 дуэлей — 180 обучающих (9 пар × 2 роли × 10), 60 отложенных (3 пары × 2 роли × 10)**. Размеры частей: 59 / 59 / 59 / 59 / 4. На первых 177 записях выполнена предварительная подгонка; после полного сбора выбор повторён только по всем 180 обучающим. До выбора исходы holdout не валидировались, не превращались в бойцов и не использовались в оценках. Сбор не перезапускался. Отсчёт модели с нуля, `TIME_LIMIT_S=120`.

Старые снимки содержат `weapon_damage[8]`, но не `damageTotal`: у записанного оружия все восемь значений нулевые. [Справочник](../data/npc/far-fight-weapons.json) получен непосредственным выполнением конструкторов `C_ITEM` из `GOTHIC.DAT` через ZenKit 1.3.0.4. SHA256 исходника совпал с указанным в `programs.json` игровой базы; хеш и точная команда чтения сохранены в справочнике. У крестьянского топора `damageTotal=7`, булавы — 10, одноручного оружия милиции/наёмников — 40, двуручного — 60. Сохранены `damagetype`, `flags` и `damage[8]` всех семи инстанций оружия 12 пар.

`npcduel` снимает только что созданного NPC до извлечения оружия. Адаптер восстанавливает 48 значений `story_eval` и вызывает общий с сервером `combatant_from_values`: замена вклада извлечённого оружия надетым ближним, выбор 1H/2H по флагам и соответствующих таланта/шанса крита. Для безоружного `VLK_474_BUERGER` `HITCHANCE[0]=0` прочитан из того же DAT. Будущие снимки содержат `weapon_damage_total` и `hitchance.fist`; сводка и проверка принимают обе формы.

## Метод и кросс-проверка

Цель — сумма логарифмов вероятностей исходов отдельных дуэлей: `Σ count(outcome) × log(max(1/800, P(outcome)))`, без перенормировки после отсечения. Для каждой ячейки — 400 розыгрышей с общими случайными числами, SHA256 от фиксированного пространства `far-fight-fit-v1`, id пары и ролей. Векторный расчёт воспроизводит Python RNG (`expovariate` и `randrange`) в порядке событий; тест сверяет все 400 исходов и потери HP со скалярным серверным симулятором, включая одну и две нулевые частоты. Урон удара и зерно серверного дела не менялись.

- А: `rate_base`, `rate_per_tier`, `damage_scale`.
- Б: А и множитель `max(0, 1 − parry_per_tier × tier_защитника)` для частоты атакующего.
- В: Б и `starter_rate` для зачинщика (`fighter` на сервере, `attacker` в записи).

Детерминированная сетка: `rate_base=[0.05,0.2,0.8]`, `rate_per_tier=[0,0.5,2]`, `damage_scale=[0.25,1,2]`, `parry_per_tier=[0,0.25,0.5]`, `starter_rate=[0.5,1,2]`: 27 / 81 / 243 точки для А / Б / В. Затем три уровня координатного уточнения с начальными шагами `[0.1,0.5,0.25,0.125,0.5]`, на каждом следующем уровне вдвое меньше. На каждом уровне проходы повторяются до отсутствия строгого улучшения; на плато текущая точка сохраняется. Равные улучшающие кандидаты выбираются лексикографически. Границы соответственно `[0.01,1.6]`, `[0,4]`, `[0.11,4]`, `[0,1]`, `[0.125,8]`.

Кросс-проверка «без одной пары» исключает оба направления целой пары из подгонки. Всего 9 сгибов каждого варианта; 1040 различных оценок коэффициентов с переиспользованием расчётов. Сравнивается геометрическое правдоподобие на дуэль `exp(LL / 180)`. Выбирается первый по сложности вариант, для которого `best / candidate < 1.01`. Отложенные пары не участвуют.

## Что модель не ловит

- **Пустые дуэли.** В обучении 22/180 таймаута (12,22%), в 20/22 оба NPC нанесли ноль попаданий. Выбранный Б ожидает 0.204 дуэли вообще без попаданий из 180 по независимым часам; наблюдается 20. На holdout все 14/60 таймаутов (23,33%) прошли без попаданий с обеих сторон. Повтор v2 на Mac до #751 с полной симуляцией не подтверждает уход по распорядку: безоружный нападающий выбирает удар с разбега издали по ещё не отвечающей цели. Из 281 замаха 245 — `T_FISTATTACKMOVE`; медиана начальной дистанции — 233 см, досягаемость бегового удара — около 58 см, смещение цели за замах — 8 см. В 244 случаях магнит остановлен с `no_preview`; `legacy applied` — 68/281, физических попаданий с потерей HP — 0. По разбору v1 ведущим, этот NPC не попал в 16/20 дуэлей как нападающий, хотя защищаясь, попадал кулаками. У 2H seed 18 магнит работает (29/29 предварительных контактов, остановка `predicted`), но удар также не достаёт: `legacy applied` — 24/29, физических попаданий — 0, минимальный просвет — 4,9 см. Ведущий принял стенд с пятью такими дуэлями; [полные поля повтора](../scripts/bench/README.md#native-npc-calibration-duels), исправление ближнего боя — отдельная задача.
- **Потери HP.** На holdout модель недооценивает медиану потерь победителя на 0,416 и 0,462 доли максимального HP у двух направлений `bengar-equals`, на 0,326 у милиционера против наёмника с мечом. Приёмка допускает 0,15. Подгонка по исходам не гарантирует распределение остаточного HP.
- **Талант и тактика.** В обучении 360 наблюдений бойцов, представлены только tier 0/1. Частоты попаданий ниже. При `parry_per_tier=0.5` частота против tier 2 обнуляется; tier 2 в обучении нет, такая экстраполяция не проверена.

## Воспроизведение и проверки

`FAR_FIGHT_RUN` — папка исходного прогона, входы читаются без изменений. Python запускается в среде сервера с уже имеющимся NumPy. Подгонка без приёмки:

```sh
cd server
uv run python ../scripts/far_fight_fit.py "$FAR_FIGHT_RUN"/duels-00{0,1,2,3,4} \
  --out ../.bench/far-fight-fit/full-training.json
uv run python ../scripts/far_fight_fit.py "$FAR_FIGHT_RUN"/duels-00{4,3,2,1,0} \
  --out ../.bench/far-fight-fit/full-repeat.json
cmp ../.bench/far-fight-fit/{full-training,full-repeat}.json
```

Оба полных расчёта дали побайтно одинаковый JSON: 37921 байт, SHA256 `8722452e417a9abd8d5ebaf0150cba340067da68b6167fa22bde265859c67c0a`. Повторено также на первых 177 записях, результат воспроизводился.

Команда уже выполненного единственного запуска приёмки (после двух одинаковых расчётов обучения):

```sh
uv run python ../scripts/far_fight_fit.py "$FAR_FIGHT_RUN"/duels-00{0,1,2,3,4} \
  --accept --out ../.bench/far-fight-fit/acceptance.json
```

Скрипт сам не меняет коэффициенты сервера. Тесты в существующих `scripts/tests/test_melee_balance_report.py` и `server/tests/test_npc_far.py` закрепляют разбор старых/новых снимков, независимое равенство серверному бойцу, ручное правдоподобие, точные 400 розыгрышей, детерминизм, сходимость уточнения, исключение holdout и нейтральность Б/В.

### Замахи и заранее заданное объединение

Для ответившего защитника `rate_swings = swings − 1`, `exposure_s = (duration_ms − max(first_received_hit_ms, defender_first_swing_ms))/1000`: первый ответ уже задаёт `response_delay`, экспоненциальны только следующие замахи. Без первого ответа оба вклада в частоту равны нулю. Исходные `swings` остаются для объединения ячеек и p_hit.
