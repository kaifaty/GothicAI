# Прогрев Sol перед ходом NPC: замер 2026-11-01

**Вопрос.** Ускорит ли ответ Sol (`gpt-6.1-sol`, подписка ChatGPT) заранее отправленный запрос с инструкциями и историей NPC, как у Gemma ([прогрев Gemma](../../../docs/npc-agent.md#реплики-в-бою-быстрая-модель))?

**Итог: не ускорит, не строим.** Шлюз подписки принимает прогрев `generate: false`, но до модели он не доходит: настоящий запрос после него читает промпт заново, и первое слово приходит так же, как без прогрева. 20 пар: медиана 2,01 с без прогрева и 1,93 с с ним. Парная разница — медиана 0,16 с, 95% доверительный интервал −0,45…+0,39 с. Прогрев быстрее в 12 парах из 20, знаковый тест p = 0,50. Время Sol уходит не на чтение промпта: ~0,7 с до модели, ~0,8 с у модели до первого токена, ~0,4 с на доставку.

## Что уже было до замера

- У каждого NPC свой WebSocket, он открывается заранее (`open_ahead`), рукопожатие 1,3–1,8 с игрок не ждёт. Со второго хода работает кэш промпта ([как устроено](../../../docs/npc-agent.md#ход-разговорной-модели)).
- По живым трассам 18 и 20 октября (уже с WebSocket) первый шаг хода без кэша — медиана 2,00 с до первого слова (12 ходов, p75 2,48 с), с кэшем 4–6,8 тыс. из 8–10 тыс. токенов — 1,90 с (45 ходов, p75 2,21 с).
- У WebSocket-режима OpenAI есть прогрев: `response.create` с `generate: false` готовит состояние следующего хода и возвращает id для `previous_response_id` ([документация](https://developers.openai.com/api/docs/guides/websocket-mode)).

## Как мерили

[`probe.py`](probe.py) повторяет первый шаг настоящего хода Кавалорна из трассы 20 октября: инструкции, 15 инструментов, история, обстановка и фраза героя «Ковалорн, дружок.», 8,3 тыс. входных токенов. Трасса лежит вне git (`~/.local/share/gothic-ai/traces/2026-10-20.jsonl`, `t=1792510665.659`).

Каждая попытка открывает своё соединение, как `open_ahead`, и через 2,0 с после открытия (герой говорит, затем распознавание) шлёт настоящий запрос:
- **cold** — запрос целиком, до него ничего не отправлялось: первый ход с NPC сейчас;
- **warm** — сразу после открытия соединения прогрев `generate: false` с инструкциями, инструментами и историей; настоящий запрос продолжает его через `previous_response_id` и шлёт только обстановку и фразу.

Случайная метка в начале инструкций не даёт попыткам делиться кэшем. Пары чередуют порядок. Кроме времени на клиенте сохраняется разбивка сервера из события `responsesapi.websocket_timing`: ожидание до модели (`pre_inference_ms`), очередь, время до первого токена у модели и сколько токенов промпта она взяла из кэша. Результаты — [`results.jsonl`](results.jsonl).

```bash
cd server
uv run python ../reports/npc-agent/2026-11-01-sol-prewarm/probe.py run ~/.local/share/gothic-ai/traces/2026-10-20.jsonl --t 1792510665.659 --pairs 20 --out ../reports/npc-agent/2026-11-01-sol-prewarm/results.jsonl
```

## Результаты

20 пар, 60 запросов (40 настоящих и 20 прогревов), ошибок нет. Время — от отправки настоящего запроса до первого токена текста или аргументов вызова.

| | cold | warm |
|---|---|---|
| первое слово, медиана | 2,011 с | 1,930 с |
| p25 / p75 | 1,810 / 2,482 с | 1,724 / 2,554 с |
| минимум / максимум | 1,627 / 4,965 с | 1,554 / 3,943 с |
| сервер: до модели (`pre_inference_ms`), медиана | 710 мс | 694 мс |
| сервер: очередь модели, медиана | 199 мс | 169 мс |
| сервер: модель до первого токена, медиана | 802 мс | 774 мс |
| токенов промпта из кэша модели, медиана | 128 из 8 703 | 128 из 8 703 |
| остаток (первое слово − до модели − модель), медиана | 405 мс | 384 мс |

**Прогрев не загружает модель.** У прогрева `num_engine_calls = 0`: сервер принимает запрос и возвращает id, но промпт модели не отдаёт. Поэтому настоящий запрос после него читает все ~8,6 тыс. токенов заново, в обоих вариантах из кэша 128. `previous_response_id` от прогрева работает: настоящий запрос шлёт только обстановку и фразу. Время до модели при этом не сокращается: 694 мс против 710.

**Цена прогрева.** Медиана 0,58 с, максимум 1,93 с, на сервере 0,29 с. Засчитывается 6 367 входных токенов, ответа нет. На подписке это каждый раз квота, а соединение всё это время занято: настоящий запрос ждал бы окончания прогрева.

**Кэш и без прогрева почти не влияет.** В 7 из 40 запросов модель случайно взяла из кэша 4 224–4 736 токенов: метка в начале инструкций не отрезала общий для попыток кусок с инструментами. Распределились они поровну (3 cold, 4 warm). Первое слово в них не быстрее: медиана 2,60 с против 1,91 с у остальных, модель до первого токена 1 011 мс против 795. Выборка мала, но это согласуется с трассами: 2,00 с без кэша и 1,90 с с ним.

## Что из этого следует

- Прогрев по схеме Gemma Sol не ускоряет: у Gemma на 3090 чтение промпта и есть почти вся задержка первого слова, у Sol — небольшая её часть.
- То, что прогрев мог бы дать, уже есть: соединение открывается заранее (`open_ahead`), продолжения хода идут через `previous_response_id`.
- Из ~2 с первого слова мы не управляем ни ~0,7 с до модели, ни ~0,4 с доставки. Это шлюз подписки: проверки, модерация, маршрутизация. Время модели до первого токена (~0,8 с) от кэша почти не зависит.
- Сервер сам присылает разбивку времени в событии `responsesapi.websocket_timing` (`timing_metrics`). Если понадобится разбирать задержки Sol в игре, её можно писать в трассу хода.
