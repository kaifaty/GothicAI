# Текстуры: мип по размеру на экране

Исследование перед работой (2026-11-10). Повод — [стресс-замер](../../performance/2026-11-10-content-stress/README.md): память текстур первой выходит за бюджет, уже на текстурах ×2 по стороне.

## Итог

- Сейчас уровень текстуры выбирается по кольцу кусков: в двух кольцах вокруг героя (до 128–192 м) — вся цепочка мипов, дальше — без двух старших. Память растёт как квадрат стороны текстуры: 81 → 234 → 901 МиБ на маршруте при ×1, ×2, ×4.
- Если держать мип, который реально нужен экрану, память растёт с размером текстур намного медленнее. Для текстур ландшафта Хориниса в 1440p по правилу, как оно сделано в движке (материал в куске, запас в один уровень, спрос степенью двойки): 19–24 МиБ вместо 25–28 при ×1, 126–179 вместо 404–451 при ×4, 372–541 вместо 1614–1803 при ×8. Точный расчёт без запаса дал бы 9–13, 76–96 и 232–314 МиБ.
- Для этого не нужна обратная связь с GPU и новые проходы: хватает расчёта на CPU по расстоянию и плотности текселей. Владельцы спроса остаются прежними (материал в куске, статичный объект, NPC): расчёт по материалу в куске требует на 8–27 % больше памяти, чем расчёт по каждому треугольнику, при ×1 и ×2 и на 20–60 % больше при ×4 и ×8.
- Вид не должен измениться вообще: правильно выбранный мип — тот, который видеокарта и так бы взяла. Приёмка — кадры с выбором мипов против кадров со всеми полными текстурами.
- **Поправка 2026-11-10.** Первая версия переписи ставила точку обзора не туда: файлы кусков хранят ось x зеркально, и «рынок», «гавань» и «лес» считались от зеркальных мест. Её числа (7 МиБ при ×1, 49–54 при ×4, выигрыш в 8–10 раз) были занижены примерно вдвое. Ошибку нашёл исполнитель шага 1 по дампу из движка; ниже — пересчёт, он сходится с движком (лес, ×4, 1117 пикселей: 96,5 МиБ по переписи, 95,5 МиБ по дампу).

## Цель

Память текстур определяется разрешением экрана и бюджетом, а не размером исходных текстур. Текстуры 2K–4K можно ставить, не меняя бюджет; качество вблизи остаётся полным.

### Какой мип нужен

Поверхность с плотностью `D` текселей на метр на расстоянии `d` метров от камеры занимает на экране `ppm(d) = H / (2·d·tan(fov/2))` пикселей на метр, если повёрнута к камере лицом (`H` — высота кадра в пикселях, `fov` — вертикальный угол). Нужный уровень:

```
λ = log2(D / ppm(d)) = log2(D · d · 2·tan(fov/2) / H)
уровень = floor(λ), не меньше 0
```

При `H = 1440` и `fov = 67,5°` (умолчание игры) `ppm(d) ≈ 1077 / d`.

- Решает **самое растянутое** использование текстуры — наименьшая плотность: там тексели на экране крупнее всего.
- Плотность треугольника берётся как корень из отношения площадей в UV и в мире. Строго видеокарта с анизотропной фильтрацией выбирает мип по более редкой из двух осей текстуры; на растянутой развёртке это резче. По площади мира растяжение (средняя плотность к плотности редкой оси) — 1,07 в медиане, 1,71 на 95-м процентиле, 2,14 на 99-м, то есть до одного уровня. Это покрывает запас; расчёт по редкой оси (`census.py --density axis`) стоил бы ещё 25–45 % памяти.
- Оценка «лицом к камере» — верхняя граница нужной резкости. Наклонная поверхность с анизотропной фильтрацией (в движке включена по умолчанию) берёт мип по короткой оси следа, то есть тот же, что лицом. Поэтому оценка не занижает.
- У края кадра перспектива растягивает поверхность до `1/cos²θ` раз: в углу 16:9 — до 2,85 раза, это 1,5 уровня. Отсюда запас в один уровень по умолчанию; хватает ли его, покажет приёмка по кадрам.

### Перепись мира

[`census.py`](census.py) читает куски мира готовой базы и заголовки DDS и считает байты текстур ландшафта (327 текстур в 16 кольцах от точки) при разных правилах. База Mac, Хоринис, 1440p (`--density area`):

| МиБ, ×1 / ×2 / ×4 / ×8 по стороне | рынок | гавань | лес |
|---|---|---|---|
| все полные | 52 / 209 / 835 / 3340 | то же | то же |
| кольца, как было | 28 / 112 / 446 / 1782 | 28 / 113 / 451 / 1803 | 25 / 101 / 404 / 1614 |
| по каждому треугольнику, без запаса | 12,0 / 27,8 / 67,3 / 195 | 11,0 / 29,2 / 70,7 / 199 | 9,0 / 22,4 / 63,4 / 187 |
| по материалу в куске 64 м, без запаса | 12,9 / 35,2 / 95,8 / 314 | 12,4 / 36,4 / 90,5 / 265 | 9,5 / 25,1 / 76,1 / 232 |
| то же с запасом в один уровень (`--bias 1`) | 18,3 / 47,6 / 137 / 379 | 16,8 / 46,7 / 143 / 359 | 13,3 / 33,5 / 96,0 / 300 |
| как в движке: запас и спрос степенью двойки (`--bias 1 --quantise`) | 24,3 / 67,4 / 179 / 502 | 23,8 / 61,5 / 175 / 541 | 18,5 / 47,8 / 126 / 372 |

В 1080p без запаса (материал в куске) на рынке — на 7–18 % меньше. Клетка 8 м вместо куска при запасе в уровень экономит 2–4 % при ×1, 10–18 % при ×4 и 17–26 % при ×8.

Что из этого следует:

- Выигрыш правила, как оно сделано, против колец: в 1,2–1,4 раза при ×1, в 1,7–2,1 при ×2, в 2,5–3,2 при ×4, в 3,3–4,3 при ×8. Память всё ещё растёт с размером текстур, но примерно как сторона в степени 1,5, а не в квадрате.
- Запас в один уровень стоит около 40 % байт, округление спроса до степени двойки — ещё около 30 %. Это два рычага на случай нехватки памяти: порядок действий сверх бюджета (шаг 3) снимает запас, а округление можно сделать вдвое мельче ценой более частого пересчёта владельцев.
- Дробить владельцев мельче куска имеет смысл только для текстур ×4 и крупнее.
- На верхнем уровне без запаса при ×4 остаются 25–35 текстур из 327, при ×1 — 51–73.
- Плотность текселей ландшафта оригинала по площади: медиана 19 текселей на метр, 95-й процентиль — 105, 99-й — 190. При ×4 медиана — 76. Современный ориентир для игры от третьего лица — 512–1024 на метр. То есть ландшафт оригинала растянут сильно, и даже ×8 вблизи не избыточен.

Перепись считает только текстуры меша мира. Статичные объекты, NPC, предметы, небо и интерфейс в неё не входят; на маршруте они дают остальное до 81 МиБ.

## Как решают другие

| Кто | Как выбирает мип | Бюджет и поведение сверх него |
|---|---|---|
| Unreal, обычный стриминг | По каждому примитиву: границы, «размер текселя в мире», точка обзора; затем видимость | Пул в МБ, может ограничиваться видеопамятью. Сверх пула снимает по одному мипу: сначала невидимые и давно не виденные, ландшафт и персонажи держит дольше. Есть общий сдвиг мипов для малых пулов |
| Unity | Границы рендерера, камера и «метрика распределения UV» меша | Бюджет 512 МБ по умолчанию. Предел снижения (2 уровня) сильнее бюджета, поэтому бюджет может быть превышен. Расчёт размазан по кадрам: после смены плана нужно ждать |
| Tainted Grail на Unity | Свой расчёт: обратная плотность UV × множитель от камеры, расстояния и радиуса; минимум по всем владельцам текстуры | 3,4 ГБ со всеми полными против 1,2 ГБ со стримингом |
| Titanfall 2 | Заранее посчитанные гистограммы покрытия экрана по материалам и мипам для столбцов мира; для динамики — по градиентам UV треугольников при загрузке, вклад ∝ 1/(tan(fov/2)·d)² | Мипы меньше 64 КиБ постоянны. Не снимает, пока не грузит что-то важнее. 2 запроса чтения в полёте, создание текстур — не больше 2 за кадр в своём потоке. Пул 375–1250 МиБ на ПК плюс около 400 МиБ постоянных; около 0,8 мс CPU на кадр |
| Sampler Feedback, виртуальные текстуры | GPU сам пишет, какой мип запросил | Точно, учитывает перекрытия, но разбор обратной связи стоит времени на каждый ресурс; три младших мипа всегда на месте. Titanfall 2 от новых проходов GPU отказался |

Источники: [Unreal: обзор](https://dev.epicgames.com/documentation/en-us/unreal-engine/texture-streaming-overview-for-unreal-engine) и [настройка](https://dev.epicgames.com/documentation/en-us/unreal-engine/texture-streaming-configuration-in-unreal-engine); [Unity: стриминг мипов](https://docs.unity3d.com/2022.3/Documentation/Manual/TextureStreaming.html) и [API](http://docs.unity3d.com/2022.3/Documentation/Manual/TextureStreaming-API.html); [Tainted Grail](https://dev.to/kamilvdono/deep-dive-tainted-grail-4-mipmaps-streaming-1aj3); [Titanfall 2, GDC 2017](https://media.gdcvault.com/gdc2017/Presentations/Barb_Chad_EfficientTextureStreaming.pdf); [Sampler Feedback Streaming](https://github.com/GameTechDev/SamplerFeedbackStreaming); [BeamNG](https://documentation.beamng.com/modding/materials/texture_streaming/).

Ловушки, которые они описывают:

- **Бюджет, который нельзя соблюсти.** У Unity предел снижения сильнее бюджета. У нас так же: ближнее кольцо не понижается ради цели. Правило сверх бюджета должно доводить до конца.
- **Нулевой и слишком малый бюджет.** У Titanfall 2 нулевой пул ломал игру; малый даёт заметную подгрузку.
- **Владельцы без плотности UV.** Процедурные меши, декали, частицы, шейдеры не на UV0 в Unity требуют ручного уровня. У нас такие владельцы должны оставаться на полном уровне, а не получать ноль.
- **Смена плана и телепорт.** Расчёт, размазанный по кадрам, отстаёт; Unity и Unreal советуют ждать или подгружать заранее. Titanfall 2 выручали данные, привязанные к месту.
- **Дёрганье на пороге.** Документированной «мёртвой зоны» ни у кого не нашлось; Titanfall 2 просто не снимает мип, пока память не нужна под более важное. У нас понижение уже идёт только под давлением памяти и после 5 секунд.
- **Создание текстур в главном потоке и «асинхронное» чтение, которое блокирует.** У нас чтение и загрузка уже в фоне, публикация — одна за кадр.
- **Предсказание по скорости камеры** в источниках не описано.

## Что умеет движок

По коду на `98b818fc1` ([как работает сейчас](../../../docs/world-streaming-textures.md)):

- **Два уровня.** `Full` и `Tail` (`firstMip = 2`, стороны не меньше 64) — булево поле записи текстуры. Читатель `Pixmap::loadDdsMipTail(input, firstMip, minSize)` уже принимает любой первый уровень.
- **Спрос — в кольцах кусков.** Владелец сообщает расстояние Чебышёва своего куска до куска героя или камеры (0–4) или «всегда полный». Текстура берёт минимум по владельцам; `≤ 2` — полный. Владельцы: пакеты ландшафта (материал в куске), статичные объекты, NPC, предметы в мире; герой, частицы, небо и интерфейс — всегда полные.
- **Пересчёт — по событиям** смены куска героя или камеры, без обхода владельцев в кадре.
- **Одна загрузка в полёте** и одна публикация за кадр; повышение сразу, понижение — после 5 секунд, только при превышении цели 192 МиБ, по LRU.
- **Подмена без пересборки:** identity текстуры и слоты bindless сохраняются, меняется payload. Текстура при смене уровня создаётся заново целиком.
- **Анизотропная фильтрация** включена по умолчанию в сэмплерах Tempest.

Пробелы:

- Плотность UV нигде не считается и не хранится: ни в кусках мира, ни в мешах.
- Расстояние в метрах до границ владельца для текстур не используется.
- Tempest не сообщает объём видеопамяти: бюджет задаётся только настройкой.
- Хвост читается только у DXT1/3/5. Материалы в BC4/5/7 всегда были бы полными.
- Метрика недобора есть только для «ближняя текстура на хвосте».

## Способ

1. **Спрос в единицах разрешения.** Владелец сообщает не кольцо, а нужное разрешение: сколько пикселей экрана приходится на одну единицу UV, `R = ppm(d) / u`, где `u` — наименьшая плотность UV владельца (единиц UV на метр), `d` — расстояние от камеры или героя до его границ. Величина не зависит от размера текстуры, поэтому albedo, normal и ORM одного материала получают каждый свой уровень: `floor(log2(√(W·H) / R)) − запас`. Спрос округляется до степени двойки: владелец меняет регистрацию, только когда расстояние меняется примерно вдвое.
2. **Плотность UV владельца** считается один раз: у пакета ландшафта — при сборке пакета куска, у меша — при его загрузке (для объекта умножается на масштаб). Вырожденные треугольники не учитываются. Нет плотности — владелец остаётся на полном уровне.
3. **Уровней столько, сколько мипов.** Запись хранит номер первого резидентного уровня. Нижний предел прежний: стороны не меньше 64.
4. **Загрузка сразу до нужного уровня**, не по одному мипу: текстура всё равно создаётся заново. Несколько загрузок в полёте (начать с двух), первой идёт текстура с наибольшим недобором.
5. **Понижение как сейчас:** после задержки и только под давлением памяти. Пока память в цели, лишнее не выбрасывается.
6. **Бюджет от видеопамяти** (отдельный шаг): Tempest сообщает объём (`VK_EXT_memory_budget`, `recommendedMaxWorkingSetSize`), цель — его доля с нижней и верхней границей; настройка игрока сильнее. Сверх цели по порядку: текстуры без спроса; понижение до нужного уровня; запас 1 → 0; общий сдвиг на уровень, начиная с дальних. Обязательный полный уровень (герой, интерфейс) не трогается.
7. **Выключатель:** прежнее правило колец остаётся за флагом на время перехода.

Шаги (каждый — свой PR):

| Шаг | Что | Зачем отдельно |
|---|---|---|
| 1 | Уровни вместо двух состояний; плотность UV и спрос в единицах разрешения для ландшафта и статичных объектов; две загрузки в полёте; метрики | Основной выигрыш памяти |
| 2 | NPC, предметы в мире и интерактивные объекты (mobsi) по расстоянию; начальная загрузка по уровням; первый кадр после телепорта | На ×4 эти владельцы держат около половины памяти; загрузка на ×4 возвращается к исходной |
| 3 | Объём видеопамяти из Tempest, цель от него, порядок действий сверх цели | Нужен замер на Mac с общей памятью |
| 4 | По итогам замеров: больше загрузок в полёте, упреждение по скорости | Только если метрика недобора не ноль |
| 5 | Хвост и чтение BC4/5/7 | Когда свои материалы перейдут на эти форматы |

BC7 и BC5 память не уменьшают (8 бит на пиксель, как DXT5); это шаг про качество, а не про бюджет.

## Приёмка

Стенд — наборы стресс-замера `base`, `t2`, `t4` на Ryzen, те же проходы.

1. **Память.** Живые текстуры на маршруте в окне 1728×1117: `t2` — в цели 192 МиБ (было 234–246), `base` — не больше прежних 81 МиБ. `t4` (было 901–946): ландшафт и статика — не выше правила по переписи (ландшафт при ×4 — 126–179 МиБ в 1440p) плюс общие с другими владельцами текстуры; вся память `t4` в цель одним шагом 1 не укладывается и проверяется после шагов 2 и 3.
2. **Вид.** `streaming-shots` (пять неподвижных точек, детерминированный кадр): кадры с выбором мипов против кадров той же базы со всеми полными текстурами (`OPENGOTHIC_TEXTURE_MIPS=0`) — в пределах шума стенда, на `base` и `t4`. В конце — ролик прохода по городу на `t4` для глаза пользователя.
3. **Недобор в движении.** Новая метрика: текстуро-секунды, когда резидентный уровень грубее нужного. На беге 5 м/с после прогрева — ноль. На полёте 20 м/с и после телепорта — измерить; время до нуля после телепорта не хуже сегодняшнего.
4. **Кадр.** p99 облёта — в сегодняшнем разбросе 11,3–12,1 мс; зоны `texture_update` и `texture_demand_elapsed_sum` растут не больше чем на 0,1 мс в среднем на кадр.
5. **Загрузка.** `t4` с тёплыми кэшами — не больше `base` + 0,3 с после шага 2 (сейчас 5,18 против 4,27 с).
6. **Тесты.** Модульные тесты выбора уровня, порядка загрузок и понижения; проход `check_walk`.

## Ограничения

- Увеличенные текстуры стресс-наборов не несут новых деталей: память и выбор мипов ведут себя как у настоящих, а вид — нет. Ошибка выбора на них видна как потеря резкости исходного уровня, не новых деталей.
- Перекрытия не учитываются: текстура за стеной в двух метрах получит полный уровень. Обратная связь с GPU решила бы это; откладываем, пока расчёт на CPU укладывается в бюджет.
- Перепись сделана на базе Mac и только для меша мира.
- Первый кадр после телепорта: синхронно, в пределах 300 мс, догружаются только текстуры с недобором от двух уровней. Недобор в один уровень остаётся на несколько кадров; на `t4` это слегка мягкая земля у камеры. Владельцы кусков, которые после прыжка ещё не опубликованы, в догрузку не попадают.
- Mac и 1440p на стенде не измерены, как и в стресс-замере.
