# Попадание в кэш переписи без временных тел — 2026-11-05

Следующий шаг после [кэша переписи](census-cache.md#что-дальше). Там при попадании стадия placed items NEWWORLD на Ryzen стоила 273,3 мс. Из них 252,8 мс уходили на подготовку временных тел, которые нужны только запросам переписи, а при попадании запросов нет.

## Что сделано

- **Тела создаются только для живой переписи.** Это промах, выключенный кэш (`OPENGOTHIC_PLACED_CENSUS_CACHE=0`) и сверка (`OPENGOTHIC_PLACED_CENSUS_CHECK=1`). Тогда путь прежний: тело на каждого кандидата, перепись, удаление тел в порядке кандидатов.
- **Ключ без тел.** `placedItemCensusInputs` больше не читает тела кандидатов. Для каждого кандидата хэшируется то, из чего строится его тело (`addDynamicObj`): матрица Item, его материал (`ItemMaterial`) и `bboxMesh` меша. Исходные вершины оболочки (`ProtoMesh::appendItemVertices`) хэшируются по разу на visual в верхнем регистре, как ключ кэша оболочек. Подвижные vob хэшируются как раньше. Теперь сам код построения тела (`itemHullShape`, `addDynamicObj`, `CollisionWorld::addBody`) в ключ не попадает. Поэтому его правка, меняющая тело при тех же входах, поднимает `PlacedCensusCache::RulesVersion` — сейчас он 2. Файлы версии 1 дают промах `version` и пересчитываются один раз. Ключ считается быстрее: 4,8 мс против прежних 6,7, потому что формы Jolt больше не сериализуются.
- **Побочные эффекты временных тел** и как каждый сохранён при попадании:

| Эффект временных тел | Кто от него зависит | При попадании |
|---|---|---|
| Загрузка меша (`proto`), если его ещё нет | тело Item позже, ключ | Сохранён: `Item::physicsProto()` грузит меш так же, для всех кандидатов |
| Оболочки `itemHullShape` в кэше `DynamicWorld` (153 visual) | тела допущенных Item рядом с героем, брошенные Item | Строятся только для 77 visual из 227 допущенных: их тела `tickPlacedItems` создаёт рядом с героем, до 4 за кадр, и оболочка не должна строиться в кадре. Оболочки исключённых предметов при попадании не строятся; Item с таким visual, выброшенный позже, построит оболочку при создании тела (~1,5 мс один раз на visual) |
| ID тел Jolt: 2331 раз выдать и вернуть в список свободных (LIFO, номер последовательности +1) | все тела, созданные позже: Jolt сортирует по `BodyID` контакты (`SortContacts`) и активные тела | Сохранён: `CollisionWorld::cycleBodyIds(n)` создаёт и удаляет n пустых статичных тел-заглушек (сфера 1 см) в том же порядке. В broadphase они не попадают, `n` — число кандидатов с мешем. 0,34 мс |
| Узлы broadphase от добавления и удаления тел | порядок пар столкновений | Не сохраняется и не нужен: при `CROSS_PLATFORM_DETERMINISTIC` Jolt упорядочивает контакты сам (по ключу и `BodyID`), порядок пар broadphase на итог не влияет. Это подтверждают стенды ниже |
| `invalidateVobIndex` | поиск vob по индексу | Сохранён: один вызов в конце |
| `CollisionWorld::bodies`/`rigid`, активные тела, масса, `setItem`, сон | — | Временные тела к концу шага удалены в обоих путях: после шага у расставленных Item тел нет, их создаёт `tickPlacedItems` |
| `placedAllowed`, `validation`, связь Item с ZEN-ID | `tickPlacedItems`, сейв | Без изменений: берутся из итога переписи |

- **Сравнение на уровне тел.** Команда стенда `placed-items census` и конец `placed-items probe` дописывают строку в `placed-items-digest.jsonl`. В строке — SHA-256 по всем телам Jolt: ID с номером последовательности, тип движения, слой, сенсор, активность, тип и границы формы, центр масс, поза, AABB, скорости (у кинематических — без позы и скоростей). Второй отпечаток — по каждому расставленному Item с телом: индекс, ZEN-ID, сон, матрица.
- Счётчик `physics_prepare` зонда теперь считает кандидатов и тела отдельно: на живом пути `count=4662` (2331 + 2331), при попадании — `2558` (2331 + 227 оболочек). Время в нём то же по смыслу: подготовка без native body.

## Эквивалентность

- **Стенд `placed-items-census`** (NEWWORLD, 126 участков по 12 м, ≥300 нативных шагов на каждый) при `OPENGOTHIC_PLACED_CENSUS_CACHE=0` и при тёплом кэше. Побайтно совпали `placed-items-census.jsonl` (2331 строка, `sha256 bbc63a23…`), `placed-items-probe.jsonl` (227 строк, `3da79ec6…`) и `placed-items-digest.jsonl` (`37456d55…`). В digest после переписи 7730 тел Jolt, 4 расставленных Item с телом; после пробы 7824 тела. ID, позы, сон и скорости всех тел совпали, в том числе у тел, созданных после шага. Из 141 события различаются только `classification_ms` и `world_load_ms` (848,0 → 129,5 мс и 2450,7 → 1733,8 мс).
- **Сверка на новом старте:** `OPENGOTHIC_PLACED_CENSUS_CHECK=1`, зонд NEWWORLD на тёплом кэше — `hit, 2331 items`, `check: passed, 2331 items identical`, exit 0.
- **Сверка из сейва** (`session-placed-items.sav`): `hit`, `check: passed, 2331 items identical`, exit 0.
- **`load_rewind` в режиме сверки** (изолированный кэш, файл удалён перед запуском). Новый старт — `miss (absent), recomputed 2331 items`. Загрузка слота 7 — `hit` и `check: passed, 2331 items identical`. Сценарий — 4 проверки, 0 провалов, exit 0.
- **Стенд `placed-items`** (численный стенд шага 5 этапа 8) красный на `main` по [#851](https://github.com/kaifaty/GothicAI/issues/851). Off и warm ветки оба падают на том же шаге: `ragdoll arena failed: placed Item owned table preparation requires admitted owned and excluded authored Items on one native table`, exit 1. До провала все 14 событий `placed_items_*` совпали между off и warm; различаются только `classification_ms`, `world_load_ms` и размер архива сейва (`bytes` 10 071 943 / 10 072 700, как и в #850). Off ветки сравнён и с прогоном `main` из #850 (`9a72c18c3`): `placed-items-census.jsonl` совпал побайтно, 13 общих событий — с теми же тремя исключениями. Новое событие `placed_items_digest` в обоих прогонах ветки одинаково. Значит, правка не меняет вывод стенда до провала.

Допуск — `pgrep -fl Gothic2Notr` пуст и LA1 ≤8. Во время работы LA1 на Mac был 230–695, поэтому игровые замеры Mac не запускались (n=0). Mac только собрал игру (`engine-targets.sh`, Apple clang, без ошибок).

## Что дальше

Из 124 мс стадии при попадании ~110 мс — построение 77 оболочек допущенных visual. Их можно хранить в производном кэше рядом с итогом переписи: Jolt умеет `SaveBinaryState`/`sRestoreFromBinaryState` для `ConvexHullShape`. Тогда попадание будет стоить около 10 мс. Другой путь — строить оболочки лениво при первом пробуждении. Но тогда при подходе героя в кадр попадёт до 4 × 1,5 мс, поэтому здесь он не выбран.
