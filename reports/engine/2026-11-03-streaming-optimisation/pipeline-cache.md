# Кэш пайплайнов на диске — 2026-11-03

Пункт 2 таблицы [исследования](README.md#3-что-делать-нам-по-выгоде). Продолжение [базы](baseline.md#первый-кадр-и-пайплайны): там первый кадр Ryzen ~1,2 с и ~50 графических пайплайнов после загрузки; Vulkan передавал `VK_NULL_HANDLE` вместо кэша, Metal компилировал MSL при каждом старте.

## Что сделано

- **Vulkan.** Один `VkPipelineCache` на устройство (`gapi/vulkan/vpipelinecache.*`), его получают все `vkCreateGraphicsPipelines` и `vkCreateComputePipelines`. Файл `<OPENGOTHIC_BASE_CACHE>/derived/pipelines/vulkan-<vendor><device>.bin`: свой заголовок (магия, vendor, device, версия драйвера, версия API, `pipelineCacheUUID`, размер, FNV-1a данных), затем данные драйвера, у которых ещё раз сверяется `VkPipelineCacheHeaderVersionOne`. Несовпадение, повреждение или отказ драйвера — одна строка `pipeline cache: ignored <файл>: <причина>` и пустой кэш.
- **Metal.** Один `MTLBinaryArchive` на устройство (`gapi/metal/mtpipelinecache.*`). Render- и compute-PSO сначала создаются из архива с `PipelineOptionFailOnBinaryArchiveMiss`; при промахе функции пайплайна добавляются в архив, и состояние создаётся уже из него. Имя файла `metal-<хеш>.bin` — хеш имени GPU, строки версии ОС, версии MSL и константы формата архива. Внутри архива Metal сверяет функции по хешу их скомпилированного кода, поэтому изменённый шейдер просто промахивается, а обновление ОС меняет имя файла. Mesh-PSO идут прежним путём. Каждая запись строит **новый** архив из копий дескрипторов всех PSO этой сессии; их бинарники берутся из загруженного архива. Загруженный с диска архив никогда не пересериализуется (почему — в разделе о пикселях). Поэтому PSO, которых в сессии не было, из файла выпадают и при следующей встрече снова промахиваются. Файл больше 64 МБ при старте отбрасывается — это страховка. Журнал при записи пишет `hits/misses/failures` и `pipelines/lost`.
- **Запись.** Атомарно: временный файл рядом, затем `rename`. Устройство пишет кэш при уничтожении (чистый выход) и один раз через 20 с игры после загрузки (`common/mainwindow.cpp`) в фоновом потоке, чтобы после падения кэш остался. Неизменённый кэш Vulkan не перезаписывается.
- **Где.** Каталог задаёт игра до создания устройства (`game/main.cpp` → `Tempest::Device::setPipelineCacheDirectory`): рядом с производными кэшами коллизии и высот путей, но без отпечатка базы — ключ зависит от GPU и драйвера, а не от данных игры. Инструменты Tempest без этого вызова кэш не включают.
- **Выключатель.** `OPENGOTHIC_PIPELINE_CACHE=0` — без чтения и записи (на Vulkan снова `VK_NULL_HANDLE`, на Metal прежние вызовы без архива). По умолчанию включено.
- **Зонд.** Новая операция `convert` считает перевод SPIR-V → MSL на Metal, чтобы сравнить его с `library` (`newLibrary`) и `graphics`/`compute` (PSO).

Шейдеры, материалы, вид, порядок загрузки и прежние форматы не менялись.

Off2 отличается от off1 сдвигом камеры и листвы: стенд не строго детерминирован между запусками, а off2 шёл под другой нагрузкой и вдвое дольше. Поэтому побайтное совпадение off/warm — сильное свидетельство, а не случайность пустой сцены. Склейки off | warm — [`pipeline-cache-shots/`](pipeline-cache-shots/).

Пару на Vulkan (Ryzen, тот же стенд) сняли с очереди по той же причине — старт через много часов. На Vulkan кэш по спецификации не влияет на результат пайплайна: драйвер берёт из него только уже скомпилированный код того же create info.

**Дефект, найденный по ходу, и его исправление.** В первой версии запись пересериализовала тот же архив, который Metal загрузил с диска и в который в этой сессии добавлялись новые PSO.
- Во время warm1 сработала запись через 20 с игры: `saved 26963920 bytes … (play, hits=150 misses=1)`. Файл вырос с 5,3 до 27 МБ ради одного нового PSO (снимок экрана).
- Следующий e2e `load_rewind` на этом архиве дважды упал при записи: `Failed to generate machO … expecting 'fragment' stage in pipeline no. '145'`. Файл остался прежним — атомарная запись сработала.
- Сначала проверили гипотезу про PSO без растеризации; она не подтвердилась, ошибка осталась на том же номере.
- С пустым архивом тот же e2e записал 5 590 544 байта (145 PSO) без ошибок. Значит, ломается пересериализация загруженного архива с добавлениями, а не какой-то PSO.

Исправление — запись всегда собирает новый архив из дескрипторов сессии (см. «Что сделано»). Проверки на финальном бинаре:
- стенд снимков на архиве из e2e: `loaded`, затем `saved 5333424 bytes … (play, hits=138 misses=13 …, pipelines=151 lost=0)`;
- e2e `load_rewind` на этом архиве: `saved 5594720 bytes … (play, hits=138 misses=15 …, pipelines=153 lost=0)`, **4 проверки, 0 провалов**;
- кадры warmshot2 (финальный бинарь) против off1 тоже побайтно одинаковы во всех трёх точках (LA1 5,36).

Цена такого подхода — PSO, специфичные для сценария, перекатываются: стенд снимков и e2e каждый раз промахиваются на 13–15 «своих» PSO, которые выпали после чужой записи. В обычной игре один сеанс покрывает почти все PSO мира. e2e завершает игру сигналом SIGTERM, без выхода, поэтому кэш там сохраняет именно запись через 20 с игры.

## Перевод SPIR-V → MSL на Mac: исходные данные для следующего PR

Решение 2026-11-04: кэш перевода — отдельная задача и отдельный PR, в этот не входит. Ниже — то, с чего её начинать.

- **Сколько.** Операция зонда `convert` охватывает весь `spirv_cross::CompilerMSL` в конструкторе `MtShader` (`gapi/metal/mtshader.cpp`): разбор SPIR-V, опции, `compile()`, разбор привязок. В 8 запусках Mac — **256–412 мс CPU на старт**, медиана ≈ 318 мс, на **292 шейдера** (≈ 1,1 мс на шейдер). Для сравнения в тех же запусках `newLibrary` стоит 13–55 мс, все PSO вместе — 10–59 мс.
- **Когда.** 290 из 292 переводов заканчиваются до конца загрузки мира (`load_end`), ещё 2 — в первые 10 с после неё. `Shaders::Shaders()` переводит синхронно только `bink` и `downscale`, остальное — в фоновом потоке `Shader compilation` (`common/graphics/shaders.cpp`).
- **Ждёт ли загрузка.** На Mac при тёплом системном кэше Metal — почти нет. Разрыв `world_read_total` → `physics_static`, где на Ryzen видно ожидание компиляции, на Mac больше самой стадии физики всего на 14–75 мс (8 запусков), а строки `Shader compilation took` нет: фоновая компиляция укладывается меньше чем в 1 с. Значит, перевод нагружает CPU во время старта и загрузки, но в критический путь загрузки сейчас почти не попадает. Иначе может быть при холодном системном кэше Metal, когда `newLibrary` на том же потоке становится дорогим: это стоит проверить в той же задаче.
- **Что кэшировать.** Текст MSL и то, что перевод даёт кроме него: `mslBinding`, `mslBinding2`, `mslSize` для push-констант, слияние одинаковых привязок, `bufferSizeBuffer`. Ключ — хеш SPIR-V, опции `CompilerMSL` (версия MSL, `argument_buffers_tier`, `r32ui`-выравнивание и прочие поля из `MtDevice::prop`) и версия SPIRV-Cross. Это новый формат файла.
- **Как принимать.** `convert` в зонде 256–412 → около 0 мс при тёплом кэше; пиксели off/warm побайтно равны, так же как в этом PR.

## Выбор механизма Metal

Выбран **`MTLBinaryArchive` для render- и compute-PSO**, библиотеки остаются на системном кэше Metal.

- **Почему не кэш скомпилированного `.metallib`.** У Metal нет публичного API, который сохраняет библиотеку, собранную из исходника во время работы. `newLibrary(data)` читает только готовый `.metallib`, а сделать его может лишь `xcrun metal` из Xcode, которого у игрока нет. `MTLDynamicLibrary::serializeToURL` не подходит: в динамической библиотеке не бывает `vertex`/`fragment`/`kernel`-функций. Повторную компиляцию одинакового MSL система и так берёт из `libraries.data` — это видно по 55 мс на 292 библиотеки.
- **Почему архив.** Это единственный публичный дисковый кэш GPU-бинарей PSO, своё приложение им управляет. Он не зависит от вытеснения общего системного кэша. Изменённый шейдер даёт другую функцию и просто промахивается; обновление ОС меняет имя файла. Промах `FailOnBinaryArchiveMiss` дешёвый, а при добавлении функции компилируются один раз — в архив, состояние потом берётся из него.
- **Что дальше дешевле всего снимет время на Mac.** По замеру это не компиляция, а SPIRV-Cross: ~0,3 с CPU на каждом старте. Это отдельная задача (раздел выше).

## Проверки

- Сборка Mac `Gothic2Notr` (`scripts/build-engine.sh`, 2 задания) — проходит на финальном коде.
- Сборка Linux на Ryzen через `gq`: финальный код (коммит `8bac755`, после него менялись только отчёты) — полная пересборка движка, 389 целей, configure + build 131 с, без ошибок. Ранее через `gq` собирались первая версия и версия с разделяемой блокировкой; в промежутке финальные Vulkan-файлы проверялись `g++ -fsyntax-only`.
- `python3 scripts/check.py run` — 85 passed, 121 subtests; после слияния с `main` — 86 passed, 124 subtests. Сборка Mac на слитом дереве тоже прошла. Изменённые C++-файлы тестов не выбирают; выбраны тесты скриптов.
- e2e `load_rewind` на Ryzen (Vulkan, `SCENARIO=load_rewind scripts/ryzen.sh e2e`, 2026-11-04 после ожидания в очереди): **4 проверки, 0 провалов, exit 0**, 47 с. В журнале: `empty, will write …/vulkan-000010de00002206.bin`, затем `saved 3267835 bytes in 5 ms (play)` — запись через 20 с игры; e2e завершает игру через SIGTERM, выхода нет. До этого, пока Ryzen был занят, e2e четыре раза шёл на Mac: первый запуск — 4/4 с отказом записи архива Metal; второй — то же после первой, неверной правки; третий — с пустым архивом, 4/4; финальный — 4/4, запись архива прошла.
- Повреждённый файл Vulkan — тихий промах, одна строка, перезапись (раздел Ryzen).

## Открытые вопросы

- **Перекат PSO между сценариями на Metal.** Файл содержит PSO последней записавшей сессии. Объединить с PSO прежних сессий без пересериализации загруженного архива можно, только если хранить сами дескрипторы (в Metal 4 для этого есть `MTL4PipelineDataSetSerializer`). Цена сейчас — 13–15 промахов, десятки миллисекунд.
- **Кэш перевода SPIR-V → MSL на Metal** — сделан следующим PR: [msl-cache.md](msl-cache.md).
- **Холодный старт Mac (17 с в базе).** Проверить вклад архива при пустом системном кэше Metal можно, только стерев общий кэш `com.apple.metal` пользователя, — это решает пользователь.
- **Mesh-PSO на Metal** идут без архива: на Mac mesh-шейдинг по умолчанию выключен (`commandline.h`), `addMeshRenderPipelineFunctions` не проверялся.
- **`scripts/loadprobe.sh local`** считал Mac занятым, пока жива любая сессия агента, в чьей командной строке есть `Gothic2Notr` (`pgrep -fl`). Исправлено в [следующем PR](msl-cache.md): проверка идёт по `pgrep -x Gothic2Notr`.
