# Mass-редизайн дальней симуляции NPC: исследование

Дата: 2026-11-27. Статус: исследование (новое — сначала исследование). Код `main` `1251e9bbb`. Одобрено пользователем как направление после отрицательного A/B существующего Society-владения на 10k.

Предыстория: [замер масштаба](../2026-11-26-npc-scale/README.md) (10k ~20 с/кадр, 99% `Npc::tick`), [архитектура 10k и фаза 0](../2026-11-26-npc-10k-logical/README.md) (Society-стенд сутки 10k за 0,31 с), [A/B существующего владения](../2026-11-27-society-far-ownership/README.md) (ON +3,1 с/кадр, 0,3 пропуска — shadow-match не масштабируется). Вердикт: рычаг для 10k — событийное ядро, которое **ведёт** дальних NPC, а не теневое совпадение; событийный допуск вместо покадрового скана.

## Цель

Дальние NPC (вне кадра и ближней зоны) симулируются событийным data-oriented ядром: распорядок по очереди событий, движение по графу coarse-шагом, восприятие по пространственным ячейкам, допуск O(1) на NPC. Ядро применяет состояние/позицию к нативному `Npc`; нативный движок владеет героем, ближней зоной, боем, взаимодействиями и пробуждениями. Ориентир: 10k NPC ≤ 33 мс/кадр (реальное время) при герое одном; суточный паритет поведения; городская пара без регрессии; невидимость (упрощение только вне кадра, поза до первого видимого кадра).

## Как это решают другие (эталон с числами и ловушки)

- **Unreal MassEntity (Mass Gameplay).** Data-oriented ECS: процессоры идут по архетипам чанками, параллельно; структурные изменения (создание/удаление сущностей, смена архетипа) откладываются в command buffer и применяются в sync points; зависимости процессоров задают порядок. LOD симуляции (MassLOD) и раздельное визуальное представление. [Epic, Mass Gameplay](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-mass-gameplay-in-unreal-engine). Ловушка: отложенные мутации требуют явных sync points и детерминированного порядка процессоров; наивный parallel-for по сущностям с мутациями даёт гонки — ровно наш барьер B.
- **Unity DOTS/ECS + Job System.** Burst-компилируемые системы по чанкам, `CullUpdateTransforms` сохраняет автомат/root motion, но пропускает кости/IK у невидимых. [Unity, CullUpdateTransforms](https://docs.unity3d.com/2019.4/Documentation/ScriptReference/AnimatorCullingMode.CullUpdateTransforms.html). Ловушка: детерминизм float при параллельном суммировании; порядок систем фиксирован.
- **Genshin Impact (miHoYo, GDC 2021).** Три уровня AI, частоты 30/5 Гц для групп модулей, остановка дальних обновлений, вынос работы в задачи; 2–3 мс → бюджет 0,5 мс на Apple A12. [доклад](https://media.gdcvault.com/GDC%2B2021/20210528_%2BGDC21_shuo_presentation%2B_Final.pdf). Берём: независимые частоты подсистем и остановку дальних; свои частоты проверяем по местным маршрутам.
- **Snowdrop / Avatar (Ubisoft, GDC 2024).** Узкие быстрые пути + группировка NPC по зависимостям для распараллеливания; в столичных сценах ~40% работы NPC — анимация, ~60% — граф; отдельно подчёркнут порядок исполнения. [доклад](https://media.gdcvault.com/gdc2024/Slides/GDC%2Bslide%2Bpresentations/Simmons_Joshua_Upgrading_the_Snowdrop.pdf). Берём: группировка по зависимостям вместо глобального порядка; наш графовый путь уже дешёв, дорого — покадровые проверки.
- **Assassin's Creed Unity (Ubisoft, GDC 2015).** Массовка дешёвым движением с пространственным разбиением + пул полноценных NPC рядом с игроком. [доклад](https://media.gdcvault.com/gdc2015/presentations/Cournoyer_Francois_Massive_Crowd_On_ACU.pdf). Берём: пул полных у героя, дешёвый фон; это наша целевая форма.
- **Kingdom Come: Deliverance 2.** ~2400 NPC + уровни детализации ИИ. [GDC](https://gdcvault.com/play/1035718/Supporting-Thousands-of-NPCs-in). S.T.A.L.K.E.R.: два режима, граница ~150 м, вдали нет анимации, движение по графу, бой формулой. [интервью](https://www.gamedeveloper.com/game-platforms/interview-inside-the-ai-of-i-s-t-a-l-k-e-r-i-).
- **DetourCrowd / Unity NavMesh.** Коридор + ограниченный набор соседей для избегания; бюджет асинхронных поисков. [DetourCrowd](https://github.com/recastnavigation/recastnavigation/blob/main/DetourCrowd/Include/DetourCrowd.h). Берём: ограничение соседей и бюджет поисков; у нас граф и высоты пути уже есть.

Общий паттерн: **data-oriented раскладка + событийное расписание + пространственные ячейки + пул полных у игрока + отложенные структурные мутации с детерминированным порядком**. Ловушки, общие для всех: детерминизм (порядок float/RNG/разрешения конфликтов), полнота пробуждения (каждый нативный читатель должен разбудить NPC до чтения), вырождение контента при масштабе (очереди за места).

## Что умеет наш движок (по коду; карта барьеров — ниже)

- **Society-ядро** (`common/society/`): событийный мир (очередь, не тики), SoA-состояние (`place/dest/depart/arrive/entry/stateEnd/state/flags`), позиция идущего `Paths.along`, распорядок по правилам движка, паритет 99,76% отметок; сутки 1053 NPC за 2,3 мс, 11 053 за 0,31 с. Режим decisions моделирует вместимость/брони/очереди (`objectUse/pointUse/routineWait`, `PlaceHeld/PlaceReleased`). **Ядро уже вычисляет всё для реконструкции дальнего NPC** — но сегодня оно тень и не пишет `Npc`.
- **Уровни/движение/поза**: Full/Simplified по куском 64 м, графовое движение (`WayPath`+`WayHeights`), логическое тело (`NpcLogicalState`), cadence (`NpcSimTick`), LOD анимации с догоном `catchUpAnimation`, сон/ожидание без коллизии. Позы и шаг Jolt на 10k уже дёшевы (7 / 1,4 мс) — дорого внутри `Npc::tick`.
- **Параллелизм**: пул `Workers` (до 16), параллельный проход поз. Command-buffer/отложенных мутаций для тиков нет (барьер B).
- **Детерминизм/паритет**: `npc-day-parity` (побайтно по полям, допуски -6c для позиций/покрытия), приватные RNG-потоки `GameScript::isolateRandom` по ключу журнала.

## Пробелы (карта барьеров, file:line в worktree)

Порядко-зависимые эффекты `Npc::tick`, которые ведущее ядро должно воспроизвести или избежать:
1. **Общий скриптовый RNG** (`gamescript_dayrandom.cpp:8-17`): в живой игре `isolatedRandom` пуст, каждый бросок потребляет единый `randGen` в порядке тика (сортировка по id, `worldobjects_walk.cpp:179-187`). Потребители дальних спокойных — биты распорядка/жестов (`gamescript_socialroutines.cpp:66-70`, `gamescript_activities.cpp:315-355`), не ходьба. Пропуск тика убирает бросок и сдвигает всех поздних NPC. Бенч изолирует потоки (`npcdayjournal.cpp:310-313`), игра — нет.
2. **Брони FP/guard** (`fplock.cpp:13-45`, `world.cpp:2130-2171`, `npc_activityevents.cpp:390-486`): FCFS в порядке тика, ждущие просыпаются по освобождению. Побеждает тот, кто тикает первым и attaches.
3. **Mob-резервации** (`mobreservations.cpp:32-109`): FCFS + вытеснение + истечение; только для mob-занятий, не для чистых идущих.
4. **Insert/remove npcArr скриптами** (`worldobjects.cpp:686-790`): оставить нативу, не пересортировывать массив.
5. **Пробуждения**: бой (`setTarget`/`refreshMeleeFighter`), урон/восприятие, физшум, близость героя, кадр, команды скрипта, смена распорядка, save/load, `setDayTime` — уже освобождают тень через `wakeSociety`; ведущее ядро должно чтить тот же набор и подавлять **само**-пробуждение при записи.

Бой, melee-окна, BloodSpawn, BodyController, attention/lookAt **не относятся** к дальним спокойным (нет цели, NoWeapon, >60 м, восприятие гейтится политикой `npc_perception.cpp:75-79`) — только условия освобождения.

**Порядко-независимость дальних спокойных идущих (ключевой факт):** `implSimpleGoTo` (`npc_movement.cpp:516-690`) меняет только свои позицию/курсор wayPath/состояние ребра/анимацию тела; не тянет RNG, не разрешает спорные брони посреди ребра, не трогает чужих NPC; детерминирован по часам мира + зерну (скорость из анимации, кэш ground-профиля, скорость поворота гильдии). Порядковые связи — только на событиях: терминальная бронь FP, биты распорядка/жестов, re-path по живым целям (исключён для подтверждённого статического ребра). Существующий cadence уже принимает dt-дрейф (профиль 6c).

Пробелы ведущего ядра (почему текущее society-ядро не может писать Npc паритет-безопасно): позиция (экспорт несёт авторский `pos`, натив ходит по `groundPos`+`groundProfile.heightAt` — y/прогресс различаются, zero-паритет недостижим); курсор ходьбы (ядро знает `place/dest/depart/arrive`, нативу нужны `go2.wp+wayPath+simpleMovement.edge*`); тайминги состояний (равномерный StartDelay 20 с против состояние-зависимых квантованных по восприятию); стадия занятия/жесты (нет `ActivityEvents::Stage`/таймера/броска); идентичность FP/брони (routine-only ядро без модели броней); мост RNG (xoshiro ядра ≠ randGen игры); само-пробуждение при записи; save/load; область ( tractable subset — дальние спокойные люди на подтверждённых графовых рёбрах с распорядком, без боя/взаимодействия).

## Целевая архитектура

**Главный вывод карты:** не нужно, чтобы ядро писало состояние из своей приближённой модели (это упирается в zero-паритет). Нужно перестроить **когда и как** исполняется нативный дальний путь, сохранив нативный исполнитель для точности:

1. **Параллельная интеграция дальних спокойных идущих.** `implSimpleGoTo` порядко-независим → выносится в параллельный проход `Workers` (как существующий проход поз `worldobjects.cpp:928-1036`). Это снимает последовательную цену интеграции.
2. **Порядковый серийный хвост событий.** Биты распорядка/жестов (общий RNG в sorted-id порядке), брони FP (FCFS), insert/remove скриптами, пробуждения — в серийном хвосте после параллельного прохода, ровно паттерн анимационного хвоста (`worldobjects_animtail.cpp:23-117`). Паритет RNG/броней сохраняется порядком.
3. **Событийное расписание вместо покадрового скана.** Society-ядро — не писатель состояния, а **поставщик расписания**: очередь событий (сроки распорядка, прибытия, жесты) говорит, какие NPC_due_ в этом кадре. Дальний NPC не тикает каждый кадр и не проходит eligibility-скан; он интегрируется coarse-шагом по событию/сроку. Допуск — пространственные ячейки + флаги состояния, O(1) на NPC (ячейки 64 м уже есть, `collectLatePoses`).
4. **Нативный исполнитель сохраняется.** Позицию/курсор/брони/RNG считает натив (точно), ядро лишь планирует когда. Паритет: zero-профиль для RNG/броней/состояний при сохранении порядка хвоста; 6c для coarse-дрейфа позиций.
5. **Пул полных у героя.** Ближняя зона/бой/взаимодействия/видимое — нативный полный тик (вердикт D). Пробуждение — существующий набор `wakeSociety` + подавление само-пробуждения при владении.

Переиспользуемый скелет уже есть: `Workers::parallelTasks` + per-index план + порядковый хвост (анимация), отложенные мутации (`AiQueue`, `BodyController::deferNative`, очереди триггеров/восприятия/ячеек), `societyDueStep`-мост часов (`worldobjects_npctick.cpp:167-196`), `Pending`-куча ядра.

## Фазы и приёмка

| Фаза | Что | Приёмка |
|---|---|---|
| **A. Параллельная интеграция + событийный cadence дальних спокойных идущих** | вынос `implSimpleGoTo` в параллельный проход; серийный хвост RNG/броней; cadence по расписанию ядра вместо покадрового; допуск по ячейкам; флаг владения с подавлением само-пробуждения | суточный паритет (zero для RNG/состояний, 6c для позиций); npcscale 10k: цена падает на долю спокойных идущих; городская пара без регрессии; контракты пробуждения |
| **B. Событийные биты распорядка/жестов** | биты Loop/жестов по срокам ядра в серийном хвосте, без покадрового tickRoutine для владеющихся; воспроизведение бросков RNG в порядке | паритет ZS/TA-покрытия и таймингов (6c offset ≤8 с); inventory-различия только с аттестованным script-random provenance |
| **C. Очереди/вместимость для спорных состояний** | smalltalk/mobsi-очереди через событийную модель вместимости/броней (society decisions `objectUse/pointUse/routineWait`), без покадровых повторов | паритет броней/очередей; npcscale 10k цена спорной доли; вырождение контента зафиксировано |
| **D. Масштаб 10k + контент** | сборка A+B+C, замер 10k ≤33 мс; масштабирование точек распорядка/объектов под 10k (отдельная контентная задача) | npcscale 10k ≤33 мс/кадр; паритет; город без регрессии |

Каждая фаза — за выключателем (по умолчанию ВЫКЛ), включение по умолчанию — решение пользователя. Невидимость: упрощение только вне кадра, поза до первого видимого кадра.

## Бюджет

- Исследование (эта заметка): 0 прогонов.
- Фаза A (прототип): 1 суточный паритет (пара OFF/ON) + 1 npcscale 10k + 1 городская пара ≈ 4 прогона dev-ubuntu/Ryzen ~60–90 мин; повтор только при разнице в шуме. Сверх — спросить пользователя.
- Фазы B–D: отдельные партии со своим бюджетом после приёмки предыдущей.

## Риски

- **Паритет RNG/броней:** серийный хвост должен воспроизвести sorted-id порядок бросков и FCFS броней; любое отклонение сдвигает журнал. Гейт — zero-профиль паритета на RNG/состояниях.
- **Полнота пробуждения:** пропущенный wake = видимый глюк или разрыв паритета; набор `wakeSociety` уже доказан в пилотах, но ведущее владение добавляет само-пробуждение при записи.
- **Вырождение контента ограничивает выигрыш:** на 10k/1000-контенте большинство NPC в спорных social/mobsi состояниях, а не в спокойной ходьбе; tractable subset фазы A мал в вырожденном стационаре. Фаза C (очереди) и контент нужны для полного выигрыша.
- **Объём:** это редизайн дальнего пути (рычаг B), не инкремент; каждая фаза самостоятельна и принимается отдельно.

**99,4% цены — graph fallback в нативную физку.** ~2883 NPC/кадр идут нативным физическим путём по 6,5 мс/тик; графовый путь уже дешёв (5,3 мкс/NPC, в 1230 раз дешевле). Причины fallback (game.log): «no continuous ground support» 2228, «ground profile reaches a different floor» 862 — спавн вне waynet (джиттер), профиль WayHeights не покрывает позиции/ребро.

**Переопределение фазы A.** Рычаг — НЕ параллелизация графовых идущих (они уже 5,3 мкс, параллелить нечего), а **устранение fallback**: абстрактная опора для дальних спокойных идущих (граф держит опору по WayHeights/интерполяции ребра без покадрового подтверждения), нативная физика только при пробуждении (препятствие, ближняя зона, бой, удар, потеря опоры). Перевод 2883 NPC/кадр с 6,5 мс на ~5,3 мкс снимает ~18,8 с/кадр → 10k с ~19 с до ~0,1 с/кадр, цель ≤33 мс достижима без Mass-параллелизации. Это фаза 1 исходной архитектуры («идущие без fallback»), подтверждённая числом как главный рычаг.

Приёмка фикса fallback: суточный паритет (6c: stationary p95 ≤1 м, moving report-only, ZS/TA-покрытие, RNG/брони в порядке); npcscale 10k ≤33 мс/кадр; городская пара без регрессии; контракты пробуждения (препятствие/потеря опоры → нативная физика до первого физического шага). Риск: абстрактная опора даёт дрейф позиции против физики — принимается 6c для дальних вне кадра; ближние/видимые остаются нативными.

Артефакт: `.bench-out/class-10k/` (stats с бакетами, game.log причины fallback).

## Ограничения

- Дёшево ≠ осмысленно: 10k на контенте ~1000 NPC вырождается в очередях; масштабирование контента — отдельная задача.
- Городские 8 мс не лечатся: ближние активные Full-tier нативные (вердикт D).
- Невидимость: упрощение только вне кадра; видимый LOD (N4) отклонён.
- Паритет поведения обязателен: ведущее ядро не меняет журнал симуляции.
