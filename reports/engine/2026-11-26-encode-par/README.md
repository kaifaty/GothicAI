## Коррекция диагноза

«C = параллельная запись команд (secondary command buffers)» — **неверная постановка**. Разбор 8 ноября и карта Tempest (это исследование) показывают:
- Рендер GPU-driven: ~69–79 графических команд/кадр (indirect draw на бакет). Сама запись API дешёвая.
- `encode_main` (рынок 1,628 мс, лес 1,553 мс, LTO) — преимущественно **CPU-подготовка до записи**: ветер/морфы (`preFrameUpdate`), упаковка `InstanceStorage`, частицы, свет, видимость, `prepareUniforms`.
- Secondary command buffers в Tempest **отсутствуют** (нет `vkCmdExecuteCommands`/`RENDER_PASS_CONTINUE`); есть chunks (несколько PRIMARY на буфер) и многопоточная запись transfer-буферов (UploadEngine). Кэши PSO/descriptor/bindless защищены глобальными замками; главный сериализатор — `VPoolCache::allocBindless` (линейный скан 32 слотов под мьютексом на каждый грязный draw).

Параллелить только запись ~69 команд — мало (вывод 8 ноября: «записывать команды параллельно или кэшировать их не нужно»). Реальный резерв — **параллелить/выносить CPU-подготовку** и **дедупликация дескрипторов (R3)**.

## C1: параллельный цикл ветра

`OPENGOTHIC_WIND_PARALLEL=0` оставляет цикл на вызывающем потоке; по умолчанию снимок `objectsWind` раздаётся пулу Workers (`parallelFor`, grain 64). Порядок-независимость по коду:
- матрица — чистая функция (`WorldWind::shaderMatrix`, worldwind.h:22);
- `InstanceStorage::Id::set` — memcmp/memcpy в непересекающиеся слоты `dataCpu` + атомарный `bitSet` dirty-bitmap (instancestorage.cpp:28-33,133-155);
- `DrawClusters::markClusters` — атомарный `fetch_or` (drawclusters.cpp:289-297); сферы кластеров — непересекающиеся слоты на объект;
- `TreeBoughRender::setTransform` — запись в разные узлы map без вставок (treeboughrender.cpp:173-177);
- join Workers синхронизирует записи до `commit` хранилища на главном потоке; порядок dirty-битов не влияет на результат (bitmap OR, скан при commit детерминирован).

Счётчики `computed/skipped` — атомарные, сумма та же. Кадр должен быть идентичен; приёмка — счётчики + цена по зонам OFF/ON (кадровые пары для ветра не годятся: фаза зависит от часов мира, два прогона всегда покажут разную фазу).

Бюджет: 1 диагностический прогон (выполнен) + пара OFF/ON заявками `market forest shot` (2 заявки, одна сборка; shot — проверка вида на грубую порчу). Сверх — спросить.

| lights_tick | 0,094 | 0,126 (+0,032) | 0,095 | 0,124 (+0,029) |

| encode_main | 1,359 | 1,418 (+0,058) | 1,288 | 1,341 (+0,052) |

**Отрицательно в обоих местах.** Причина: циклы малы (0,08–0,09 мс последовательно), а каждый `parallelFor` — пробуждение пула + join (~десятки мкс) под квотой заявки gq `CPUQuota=400%`; разбросанные memcpy 256 Б и обновления светов memory-bound и не масштабируются. Лишние dispatch'ы ещё и отбирают квоту у параллельного ветра (wind_prepare вырос без правки). Порог окупаемости параллелизма на стенде — заметно выше 0,1 мс последовательной работы; C1 (0,52 мс) его проходит, C2 — нет.

Правка C2 откачена полностью (включая атомарный `markAsDurtyNoSync` — он был нужен только параллельному tick). Зоны C2 оставлены: они атрибутируют остаток подготовки для будущих решений. Код движка = main + C1.

## План (по правилам: диагноз до правки)

1. **Разметка и диагноз C1 — выполнено:** зоны подготовки добавлены, прогон нашёл цель (wind_prepare 0,519 мс).
2. **Партия C1 — слита (#1842):** параллельный цикл ветра на Workers, по умолчанию ВКЛ после приёмки пользователем 2026-11-26.
3. **C2 — отклонён замером:** параллельные lights tick и копия плана storage отрицательны (+0,03/+0,02 мс lights, +0,02/+0,01 copy, wind +0,005/+0,03 от конкуренции за квоту); циклы 0,08–0,09 мс не окупают пробуждение пула под CPUQuota 4 ядра. Правка откачена, зоны оставлены.
4. **R3 (отдельно):** хэш-поиск/дедупликация `allocBindless` вместо линейного скана — снижает per-draw цену и contention при параллельной записи.
5. **Дальше (кандидаты, не первый шаг):** конвейер игровой/рендер-поток (~1,6 мс, двойная буферизация VisualObjects) и B (параллельные тики NPC) — большие проекты, решение пользователя.

## Критерии приёмки

- C1: счётчики `wind_computed/wind_skipped` те же OFF и ON (тот же набор объектов); `wind_prepare` и `encode_main` значимо ниже OFF (порог ~0,1 мс); shot-кадры без порчи растительности. Попиксельное сравнение прогонов не используется: фаза ветра зависит от часов мира и гуляет между прогонами (урок партии ветра). Суточный паритет NPC не нужен: правка только в рендере, симуляцию не трогает.
- Бюджет партии C1: 1 диагностический perf-прогон (выполнен) + пара OFF/ON (2 заявки `market forest shot`) + проверка вида в тех же заявках. Сверх — спросить.

## Ограничения

- Параллелизм подготовки требует фиксации игрового состояния до fork (DrawBuckets/InstanceStorage commit, hiddenTypes, per-fId буферы); барьеры ресурсов — у владельца (per-buffer ResourceState не видит чужие чтения).
- Metal: в encode_main сидят синхронные ожидания upload (MtBuffer::update) — другой фикс (буфер декалей в Upload-кучу / updateAsync), не параллелизм.
- Secondary command buffers — отдельный большой проект с ограниченной отдачей (69 команд); не первый шаг.

## Общее состояние циклов подготовки (код, до замера)

- `objectsWind/objectsTree/objectsLevels` — `std::unordered_set<size_t>` (visualobjects.h:332-336): для Workers нужен снимок в вектор.
- Ветер (`preFrameUpdateWind`, visualobjects.cpp:1212): LOD-тест + чистый `WorldWind::shaderMatrix` + `updateInstance`. Сам цикл порядок-независим, но `updateInstance` (306) пишет не только свой слот: `clustersMem.markClusters` (352-357) и `drawCmd.setBoughTransform` (331) — общее состояние. Параллелить можно только вычисление матриц; запись слотов и marks — либо под замком, либо serial-фаза после fork.
- Деревья (`preFrameUpdateTrees`, 937): общий кэш `fades[64]` на стекe цикла + `clustersMem.markClusters` — наивный parallel-for небезопасен.
- Уровни (`preFrameUpdateLevels`, 1046): общие `impostorDraws`, `count[]`, `shadowProbe`, `drawCmd.addClusters` — нужен редизайн, не первый кандидат.
- `prepareUniforms` (renderer.cpp:676) — только сеттеры, дешёвый.
- Workers: `parallelFor` по непрерывному массиву, grain 64, ≤128 элементов на вызывающем потоке; вложенный параллелизм не поддержан. Пул уже используется проходом поз NPC — fork в encode не должен пересекаться с ним по времени (кадр последователен: finishStep → encode).
