# Сдача руды Беннету без полной таблицы символов

Пилот для проверенной «Ночи Ворона». Условие показа и ответ `DIA_BENNET_BRINGORE` работают через подготовленный StoryGraph и состояние движка. Выдача поручения, остальные диалоги и загрузка мира продолжают пользоваться текущим путём. Формат сохранений остаётся совместимым. Основа — `main` на `192e87c98` и [перенос Daedalus](README.md).

## Что делает исходная ветка

Цепочка сверена по готовым `story-programs.json`, `storygraph/story.json`, `symbols.json` и `dialog-infos.json` из базы с отпечатком `309f56cad534329f…`. Проверенная программа имеет SHA `a1918ecb7239b6f48cb98dda5e6ff7eb7ab8099085b3d7adec603c1431de641c`.

| Запись | Значение |
| --- | --- |
| NPC | `SLD_809_BENNET`, ID 11668 |
| Диалог | `DIA_BENNET_BRINGORE`, ID 23822, порядок 9, однократный, обычный |
| Условие | `DIA_BENNET_BRINGORE_CONDITION`, ID 23823. Поручение в состоянии `LOG_RUNNING` (1), у героя есть хотя бы 5 `ITMI_NUGGET` |
| Действия | `DIA_BENNET_BRINGORE_INFO`, ID 23824. Две реплики, передача 5 единиц руды Беннету, ещё две реплики, возврат 2 единиц герою, затем `LOG_SUCCESS` (2) |

Итог для инвентарей — у героя на 3 единицы руды меньше, у Беннета на 3 больше. Эффекты ограничены репликами, передачами и изменением флага. В каталоге квестов у этой переменной `topics=[]`. Единственный вложенный помощник — `B_GIVEINVITEMS`, вызванный дважды. Выдачу поручения через `DIA_BENNET_WANNASMITHORE` оставляем вне пилота. Она по-прежнему может записывать состояние `LOG_RUNNING`.

## Перенос

1. **Собрать привязки при создании сессии.** Для проверенного SHA взять из существующих каталогов C_INFO, обе программы StoryGraph, ID NPC и руды (`ITMI_NUGGET`, 6928), поля предмета, параметры уведомлений и неизменяемые данные реплик. Сохранить узкую запись ветки с готовыми ID и проверенными зависимостями. Для пилота достаточно текущих файлов базы и их манифеста.
2. **Перенести флаг во владение движка.** Хранить `MIS_BENNET_BRINGORE` как `int32_t` в `GameScript`, привязав один раз к старому имени. Условие и ответ читают и меняют это поле напрямую. Выдача поручения, запросы моста и кодек `game/daedalus` продолжают видеть то же значение через привязку. `game/quests` сохраняет прежнюю пару ID героя и известного диалога. [Шаблон привязки](../../../OpenGothic/common/game/gamescript_activities.cpp#L12) · [Кодек сохранения](../../../OpenGothic/common/game/gamescript.cpp#L539)
3. **Подключить условие и ответ к штатному выбору диалога.** Для этой записи после выбора кандидата по ID использовать явные ссылки на говорящего и героя. В `dialogChoices()` и `exec()` выбрать нативный обработчик до поиска функции и регистрации знания через символы. Учёт известного диалога использует готовые ID. Сохранить порядок меню, очередь реплик и приоритет явной подмены режиссёра. При проверке нуля обращений используется штатный диалог с `GOTHIC_AI=0`. При включённом мосте совместимые фильтры, подмены и уведомление о выборе остаются на своей границе. [Входы диалога](../../../OpenGothic/common/game/gamescript.cpp#L813) · [Шаблон исполнителя](../../../OpenGothic/common/game/gamescript_preparedprograms.cpp#L108)
4. **Выполнить обе передачи через типизированный хост.** Использовать `NativeInterpreter`, явные `Npc&` для `SELF` и `OTHER`, очередь `AI_OUTPUT` с текущим порядковым номером и общий алгоритм `InventoryTransfer`. Разрешить два последовательных вызова с готовым ID руды. Для пустого стека добавлять экземпляр из подготовленной записи `ITMI_NUGGET` с тем же ID и полями, что у штатного конструктора. Для заполненного стека использовать прежнее слияние. Общую фабрику предметов оставить для остальных путей. Сохранить оба уведомления о передаче и данные совместимости `GIVER`, `TAKER`, `ITEM` и `InventoryTransfer::Variables`. Подготовленные узкие привязки для этих значений создаются при инициализации. Перед первым эффектом проверить наличие двух программ, допустимые вызовы и подготовленную запись руды. Отказ до исполнения оставляет инвентари и флаг прежними. [Передача предмета](../../../OpenGothic/common/game/gamescript_inventorytransfer.cpp#L8) · [Создание при пустом стеке](../../../OpenGothic/common/game/inventory.cpp#L251)

Запрет на обращения к полной таблице действует во время проверки условия, регистрации известного диалога, исполнения ответа и обеих передач, включая создание пустых стеков. Начальная сборка привязок, загрузка мира и сохранения используют текущее полное состояние. В изолированном контракте тот же исполнитель и те же операции не получают `DaedalusScript` или `DaedalusVm`. В игровом контракте установить запрет на `find_symbol_*` и перечисление символов на границе до выбора обработчика. Проверить также отсутствие обхода через `vm.global_*` в самом хосте. Ноль инструкций Daedalus фиксируется отдельно.

## Сохранения и приёмка

**Вход A, исторический сейв.** Неизменённый архив v55 из [`load_rewind`](README.md), `native-game-runtime/load_rewind-cf8df3e53/run/save_slot_1.sav` на общем хранилище. SHA-256 `c2852f4c009f23225e1c9c70f564ca36b4c12e8220736d1c72a1dbfce8d3372f`. Проверено чтением архива. Мир `NEWWORLD`, глава 1, Беннет присутствует, `MIS_BENNET_BRINGORE=0`, секция `game/daedalus` есть, `game/symbols` отсутствует. Загрузить исходные байты через `GameSession(Serialize&)` и проверить восстановление мира, флага и отсутствие предложения о сдаче. Исходный файл использовать только для чтения.

**Вход B, сейв прежней схемы с активным поручением.** На допилотной игровой части `192e87c98` в профиле `OPENGOTHIC_LEGACY_DAEDALUS=ON` загрузить копию A. Фикстура задаёт герою `GIL_SLD`, талант кузнеца и ровно 5 единиц руды через штатный инвентарь. Начать поручение обычным `DIA_BENNET_WANNASMITHORE` и проверить `MIS_BENNET_BRINGORE=1`. Убрать руду у Беннета штатной операцией инвентаря для случая с пустыми стеками. Сохранить через `GameSession::save` в отдельный слот. Эта фиксированная подготовка создаёт сейв старой игровой сборкой и даёт ненулевую строку для проверки загрузчика. Вход A хранится побайтно. Вход B пишет штатный сериализатор. Для запуска можно перенести на допилотную ревизию только тестовую фикстуру подготовки и сверки, сохранив игровой код эталона.

| Проверка | Ожидаемый результат |
| --- | --- |
| Исходная VM на копии B | Прогнать условие и ответ при `GOTHIC_AI_STORYEXEC=0` и `OPENGOTHIC_ACTIVITY_RECORDS=0`. Положительная трасса должна подтвердить исполнение обоих исходных вызовов `B_GIVEINVITEMS`. Сохранить порядок реплик, уведомлений, изменений инвентарей и флага как эталон |
| Нативная сборка на той же B | Загрузить файл через обычный читатель, увидеть `LOG_RUNNING` в типизированном поле и выбрать ответ штатным путём. Проверить промежуточные количества `0 / 5` после первой передачи и итог `2 / 3` для героя и Беннета, тот же порядок эффектов и `LOG_SUCCESS`. Обе выдачи проходят через создание пустого стека. Внутри границы 0 обращений к таблице и 0 инструкций |
| Слияние стеков | В дополнительном случае того же контракта герой начинает с 6 единицами, Беннет с 1. Сверить `1 / 6` после первой передачи и `3 / 4` в конце. Проверить сохранение характеристик заполненных стеков при пополнении |
| Сохранение после сдачи | Создать новый слот, уничтожить сессию и загрузить его. Восстановлены `LOG_SUCCESS`, количество руды, известный диалог и ссылки передачи. Повторная проверка меню скрывает предложение, количества и очередь уведомлений сохраняются |
| Условие и приоритеты | Изолированный контракт проверяет флаг `0/1/2`, количество `4/5`, несоответствие ID диалога и отсутствующую зависимость до эффектов. Игровой контракт проверяет сохранение приоритета явной подмены режиссёра отдельно от трассы со снятым мостом |

Добавить прицельный случай в существующий [`gothic-placed-items-contract`](../../../OpenGothic/tests/placed_items_contract.cpp#L3739) с явным путём к неизменённому файлу A и рабочей папкой задачи. Один безоконный запуск совместимого профиля для подготовки B и эталона, один безоконный запуск штатного профиля для контракта и перезагрузки. Эталон использует готовую полную базу с тем же SHA программы, штатный профиль — готовую базу без байткода. До 12 минут Ryzen на профиль через `gq`. Один штатный `load_rewind` на той же копии A, до 4 минут окна Ryzen, отдельно проверяет обычный вход и загрузку через игру. Игровая сверка ветки выполняется контрактом. Бюджет свежих импортов и суточных прогонов — 0. Для CI применяются `scripts/check.py plan/run`, проверка `tests` и прежняя проверка линковки штатных целей, если меняется состав зависимостей.
