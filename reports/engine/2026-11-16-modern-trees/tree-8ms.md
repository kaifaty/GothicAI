# Лес из 1 024 елей в 8 мс: оставшиеся варианты

Дата: 2026-11-25. Статус: исследование закончено; решения пользователя приняты, исполнение начато. Бюджет прогонов и очереди исследования — 0: всё ниже взято из кода, открытых PR и сохранённых прогонов на Ryzen. Цель — полный кадр ≤ 8 мс на стенде `perf-trees` с 1 024 елями (RTX 3080, Vulkan, TAAU 1280×720 → 2560×1440). Заметка сводит состояние после мер 18–25 ноября и размечает оставшиеся варианты; она продолжает [исследование способов](tree-optimization.md), [цену теней](tree-shadow-cost.md) и план 8 мс от 22 ноября (раздел «Плотный лес при 720p» в [плане деревьев](../../../docs/trees-plan.md), приходит с PR #1705).

**Решения пользователя 2026-11-25:** цель 8 мс — по медиане (P50); огрубление силуэта тени на средней дистанции (A1) и изменения маски тумана до ~6 % текселей (A2 m4) приемлемы; снижение внутреннего разрешения (E) запрещено. Партия 1 и диагностика B1 поставлены исполнителям Codex: ветки `codex/tree-8ms-batch1` (от лестницы PR #1705) и `codex/tree-8ms-b1-diag` (от main).

## Коротко

1. **Сейчас кадр не укладывается в 8 мс ни в одном окне.** Прогретый лес: P50 11,3–11,5 мс, P95 12,2–12,5; проход героя P50 10,8–11,0; под елью при низком солнце P50 14,2–14,6. Доля кадров в бюджете 8 мс — 0 %. Разрыв по медиане — около 3,4 мс, по P95 — около 4,5.
2. **Одной меры нет.** Крупнейшие невлитые рычаги: L4 для средней хвои в солнечных тенях (измерено −1,0 мс кадра изнутри) и отсев скрытой хвои, которая даёт 82,8 % поданных треугольников и ноль пикселей (оценка −1,0…−1,6 мс, нужен прототип). Остальное — по 0,1–0,5 мс.
3. **Второй потолок — процессор.** Главный поток вне ожидания слота — около 9,3 мс в прогретом лесе. Даже при GPU 8 мс кадр не уложится, пока CPU не станет ≤ 8: нужно снять ещё ~1,3 мс вне рендера деревьев.
4. **Полтора десятка путей уже проверены и не дали воспроизводимого выигрыша** (раздел 2). Повторять их прогонами не нужно.
5. **Реалистичный путь** — партия теней (−1,3…−1,9 мс) + скрытая хвоя (−0,7…−1,3 мс) + мелочи (−0,2…−0,4 мс) + CPU (−1,3 мс). Сумма покрывает разрыв по медиане; P95 и низкое солнце остаются отдельной работой.

## 4. Оставшиеся варианты

### A. Солнечные тени — атлас 2,9 мс, потолок 4,2 мс

Потолок измерен 22 ноября: полное отключение солнечных теней елей даёт кадр 12,84 → 8,68 мс изнутри и 12,31 → 9,62 на проходе (архив `fir-cpu-sun-cost-20261122T162054Z`). Всё ниже — доли этого потолка.

**A1. L4 для средней хвои в солнечных m0–m6 — приоритет 1.** Замеряно 22 ноября (архив `fir-mid-sun-20261122T165000Z/abba/`): ели высотой 225–914 px при 1080p (изнутри 195 из 1 024) отдают солнцу L4 (1 180 треугольников) вместо L1/L2 (14 412 / 5 189). Солнечных треугольников хвои −24,6 % изнутри и −23,7 % на проходе; `VSM-rendering` 5,01 → 3,95 и 3,90 → 3,18; **кадр −1,02 / −0,70 мс по среднему, −1,03 / −0,77 по P95**, воспроизведено в обеих парах A/B/B/A. Это 24–25 % потолка. Правило партии 1 выбирает диапазон тени иерархии (`treelevelband.h`, `visualobjects_levelband.cpp`) поверх лестницы PR #1705. В полосе полной хвои L4 занимает долю L1. В полосах L1/L2 и L2/L4 одна сторона подаёт целый L4. Риск для вида: силуэт тени на средней дистанции грубеет, мелкие просветы заполняются; приёмка — клип отлёта и возврата через полосу 225–914 px и пары под елью, смотрит пользователь.

**A2. Геометрия записей, нужных только туману — приоритет 2.** Разметка тумана добавляет 120 853 пары и 6,22 млн треугольников изнутри; атлас без неё 2,05 против 3,39 мс (замер 25 ноября, архив `sun-fog-demand/result-confirm/`). L4 на m5–m6 уже влит (−0,43 мс атласа). Остаток: m4–m7 дают ещё 3,93 млн добавленных треугольников изнутри. Варианты по возрастанию риска:
- L4 на m4 (диапазон m4–m6 целиком): атлас 3,399 → 2,788, кадр P50 11,877 → 11,230, но маска тумана меняется в 5,745 % текселей, максимум 18 из 32 шагов (архив `sun-fog-lod/result-lod-paired/`). Против влитого m5–m6 добавляет ~0,15 мс кадра, но меняет 5,7 % текселей маски вместо 1,8 %.
- Отдельная грубая крона или теневой импостер только для записей без приёмников поверхностей: импостер — 2 треугольника вместо 1 408, глубина уже запечена в атлас; нужна ориентация к солнцу (нынешний импостер обращён к камере) — средняя правка `DrawCommands` и шейдеров. Приёмка — маска тумана и полное освещение тумана в движении, прямые тени поверхностей совпадают.
- Более грубые страницы тумана (сдвиг m4–m7 на уровень): −0,19 мс, но 5,6 % текселей и до 17 шагов — хуже, чем L4 при том же выигрыше; не рекомендуется.

**A3. Ближняя L1 на m4–m6.** Замеряно 22 ноября (архив `fir-near-m456-20261122T180706Z/abba/`): P95 кадра −0,245 мс на проходе, изнутри неопределённо; `VSM-rendering` 3,81 → 3,57 и 3,11 → 2,84. Маленькая мера после A1; контроль уже использует среднюю L4.

**A4. Более узкая граница глубины тумана.** Сейчас для всех отсчётов эпиполярной линии берётся `min(dBegin, dEnd)`, хотя глубина видимого участка меняется вдоль неё. Более точная граница уменьшит запросы страниц тумана. Числа нет; нужна сверка полного освещения тумана и прямых теней. Дешёвая правка шейдера, но выигрыш неизвестен.

**A5. Квантование поворота солнца + кэш статичных страниц.** Только если A1–A4 не хватит. При живых часах точное переиспользование 0 %; квантование шага солнца рискует ступенчатым движением тени, а кэш ламп показал +1,6 мс на инфраструктуре. Крупная правка с высоким риском; начинать с диагностики доли пригодных плиток при квантованном солнце.

### B. Главный вид — `GBuffer` 2,8–2,9 мс

**B1. Скрытая хвоя против глубины, содержащей ближние кроны — приоритет 2, после диагностики.**

Факты (замер 22 ноября, архив `fir-view1-pixels-20261122T184646Z/`): из 1 024 елей **990 не дают ни одного пикселя**; 626 из них уже не подают хвою (кластерное отсечение), а **364 ели подают 3 671 029 треугольников хвои — 82,77 % всей поданной хвои — и не выигрывают ни одного пикселя**. Видимы 34 ели, 763 999 треугольников.

Почему нынешнее отсечение их не видит: ранняя глубина (`HiZ-history-depth`) рисует победителей прошлого кадра, но **кроны со срезом пропускает** — срез кадра ещё не выбран (`finishBoughVisibility` идёт после ранней отрисовки, [renderer_hiz_history.cpp](../../../OpenGothic/common/graphics/renderer_hiz_history.cpp)). В 489 014 из 489 016 пикселей видимой хвои ранняя глубина дальше самой хвои (PR #1705). Против этой же глубины тестируют лапы режимы PR #1710 и трава — поэтому отсечение по глубине изнутри даёт 0. Геометрия, закрывающая задние ели, появляется только в основном проходе.

Кандидат: **рисовать в ранней глубине срез прошлого кадра** (выбор хранится по экземплярам, геометрия обеих версий уже в буферах, ветер считает тот же шейдер), затем тестировать узлы текущего среза по свежей пирамиде до записи в `boughEmit`. Это двухфазный HZB ([UE 5.1](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-5.1-release-notes), [UE 5.2](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-5.2-release-notes)) на уровне узлов: отвергнутые узлы можно перепроверить по свежей глубине после ранней отрисовки, как 3б перепроверяет кластеры. Отсечение действует только в главном виде: скрытая от камеры ветвь может отбрасывать видимую тень.

Оценка: ранняя глубина +0,3–0,5 мс (видимые кроны ~0,76 млн треугольников), `GBuffer` −1,0…−1,6 мс (3,67 млн × 0,45 нс за вычетом цены теста). Чистыми −0,7…−1,3 мс изнутри; на проходе меньше из-за движения камеры. **Сначала диагностика одним прогоном:** посчитать узлы, доказуемо закрытые по итоговой пирамиде прошлого кадра (`hiz.hiZ` уже содержит кроны) — это верхняя граница без изменения ранней отрисовки. Если ≥ 20 % поданной хвои — прототип и серия A/B/B/A.

Приёмка: ноль потерянных пикселей, побитовое совпадение глубины и ID до TAAU на тех же тиках, ветер, поворот, телепорт, сброс истории; клип прохода смотрят ведущий и пользователь. Риск: рост ранней отрисовки и ложное отсечение при рассогласовании фаз ветра — коробка узла берётся с запасом ветра, как в PR #1710.

**B2. Карта нормалей только у ближней хвои.** Замер 25 ноября (архив `tree-normal-cost-20261125/result-timed/`): отключение чтения карты нормалей у всех крон даёт `GBuffer` 2,912 → 2,782, кадр 11,362 → 11,244 (−0,12 мс). В партии 1 обычный GLB сохраняет карту на L0/L1. В компактном срезе на вершинные нормали переходит вся крона ниже авторского порога L2. У стендовой ели он равен 200 px во внутреннем кадре 720p. Нормали оболочки уже есть в вершинах. Приёмка — пары кадров на порогах.

**B3. Тесный контур карточек (6–8 вершин).** Закрашенная площадь падает примерно вдвое, но треугольников становится больше, а `GBuffer` на этом стенде ограничен геометрией (0,45 нс на треугольник среза). Ожидание малое; контентная правка генератора. Низкий приоритет.

**B4. Ранний импостер (вариант В, 100 px).** Правка только набора: помогает внешним видам (с 300 м прогноз хвои ×0,01 к L0–L4), изнутри леса почти ничего не меняет. Вид принимает пользователь; атлас на 100 px даёт 0,68 текселя на пиксель на верхнем крае стыка.

### C. GI — 2,0–2,3 мс

Дешёвые пути исчерпаны (раздел 2). Осталось:
- **Удержание проб без обвала доступности.** Редкий пересвет экономит пересвет (P95 суммы GI 2,52 → 2,00), но пробы, нужные соседям, вытесняются и трассируются заново. Предмет проверки — ранний сигнал изменения света (нынешний порог видит перемену после выбора следующей порции направлений) и продление жизни проб, созданных по запросу соседей, без блокировки новых запросов. Верх ~0,5 мс, риск запаздывания при смене суток (уже наблюдалось +32 % яркости через 0,5 с).
- **Длина солнечного луча из точки попадания — 500 м.** Ограничение по вкладу в тексель (дальние заслонки важны только при низком солнце). Диагностика чтений альфы по расстоянию уже есть: от 5 м заменяемы 19,8 % чтений изнутри, из них 790 850 — лучи к солнцу. Числа выигрыша нет.
- **Микрокарты непрозрачности.** По [прежнему исследованию](tree-optimization.md#что-не-подходит) аппаратное ускорение — с RTX 40; на RTX 3080 выигрыша ждать не стоит. Расширение может быть доступно — проверять возможности карты прежде чем тратить прогон.

Ожидание ≤ 0,3–0,5 мс при высоком риске для света. После A и B.

## 5. Порядок и бюджет прогонов

Замеры — по бюджету [AGENTS.md](../../../AGENTS.md#тесты): точное число прогонов и минут, один контроль на партию, цена партии — общим прогоном после слияния. Стенд прогревает карту перед первым замером. Пары сравниваются по обе стороны середины серии.

| Партия | Что | Прогоны | Лимит очереди |
|---|---|---:|---:|
| 1 | Довести до продукта замерянное: A1 (средняя L4) + A2 (L4 тумана m4) + B2 (нормали дальних). Серия C/A1/F/F/A1/C, где C — контроль, F — полная партия. Диагностика пар и маски тумана отдельно от таймингов | 6 + 1 | до 6 мин |
| 2 | Диагностика B1: узлы, доказуемо закрытые по итоговой пирамиде прошлого кадра | 1 | до 2 мин |
| 2б | Если диагностика ≥ 20 %: прототип B1, серия A/B/B/A | 4 | до 5 мин |
| 3 | CPU (D) — отдельный план, вне этой заметки | — | — |

В партии 1 прогрев длится не меньше 50 с. Разности C − A1 и C − F проверяются в обеих парах. Разность средних A1 и F оценивает общий вклад A2 и B2. Если вся серия вместе с диагностикой не укладывается в 6 минут, остаётся C/F/F/C. При расчёте времени кадра первые 250 мс каждого окна исключаются. Частота SM пишется по окнам. Диагностика сравнивает два атласа на одном тике при включённом A1, чтобы проверить точное совпадение прямой солнечной тени и измерить изменение маски при переходе тумана с m5–m6 на m4–m6.

Итого первых двух партий: **до 12 прогонов, ~13 минут очереди**. Правило остановки: если партия 1 даёт меньше 1 мс или диагностика B1 меньше 20 % — остановиться и показать числа пользователю, третий круг подбором не начинать. Вид каждого шага (тени средней дистанции, маска тумана, нормали дальних крон) принимает пользователь по клипу и парам; до него смотрит ведущий.

Ожидаемый итог партии 1 + B1: −1,7…−3,2 мс изнутри (P50 11,4 → 8,2–9,7). До 8 мс по медиане остаётся CPU и мелочи; P95 и низкое солнце — следующая работа.

## 6. Ограничения и открытые вопросы

- **Mac не измерен вовсе.** На Metal нет меш-шейдеров: компактная подача среза там не работает, цена другая. Все числа — RTX 3080.
- **Пилот выключен по умолчанию.** Числа выше — с включённым пилотом. Включение даёт принятые пользователем плавные переходы, но без отсева скрытой хвои стоит +2,9 мс `GBuffer` изнутри против выключенной схемы (замер 21 ноября). После B1 и партии теней нужен один сравнительный прогон «выкл против вкл со всеми мерами» для решения об умолчании.
- **8 мс — полный кадр**, включая симуляцию, запись команд и показ; цель только по GPU была бы легче. Метрика недавних опытов — доля интервалов в бюджете 8 мс (сейчас 0 %).
- **Низкое солнце — худший вид** (14,2 мс): длинные тени раздувают пары m4–m6, солнечные лучи GI идут на 500 м. Партия 1 помогает и там (L4 тумана m4–m6: атлас 6,25 → 5,70, кадр P50 14,93 → 14,52), но отдельной цели по этому виду нет.
- Числа одиночных прогонов помечены в источниках; стандарт принятия меры — воспроизводимость в обеих парах A/B/B/A после прогрева.

Решения пользователя (2026-11-25):
1. Цель 8 мс — **по медиане (P50)**. P95 и низкое солнце — следующая работа после достижения медианы.
2. Изменения силуэта тени на средней дистанции (A1) и маски тумана до ~6 % текселей (A2 m4) **приемлемы**; приёмка всё равно по клипу и парам.
3. Снижение внутреннего разрешения (E) **запрещено**.

## Диагностика B1: скрытая хвоя по глубине прошлого кадра

Штатная `hiz.hiZ` строится из ранних заслонов до отрисовки крон. Для диагностики `OPENGOTHIC_BOUGH_HIZ_DIAG_EVERY=16` сохраняет отдельную пирамиду максимумов `R32F` после полного `GBuffer` и матрицу камеры с джиттером этого кадра. При TAAU 1280×720 база пирамиды 128×64, один её тексель покрывает до 16×16 пикселей глубины. После разрыва истории нужен новый опорный кадр.

Шейдер повторяет штатный выбор среза. Для узлов компактной кроны он проецирует коробки экземпляров с полным запасом хода вершин на ветру по правилу PR #1710. Для каждой коробки проверяются все пересечённые тексели с припуском в один пиксель. Узел считается закрытым, только если его ближайшая глубина строго больше максимума по этому следу с учётом погрешности проекции и шага D16. Фон и неопределённая проекция сохраняют узел. Коробки целиком за плоскостью отсечения текущего кадра учитываются отдельно. Знаменатель включает всю поданную хвою, включая кроны, которые пошли целым GLB. На диагностическом кадре он сверяется со штатным `tree_bough_triangles` после fence.

Первый запуск на Ryzen (`gq quiet` `38347eefea3c`) открыл мир и выставил TAAU 1280×720 → 2560×1440, но завершился до первого диагностического кадра с `Invalid texture`. При переносе исходников сохранились старые даты файлов. В одном бинарнике `buildHiZ` обращался к `hiz.hiZ` по смещению `0x51c8`, а `drawTreeHistory` по `0x52a0`. Чистая сборка в отдельном каталоге устраняет смешение объектных файлов. Журнал исходной заявки и контрольные суммы лежат в `/mnt/shared/gothic-ai/tree-8ms-b1-diag/output/`.

В чистой сборке `buildHiZ` и `drawTreeHistory` обращаются к одному смещению `0x52a0`. Все 643 штатных SPIR-V-модуля побитово совпали со сборкой исходного `main`, модуль диагностики прошёл `spirv-val`.
