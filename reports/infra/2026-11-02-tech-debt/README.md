# Учёт техдолга: замеры в CI и issues без дубликатов

**Цель.** Долг виден и не теряется при темпе ~170 коммитов в день. Еженедельная джоба GitHub Actions замеряет код и документы, по каждой находке ведёт один issue и не плодит дубликатов. Долг, взятый сознательно, агент записывает сам в том же PR (правило в `AGENTS.md`). Решение пользователя 2026-11-02.

## Как это делают другие

- **Горячие точки = размер × частота правок** (A. Tornhill, «Your Code as a Crime Scene»; CodeScene). Большой, но холодный файл почти ничего не стоит: процент платят только те, кто его правит. Холодный долг не гасим.
- **Замечание на каждое нарушение** (SonarQube, Code Climate) даёт шум, и трекер перестают читать. Их же приём «Clean as You Code» — строгость к новому коду при неизменном старом — это наш будущий храповик в PR.
- **Дубликат по заголовку** (todo-to-issue и похожие экшены): правка заголовка рождает дубль. Боты вроде Renovate держат скрытую метку в теле своего issue и находят его по ней.
- **GitHub API:** у закрытого issue есть причина закрытия (`stateReason` в `gh --json`). Правка тела issue уведомлений не шлёт, комментарий шлёт. Issue от `GITHUB_TOKEN` создаёт `github-actions[bot]`, и других workflow он не запускает.

## Способ

`scripts/debt.py scan` печатает находки в JSON, `scripts/debt.py sync` сверяет их с issues. Пороги и исключения лежат в конфиге рядом со скриптом. У каждого вида свой порог открытия и более низкий порог закрытия: гистерезис, чтобы issue не мигал. Пороги откалиброваны на замерах выше.

| Вид, ключ | Открыть | Тяжёлый уровень | Закрыть | Сегодня |
|---|---|---|---|---:|
| `hotspot:<путь>` | ≥ 2 500 строк и произведение ≥ 300 000 | произведение ≥ 1 200 000 | произведение < 150 000 или < 2 000 строк | 8 |
| `doc-now:<путь>` | «Как работает сейчас» ≥ 60 КБ | ≥ 120 КБ | < 20 КБ | 6 |
| `doc-file:<путь>` | `docs/README.md` и `docs/features.md` ≥ 150 КБ | ≥ 300 КБ | < 60 КБ | 2 |
| `ruff:<проект>` | ≥ 10 нарушений | ≥ 100 | 0 | 1 |
| `orphan-scripts` | ≥ 1 скрипт без ссылок | — | 0 | 1 |

Всего сегодня 18 находок. Исключения: `OpenGothic/lib`, `reports/`, `research_notes/`.

**Сверка (sync).** Находку ищут по скрытой метке в теле issue, а не по заголовку. Читаются все issues с меткой `долг`, открытые и закрытые.

| Состояние | Действие |
|---|---|
| Ключа нигде нет | Создать issue с метками `долг` и `долг-авто`. Не больше 5 за прогон, тяжёлые первыми, остальные ждут следующего прогона |
| Есть открытый issue | Обновить в теле блок замеров «было → стало». Комментарий — только при переходе на тяжёлый уровень |
| Закрыт как `completed`, находка выше порога открытия | Переоткрыть с комментарием |
| Закрыт с другой причиной (`not_planned`, `duplicate`) | Не трогать, пока число не вырастет в 1,5 раза от записанного при закрытии |
| Свой открытый issue, находка ниже порога закрытия | Комментарий и закрытие как `completed` |
| Issue без `долг-авто`, но с ключом | Находка считается записанной. Ничего не создавать и не менять |

**Сбои.** Если чтение issues не удалось или пришло неполным, прогон не пишет ничего: неполное чтение — главный источник дублей. Создание в одном прогоне не повторяется. При ошибке прогон падает, а следующий заново читает список и доделывает. Повторный прогон без изменений в коде ничего не пишет.

**Тело issue.** Числа находки, частота правок как мера процента, пороги открытия и закрытия. Поля «процент» и «как погасить» пусты — их заполняет еженедельный разбор. Скрытые `<!-- debt-key: … -->` и `<!-- debt-data: {json} -->`: из последнего берётся «было» и число на момент закрытия.

**Запуск.** Cron по понедельникам в 06:00 UTC и `workflow_dispatch`; запись в issues — только на `main`. На PR, который меняет сам `debt.py`, его конфиг или workflow, джоба идёт в режиме `--dry-run` и кладёт план в сводку джобы: последствия правки порогов видны до мержа.

## Приёмка

1. Тесты на поддельном GitHub API покрывают каждую строку таблицы сверки, лимит 5 созданий, неполное чтение (ноль записей) и повторный прогон (ноль записей).
2. `scan` на `main` даёт находки из таблицы «Сегодня» с точностью до коммитов, которые влили после замера.
3. План `sync --dry-run` против живого репозитория пользователь видит до того, как джоба начнёт писать.
4. Первый живой прогон создаёт не больше 5 issues. Сразу за ним ручной прогон: 0 созданий, 0 комментариев.
