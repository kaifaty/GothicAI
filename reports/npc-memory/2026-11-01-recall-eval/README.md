# Замер поиска в памяти NPC (`recall`) и выбор модели эмбеддингов, 2026-11-01

**Вопрос.** Насколько хорошо `MemoryStore.search` находит старые реплики NPC по запросу `recall{query}`. Хватит ли поправить поиск по словам или нужны эмбеддинги, и какие — для русского. Повод — внешний разбор репозитория: «поиск по совпадению слов плохо ловит смысловые связи».

**Итог.**
- **Словами поиск работает:** на вопросах теми же словами текущий поиск почти не ошибается.
- **Пересказ без общих корней он находит в 22 из 50 случаев,** обычно на 4–6 месте, то есть случайно. BM25 со стеммером Snowball добавляет одно попадание.
- **Эмбеддинги находят 36–47 из 50.** Лучшая модель на наших репликах — **FRIDA** (ai-forever, 823 млн параметров, MIT): 47 из 50 на истории одного NPC и 45 из 50 на длинной смешанной.
- **Где считать:** FRIDA — на `dev-ubuntu`, на видеокарте в bf16, около 1,5 ГБ видеопамяти. BM25 остаётся запасным путём.
- **Если видеопамяти жалко:** multilingual-e5-large (1 ГБ) или USER2-base (0,3 ГБ, быстра и на CPU).

## Как поиск работает сейчас

`DialogueManager._recall` ([dialogue.py](../../../server/src/gothic_ai/dialogue.py)) вызывает `MemoryStore.search` ([memory.py](../../../server/src/gothic_ai/memory.py)) по репликам старше тех, что модель уже видит. В подсказке — до 40 последних реплик, при переполнении старшие сворачиваются в сводку, 16 остаются дословно. Поиск устроен так:
- просматривает до 2000 последних реплик этого NPC в ветке;
- корень слова — первые четыре буквы слова от трёх букв (`STEM = 4`);
- вес реплики — сколько корней запроса встречается в её тексте как подстрока;
- отдаёт шесть лучших и добивает до шести самыми свежими.

Стоп-слов нет, вес редких слов не учитывается. Служебные заметки (`developer`: «[Новая встреча с героем, день 1, 08:21]», «[Герой перебил тебя; ты успел сказать: …]») ищутся наравне с речью. В выгрузке их 466 из 959 строк.

## Данные и набор вопросов

- **Истории.** Реплики из `~/.local/share/gothic-ai/memory.sqlite3` на Mac: 959 уникальных строк, 806 разных текстов, пять NPC. В git их нет — там речь игрока, — выгрузка лежит в `~/.local/share/gothic-ai/evals/recall/messages.json`, команда — в шапке [`recall_eval.py`](../../../scripts/recall_eval.py).
  - **own** — все реплики одного NPC из всех веток подряд: Кавалорн 435 строк, Ксардас 170. Так выглядела бы долгая игра, в которой герой много раз с ним говорил.
  - **mixed** — те же вопросы, но в историю добавлены реплики остальных NPC (959 строк): замена длинной игры с посторонним материалом.
- **Вопросы** — [queries.json](queries.json): 25 тем, 83 вопроса в четырёх видах:
  - `same` (25) — словами самих реплик: «кинжал за пять золотых», «мантия»;
  - `form` (8) — другие формы и соседние слова: «кинжалом из сундука», «после падения барьера»;
  - `para` (25) — пересказ без общих корней: «нож, который ты мне продал», «твой балахон», «попойка, выпивка»;
  - `para2` (25) — второй пересказ на каждую тему, добавлен для выбора модели, чтобы разница между моделями не тонула в шуме: «клинок, что ты уступил за горсть монет», «предлагал вместе напиться».
- **Разметка.** У каждой темы есть регулярное выражение по тексту реплик, написанное по чтению истории независимо от вопросов. Попадание — хотя бы одна подходящая реплика среди шести, которые вернул метод. MRR — средняя обратная позиция первой подходящей.

Добивка свежими репликами не дала ни одного попадания: в длинной истории нужная строка среди свежих не оказывается. В первом круге, где было только 25 пересказов, multilingual-e5-small нашла 14 из 25 в own и 10 из 25 в mixed. Слияние BM25 с bge-m3 через RRF на пересказе было не лучше чистой bge-m3. Флаг `--hybrid` повторяет это слияние для всех моделей. Полная таблица по каждому вопросу — вывод `recall_eval.py`.

**Почему текущий поиск промахивается — два примера из истории Ксардаса:**
- «деньги» → корень `день` → все шесть ответов вида «[Новая встреча с героем, день 1, 08:21]». Реплика «Золота при себе у меня тоже нет» не находится.
- «твои исследования» → корень `твои` совпадает чаще, чем `иссл`, и при равном весе побеждают свежие строки. В ответе «Я не намерен слушать твои пошлости», а «мои исследования могут дать тебе больше» — нет.

**Что видно из таблицы:**
- **Словами задача почти решена.** На `same` и `form` все методы дают 24–25 из 25 и 7–8 из 8.
- **Пересказ — разрыв, который лексика не закрывает.** BM25 со Snowball прибавляет одно-два попадания из 50. Стоп-слова снижают счёт: часть «попаданий» лексики случайна и держится на служебных словах вроде «кто» и «твой».
- **На наших репликах порядок моделей не тот, что в публичных рейтингах.** На поиске ruMTEB впереди bge-m3 и USER-bge-m3: 74,8 и 73,6 против 67,1 у e5-base. У нас обе в хвосте. Рейтинги собраны на формальных текстах, а у нас короткие разговорные реплики с ошибками распознавания: «икшаешься», «пивасиком». Поэтому решает свой набор.
- **В длинной истории пересказ теряется у всех, у FRIDA меньше всего:** 47 → 45 из 50, у e5-large 45 → 39, у e5-base 41 → 33.

**Насколько надёжен отрыв FRIDA** — парный знаковый тест по 50 пересказам: считаются вопросы, где нашла одна модель, а другая нет.

| пара | own | mixed |
|---|---|---|
| FRIDA — e5-large | 3 : 1, p = 0,63 | 8 : 2, p = 0,11 |
| FRIDA — USER2-base | 7 : 1, p = 0,07 | 8 : 1, p = 0,04 |
| FRIDA — e5-base | 8 : 2, p = 0,11 | 14 : 2, p = 0,004 |

FRIDA надёжно лучше e5-base и почти надёжно лучше USER2-base. От e5-large она впереди во всех цифрах, но на таком наборе это ещё не доказано.

## Выбор модели

Замеры на `dev-ubuntu`: запрос — среднее из 20, CPU — два ядра (`taskset -c 0,1`, `OMP_NUM_THREADS=2`), реплики — пачками по 32.

| модель | параметры, вектор | видеопамять (веса) | RTX 3090 | CPU: запрос | CPU: реплика | лицензия |
|---|---|---|---|---|---|---|
| FRIDA | 823 млн, 1536 | 1,53 ГБ, bf16 | 12,8 мс | 473 мс | 325 мс | MIT |
| multilingual-e5-large | 560 млн, 1024 | 1,04 ГБ, fp16 | 7,2 мс | 170 мс | 136 мс | MIT |
| USER2-base | 149 млн, 768 | 0,28 ГБ, fp16 | 9,7 мс, bf16 | 82 мс | 61 мс | Apache 2.0 |
| multilingual-e5-base | 278 млн, 768 | ~0,6 ГБ, fp16 | 3,2 мс | 37 мс | — | MIT |

- **FRIDA нельзя запускать в fp16:** вектор расходится с fp32 (косинус 0,958; модель на основе T5). В bf16 косинус 0,998 — можно. Набор считался в fp32.
- **Префиксы обязательны** и стоят в `PREFIXES` скрипта: FRIDA и USER2 — `search_query: ` / `search_document: `, e5 — `query: ` / `passage: `.
- **Место в базе:** вектор FRIDA — 6 КБ на реплику в float32, 3 КБ в float16. 10 тысяч реплик — 30–60 МБ; перебор в numpy — миллисекунды.
- **Видеопамять на `dev-ubuntu`:** сейчас занято 13,4 из 24 ГБ (Gemma и Strands), так что FRIDA помещается. Цель «всё на одном ПК от 16 ГБ» туже: Gemma и Strands уже берут около 14 ГБ. Там FRIDA придётся считать на CPU — 0,5 с на запрос рядом с шагом модели в 4 с терпимо, — или взять e5-large либо USER2-base.

**Не проверены:**
- EmbeddingGemma-300m — закрыта на Hugging Face, лицензию Gemma нужно принять вручную;
- GigaEmbeddings (3 млрд) и Qwen3-Embedding 4B/8B — велики для нашего бюджета видеопамяти;
- jina-embeddings-v3 — некоммерческая лицензия.

## Ограничения замера

- **Вопросы и разметку писал я, зная устройство поиска.** Второй пересказ я писал до прогона моделей.
- **Настоящих запросов `recall` в логах нет** — ни на Mac (`~/Library/Logs/GothicAI`), ни в логах e2e на Ryzen. Как модель формулирует запрос, я предположил: короткая тема или вопрос героя.
- **В реальной игре поиск пока почти не работает.** Каждая ветка в базе — новая игра с первого дня, в ней 5–20 реплик с одним NPC, до свёртки в сводку дело не доходит. Истории own и mixed склеены из многих веток и моделируют будущее, а не сегодняшнюю игру.
- **Не измерены:**
  - поиск по знаниям — `knowledge.recall` ищет свои корни (слово без одной-двух последних букв) подстрокой в тексте тем, с теми же слабостями;
  - качество сводки, которую модель переписывает по кругу в 1200 символов.

## Что делать дальше

1. **Сервис эмбеддингов на `dev-ubuntu` с FRIDA в bf16,** пользовательский юнит, как у остальных моделей. Так требует [AGENTS.md](../../../AGENTS.md): модели игры живут там, на Mac — ни одной.
   - Векторы хранить в той же SQLite, в отдельной таблице по хэшу текста: ветки копируют события при загрузке, а вектор одной и той же реплики копировать не нужно.
   - Реплика кодируется при записи, в фоне.
   - Модель — настройка, а не константа: её можно сменить на e5-large или USER2-base, если не хватит видеопамяти.
2. **Запасной путь — BM25 + Snowball,** когда сервис недоступен. Он не хуже текущего на всех видах вопросов.
3. **Служебные заметки** вида «[Новая встреча…]», «[Герой перебил тебя…]», «[Ты закончил разговор]» убрать из поиска или искать отдельно: это половина строк и главный источник ложных совпадений.
4. **Приёмка на этом наборе:**
   - с FRIDA — own «пересказ» ≥ 45/50, mixed ≥ 43/50 (замер минус два);
   - `same` 25/25, `form` 8/8;
   - без сервиса — не хуже строки BM25;
   - добавка к ходу с `recall` ≤ 50 мс.
5. **Отдельно** — сводка: устойчивые факты о герое (имя, обещания, отданное, долги) код берёт из хроники ветки, а модели оставляет отношение и впечатления.

Повторить замер:

```bash
cd server && uv run --with snowballstemmer python ../scripts/recall_eval.py \
  --messages ~/.local/share/gothic-ai/evals/recall/messages.json \
  --queries ../reports/npc-memory/2026-11-01-recall-eval/queries.json \
  [--vectors <файлы .npz из recall_eval.py embed>] [--hybrid]
```

Векторы считались на `dev-ubuntu` во временном окружении `~/gothic-ai/recall-eval/` (sentence-transformers 6.2, torch 2.15). Окружение, копия реплик и скачанные модели после замера удалены.
